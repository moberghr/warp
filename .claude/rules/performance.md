# Performance

- **§6.1** The worker fetch/execute hot path is sacred. **NEVER add logic** to `WarpWorkerService` (single-worker mode) or `WarpDispatcher` / `WarpDispatcherWorker` (dispatcher mode) beyond fetch, execute, signal. New orchestration belongs in an `IServerTask` implementation (§2.3).
- **§6.2** Statistics use Counter rows (write-optimised) aggregated into Statistic rows by `CounterAggregator`. **Never** update `Statistic` rows directly from hot paths — write to `Counter` and let the aggregator collapse them.
- **§6.3** Signal-driven wake-up. `ServerTaskSignals<TContext>` has three channels (`ServerTaskSignal`, numbered from 1): `SignalJobFinalized` wakes `Orchestrator`; `SignalMessageEnqueued` wakes `MessageRouter`; `SignalJobEnqueued` shortcuts every local `WarpWorker`'s backoff so a same-server `Enqueued` `Kind=Job` row is picked up without waiting for the poll interval or a DB round-trip (§2.9). **Don't reduce poll intervals** as a performance hack — register/fire a signal instead. **Every site that puts a row into `Enqueued` must announce it, including the ones that MODIFY an existing row** — `NotificationDispatch.CapturePending` only walks the change tracker for **Added** `Job` entries, so a `Scheduled→Enqueued` activation or a `Processing→Enqueued` requeue is invisible to it and has to build its own `Notification` from the flip (`ScheduledJobActivation`, `StaleJobRecovery`). Both then **buffer it and dispatch from `OnCommittedAsync`** whenever there is an ambient transaction (§8.25) — under the task host `ExecuteAsync` runs inside the lock transaction, so an inline dispatch wakes a worker onto a row it cannot see yet and it sleeps again having found nothing; with no ambient transaction (a direct caller — test, admin trigger) the `SaveChanges` already committed, so the wake fires inline because nothing will call the hook for it. Missing that wake is silent: the row is correct and simply waits out a worker's backoff, up to `MaxPollingInterval` — which `UseDatabasePush()` raises from 30s to **5 minutes** — and it poisons the queue-wait SLI (§8.26) the same way the recurring-scheduler bug did (§8.9). Crash-recovery requeues shipped without it.
- **§6.4** Select only the columns you need. Use `.Select()` projections for read paths — never load full entities for read-only display.
- **§6.5** Avoid initializing collections inside loops.
- **§6.6** No premature optimization. Measure before optimizing. The `src/benchmarks/` projects (`Warp.Benchmarks`, `Warp.PerfTest`, `Warp.ServerBenchmarks`) exist for this — use them.
- **§6.7** Default `WorkerCount = Math.Min(Environment.ProcessorCount * 5, 20)`. Workers can be split into groups with independent queues and polling intervals via `opt.AddWorkerGroup()`.
- **§6.8** Pause/Resume is **not instantaneous** — `PauseServer`/`PauseWorkerGroup` writes `PausedAt`; each server's worker pool keeps fetching until that server's next `Heartbeat` tick refreshes the holder (cadence `HealthCheckInterval`, default 5s), and an in-flight worker iteration that already passed its pause check completes its current claim. Treat pause as "no new fetches after up to one heartbeat", not as a synchronous barrier.
