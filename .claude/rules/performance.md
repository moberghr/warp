# Performance

- **§6.1** The worker fetch/execute hot path is sacred. **NEVER add logic** to `WarpWorkerService` (single-worker mode) or `WarpDispatcher` / `WarpDispatcherWorker` (dispatcher mode) beyond fetch, execute, signal. New orchestration belongs in an `IServerTask` implementation (§2.3).
- **§6.2** Statistics use Counter rows (write-optimised) aggregated into Statistic rows by `CounterAggregator`. **Never** update `Statistic` rows directly from hot paths — emit a counter increment and let the aggregator collapse it. **On the WORKER path that means the in-memory `WarpCounterBuffer`, not a `Counter` row**: a finalizing job emits ~20 increments against the same ~20 keys, so a row each meant 2M rows per 100k jobs folding down to ~20 `Statistic` rows, and that traffic was the largest single share of the database time a server cost. `CounterBufferFlusher` writes the buffer out every `CounterBufferFlushInterval` (2s), collapsing those to one row per key per interval. Increments are STAGED during a job and committed to the buffer only after the transaction commits, so a rolled-back attempt contributes nothing; `BeginFinalizingTransactionAsync` clears the staging list, which is what stops an arm that re-finalizes after a failed commit from counting one job as both succeeded and failed. Everything OFF the worker path — adapter/endpoint/client flushers (already batched), saga, `JobCommandService`, `StaleJobRecovery`, `ErrorGroupAggregator`, `DroppedRecordReporter` — still writes `Counter` rows directly, and should: the buffer buys nothing where increments are already batched, and it trades durability to get the collapse. **Do not add a direct `Counter` row on the worker fetch/execute path** (§0.2).
- **§6.2.1** `CounterAggregator`, `ErrorGroupAggregator` and `StatisticRollup` drain a BOUNDED slice per tick (`MaxBatchesPerTick` = 20 batches on the first two, `MaxRollupRowsPerTick` = 20,000 source rows on the rollup, shared across BOTH of its passes) and set `RerunImmediately`. **Never remove the cap to "drain faster."** `IServerTask.LocksWithTransaction` defaults true, so the task host wraps the whole of `ExecuteAsync` in ONE transaction and the per-batch `SaveChanges` only flush — an unbounded drain holds a single transaction open until the table empties (measured: 51 minutes against a 500k-job backlog). That pins the vacuum horizon, so autovacuum cannot reclaim any tuple newer than its snapshot; the job table measured 43% dead tuples (`CurrentState` is in the worker's fetch index, so every transition orphans index entries and no update is HOT), the claim scan degraded from 3.3ms to 253ms, and throughput fell from 567 to 27 jobs/sec WHILE the queue was still draining — the aggregator running longer made the bloat worse, which made it slower. **On `StatisticRollup` the WRITE is what costs, not the scan** — 43 ms to read a 500,000-row `Statistic` table against 3,472 ms / 317,259 buffers for a 300,000-key `ExecuteDeleteAsync`, where the capped 20,000-key delete is 462 ms / 34,727 (PostgreSQL 18, re-measured for 7.1.0) — and its worst tick is the FIRST after an upgrade, when every legacy unmarked hourly key rolls to daily at once, or any tick after the rollup has been disabled past the hourly window. Capping it is safe only because the passes DEFER rather than drop: a fine row held back by the cap whose hourly parent pass 2 then rolls away re-creates that hourly key next tick with its own value and rolls on the tick after, so the summed value is preserved across ticks (`StatisticRollupTestsBase` asserts exactly that, and was confirmed to fail against the uncapped version). `RerunImmediately` is safe to pair with a cap because `ServerTaskLoop` re-runs only when `ExecuteAsync` returned a message and these tasks return null when they rolled nothing — an idle tick does not spin.
- **§6.3** Signal-driven wake-up. `ServerTaskSignals<TContext>` has three channels (`ServerTaskSignal`, numbered from 1): `SignalJobFinalized` wakes `Orchestrator`; `SignalMessageEnqueued` wakes `MessageRouter`; `SignalJobEnqueued` shortcuts every local `WarpWorker`'s backoff so a same-server `Enqueued` `Kind=Job` row is picked up without waiting for the poll interval or a DB round-trip (§2.9). **Don't reduce poll intervals** as a performance hack — register/fire a signal instead. **Every site that puts a row into `Enqueued` must announce it, including the ones that MODIFY an existing row** — `NotificationDispatch.CapturePending` only walks the change tracker for **Added** `Job` entries, so a `Scheduled→Enqueued` activation or a `Processing→Enqueued` requeue is invisible to it and has to build its own `Notification` from the flip (`ScheduledJobActivation`, `StaleJobRecovery`). Both then **buffer it and dispatch from `OnCommittedAsync`** whenever there is an ambient transaction (§8.25) — under the task host `ExecuteAsync` runs inside the lock transaction, so an inline dispatch wakes a worker onto a row it cannot see yet and it sleeps again having found nothing; with no ambient transaction (a direct caller — test, admin trigger) the `SaveChanges` already committed, so the wake fires inline because nothing will call the hook for it. Missing that wake is silent: the row is correct and simply waits out a worker's backoff, up to `MaxPollingInterval` — which `UseDatabasePush()` raises from 30s to **5 minutes** — and it poisons the queue-wait SLI (§8.26) the same way the recurring-scheduler bug did (§8.9). Crash-recovery requeues shipped without it.
- **§6.4** Select only the columns you need. Use `.Select()` projections for read paths — never load full entities for read-only display.
- **§6.5** Avoid initializing collections inside loops.
- **§6.6** No premature optimization. Measure before optimizing. The `src/benchmarks/` projects (`Warp.Benchmarks`, `Warp.PerfTest`, `Warp.ServerBenchmarks`) exist for this — use them.
- **§6.7** Default `WorkerCount = Math.Min(Environment.ProcessorCount * 5, 20)`. Workers can be split into groups with independent queues and polling intervals via `opt.AddWorkerGroup()`.
- **§6.8** Pause/Resume is **not instantaneous** — `PauseServer`/`PauseWorkerGroup` writes `PausedAt`; each server's worker pool keeps fetching until that server's next `Heartbeat` tick refreshes the holder (cadence `HealthCheckInterval`, default 5s), and an in-flight worker iteration that already passed its pause check completes its current claim. Treat pause as "no new fetches after up to one heartbeat", not as a synchronous barrier.
- **§6.9** **The claim's queue predicate is a SCALAR equality, and the worker issues ONE statement per queue** (`ClaimEnqueuedJobsAsync`, both providers). It was `queue = ANY(@queues)` with `ORDER BY Queue, ScheduleTime`, which returns the same rows but collapses the moment the planner's row estimate goes stale: with 54,000 claimable rows in a 300k table and stale statistics, `ANY(array)` sorted (external merge, 2,584 kB to disk) over the WRONG index with `queue` demoted to a Filter — 5,139 buffers + 584 temp / 44.6 ms — where the scalar form was an Index Cond on `(Kind, CurrentState, Queue, ScheduleTime)` at 26 buffers / 0.062 ms (720x, and `LIMIT 1` single-worker mode is hit identically at 42.1 ms). Both spellings estimate `rows=1` there; only the scalar one does not NEED the estimate to be right, because with `queue` fixed that index supplies the ordering for free, so there is no Sort and `LIMIT` stops at the first rows — a Sort must consume its entire input before emitting anything, which is why `LIMIT` bought nothing and the claim read the whole enqueued range to return one job. **Not parameter opacity** — a literal `ANY(ARRAY[...])` (40.8 ms) and `IN (...)` (40.2 ms) are just as bad, and fresh statistics "fix" it only by winning a race against a backlog that swings empty-to-full between autovacuum ticks. Do NOT re-collapse the loop into one multi-value statement to "save a round trip": the loop costs nothing measurable (statements/job within noise of the old form at 120k jobs), and a single queue — the common shape — still issues exactly one statement. **The bad plan is reachable in an ordinary workload, not just under a pinned `EXPLAIN`** — re-measured for 7.1.0 at 120k jobs published-then-drained, the old predicate took it in **2 of 6 runs** (claim 78-85M blocks and ~910 jobs/sec, against 6.9M and ~1,170 on its good runs) while the scalar form took it in **0 of 12** (6.5-7.1M blocks, 1,179-1,254 jobs/sec). The two have similar MEDIANS, so a median-to-median comparison reads as "no change" and is the wrong instrument: the old predicate is bimodal and the new one is not. An earlier session concluded the lab never reproduces the bad state; that conclusion did not survive re-measurement. Three consequences are deliberate and must be preserved: cross-queue **starvation is reproduced, not fixed** (the budget is spent down queue by queue, the same drain-the-first-queue-completely behaviour the old `ORDER BY Queue` gave, and the default group binds `{DefaultQueue, warp:webhooks}` so webhooks already wait for the default queue); ordering moved from the database collation to **`StringComparer.Ordinal`** (identical for the ASCII queue names Warp produces); and each statement is its own implicit transaction where one was atomic across queues — nothing depends on cross-queue atomicity, and a failure partway leaves claimed rows `Processing` with no worker, the crash-mid-claim case `StaleJobRecovery` already repairs.
- **§6.10** **`CompletionBatch` marks ONLY the columns finalization assigns, and that set moves in lockstep with `WarpDispatcherWorker.BuildFinalization`** (`CurrentState`, `CancellationMode`, `CurrentWorkerId`, `LastKeepAlive`, `ExpireAt`, `HandlerType`, `ScheduleTime`, `Metadata`). A batched completion arrives on a FRESH scope's context with no original values to diff against, so the `Entry(job).State = Modified` it replaces marked every one of the 21 mapped columns dirty and EF wrote all 20 non-key ones, fifty per flush transaction — including `Message`, the unbounded JSON payload, and eleven other columns finalization never touches (8 of the 20 are assigned at finalization). Measured with 4 KB payloads in dispatcher mode, 30,000 jobs, three interleaved passes: DB ms/job 0.549 -> 0.455 (-17%), the completion UPDATE itself 5,555 -> 2,233 ms exec (-60%) and 1,253,774 -> 687,511 blocks (-45%) with non-overlapping ranges, throughput unchanged; the benefit scales with payload size and is absent at payload=0. **The quiet direction of this is the dangerous one** — a new field assigned at finalization and NOT added to `MarkFinalizedColumns` is silently never persisted, with no error anywhere. Single-worker mode is unaffected (it tracks the entity and already diffs).
