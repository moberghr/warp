# Performance

> Rules only. Rationale, history, measurements and full rot-guard lists live in `.claude/references/design-notes/<section>-*.md` (one file per section from §6.2 on) — **read the note before changing a section's area**. The measurements there are why each rule exists; do not undo a rule because it looks like needless complexity.

## Hot path, counters, signals

- **§6.1** The worker fetch/execute hot path is sacred. **NEVER add logic** to `WarpWorkerService` (single-worker mode) or `WarpDispatcher` / `WarpDispatcherWorker` (dispatcher mode) beyond fetch, execute, signal. New orchestration belongs in an `IServerTask` implementation (§2.3).
- **§6.2** Statistics use `Counter` rows aggregated into `Statistic` rows by `CounterAggregator`. **Never** update `Statistic` rows directly from hot paths. **On the WORKER path increments go to the in-memory `WarpCounterBuffer`, not a `Counter` row** (`CounterBufferFlusher` writes it every `CounterBufferFlushInterval`, 2 s). Increments are STAGED during a job and committed to the buffer only after the transaction commits; `BeginFinalizingTransactionAsync` clears the staging list (stops a re-finalized attempt counting as both succeeded and failed). Everything OFF the worker path (adapter/endpoint/client flushers, saga, `JobCommandService`, `StaleJobRecovery`, `ErrorGroupAggregator`, `DroppedRecordReporter`) still writes `Counter` rows directly, and should. **Do not add a direct `Counter` row on the worker fetch/execute path** (§0.2).
- **§6.2.1** `CounterAggregator`, `ErrorGroupAggregator` and `StatisticRollup` drain a BOUNDED slice per tick (`MaxBatchesPerTick` = 20; `MaxRollupRowsPerTick` = 20,000 shared across both rollup passes) and set `RerunImmediately`. **Never remove the cap to "drain faster"**: `ExecuteAsync` runs in ONE transaction (`LocksWithTransaction`), so an unbounded drain pins the vacuum horizon and bloats the job table. The rollup passes DEFER rather than drop (summed value preserved across ticks). These tasks return null when they did nothing, so an idle tick does not spin. Guard: `StatisticRollupTestsBase`.
- **§6.3** Signal-driven wake-up. `ServerTaskSignals<TContext>` has three channels (`ServerTaskSignal`, from 1): `SignalJobFinalized` wakes `Orchestrator`; `SignalMessageEnqueued` wakes `MessageRouter`; `SignalJobEnqueued` shortcuts every local `WarpWorker`'s backoff (§2.9). **Don't reduce poll intervals** as a performance hack — fire a signal instead. **Every site that puts a row into `Enqueued` must announce it, including ones that MODIFY an existing row**: `NotificationDispatch.CapturePending` only sees **Added** `Job` entries, so a `Scheduled→Enqueued` activation or `Processing→Enqueued` requeue builds its own `Notification` (`ScheduledJobActivation`, `StaleJobRecovery`). With an ambient transaction, buffer it and dispatch from `OnCommittedAsync` (§8.25); with none (direct caller), fire inline. A missed wake is silent: the row waits out a worker's backoff, up to `MaxPollingInterval` (5 min with `UseDatabasePush()`), and poisons the queue-wait SLI (§8.26).
- **§6.4** Select only the columns you need. Use `.Select()` projections for read paths — never load full entities for read-only display.
- **§6.5** Avoid initializing collections inside loops.
- **§6.6** No premature optimization. Measure before optimizing. The `src/benchmarks/` projects (`Warp.Benchmarks`, `Warp.PerfTest`, `Warp.ServerBenchmarks`) exist for this — use them.
- **§6.7** Default `WorkerCount = Math.Min(Environment.ProcessorCount * 5, 20)`. Workers can be split into groups with independent queues and polling intervals via `opt.AddWorkerGroup()`.
- **§6.8** Pause/Resume is **not instantaneous** — `PauseServer`/`PauseWorkerGroup` writes `PausedAt`; each server keeps fetching until its next `Heartbeat` tick (`HealthCheckInterval`, default 5s), and an in-flight iteration that already passed its pause check completes its claim. Treat pause as "no new fetches after up to one heartbeat".
