# Performance

- **§6.1** The worker fetch/execute hot path is sacred. **NEVER add logic** to `WarpWorkerService` (single-worker mode) or `WarpDispatcher` / `WarpDispatcherWorker` (dispatcher mode) beyond fetch, execute, signal. New orchestration belongs in an `IServerTask` implementation (§2.3).
- **§6.2** Statistics use Counter rows (write-optimised) aggregated into Statistic rows by `CounterAggregator`. **Never** update `Statistic` rows directly from hot paths — emit a counter increment and let the aggregator collapse it. **On the WORKER path that means the in-memory `WarpCounterBuffer`, not a `Counter` row**: a finalizing job emits ~20 increments against the same ~20 keys, so a row each meant 2M rows per 100k jobs folding down to ~20 `Statistic` rows, and that traffic was the largest single share of the database time a server cost. `CounterBufferFlusher` writes the buffer out every `CounterBufferFlushInterval` (2s), collapsing those to one row per key per interval. Increments are STAGED during a job and committed to the buffer only after the transaction commits, so a rolled-back attempt contributes nothing; `BeginFinalizingTransactionAsync` clears the staging list, which is what stops an arm that re-finalizes after a failed commit from counting one job as both succeeded and failed. Everything OFF the worker path — adapter/endpoint/client flushers (already batched), saga, `JobCommandService`, `StaleJobRecovery`, `ErrorGroupAggregator`, `DroppedRecordReporter` — still writes `Counter` rows directly, and should: the buffer buys nothing where increments are already batched, and it trades durability to get the collapse. **Do not add a direct `Counter` row on the worker fetch/execute path** (§0.2). The buffer holds one mutable cell per key updated by compare-and-swap (8.0): `AddOrUpdate` took the key's bucket lock on every increment, and with every worker adding to the same few keys per job that lock was ~2% of a busy worker's CPU in contention. A drain empties each cell with a CAS and retires (then removes) a cell it finds already empty, so past time buckets' keys do not accumulate; an `Add` that finds its cell retired looks the key up again. Do not replace the CAS with `Interlocked.Add` or `Exchange`: either can write into a retired cell, and that increment is lost. Rot guard: `WarpCounterBufferTests.AddAndDrain_KeysRetiredWhileWritersReturnToThem_ConservesEveryIncrement` (fails when `Add` ignores a retired cell). The queue-wait keys and the tier suffix the worker builds per job are cached per tier bucket, like `JobStatsKeys`'.
- **§6.2.1** `CounterAggregator`, `ErrorGroupAggregator` and `StatisticRollup` drain a BOUNDED slice per tick (`MaxBatchesPerTick` = 20 batches on the first two, `MaxRollupRowsPerTick` = 20,000 source rows on the rollup, shared across BOTH of its passes) and set `RerunImmediately`. **Never remove the cap to "drain faster."** `IServerTask.LocksWithTransaction` defaults true, so the task host wraps the whole of `ExecuteAsync` in ONE transaction and the per-batch `SaveChanges` only flush — an unbounded drain holds a single transaction open until the table empties (measured: 51 minutes against a 500k-job backlog). That pins the vacuum horizon, so autovacuum cannot reclaim any tuple newer than its snapshot; the job table measured 43% dead tuples (`CurrentState` is in the worker's fetch index, so every transition orphans index entries and no update is HOT), the claim scan degraded from 3.3ms to 253ms, and throughput fell from 567 to 27 jobs/sec WHILE the queue was still draining — the aggregator running longer made the bloat worse, which made it slower. **On `StatisticRollup` the WRITE is what costs, not the scan** — 43 ms to read a 500,000-row `Statistic` table against 3,472 ms / 317,259 buffers for a 300,000-key `ExecuteDeleteAsync`, where the capped 20,000-key delete is 462 ms / 34,727 (PostgreSQL 18, re-measured for 7.1.0) — and its worst tick is the FIRST after an upgrade, when every legacy unmarked hourly key rolls to daily at once, or any tick after the rollup has been disabled past the hourly window. Capping it is safe only because the passes DEFER rather than drop: a fine row held back by the cap whose hourly parent pass 2 then rolls away re-creates that hourly key next tick with its own value and rolls on the tick after, so the summed value is preserved across ticks (`StatisticRollupTestsBase` asserts exactly that, and was confirmed to fail against the uncapped version). `RerunImmediately` is safe to pair with a cap because `ServerTaskLoop` re-runs only when `ExecuteAsync` returned a message and these tasks return null when they rolled nothing — an idle tick does not spin.
- **§6.3** Signal-driven wake-up. `ServerTaskSignals<TContext>` has three channels (`ServerTaskSignal`, numbered from 1): `SignalJobFinalized` wakes `Orchestrator`; `SignalMessageEnqueued` wakes `MessageRouter`; `SignalJobEnqueued` shortcuts every local `WarpWorker`'s backoff so a same-server `Enqueued` `Kind=Job` row is picked up without waiting for the poll interval or a DB round-trip (§2.9). **Don't reduce poll intervals** as a performance hack — register/fire a signal instead. **Every site that puts a row into `Enqueued` must announce it, including the ones that MODIFY an existing row** — `NotificationDispatch.CapturePending` only walks the change tracker for **Added** `Job` entries, so a `Scheduled→Enqueued` activation or a `Processing→Enqueued` requeue is invisible to it and has to build its own `Notification` from the flip (`ScheduledJobActivation`, `StaleJobRecovery`). Both then **buffer it and dispatch from `OnCommittedAsync`** whenever there is an ambient transaction (§8.25) — under the task host `ExecuteAsync` runs inside the lock transaction, so an inline dispatch wakes a worker onto a row it cannot see yet and it sleeps again having found nothing; with no ambient transaction (a direct caller — test, admin trigger) the `SaveChanges` already committed, so the wake fires inline because nothing will call the hook for it. Missing that wake is silent: the row is correct and simply waits out a worker's backoff, up to `MaxPollingInterval` — which `UseDatabasePush()` raises from 30s to **5 minutes** — and it poisons the queue-wait SLI (§8.26) the same way the recurring-scheduler bug did (§8.9). Crash-recovery requeues shipped without it.
- **§6.4** Select only the columns you need. Use `.Select()` projections for read paths — never load full entities for read-only display.
- **§6.5** Avoid initializing collections inside loops.
- **§6.6** No premature optimization. Measure before optimizing. The `src/benchmarks/` projects (`Warp.Benchmarks`, `Warp.PerfTest`, `Warp.ServerBenchmarks`) exist for this — use them.
- **§6.7** Default `WorkerCount = Math.Min(Environment.ProcessorCount * 5, 20)`. Workers can be split into groups with independent queues and polling intervals via `opt.AddWorkerGroup()`.
- **§6.8** Pause/Resume is **not instantaneous** — `PauseServer`/`PauseWorkerGroup` writes `PausedAt`; each server's worker pool keeps fetching until that server's next `Heartbeat` tick refreshes the holder (cadence `HealthCheckInterval`, default 5s), and an in-flight worker iteration that already passed its pause check completes its current claim. Treat pause as "no new fetches after up to one heartbeat", not as a synchronous barrier.
- **§6.9** **The claim's queue predicate is a SCALAR equality, and the worker issues ONE statement per queue** (`ClaimEnqueuedJobsAsync`, both providers). It was `queue = ANY(@queues)` with `ORDER BY Queue, ScheduleTime`, which returns the same rows but collapses the moment the planner's row estimate goes stale: with 54,000 claimable rows in a 300k table and stale statistics, `ANY(array)` sorted (external merge, 2,584 kB to disk) over the WRONG index with `queue` demoted to a Filter — 5,139 buffers + 584 temp / 44.6 ms — where the scalar form was an Index Cond on `(Kind, CurrentState, Queue, ScheduleTime)` at 26 buffers / 0.062 ms (720x, and `LIMIT 1` single-worker mode is hit identically at 42.1 ms). Both spellings estimate `rows=1` there; only the scalar one does not NEED the estimate to be right, because with `queue` fixed that index supplies the ordering for free, so there is no Sort and `LIMIT` stops at the first rows — a Sort must consume its entire input before emitting anything, which is why `LIMIT` bought nothing and the claim read the whole enqueued range to return one job. **Not parameter opacity** — a literal `ANY(ARRAY[...])` (40.8 ms) and `IN (...)` (40.2 ms) are just as bad, and fresh statistics "fix" it only by winning a race against a backlog that swings empty-to-full between autovacuum ticks. Do NOT re-collapse the loop into one multi-value statement to "save a round trip": the loop costs nothing measurable (statements/job within noise of the old form at 120k jobs), and a single queue — the common shape — still issues exactly one statement. **The bad plan is reachable in an ordinary workload, not just under a pinned `EXPLAIN`** — re-measured for 7.1.0 at 120k jobs published-then-drained, the old predicate took it in **2 of 6 runs** (claim 78-85M blocks and ~910 jobs/sec, against 6.9M and ~1,170 on its good runs) while the scalar form took it in **0 of 12** (6.5-7.1M blocks, 1,179-1,254 jobs/sec). The two have similar MEDIANS, so a median-to-median comparison reads as "no change" and is the wrong instrument: the old predicate is bimodal and the new one is not. An earlier session concluded the lab never reproduces the bad state; that conclusion did not survive re-measurement. Three consequences are deliberate and must be preserved: cross-queue **starvation is reproduced, not fixed** (the budget is spent down queue by queue, the same drain-the-first-queue-completely behaviour the old `ORDER BY Queue` gave, and the default group binds `{DefaultQueue, warp:webhooks}` so webhooks already wait for the default queue); ordering moved from the database collation to **`StringComparer.Ordinal`** (identical for the ASCII queue names Warp produces); and each statement is its own implicit transaction where one was atomic across queues — nothing depends on cross-queue atomicity, and a failure partway leaves claimed rows `Processing` with no worker, the crash-mid-claim case `StaleJobRecovery` already repairs. **The rows a claim RETURNS are sorted by `ScheduleTime` in memory** (`ClaimFromQueueAsync`, both providers, skipped for a single row, so single-worker mode pays nothing): the inner `SELECT` picks the oldest rows, but `UPDATE ... RETURNING` / `OUTPUT` hands them back in no particular order (id order on PostgreSQL), and the dispatcher starts a claimed batch in list order, so a newer job of the batch could start before an older one. Rot guard: `ConcurrentClaimTests.ClaimEnqueuedJobs_BatchClaim_ReturnsTheOldestJobsOldestFirst` (fails on PostgreSQL without the sort).
- **§6.10** **(Superseded in part by §6.13: the batch no longer goes through the change tracker; the same column list now lives in the provider statements.)** **`CompletionBatch` marks ONLY the columns finalization assigns, and that set moves in lockstep with `WarpDispatcherWorker.BuildFinalization`** (`CurrentState`, `CancellationMode`, `CurrentWorkerId`, `LastKeepAlive`, `ExpireAt`, `HandlerType`, `ScheduleTime`, `Metadata`). A batched completion arrives on a FRESH scope's context with no original values to diff against, so the `Entry(job).State = Modified` it replaces marked every one of the 21 mapped columns dirty and EF wrote all 20 non-key ones, fifty per flush transaction — including `Message`, the unbounded JSON payload, and eleven other columns finalization never touches (8 of the 20 are assigned at finalization). Measured with 4 KB payloads in dispatcher mode, 30,000 jobs, three interleaved passes: DB ms/job 0.549 -> 0.455 (-17%), the completion UPDATE itself 5,555 -> 2,233 ms exec (-60%) and 1,253,774 -> 687,511 blocks (-45%) with non-overlapping ranges, throughput unchanged; the benefit scales with payload size and is absent at payload=0. **The quiet direction of this is the dangerous one** — a new field assigned at finalization and NOT added to `MarkFinalizedColumns` is silently never persisted, with no error anywhere. Single-worker mode tracks the entity and diffs, which has its own quiet failure: a column another writer changed on the ROW while the worker held the entity (`CancellationMode`, set by `DeleteJob`) is not a diff when the worker assigns the value the entity already has, so `ClearCancellationMode` marks it modified explicitly. **Rot guard for both: `WorkerPathLockstepTests`** runs one job to rest (completed, failed after a retry, cancelled, parked by an outcome) in each mode and compares every mapped column of the row, read from the EF model so a new column is covered without editing the test; verified to fail when `ExpireAt` is removed from `MarkFinalizedColumns`.
- **§6.11** **`Orchestrator.FinalizeParentsAsync` finds ready parents with one branch per kind (`Kind = Message` UNION ALL `Kind = Batch`), each `ORDER BY CurrentState, CreateTime` + `Take`, and that shape is load-bearing** (the §6.9 lesson on a second query). As one `Kind IN (...) AND CurrentState IN (Awaiting, Processing)` predicate the planner estimated one row either way and chose `(CurrentState, ScheduleTime)` with `Kind` as a Filter. Every job passes through `Processing`, so until vacuum catches up that index range holds an entry for every row that has since left it, and the query walked all of them and visited the heap for each to return nothing: **10,004 pages per call against 6**, reproduced on a table with no batch or message in it, and 1,147,074 pages across a 10,000-job lab run against 4,008 after (the task ticks on almost every finalization, so that was up to ~100 pages per job). A scalar `Kind` alone is NOT enough (the two index costs tie and the wrong one still wins); it takes the scalar `Kind` AND an `ORDER BY` only the `(Kind, CurrentState, CreateTime)` index can supply. Statement count is unchanged (one statement). **Rot guard: `OrchestratorReadyParentsPlanTests`** measures the pages the real query reads (PostgreSQL `EXPLAIN (ANALYZE, BUFFERS)`, SQL Server `STATISTICS IO`) with 3,000 rows that have just left `Processing` and no batch or message, and fails above 200: the old shape reads 2,949 on PostgreSQL, the new one 4. **SQL Server never had the problem** (8 logical reads with either shape), so the change costs it nothing. This was also the swing behind the perf workflow's bimodal Buffers/job column; the two sides of that comparison now each get a fresh PostgreSQL container (`.github/scripts/start-bench-postgres.sh`), since sharing one, head first, read ~50 buffers per job higher on "head" for identical code. **The "which awaiting rows can move?" half had its own version of this, and is now three steps that can each be served only one way** (`AwaitedParentIdsQuery` -> `AwaitedParentStatesQuery` -> `AwaitingChildrenOfQuery`, shared by the activation and the deleted-parent sweep). It was one statement per question, awaiting rows `WHERE EXISTS(parent WHERE id = the row's parent AND state = Completed)`, measured at 2 and 12 pages on a table with no continuation in it, which is the wrong table to measure on: in a batch workload PostgreSQL found the parent through the STATE index and checked the id afterwards, so for each awaiting row it read every Completed row in the table and discarded all but one (505 awaiting rows, 250 completed: 126,250 rows discarded, **5,063 pages per call**, cost = awaiting rows x completed rows, on almost every job completion). A scalar subquery on the parent's id is deterministic but still two key lookups per awaiting ROW (3,042 pages, and it made SQL Server worse: 2 -> 1,083). The three steps read each DISTINCT parent once: 500 jobs in five continuation batches wait on ten parents, **13 + 15 pages per pass, plus 46 when something is ready**; SQL Server is level (42 against 41). Statements per pass do not go up: one when nothing is awaiting (was two), two when rows wait but none can move (was two), one more for each of ready and deleted. **Past 1,000 awaited parents the pass stops reading them all** (`ServerTaskSignals.ManyAwaitedParents`, set and cleared by the Orchestrator from the size of the set it last read): 100,000 single-job continuations on 100,000 parents was a scan of every awaiting row plus 100 lookup statements on every job completion. In that mode a pass asks only about the jobs a wake said reached a terminal state (`AwaitedParentIdsAmongQuery`, the `(ParentJobId, CurrentState)` index with both columns bound) and the whole set is read on a sweep alone, 5,000 parents at a time, each sweep carrying on from the last one's cursor (`NextSweepSlice`) so nothing is starved. That is why a wake carries a second id list, the SETTLED jobs: the worker sends the job's own id once it is at rest (never for a requeue), `DeleteJob`/`BulkDeleteJobs`/`StaleJobRecovery` send theirs, `NotificationDispatch.CapturePending` names the parent of every ADDED `Awaiting` row (a continuation published after its parent finished has nothing else to wake for it), and the Orchestrator adds the parents it finalizes and the rows it fails, plus anything it could not finish in one pass (`NoteFinalized`). Below the threshold nothing changes: the settled ids are taken and ignored, because one scan of a small awaiting range (2 to 13 pages) is cheaper than an index probe per finished job. Push payload grammar: `parents[;settled]`, at most 128 ids. Rot guards: `OrchestrationTaskTests.RunOrchestration_MoreAwaitedParentsThanOnePassReads_ChecksNamedJobsAndSweepsTheRest`, `OrchestratorReadyParentsPlanTests.AwaitedParentIdsAmongQuery_ThousandsOfAwaitingRows_ReadsOnlyTheNamedJobs`, `FinalizedParentHintsTests.NextSweepSlice_*`. This was the swing behind the batch scenario reading 2,948 buffers per job in one CI run and about 165 in the others. Rot guard: `OrchestratorReadyParentsPlanTests.AwaitingRowQueries_BatchWorkloadAmongManyCompletedJobs_EachReadAHandfulOfPages`. **A wake names the parents to check; every parent in flight is checked only on a sweep.** Even with the right plan, the ready-parents query reads each in-flight parent (about 11 pages each on PostgreSQL: 10,924 per pass with 1,000 messages in flight and none ready, 10 on SQL Server) and it ran on every job completion, so message routing cost passes x in-flight parents and read anywhere from 164 to 1,643 pages per job on identical code. The worker now passes the finished job's `ParentJobId` (already on the claimed row: no query, §0.2) with its wake, `ServerTaskSignals.SignalJobFinalized(Guid?)` / `SignalJobsFinalized` for a dispatcher flush, and the same ids travel in the push payload after `F:` (`FinalizedParentsPayload`: ids, `-` for no parent, nothing for unknown, at most 64 per notification). `Orchestrator` takes them with `TakeFinalizedParents` and runs `HintedReadyParentsQuery` (the same readiness check, parents found by primary key), and runs the full `ReadyParentsQuery` only on a **sweep**: the first pass of the process, once per `OrchestrationInterval` (stopwatch, not `TimeProvider`), after the public no-argument `SignalJobFinalized()` (a reconnect drain, a bare `F:` from a pre-8.0 server), after a full sweep slice, and when the bounded hint set (10,000) overflows. A pass that throws returns its work (`ReturnFinalizedParents`). **Every site that puts a child into a terminal state names its parent, not only the worker**: `JobCommandService.DeleteJob` / `BulkDeleteJobs` (so `CancelBatch` too) dispatch after their commit, and `StaleJobRecovery`'s deleted and failed arms buffer theirs for `OnCommittedAsync`; a new site that finishes a child must do the same, or its parent waits for the sweep. The sweep remains the backstop for what cannot name a parent or cannot reach the Orchestrator (a wake lost with a crashed process, a delete from a dashboard-only process without `UseDatabasePush()`), up to `OrchestrationInterval` (10 s; 1 min with push): do not remove it, and do not make a wake-only signal request one (with push, every completion echoes back through the listener). Rot guards: `OrchestratorReadyParentsPlanTests.HintedReadyParentsQuery_ThousandMessagesInFlight_ReadsOnlyTheNamedParents`, `FinalizedParentHintsTests` (NoDb), `OrchestrationTaskTests.RunOrchestration_ParentNamedByAFinishedJob_OnlyThatParentIsFinalized`, `MessageIntegrationTests.GivenNoParentSweepDue_WhenHandlersFinish_ThenWorkerNamesTheMessageAndItCompletes` in both worker modes, `JobCommandServiceTests.DeleteJob_ChildOfAMessage_NamesTheParentForTheOrchestrator`, and `NoRestartCrashRecoveryTests.RequeueStaleJobs_FailedChildOfAMessage_NamesTheParentForTheOrchestrator`.
- **§6.12** **Nothing is written for a job between its claim and its handler.** Both worker modes used to commit before the handler ran: single-worker mode saved the "Processing" `JobLog` on its own (one statement, one commit), and dispatcher mode issued a guarded ownership `UPDATE` and then that same insert (two statements, two commits), for every job. Neither is needed up front. **The "Processing" row is deferred** (`DeferredJobLog`): the job monitor's first flush writes it for a job that runs that long, otherwise it rides the finalizing write, and whichever asks first takes it, so it is written once. It keeps the receiving worker's id and the instant the worker took the job. **The dispatcher's ownership check is skipped for a fresh claim** (`WarpDispatcherWorker.ConfirmOwnership`): `StaleJobRecovery` reclaims a job only when its `LastKeepAlive` is a whole `InvisibilityTimeout` old, so a job received within `InvisibilityTimeout / 2 - CancellationCheckInterval` of its claim cannot have been reclaimed; the other half of the timeout is margin for two servers' clocks. A job that waited in the channel longer than that still gets the guarded renewal (`RenewClaim`), which is what keeps a reclaimed prefetched job from running twice (`DispatcherPrefetchTests`). Consequences, all accepted: a short job's "Processing" row appears when it completes; a job that dies with its process before its first flush has none; and in dispatcher mode the row carries the worker GROUP's id from the claim until the first keep-alive stamps the worker's, so several running jobs can share one `CurrentWorkerId` and readers must not key a dictionary on it (`DashboardStatsService` uses `DistinctBy`). The queue-wait increments go to the counter buffer at receipt, since the claim that made the job ours is already committed. Do not move either write back in front of the handler. Rot guards: `WorkerExecutionIntegrationTests.GivenLongRunningHandler_WhileItRuns_ThenItsProcessingLogAndItsWorkerAppear` and `GivenShortHandler_WhenItCompletes_ThenItsProcessingLogIsWrittenWithTheCompletion` (both modes), `ServerQueryTests.GetServers_SeveralRunningJobsUnderOneId_StillLoads`, and `WorkerPathLockstepTests` for the two modes agreeing on the log rows.
- **§6.13** **Dispatcher completions are flushed per worker GROUP, in one set-based statement.** Two things made the batched completion batch very little. **The buffer was per worker**, and each worker flushed its own whenever it found the channel empty for a moment, so at ten workers a flush held about two jobs: a transaction for every second job. `WarpDispatcherHost` now builds ONE `CompletionBatch` per group and every worker of the group adds to it. It is flushed when it is full (`CompletionBatchSize`), when its oldest entry has waited `CompletionFlushInterval` (a timer started by the first completion of each buffer, so it fires even when every worker is inside a long handler), and the moment the group has nothing left claimed (`DispatcherWorkerAvailability.Outstanding == 0`), which is what keeps a lone job from waiting for the timer. Do not put back a flush on "this worker is idle". **A timer flushes only the buffer it was started for** (`CompletionBatch` numbers each buffer; `Holds(generation)`), never whatever is buffered when it fires: a buffer flushed early (full, or the group idle) left its timer running, and when that timer flushed the next, moments-old buffer, batches fell from ~15 jobs to ~9 and throughput 9-20% on CI. Nor by `IsTimeElapsed`, whose clock is not the timer's: a timer firing a hair early then stranded its buffer behind a long handler. **The writes are done by one `CompletionFlusher` per group, never by a worker**: workers add and go back to their channel, the flusher loop is woken by whoever sees a trigger and re-checks the triggers before writing, so the group has one flush in flight and the next buffer fills behind it. A worker that wrote the flush itself could not run its next job for that round trip (`BatchedCompletionIntegrationTests.GivenACompletionWriteThatHangs_WhenTheWorkerHasAnotherJob_ThenItRunsIt` fails on that shape). The host stops the flushers after every worker has stopped; the flusher's final flush writes what is left. **The flush wrote one UPDATE and one INSERT per row** through the change tracker. It is now `IWarpSqlQueries.CompleteJobsAsync`: PostgreSQL unnests one array per column in a single statement (a data-modifying CTE updates the jobs, inserts their log rows and returns the ids it wrote); SQL Server reads two JSON documents with `OPENJSON` in one batch. The log rows are inserted only for jobs the update found, so a job whose row was deleted while it ran is skipped with its logs, counts nothing, and cannot fail the batch on the foreign key. **On SQL Server `INNER LOOP JOIN` with the JSON rows outermost and `ROWLOCK` are load-bearing**: without them the join scanned the job table, locked other workers' rows and concurrent flushes deadlocked (the batched-completion tests timed out on it). The columns written are the eight finalization assigns (rule 6.10's list, which now lives in the two provider statements, not in `MarkFinalizedColumns`); a new one must be added to BOTH statements, and `WorkerPathLockstepTests` is what catches a miss, since single-worker mode still finalizes through EF. Only an `ErrorOccurrence` row (§8.29) is still saved by EF, in the same transaction. `SaveChanges` inside the worker's explicit finalizing transactions runs with `AutoSavepointsEnabled = false`: a failed save abandons the transaction, so the SAVEPOINT / RELEASE pair EF adds was pure overhead (two statements per job in single-worker mode). Measured on the load lab, dispatcher mode, 10 workers, 2,000 jobs, PostgreSQL, publish included: 7.09 statements, 0.98 transactions and 0.293 ms of database time per job before; 2.87, 0.48 and 0.153 after. The set-based statement ALONE, with per-worker buffers, cut statements to 4.61 but RAISED database time to 0.350 ms per job, because a two-job flush pays for a larger statement and gets nothing back: the two changes belong together. Rot guards: `CompletionBatchTests` (the real statement on both providers, a missing row, an injected statement failure isolated by the split), `BatchedCompletionIntegrationTests` (size, time and idle triggers) and `WorkerPathLockstepTests`.
- **§6.14** **A worker group watches all its running jobs in one loop** (`RunningJobMonitor`, one per group, built by `WarpDispatcherHost` and `WarpSingleWorkerHost`; a `WarpWorkerService` built on its own, as tests do, gets a private one). Each running job used to have a monitor of its own: every `CancellationCheckInterval` a cancellation `SELECT` and a keep-alive `UPDATE` per job, and a save per job per `LogFlushInterval` for any job that logged, so a group running N long jobs paid 2N statements per check. Now each tick drains every registered job's handler logs, progress rows and (once the job has run a whole tick) its deferred "Processing" row (§6.12) into one save, and every `CancellationCheckInterval` ONE statement (`IWarpSqlQueries.RenewRunningJobsAsync`: `unnest` on PostgreSQL, `OPENJSON` with `INNER LOOP JOIN`/`ROWLOCK` on SQL Server, jobs in id order like the completion) renews `LastKeepAlive`, stamps each job's worker, touches only rows still `Processing` (so a renewal racing a completion writes nothing to the finished row) and returns the jobs whose `CancellationMode` asks for cancellation, which are cancelled after their logs are saved. The loop runs only while something is registered, so an idle group costs nothing; a worker whose stopping token fired is no longer watched. A failed renewal is logged and retried at the next check, separately from the log save. The statement runs through EF's `SqlQueryRaw`, not a bare command, so EF command interceptors see it (its rows are aliased `beat`, which is how `FailFirstKeepAliveInterceptor` finds it). A worker disposes its registration before finalizing a job; anything that renews or flushes for a job must go through the monitor, never a per-job loop again. Rot guards: `WorkerExecutionIntegrationTests.GivenTwoLongRunningHandlersInOneGroup_WhileTheyRun_ThenOneRenewalStampsBoth` (one statement renews both, so they carry the same instant), `GivenOneKeepAliveRenewalFails_WhileTheHandlerRuns_ThenLaterRenewalsStillHappen`, the cancellation tests, both modes.
- **§6.15** **The job table's claim, scheduled, parent and expiry indexes are partial** (`WarpPartialIndexes`, applied at the end of `ApplyWarpModel`): the claim index `(Kind, CurrentState, Queue, ScheduleTime)` holds only `CurrentState = Enqueued`, `(CurrentState, ScheduleTime)` only `Scheduled`, `(ParentJobId, CurrentState)` only rows with a parent, `(ExpireAt)` only rows with an expiry. A non-HOT update (every state transition is one: `CurrentState` is indexed) writes a new entry into EVERY index of the table unless the index is partial and the new row falls outside it, so a job's insert, claim and completion wrote 21 index entries, most of which no reader ever looked at. Measured on the load lab (10,000 jobs, dispatcher, PostgreSQL): 3,777 to 2,938 WAL bytes per job and 78 to 61 buffer hits per job; the `--tune=partial` lab lever reproduces it against whole indexes. The filters are SQL naming the columns as the host's naming convention spells them, quoted with double quotes (PostgreSQL always accepts them; SQL Server does with QUOTED_IDENTIFIER on, which a filtered index requires anyway). Readers must keep stating the predicate the index needs: the claim and scheduled activation compare `CurrentState` to a LITERAL (a parameter would stop SQL Server using a filtered index, and a PostgreSQL generic plan too), and the parent and expiry lookups compare with `=`/`<`, which imply `IS NOT NULL`. The dashboard listing index `(Kind, CurrentState, CreateTime)` stays whole: it lists every state. Upgrading recreates four indexes, which locks a large job table while it runs; release note. Rot guard: `JobPartialIndexTests` (both namings); the plan tests (`ClaimPlanStabilityTests`, `OrchestratorReadyParentsPlanTests`) run against the partial schema.
- **§6.16** **A dispatcher's claim starts at a watermark while its claims come back full** (`ClaimWatermark`, one per `WarpDispatcher`, passed to `IWarpSqlQueries.ClaimEnqueuedJobsAsync`; single-worker mode passes `null`). A job that leaves `Enqueued` leaves its claim-index entry behind until vacuum, right where every claim starts reading, so under a backlog each claim walked the dead entries earlier claims had emptied: about 98 index entries read per claim of ten jobs. After a FULL claim from a queue the next one adds `ScheduleTime >= <newest schedule time it took>` (a second cached SQL variant per provider), so the index range scan starts past them; a SHORT claim, and any claim once `HeadClaimInterval` (1 s) has passed since the last head read, reads from the head again. That is what catches a row that became claimable BEHIND the watermark (a scheduled job activated with its original due time, a job a long publishing transaction committed late): it waits at most a second, and only while a backlog exists. No margin before the watermark: 100 ms of margin at 1,000 jobs/s was a hundred dead entries re-read per claim, and the head read covers what a margin would. Measured on the load lab (10,000 jobs, dispatcher, PostgreSQL, after §6.15): claim-index tuples read 93,818 to 22,924, buffer hits 61 to 53 per job. Rot guard: `ConcurrentClaimTests.ClaimEnqueuedJobs_WithAWatermark_SkipsTheEmptiedHeadAndStillReachesAnOlderJob` (both databases; fails without the watermark and without the head read).
- **§6.17** **The worker never resolves or saves the application's DbContext** (8.0; both worker modes). A handler owns its context and its pipeline: it calls `SaveChangesAsync` (or `IPublisher`/`IBatchPublisher.SaveChangesAsync`) for its own work, and a job it stages without saving is discarded with its scope, like anywhere else; the `WarnOnUnsavedStagedJobs` warning now covers handler scopes too. Until 7.x the worker resolved `TContext` in every handler scope and called `SaveChangesAsync` after the handler, so every job built a full EF context (options, EF's per-context services) even when the handler never touched the database: measured on the load lab, ~0.94 application contexts initialized per empty job and most of the ~94 KB the worker allocated per job. Do not reintroduce a worker-side resolve or save of `TContext`, not even to check for unsaved changes. **The same holds for the addon pipeline stores**: the concurrency resolver, the rate-limit store and resolver and the circuit-breaker store read and write Warp's own tables through `DeferredWarpContext` (Warp's server context, opened on first use and disposed with the job's scope), never `TContext`; their behaviours are built for every job, so a job with no `[Mutex]`/`[Semaphore]`/`[RateLimit]`/circuit-breaker state to touch builds no context at all. Their caches are allocated on first use for the same reason. The admin managers (`ConcurrencyLimitManager<TContext>`, `RateLimitManager<TContext>`) stay on `TContext` because `AddWarp`-only hosts have no server context; moving them is #344. Rot guard: `PolicyBehaviorContextTests` (resolving the pipeline with all three addons constructs no `TContext`). Sagas are separate: the saga proxy saves for the saga handler (§8.17). Release note: breaking for handlers that relied on the worker's save. Rot guard: `WorkerExecutionIntegrationTests.GivenAHandlerThatStagesAJobWithoutSaving_WhenItCompletes_ThenTheStagedJobIsNotCommitted` (both modes).
- **§6.18** **A signal-woken server task runs at most once per `ServerTaskSignalInterval`** (default 500 ms; `ServerTaskLoop.HoldBeforeNextRun`). Every completion flush wakes the `Orchestrator` (about ten times a second per server under load) and every enqueued message the `MessageRouter`, and each pass pays a scope, a lock transaction (which N-1 servers then fail to take), its queries and a bookkeeping update: on a drain profile the server-task loops were about a quarter of a worker process's CPU, the orchestrator alone about an eighth, for jobs with no parent at all. After a pass the loop holds for the rest of the interval (never longer than the task's own interval); a wake arriving meanwhile stays pending on the semaphore, so the next pass runs when the hold ends and no wake is lost. A continuation or a routed message therefore waits at most the interval. Tasks that rerun immediately after doing work (`RerunImmediately`) skip the hold. `WarpTestServer` sets it to zero. Rot guards: `ServerTaskLoopBookkeepingTests.RunAsync_WokenAgainWithinTheSignalInterval_RunsAgainWhenItEnds`, `HoldBeforeNextRun_*`.
- **§6.19** **A dispatcher whose group is full waits for a worker to free a slot; it does not poll** (`DispatcherWorkerAvailability.WaitForFreeSlotAsync`, released when the group goes from no free slot to one; a 1 s backstop timeout). It slept 10 ms instead. With quick jobs, the workers empty the group's buffer (workers + prefetch) in about a millisecond, so they then sat idle for the rest of the sleep: one server with 10 workers was capped at ~20 jobs per ~10 ms. On CI (one server x 10 workers, warm, 50k) Warp ran ~1,600 jobs/s with the box half idle and its worker at a third of a core, against ~3,500 for a claim loop that wakes on a freed executor. **Before sizing a claim the dispatcher also settles**: it yields while the free capacity keeps growing (at most 8 yields), so one claim covers every slot a burst of quick jobs frees rather than the first one or two (each claim is a round trip); a handler that holds its slot ends the wait at the first yield that frees nothing. The claim is still capped at the free capacity: nothing is claimed ahead of what the group can hold. Rot guards: `DispatcherWorkerAvailabilityTests.WaitForFreeSlotAsync_*`.
- **§6.20** **The dispatcher claims on a no-tracking context** (`WarpDispatcher.FetchAndDistribute` sets `QueryTrackingBehavior.NoTracking` on its claim scope's context). The scope ends as soon as the claimed jobs are handed to the channel, and nothing writes them back through EF: completions go through the set-based statement (§6.13), the ownership renewal and the unclaim through `ExecuteUpdate` on scopes of their own. Tracking them cost an identity-map entry and a snapshot per row on every claim, and with claims always full (one per ~20 jobs at ~155 claims/s on one server) the claim's client side was most of its 25-36 ms. Single-worker mode still tracks: it finalizes the claimed entity through EF. Dispatcher tests that mock the claim give the dispatcher a real (in-memory) context (`InMemoryServerContext`). Rot guard: `ConcurrentClaimTests.ClaimEnqueuedJobs_OnANoTrackingContext_ReturnsTheClaimedRowsUntracked`.
- **§6.21** **PostgreSQL job claims carry `SET LOCAL enable_sort = off`** (`PostgresWarpSqlQueries.ClaimPlanGuard`, prepended to both claim forms; it lasts for the claim's command only, whose statements run as one implicit transaction, and never reaches the pooled connection's next command). After a burst into a queue the last analyze saw (nearly) empty, the planner estimated the claim at one row and chose the dashboard's `(kind, current_state, create_time)` index: every enqueued row of the kind, filtered by queue and sorted, to return the limit. CI, 50k jobs: 48,020 rows, 22.8 ms and ~22,000 buffers per claim against 0.72 ms and ~375, throughput capped at ~700-1,200 jobs/s until autovacuum analyzed the table (6-11 s there; on a table holding millions of history rows a burst of a few percent may not trigger an analyze until the drain itself has churned enough rows). With sorting priced out, the only plan left is the claim index read in schedule order: the same rows in the same order, so the setting changes the plan, never the result; a host that removed the claim index still gets a (sorted) plan. It was present in `main` too (the whole claim index loses the same way), not introduced by §6.15. Rot guards: `ClaimPlanStabilityTests.ClaimEnqueuedJobs_BurstIntoAQueueTheStatisticsSayIsEmpty_UsesTheClaimIndexWithoutSorting` (replays the claim's command and EXPLAINs it on the stale statistics CI captured; fails without the guard) and `SetLocalInAMultiStatementCommand_LastsForThatCommandOnly`.
