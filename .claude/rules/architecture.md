# Architecture Patterns

## Unified Data Model

- **§2.1** Everything is a **Job** with a `Kind` discriminator (`Job=1, Message=2, Batch=3`). No separate Message/Batch tables. `ParentJobId` chain handles all parent-child relationships. Messages spawn N child jobs; Batches group children. Continuations chain via `ParentJobId` to a single parent.

## Worker / Server-Task Split

- **§2.2** Workers are **pure executors**. They only fetch and execute `Kind=Job` jobs. Never add orchestration, routing, parent/child finalization, or cross-cutting logic to `WarpWorkerService` or its dispatcher counterparts (`WarpDispatcher`, `WarpDispatcherWorker`).
- **§2.3** Every background task implements `IServerTask` (`Name`, `LockKey`, `DefaultInterval`, `ExecuteAsync`) and is registered as scoped. `ServerTaskHost<TContext>` resolves one per iteration, takes the distributed lock if `LockKey != null`, runs `ExecuteAsync`, and writes `ServerTask` / `ServerLog` rows. Active tasks: `Heartbeat`, `CounterAggregator`, `ServerCleanup`, `StaleJobRecovery`, `ExpirationCleanup`, `RecurringJobScheduler`, `ScheduledJobActivation`, `MessageRouter`, `Orchestrator`, `NotificationListenerTask` (when DB push is enabled).
- **§2.4** Services expose interfaces (`IJobCommandService`, `IJobQueryService`, `IRecurringJobService`, `IDashboardStatsService`, etc.). Generic implementations take `TContext : DbContext`. Inject the specific interface — **never inject `IServiceProvider`** (use `IServiceScopeFactory` when you genuinely need scope creation).
- **§2.5** `AddWarp<TContext>()` / `AddWarpServer<TContext>()` auto-configure the user's DbContext (row-lock interceptors, model customizer, `TimeProvider.System` via `TryAddSingleton`, `IWarpLockProvider`). Users register their DbContext normally. The server builder inherits from `WarpConfiguration` / `WarpServerConfiguration`, so config fields (`WorkerCount`, `PollingInterval`, `DefaultQueue`, etc.) are set directly on `opt`. **Two-builder shape:** `IOptions<WarpConfiguration>` and `IOptions<WarpServerConfiguration>` are separate singletons — `AddWarpServer` registers its builder for both, but the `TryAdd` for the Core one no-ops when `AddWarp(o => ...)` ran first, leaving two objects. Since `WarpServerConfiguration` *inherits* every Core setting, each object then exposes a complete-looking view of settings it may not own, and server-side readers of an inherited setting (`ExpirationCleanup`'s retention caps, `StatisticRollup`'s tiers, the worker's `ApplicationName`) silently read defaults while Core readers read the configured value. **Both entry points therefore call `WarpConfigurationMerge.ApplyCoreSettings`** (`Warp.Core`, reflection over `WarpConfiguration`'s writable properties) — `AddWarpServer` folds an already-registered Core configuration into its builder *before* its fail-fast validation (so the checks and the runtime see one set), and `AddWarp` folds its builder into an already-registered one for the reverse order (`AddWarpServer` first), where its own `TryAdd` no-ops and every field in its lambda would otherwise be silently discarded while the addons the same lambda registered still took effect. The rule is the same in both directions: a Core setting configured on one builder and left at its default on the other is carried over; configured on **both to different values** it throws at registration (nothing distinguishes which lambda was meant to win); left at its default on the source it is not copied, so an explicit value in the `AddWarpServer` lambda is never overwritten by the other builder's default. `EntityConfigurators` is deliberately not merged — `WarpModelCustomizer` and `WarpServerContext` both resolve `IOptions<WarpConfiguration>`, so nothing server-side can read a stale copy. New Core settings need no merge wiring (the reflection walk picks them up); `WarpConfigurationMergeTests` is the rot guard. `AddWarpWorker<TContext>`, `WarpWorkerConfiguration`, and `WarpWorkerBuilder` were **removed in 2.0** (renamed to `AddWarpServer` / `WarpServerConfiguration` / `WarpServerBuilder` — hard rename, compile error on the old names).

## In-Memory Requests & Streams

- **§2.6** In-memory `IRequest<TResponse>` goes through `IMediator.Send()` — same `IPipelineBehavior` pipeline as jobs/messages, but no DB persistence. Returns `TResponse` synchronously.
- **§2.7** `IStreamRequest<TResponse>` extends `IRequest<IAsyncEnumerable<TResponse>>` and goes through `IMediator.CreateStream()`. Request-level `IPipelineBehavior` applies automatically; enumeration-level concerns use `IStreamPipelineBehavior<TRequest, TResponse>`. No DB persistence.

## Scheduling & DB Push

- **§2.8** Future-dated jobs land in `State.Scheduled`. `ScheduledJobActivation` flips them to `Enqueued` when `ScheduleTime <= now`. Cadence is `WarpWorkerConfiguration.ScheduledActivationInterval` (default 10s) — this is the worst-case latency between `ScheduleTime` and pickup eligibility. The task is time-driven and does **not** participate in DB-push wake-up; push only accelerates what happens *after* activation. It does **emit** one, though — an activated row is an enqueue site, and since the flip is a Modified row `NotificationDispatch.CapturePending` cannot see it, so the task builds the `Notification` itself and dispatches it from `OnCommittedAsync` (§6.3/§8.25). Worker fetch queries always filter by `CurrentState == Enqueued` with a defensive `ScheduleTime <= now` predicate for pre-upgrade legacy rows. Adding new query sites that filter on `Enqueued` without the time predicate is a latent bug on upgraded deployments.
- **§2.9** DB push is an opt-in addon. `opt.UseDatabasePush()` replaces the default `NullNotificationTransport` with a provider-specific one (Postgres LISTEN/NOTIFY or SQL Server Service Broker) and registers `NotificationListenerTask`. The transport is resolved via `IWarpNotificationTransportFactory`, registered by the provider package (`opt.UsePostgreSql()` / `opt.UseSqlServer()`) — **call the provider first, push second**. Cross-process worker-fetch push only fires when `UseDispatcher = true` (individual-worker mode has a thundering-herd problem and stays on cross-process polling). **In-process is different:** every `WarpWorker` (bare and dispatcher) subscribes to the `ServerTaskSignal.JobEnqueued` channel, so a same-server `Kind=Job` commit in `Enqueued` (from `Publisher`, `MessageRouter`, `ScheduledJobActivation`, `RecurringJobScheduler`, handler outboxes) fires a local signal that shortcuts the worker's exponential backoff — no DB round-trip, independent of `UseDatabasePush`. Transports must not throw from `PublishAsync` — they log + increment `WarpTelemetry.NotificationPublishFailures` instead. Missed notifications are caught by drain-on-reconnect in the listener. **`NotificationListenerTask<TContext>` lives in `Warp.Core.Notifications`** (moved out of `Warp.Worker`) so DB-push RECEIVE works in **any** `AddWarp` process — server or not. It takes no server-only deps: bare-worker wake stays on `ServerTaskSignals.SignalJobEnqueued` (Core), and dispatcher wake goes through the Core **`IDispatcherWake`** seam (injected as `IEnumerable<IDispatcherWake>` — the optional-marker pattern of `IWarpServerPresence`; `DispatcherRegistry` in `Warp.Worker` is the sole impl, registered by `AddWarpServer`, so the set is **empty in an `AddWarp`-only process** and dispatcher-wake is simply inert there). The advisory "push enabled but `UseDispatcher=false`" warning moved to `WarpSingleWorkerHost` (the server path that has `WarpServerConfiguration`). Server/worker behavior is unchanged.
- **§2.10** Realtime dashboard push is an opt-in addon. `opt.AddDashboardPush()` registers a `WarpDashboardHub` (SignalR) at `${RoutePrefix}/api/hub` plus a `DashboardBroadcaster<TContext>` `BackgroundService` that subscribes to `ServerTaskSignals<TContext>` and broadcasts `JobFinalized` / `MessageEnqueued` events. The broadcaster is the **third** consumer of the signal pipe (after `Orchestrator` and `MessageRouter`). Per-view data (filtered job lists, job detail, logs) is **not** pushed — those surfaces stay on event-driven REST refetch. Multi-server fanout reuses §2.9; without `UseDatabasePush()`, push is single-server only. Frontend reads `${RoutePrefix}/api/addons` once at boot and uses the `push` flag to decide whether to connect to the hub or fall back to 30s polling. Because the listener now lives in Core (§2.9), a **non-server dashboard host** (`AddWarp` + a provider + `UseDatabasePush()` + `AddDashboardPush()`, no `AddWarpServer`) receives cross-process `JobFinalized`/`MessageEnqueued` NOTIFYs and drives realtime push — previously impossible, as the listener couldn't construct without server-only deps. `DashboardBroadcaster<TContext>` already takes only Core/`AddWarp`-resolvable deps.

- **§2.13** `WarpBackgroundService` is a base part of Warp (no addon opt-in). `AddWarp<TContext>` always contributes the four entities (`Definition`/`Instance`/`Lease`/`Log`) to the model **and** registers `IBackgroundServiceQueryService` (read-only — needed by dashboard-only / publisher-only processes that never start a server). `AddWarpServer<TContext>` adds the server-side pieces: `BackgroundServiceHost<TContext>`, the lease coordinator, the state service, and the log store, plus (unless `opt.DisableWorker()`) the job worker hosts and the six job-only server tasks. **The worker is a component of the server** — `opt.DisableWorker()` (sets `RunWorker = false`) gives a service-only server: shared server-host infra (server registration, `ServerTaskHost`, `BackgroundServiceHost`, `Heartbeat`/`ServerCleanup`/`ExpirationCleanup`) with no worker hosts/job tasks and no `Worker`/`WorkerGroup` rows (`WarpServerRegistration` skips groups when `!RunWorker`). A provider is still required (server tasks take locks). The worker-on path and the service-only path share a private `AddWarpServerCore<TContext>(services, runWorker)` → `AddServerHostCore<TContext>`. Users register their own services with `opt.AddBackgroundService<T>()` (single type parameter — the receiver `IWarpBuilder` is non-generic for addons that don't need `TContext`). `PerServer` scope runs an independent instance on every server; `Singleton` scope coordinates via `BackgroundServiceLease` (30s TTL, renewed in `Heartbeat` ~5s cadence, ~30s worst-case failover on hard-kill / ~0s on graceful shutdown). Lease loss signaled via `ServerTaskSignals<TContext>.PublishBackgroundServiceLeaseLost`. Orphaned `BackgroundServiceDefinition` rows (renamed/removed services with no live `Instance`) are removed by `ExpirationCleanup` once `LastSeenAt` exceeds `WarpConfiguration.BackgroundServiceDefinitionOrphanGrace` (default 2 min). Worker hot path untouched (§0.2/§6.1) — separate `BackgroundServiceHost<TContext>` drives supervisor loops. See `website/docs/features/background-services.md`.

## Addon Composition

- **§2.11** Addons are opt-in via builder methods: `opt.AddRetry()`, `opt.AddConcurrency()`, `opt.AddRateLimit()`, `opt.AddCircuitBreaker()`, `opt.AddNoRestart()`, `opt.AddTimeout()`, `opt.UseDatabasePush()`, `opt.AddDashboardPush()`. Addons compose against Core's public API only — **never use `InternalsVisibleTo` to reach into Core internals**. **Addon entities are always in the schema** — `WarpModelCustomizer` adds `ConcurrencyLimit`, `CircuitBreakerState`, `RateLimitBucket`, `RateLimitOverride`, `SagaState`, `SagaJobLink` unconditionally so the migration story doesn't depend on which hosts opt in. The builder methods gate runtime behavior only (pipeline behaviors + admin services), not the table existence.
- **§2.12** Pipeline ordering matters (DI insertion order = outer → inner):
  - `AddRetry()` MUST come **before** `AddTimeout()` — retry's `catch (Exception)` needs to see the `TimeoutException` thrown by Timeout's `Fail` mode.
  - `AddConcurrency()` MUST come **before** `AddRateLimit()` — preserves rate-limit tokens when the mutex rejects.

## Server Context (3.0)

- **§2.14** Autonomous server-internal DB work runs on an internal **`WarpServerContext<TContext>`** (`Warp.Core`, registered by `AddServerHostCore`), not the user's `TContext`. It's a runtime-only mirror of the Warp model: `ApplyWarpModel` + `WarpConfiguration.EntityConfigurators` (so it mirrors `TContext`'s full model) + table/column/schema names pinned via **`IWarpServerModelNames`** + `ExcludeFromMigrations` (TContext stays the schema owner). **`WarpServerContext` never resolves `TContext`** — the names come from the `IWarpServerModelNames` abstraction (non-generic; default impl `WarpServerModelNames<TContext>` reads `TContext`'s model once via `IServiceScopeFactory` and caches it — the *single* place `TContext` is touched, swappable for another name source). Its connection comes from the provider via `IWarpServerContextConfigurator` (pulled from `TContext`'s options); its options demote EF's command-executed event to `Debug` (quiet logging) unless `opt.EnableServerCommandLogging`. Components depend on the **`IWarpServerContext`** abstraction (exposes `DbContext Context`) and extract the context once — never the concrete generic type (keeps them decoupled + testable; tests wrap any `DbContext`). **On the server context (all autonomous server-internal DB work):** the **job worker** fetch/execute path (`WarpWorkerService` / `WarpDispatcher*` — claim, processing log, completion, the job monitor), the 10 server tasks (`Heartbeat`, `Orchestrator`, `MessageRouter`, `ScheduledJobActivation`, `RecurringJobScheduler`, `StaleJobRecovery`, `CounterAggregator`, `ServerCleanup`, `ExpirationCleanup`), and the background-service host + its write services (state/lease/log). **Stays on `TContext` — only the outbox + user code:** `Publisher`/`BatchPublisher` staging job rows in the caller's transaction, the **handler scope** (handler code + its outbox + addon pipeline stores), and the dashboard query services / `IBackgroundServiceQueryService` (must resolve in `AddWarp`-only processes). `IWarpSqlQueries<TContext>` method params are `DbContext` so the queries accept either context (worker-fetch passes the server context; cold-path commands like `JobCommandService.DeleteJob` pass `TContext`). **A server task must not mix the two.** Every sweep inside one `ExecuteAsync` shares the task host's lock transaction on the server-context connection; reaching for `TContext` mid-task puts that work on a second connection, where it cannot commit atomically with the rest and — under read-committed locking (SQL Server without RCSI) — blocks on the row locks the same task is still holding, waiting on a transaction that only commits once `ExecuteAsync` returns. A task that needs to enqueue a job stages it directly (`JobHelper.CreateJob` + `NotificationDispatch.CapturePending` → dispatch from `OnCommittedAsync`, per `RecurringJobScheduler`/`MessageRouter`/`StaleJobRecovery`) instead of through the `TContext`-bound `IPublisher`. Worker hot path: only the resolved context type changed — no orchestration added (§0.2/§6.1). Tests that wait on worker-written `JobLog` rows poll the committed row (a `TContext`-scoped EF interceptor can't observe server-context writes).

## Outbound Adapters (Warp.Adapters)

- **§2.15** **Outbound** service-call observability is the mirror of the **inbound** `Warp.Http` binding: `Warp.Http` exposes Warp handlers *as* HTTP endpoints; `Warp.Adapters.Http` observes calls Warp *makes to* other services. The protocol-agnostic core lives in `Warp.Core.Adapters`: `IWarpAdapters.BeginCall(adapter, operation, group?)` returns an `AdapterCallScope` (`Succeed`/`Fail`/`SetGroup`/`SetCorrelation`/`SetTag`) usable for any transport (SOAP proxies, vendor SDKs) via manual scopes. **Telemetry is unconditional** (null-listener pattern, zero cost without a listener): every completed scope emits a `Client`-kind Activity named `{adapter}.{operation}` plus `warp.adapter.calls`/`warp.adapter.duration` meters regardless of `AddAdapters()`. **Only DB recording is gated by `opt.AddAdapters()`** — it registers the bounded-channel `DbAdapterCallRecorder` and the `AdapterCallFlusher` `IHostedService` (drains batches on an `IServiceScopeFactory`-created `TContext` scope, §0.5). Recording is **lossy-by-design**: a full channel drops the record + increments `warp.adapter.records_dropped` — user calls are never blocked or failed (call logs are diagnostics, not an audit trail — same stance as `JobLog`). The two entities (`AdapterDefinition`, `AdapterCallLog`, both in `Warp.Core.Data.Entities` §8.13) are added **unconditionally** by `WarpModelCustomizer` (§2.11) and mirrored by `WarpServerContext` (§2.14), so the schema is stable whichever hosts opt in. `AddAdapters()` uses the non-generic `IWarpBuilder` receiver (mirrors `AddBackgroundService<T>` §2.13). Adapter stats write `Counter` rows collapsed by `CounterAggregator` (never direct `Statistic` writes, §6.2); `ExpirationCleanup` (a server task) gains two bounded deletes (expired `AdapterCallLog` rows, orphaned `AdapterDefinition` rows past `AdapterDefinitionOrphanGrace`) — the worker hot path is untouched (§0.2/§6.1). `IAdapterQueryService` is registered by `AddWarp` itself (like `IBackgroundServiceQueryService`), so **dashboard-only / publisher-only / `AddWarp`-only** processes resolve it and serve `/api/adapters*` without running a server or calling `AddAdapters()`. The **cluster-shared rate limiter** reuses the `RateLimitBucket` entity (key `warp:adapter:{name}`, disjoint namespace §8.6) with DB-backed token leasing — a differentiator per-process Polly cannot provide; the one row-lock need goes through `IWarpSqlQueries` (§1.4), no raw SQL in Core (§5.1). Shared-policy persistence is **first-writer-wins**: the first registration writes the policy onto `AdapterDefinition`; a later process whose local policy differs **enforces the persisted policy**, logs a Warning, increments `warp.adapter.config_conflicts`, and sets `HasPolicyConflict` (dashboard badge) — deploys alone never rewrite it. Runtime precedence `RateLimitOverride` admin row > persisted definition > local code; **change a shared limit via a `RateLimitOverride` admin row (which takes precedence) or by clearing the persisted policy**, not by redeploying. Two thin binding packages compose against Core's public API only (no `InternalsVisibleTo`, §0.5): `Warp.Adapters.Http` (a `DelegatingHandler` that auto-scopes `IHttpClientFactory` clients; Polly via `Microsoft.Extensions.Http.Resilience`) and `Warp.Adapters.Refit` (operation names from `RestMethodInfo`; the only package referencing Refit). See `website/docs/features/adapters.md`.
