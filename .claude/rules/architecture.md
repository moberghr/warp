# Architecture Patterns

> Rules only. Rationale, history, measurements and full rot-guard lists live in `.claude/references/design-notes/<section>-*.md` (§2.3, §2.5, §2.7.1–§2.10, §2.13–§2.20) — **read the note before changing a section's area**.

## Unified Data Model

- **§2.1** Everything is a **Job** with a `Kind` discriminator (`Job=1, Message=2, Batch=3`). No separate Message/Batch tables. `ParentJobId` chain handles all parent-child relationships. Messages spawn N child jobs; Batches group children. Continuations chain via `ParentJobId` to a single parent.

## Worker / Server-Task Split

- **§2.2** Workers are **pure executors**. They only fetch and execute `Kind=Job` jobs. Never add orchestration, routing, parent/child finalization, or cross-cutting logic to `WarpWorkerService` or its dispatcher counterparts (`WarpDispatcher`, `WarpDispatcherWorker`).
- **§2.3** Every background task implements `IServerTask` (`Name`, `LockKey`, `DefaultInterval`, `ExecuteAsync`), registered scoped. `ServerTaskHost<TContext>` splits them: a task with a `LockKey` is cluster-wide (claimed through its `ClusterTask` row by one `ClusterTaskScheduler` per server, §6.23); one without (the heartbeat) runs on its own `PerServerTaskLoop`. Both execute through `ServerTaskRunner`. Active tasks: **on every server** (`AddServerHostCore`, `DisableWorker()` included) `Heartbeat`, `ServerCleanup`, `ExpirationCleanup`, `StatisticRollup`, `MetricRollup`, `CounterAggregator`, `ErrorGroupAggregator`, `SloEvaluator`; **job-only, with a worker** (`AddWarpServerCore`) `StaleJobRecovery`, `WebhookEndpointMonitor`, `BacklogSampler`, `RecurringJobScheduler`, `ScheduledJobActivation`, `MessageRouter`, `Orchestrator`; plus `NotificationListenerTask` (when DB push is enabled). Folds that read rows any process may write are cluster-locked and live in `AddServerHostCore` (§2.13, §8.18).
- **§2.4** Services expose interfaces (`IJobCommandService`, `IJobQueryService`, `IRecurringJobService`, `IDashboardStatsService`, etc.). Generic implementations take `TContext : DbContext`. Inject the specific interface — **never inject `IServiceProvider`** (use `IServiceScopeFactory` when you genuinely need scope creation).
- **§2.5** `AddWarp<TContext>()` / `AddWarpServer<TContext>()` auto-configure the user's DbContext (row-lock interceptors, model customizer, `TimeProvider.System` via `TryAddSingleton`, `IWarpLockProvider`). The server builder inherits `WarpConfiguration` / `WarpServerConfiguration`, so config fields are set directly on `opt`. **Two-builder shape:** `IOptions<WarpConfiguration>` and `IOptions<WarpServerConfiguration>` are separate singletons, so **both entry points call `WarpConfigurationMerge.ApplyCoreSettings`** (reflection over `WarpConfiguration`'s writable properties; `AddWarpServer` merges before its fail-fast validation). A Core setting configured on one builder and default on the other is carried over; configured on **both to different values** throws at registration; a default on the source is not copied. `EntityConfigurators` is deliberately not merged. New Core settings need no merge wiring. Guard: `WarpConfigurationMergeTests`. `AddWarpWorker` / `WarpWorkerConfiguration` / `WarpWorkerBuilder` were removed in 2.0.

## In-Memory Requests & Streams

- **§2.6** In-memory `IRequest<TResponse>` goes through `IMediator.Send()` — same `IPipelineBehavior` pipeline as jobs/messages, but no DB persistence. Returns `TResponse` synchronously.
- **§2.7** `IStreamRequest<TResponse>` extends `IRequest<IAsyncEnumerable<TResponse>>` and goes through `IMediator.CreateStream()`. Request-level `IPipelineBehavior` applies automatically; enumeration-level concerns use `IStreamPipelineBehavior<TRequest, TResponse>`. No DB persistence.
- **§2.7.1** **Scope per send (#321, opt-in `opt.Mediator.ScopePerSend`, default off).** `IMediator` is registered through a factory that returns `Mediator` or the internal `ScopePerSendMediator` (async scope per `Send`, runs every `ISendScopeInitializer(parent, child)`; for `CreateStream` the scope lives for the enumeration; nested sends get their own). `WarpMediatorOptions` is a record so the merge compares it by value. `Warp.Http` dispatches in the REQUEST scope regardless via the public `ISendScopeBypass.InCurrentScope` (§0.5). Workers never go through `IMediator` (§0.2). Guard: `ScopePerSendMediatorTests`.

## Scheduling & DB Push

- **§2.8** Future-dated jobs land in `State.Scheduled`; `ScheduledJobActivation` flips them to `Enqueued` when `ScheduleTime <= now`, every `ScheduledActivationInterval` (default 10s — the worst-case latency). It is time-driven and does not participate in DB-push wake-up, but it **emits** one: it builds the `Notification` itself and dispatches from `OnCommittedAsync` (§6.3/§8.25). Worker fetch queries filter `CurrentState == Enqueued` with a defensive `ScheduleTime <= now`; **a new query site filtering on `Enqueued` without the time predicate is a latent bug** on upgraded deployments.
- **§2.13** **`WarpBackgroundService` is base Warp** (no opt-in). `AddWarp` always contributes the four entities (`Definition`/`Instance`/`Lease`/`Log`) and `IBackgroundServiceQueryService`; `AddWarpServer` adds `BackgroundServiceHost<TContext>`, lease coordinator, state service, log store, plus (unless `opt.DisableWorker()`) the worker hosts and the six job-only tasks. **The worker is a component of the server**: `DisableWorker()` (`RunWorker = false`) gives a service-only server — shared host infra and the cluster-locked folds, no worker hosts, no `Worker`/`WorkerGroup` rows, never claims a job; a provider is still required. Both paths share `AddWarpServerCore<TContext>(services, runWorker)` → `AddServerHostCore<TContext>`. Register with `opt.AddBackgroundService<T>()`. `PerServer` runs on every server; `Singleton` coordinates via `BackgroundServiceLease` (30s TTL, renewed in `Heartbeat`). Worker hot path untouched (§0.2). See `website/docs/features/background-services.md`.

## Addon Composition

- **§2.11** Addons are opt-in via builder methods: `opt.AddRetry()`, `opt.AddConcurrency()`, `opt.AddRateLimit()`, `opt.AddCircuitBreaker()`, `opt.AddNoRestart()`, `opt.AddTimeout()`, `opt.UseDatabasePush()`, `opt.AddDashboardPush()`. Addons compose against Core's public API only — **never use `InternalsVisibleTo` to reach into Core internals**. **Addon entities are always in the schema** — `WarpModelCustomizer` adds `ConcurrencyLimit`, `CircuitBreakerState`, `RateLimitBucket`, `RateLimitOverride`, `SagaState`, `SagaJobLink` unconditionally so the migration story doesn't depend on which hosts opt in. The builder methods gate runtime behavior only (pipeline behaviors + admin services), not the table existence.
- **§2.12** Pipeline ordering matters (DI insertion order = outer → inner):
  - `AddRetry()` MUST come **before** `AddTimeout()` — retry's `catch (Exception)` needs to see the `TimeoutException` thrown by Timeout's `Fail` mode.
  - `AddConcurrency()` MUST come **before** `AddRateLimit()` — preserves rate-limit tokens when the mutex rejects.

## Server Context (3.0)

- **§2.14** Autonomous server-internal DB work runs on the internal **`WarpServerContext<TContext>`** (registered by `AddServerHostCore`), a runtime-only mirror of the Warp model (`ApplyWarpModel` + `EntityConfigurators`, names pinned via `IWarpServerModelNames`, `ExcludeFromMigrations`). **It never resolves `TContext`** and mirrors NAMES only (§5.12 guarantees the physical columns agree). Connection from the provider via `IWarpServerContextConfigurator`. Components depend on the **`IWarpServerContext`** abstraction, never the concrete generic type.
  - **On the server context:** the job worker fetch/execute path, the 14 server tasks (§2.3), the background-service host and its write services, and the addon pipeline stores (through `DeferredWarpContext`, §6.17).
  - **On `TContext` — only the outbox + user code:** `Publisher`/`BatchPublisher`, the handler scope (the worker never resolves or saves it, §6.17), the addon admin managers, the dashboard query services / `IBackgroundServiceQueryService` (must resolve in `AddWarp`-only processes).
  - `IWarpSqlQueries<TContext>` method params are `DbContext`, so queries accept either.
  - **A server task must not mix the two**: `TContext` mid-task is a second connection that cannot commit atomically and can block on the task's own row locks. A task that enqueues stages the job directly (`JobHelper.CreateJob` + `NotificationDispatch.CapturePending` → dispatch from `OnCommittedAsync`), not through `IPublisher`.
  - Tests that wait on worker-written `JobLog` rows poll the committed row (a `TContext` interceptor can't see server-context writes).

## Distributed Locking

- **§2.16** Two lock shapes; **the difference is a deployment contract.** **Transaction-scoped** (`IWarpSqlQueries.RunUnderTransactionLockAsync`; `IServerTask.LocksWithTransaction` default true) is safe through any pooler. **Session-scoped** (`IWarpLockProvider.TryAcquireAsync` → Medallion) is **broken by a transaction-mode pooler** and is used only where guarded work spans multiple transactions: `RecurringJobPublisher.AddOrUpdateRecurringJob`, `MessageRouter` (`LocksWithTransaction => false`), `SagaHandlerProxy`, `SagaCommandService.ForceComplete`, `RateLimitPipelineBehavior`, the `ConcurrencyPipelineBehavior` semaphore. **Prefer the transaction-scoped lock for anything new**; say why in a comment otherwise.
- **§2.17** **Releasing a lock never throws.** Every DB-backed provider wraps its handle in **`SafeReleaseLockHandle`** (`Warp.Core.Locking`, public), which catches on `DisposeAsync` and logs at Warning. The contract is set at the provider, not the call sites. On `PostgresSemaphoreProvider` the wrap sits outside `SlotHandle`. **Do NOT re-add a rethrow.** Guard: `SafeReleaseLockHandleTests`. Operator detail: `website/docs/operations/connection-pooling.md`.

## Lossy In-Process Pipelines

- **§2.19** Every "record now, persist/publish later" pipeline uses ONE model in `Warp.Core.Buffering`: **`DrainQueue<T>`** (bounded; `TryAdd` never waits, returns `false` when full so the producer counts the drop) + **`DrainService<T>`** (wait, take up to `BatchSize`, `FlushAsync`; at shutdown drain within `ShutdownDrainBudget`). Users: the adapter, endpoint and client-event flushers and `EnqueueNotificationRelay`. **`FlushAsync` must not throw.** NOT for the worker-path `WarpCounterBuffer` (§6.2) or `JobLogCollector`. Guard: `DrainServiceTests`.
