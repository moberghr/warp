# Project-Specific Patterns

## Configuration

- **§8.1** `WarpConfiguration` via `IOptions<WarpConfiguration>`. All configurable values go through this pattern. The builder (`AddWarp<TContext>(opt => ...)`) inherits from `WarpConfiguration`, so config fields are set directly on `opt`.

## Job Lifecycle

- **§8.2** Failed jobs never auto-delete (`ExpireAt = null`). Only explicit user action (dashboard delete/requeue) or count-based cleanup (`MaxExpirableJobCount`, default null/disabled — deletes oldest by `ExpireAt` when threshold exceeded; failed jobs excluded).
- **§8.3** `ContinuationOptions` is generalized to all job kinds — any job with children can control child activation on parent failure.
- **§8.4** `RequeueJob` resets `ScheduleTime` to now. Requeued jobs always execute immediately.
- **§8.5** Cancellation uses `CancellationMode` enum (`None=0, Graceful=1`), not an immediate state change. `DeleteJob` sets `CancellationMode = Graceful`; `RunJobMonitor` detects this and cancels the handler's `CancellationToken`. If the handler ignores the token and completes, state stays `Completed` (work happened) and `CancellationMode` is cleared. Dashboard shows "Cancelling..." badge while waiting.

## Addons (Mutex, Semaphore, Timeout, RateLimit, CircuitBreaker, DB Push)

- **§8.6** Concurrency control is opt-in via `opt.AddConcurrency()`. `[Mutex("k")]` (limit fixed at 1) and `[Semaphore("k", N)]` (limit > 1) share `ConcurrencyPipelineBehavior`. Two policies via `ConcurrencyMode`: `Skip` (`[Mutex]` default — surplus → `Deleted`) and `Wait` (`[Semaphore]` default — surplus requeued). **Disjoint namespaces by design:** `[Mutex("k")]` uses `warp:concurrency:k`; `[Semaphore("k", N)]` uses `warp:concurrency:k:0..k:{N-1}`. Mixing both against the same key produces independent limits. Admin overrides via `IConcurrencyLimitManager` (precedence: `admin row > meta.Limit > 1`). Hide-on-404 dashboard nav.
- **§8.7** Timeout is opt-in via `opt.AddTimeout()`. `[Timeout(seconds: N)]` or `WithTimeout(TimeSpan)`. Two modes (`TimeoutMode`): `Delete` (default — pipeline sets `Deleted`, **not retried** by `AddRetry`) and `Fail` (throws `TimeoutException`, **caught** by `AddRetry`). Two scopes (`TimeoutScope`): `PerAttempt` (fresh budget per retry) and `Total` (`DeadlineUtc` stamped on publish). **Ordering: `AddRetry()` MUST come before `AddTimeout()`** (§2.12).
- **§8.8** Rate limiting is opt-in via `opt.AddRateLimit()`. Two styles (`Style`): `Fixed` (wall-clock window, floor-aligned to global UTC ticks) and `Sliding` (rolling window over last N starts, defensively trimmed). Two policies (`Mode`): `Skip` (default — `Deleted`) and `Wait` (rescheduled via `JobOutcome.RescheduledState`). `perSeconds` capped at `MaxWindowSeconds` (7 days). Lock is released after check-and-increment — **not** held during handler execution (unlike Mutex). Live state in `RateLimitBucket` entity. Lock-contention reschedule has 100–500ms jitter. **DB push does NOT accelerate Wait-mode reschedules** — they land in `State.Scheduled` and depend on `ScheduledJobActivation` polling. **Ordering: `AddConcurrency()` before `AddRateLimit()`** so mutex rejects don't waste tokens.
- **§8.9** `RecurringJobScheduler` creates jobs with `ScheduleTime = now`. `AddOrUpdateRecurringJob` only registers/updates the definition — does **not** create jobs. Acquires a distributed lock on the recurring-job name and saves immediately (deliberate §5.7 exception). `RecurringJobLog` is the immutable audit trail; `ExpirationCleanup` retains the last 100 logs per recurring job.

## Conventions

- **§8.10** Source generators (`Warp.SourceGenerator`, `Warp.Http.SourceGenerator`) target `netstandard2.0` and provide zero-allocation mediator dispatch and HTTP endpoint generation. `[WarpHttpGet/Post/Put/Patch/Delete]` annotations on handler classes emit `RequestDelegate`s; `IJob` / `IMessage` rejected at compile time (`WHTTP001`). **Binary I/O:** a handler whose response is `Microsoft.AspNetCore.Http.IResult` (`IRequest<IResult>`) owns the full HTTP response — `JsonResponseWriter` detects `IResult` and calls `ExecuteAsync`, skipping the JSON envelope, so `Results.Stream/File/Bytes/NotFound/Ok` all work (used for file serving, bodyless status codes). **Multipart/form uploads:** request members typed `IFormFile`/`IFormFileCollection`/`IFormCollection` or carrying `[FromForm]` bind from the form (`BindingSource.Form`, emitted as a `Mixed` shape); `MapWarpHttp` sets `multipart/form-data` and `DisableAntiforgery()` on those endpoints. A request cannot bind both a form and a JSON `[FromBody]` (`WHTTP006`). Demo endpoints: `Warp.Test.Shared/HttpEndpoints.cs` — `/http/file-echo` (upload a file, echo its contents) and `/http/text-to-file` (send text, download it as a file).
- **§8.11** **Enums always start at 1, never 0.** `Skip = 1, Wait = 2`, never `Skip = 0`. Avoids `default(T)` collisions and forces explicit assignment. Applies to `JobKind`, `State`, `CancellationMode`, `ConcurrencyMode`, `RateLimitMode`, `RateLimitStyle`, `TimeoutMode`, `TimeoutScope`, etc.
- **§8.12** **Metadata properties are addon-prefixed**, not bare names. `IRateLimitMetadata.RateLimitKey` (not `Key`), `IRateLimitMetadata.RateLimitWindowSeconds` (not `WindowSeconds`), `IConcurrencyMetadata.ConcurrencyKey` / `ConcurrencyLimit` / `ConcurrencyMode`. Prevents dict-key collisions when a single job carries multiple metadata interfaces. Avoid `Dictionary<,>` names entirely — they're a red flag for collision-prone APIs.
- **§8.13** Entity namespaces are **split**: `Job` lives in `Warp.Core.Entities`; `JobLog`, `Server`, `Worker`, `ServerTask`, `ServerLog`, `RecurringJob`, `RecurringJobLog`, `RateLimitBucket`, `RateLimitOverride`, `ConcurrencyLimit` etc. live in `Warp.Core.Data.Entities`. Same folder, different namespaces — do not collapse them.
- **§8.14** **Routed `IMessage` jobs must keep `HandlerType` on requeue.** Addons that commit inside handler scope must capture-save-fire and clear-tracker-on-conflict (saga correctness pitfalls).
- **§8.15** Real-time log flushing: `RunJobMonitor` drains `JobLogCollector` every ~1s during handler execution and persists logs to the database. Logs visible in the dashboard while the job is still processing.
- **§8.16** `MetadataConvert` was string-only until the DateTime branch added 2026-05-12 — non-primitive `IJobMetadata` properties need explicit roundtrip tests.
- **§8.17** Sagas are an opt-in addon (`opt.AddSagas()` on the builder) in `Warp.Core.Sagas`. Subclass `Saga` (or `Saga<TKey>` for typed `string`/`Guid`/`int`/`long` keys), annotate the correlation property with `[Correlate]`, mark saga-starting messages with `[StartsSaga]`, implement `ISagaHandler<TSaga, TMessage>`, register handlers via `services.AddSagaHandler<H>()`. Storage: `SagaState` row per active saga + `SagaJobLink` extension table for the activity log with FK cascade. **Delete-on-completion** — `MarkCompleted()` removes the row in the same `SaveChanges`; the correlation key is immediately reusable. No auto-expiry; `ITimeoutMessage` self-schedules at `now + Delay`, and timeout-after-completion silently drops (`Outcome = Deleted`). Proxy serializes per correlation key on `warp:saga:{TSaga.FullName}:{key}` via `IWarpSemaphoreProvider`; optimistic `Version` concurrency is defense-in-depth. Both busy and version/unique conflict outcomes use jittered `ScheduleTime` (50–250ms) to avoid hot loops. `SagaCorrelationKeyConverter` trims strings, rejects empty-after-trim and `default(T)`, caps length at 200. `SagaPiiCheck` blocks `[Correlate]` properties matching common PII names (Email/Phone/SSN/etc.) at registration time; opt out with `[Correlate(IsAnonymized = true)]`. `ISagaCommandService.ForceComplete` acquires the saga mutex and emits a structured `LogInformation` audit. Dashboard at `/warp/sagas` and `/warp/sagas/{id}` with hide-on-404 nav; activity log query caps at 200 most-recent invocations with `IsTruncated` flag. Telemetry counters `warp.sagas.started`/`completed`/`requeued` (tagged `reason=busy|version|unique`). See `website/docs/features/sagas.md`.
- **§8.18** `WarpBackgroundService` is a base part of Warp (no addon opt-in) in `Warp.Core.BackgroundServices`. `AddWarp<TContext>` always contributes the four entities **and** registers `IBackgroundServiceQueryService` (so dashboard-only / publisher-only processes can serve `/api/services` without starting a server); `AddWarpServer<TContext>` adds the server-side host, lease coordinator, state service, and log store, plus the job worker by default. **The worker is a component of the server**: `opt.DisableWorker()` (sets `RunWorker = false`; `AddWarpServer` rejects `RunWorker = true` with zero total workers) yields a service-only server — background services + supporting server tasks (`Heartbeat`/`ServerCleanup`/`ExpirationCleanup`) without the job worker or job-only server tasks (provider still required). `WarpServerRegistration` creates no groups when `!RunWorker` (and skips `WorkerCount == 0` groups otherwise), so a service-only server leaves no `Worker`/`WorkerGroup` rows. `AddWarpWorker`/`WarpWorkerConfiguration`/`WarpWorkerBuilder` were removed in 2.0 (renamed to `AddWarpServer`/`WarpServerConfiguration`/`WarpServerBuilder`). Users register their own services with `opt.AddBackgroundService<T>()` (single type parameter on the non-generic `IWarpBuilder` receiver). Subclass `WarpBackgroundService`, override `Scope` (`PerServer = 1` — default, one instance per server; `Singleton = 2` — cluster-wide lease). Storage: `BackgroundServiceDefinition` (one row per service name), `BackgroundServiceInstance` (one per server-service pair), `BackgroundServiceLease` (singleton coordination, 30s TTL renewed in `Heartbeat`), `BackgroundServiceLog` (captured user + lifecycle events; FK cascade on instance delete). All in `Warp.Core.Data.Entities`. Worst-case singleton failover ~30s on hard-kill / ~0s on graceful shutdown (lease deleted in `StopAsync` before waiting on user code). Orphaned `Definition` rows (renamed/removed services with no live `Instance`) are deleted by `ExpirationCleanup` once `LastSeenAt > WarpConfiguration.BackgroundServiceDefinitionOrphanGrace` (default 2 min). **Captive-scoped-dependency foot-gun**: subclasses are singletons — inject `IServiceScopeFactory`, not `DbContext`; `ValidateScopes=true` catches it at startup. Log capture is auto-wired (`BackgroundServiceLoggerProvider`) with `MinLogLevel` (default Information), 100/s rate cap, 4KB message truncation, 1000-row/7-day retention. **§1.2 PII responsibility** applies to log output. Telemetry counters: `warp.background_services.started` (tag: `service_name`), `warp.background_services.faulted` (tags: `service_name`, `exception_type`), `warp.background_services.lease_lost` (tag: `service_name`), `warp.background_services.restarts` (tag: `service_name`). Worker hot path untouched (§0.2/§6.1) — separate `BackgroundServiceHost<TContext>`. See §2.13, `website/docs/features/background-services.md`.

- **§8.19** **Outbound adapters** are Warp's answer to observing calls the app *makes to* other services (contrast `Warp.Http` §8.10, which exposes Warp handlers *as* inbound endpoints — the naming `Warp.Adapters.Http` vs `Warp.Http` is inbound-vs-outbound and docs state it explicitly). Protocol-agnostic core in `Warp.Core.Adapters`; HTTP binding in `Warp.Adapters.Http`; Refit sugar in `Warp.Adapters.Refit` (only that package references Refit). **Three-axis identity — memorize the litmus test:** **adapter = policy + health boundary** (registration-time; retry/timeout/rate-limit config + SLO), **group = runtime who/where** (destination, tenant, shop, region — a *runtime value*, always explicit, never heuristic-derived, unbounded), **operation = what** (the API-contract axis — `GetOrders`, `payment.completed`; bounded, may be heuristic-derived). Litmus: if swapping the value changes the request's *structure* (route/verb/payload) → operation; if it only changes *where it goes or on whose behalf* → group. Diagnosis follows the axes: an operation red across all groups = caller-side bug (malformed payload, schema drift); a group red across all operations = counterparty problem (dead token, downed receiver); everything red = the adapter/vendor itself. Enums from 1 (§8.11): `CallRecording { All = 1, FailuresOnly = 2 }`, `CaptureMode { None = 1, OnFailure = 2, Always = 3 }`, `AdapterCallOutcome { Success = 1, Failed = 2, Throttled = 3, CircuitOpen = 4 }` (`CircuitOpen` reserved for the breaker fast-follow), `AdapterRateLimitOverflow { Wait = 1, FailFast = 2 }`. **Capture is opt-in and PII-owned (§1.2):** metadata always; request bodies, response bodies, and headers each independently `None`/`OnFailure`/`Always`, truncated (`MaxCapturedBodySize` 8 KB / `MaxCapturedHeaderSize` 4 KB) and passed through the user-owned `RedactedHeaders` denylist (case-insensitive, prepopulated with `Authorization`/`Proxy-Authorization`/`Cookie`/`Set-Cookie`/`X-Api-Key`; `Add`/`Remove`/`Clear` fully overridable — mandatory `Authorization` redaction was rejected, the denylist is a default not a lock). `RecordCalls = All` (default) writes a row per call — the volume knob for hot adapters is per-adapter `FailuresOnly`; capture modes control payload richness only, orthogonal to whether a row exists. **Cardinality guards:** `MaxDistinctOperations` (default 50) collapses *heuristic-derived* operation names beyond the cap to a literal `{other}` with a one-time warning (explicit names never collapse); `MaxDistinctGroups` (default 500) does the same for group values. `IncludeGroupInMetrics` (default false) keeps group off meter tags unless opted in (bounded group sets); group is always a span attribute + counter key regardless. **Shared rate limit = coordinated config:** `adapter name = cluster-wide identity` (same name ⇒ stats merge and limits share by design; genuinely different dependencies get different names). Shared-policy persistence is **first-writer-wins**: the first registration persists the policy onto `AdapterDefinition`, and later mismatching processes **enforce the persisted policy**, log a Warning, increment `warp.adapter.config_conflicts`, and set `HasPolicyConflict` (dashboard badge) — deterministic mid-rolling-deploy, and deploys alone never change the persisted limit (conflict is preserved, not overwritten, per SC13). Runtime precedence `RateLimitOverride` admin row > persisted definition > local code; **change a shared limit via a `RateLimitOverride` admin row (which takes precedence) or by clearing the persisted policy**, not by redeploying a new code value. **Adoption + rollout guidance:** adapters need only `AddWarp<TContext>` (no server/worker) — they run in any process, alongside other job systems; recording persists via the flusher on the user's `TContext`. **Observe-first is the recommended rollout:** register with no `UseResilience`/`UseSharedRateLimit` (the passive observing handler alone, zero behavioral change — same timeouts, single attempt, same exceptions), read the data, then add policy per adapter once it justifies the split. Telemetry: `warp.adapter.calls`, `warp.adapter.duration`, `warp.adapter.records_dropped`, `warp.adapter.config_conflicts`. See §2.15, `website/docs/features/adapters.md`.
- **§8.20** **Outbound webhooks** (`Warp.Adapters.Webhooks`, opt-in via `opt.AddWebhooks(...)` inside the `AddWarp`/`AddWarpServer` lambda; builds on adapters §8.19) make durable webhook *delivery* a Warp feature. **Boundary: the host owns subscriptions + fan-out + payload building + endpoint enable/disable + its own secret tables; Warp owns everything after `SendAsync`** — delivery lifecycle, executor jobs, retry scheduling, exhaustion, signing, redelivery, dashboard. Warp models no subscriptions; the host calls `IWebhookDispatcher.SendAsync(WebhookSend)` once per destination. **The delivery, not the job, is the state machine:** the executor (`ExecuteWebhookDelivery`, an ordinary source-gen job on queue `warp:webhooks` — worker hot path untouched §0.2/§6.1) **always completes**; every attempt exception is caught and recorded as attempt failure, so webhook failures never surface as failed jobs or pollute the Jobs UI. State lives on the always-in-schema (§2.11) `WebhookDelivery` row (`Warp.Core.Data.Entities`, §8.13): `WebhookDeliveryStatus { Pending = 1, Delivered = 2, Exhausted = 3 }` (§8.11). **Self-contained row** — URL, headers, payload, schedule, success codes, signing mode + secret, group, reference all stamped at `SendAsync` time so a later config deploy never reshapes an in-flight delivery. **`SendAsync` persists `Pending` + enqueues the first attempt in the caller's transaction (outbox), returns the delivery id** (= adapter `CorrelationId`). **Attempts are adapter calls** through the auto-registered `warp-webhooks` adapter (group = endpoint, operation = event type, `CorrelationId` = delivery id; `RecordCalls = All`, response bodies always captured, request bodies never — payload already on the row; `CallLogRetention` aligned to `WebhookDeliveryRetention`) — the attempt timeline is `AdapterCallLog WHERE CorrelationId = deliveryId`, **no separate attempt table**. **No timers/scans:** each retry is a fresh executor job in `State.Scheduled` at `now + schedule[N-1]` riding `ScheduledJobActivation` (§2.8); `(RetrySchedule, AttemptCount)` fully determines the plan (schedule column never mutated), exhausted when `AttemptCount > schedule.Count`. `RetrySchedule` is per-send `IReadOnlyList<TimeSpan>` (§3 pillar: **no app-level schedule knob**): `null` = built-in `[1m,10m,1h,6h]`, `[]` = single attempt then `Exhausted`, N entries = N retries; persisted as a JSON seconds array (`"[60,600,3600,21600]"`/`"[]"`) via `RetryScheduleConverter` (§8.16 roundtrip tests mandated — empty/single/multi-hour on both providers). `SuccessCodes` `null` = any 2xx. **Cadence precision is delay + up to ~5s activation + worker pickup — a backoff, not a precision scheduler; document it.** Signing (`WebhookSigning { None = 1, StandardWebhooks = 2, Custom = 3 }`, §8.11): `None` (default, adds nothing — the legacy body-embedded-HMAC migration path), `StandardWebhooks` (HMAC-SHA256 over `{webhook-id}.{webhook-timestamp}.{payload}`, headers `webhook-id`/`webhook-timestamp`/`webhook-signature` `v1,<base64>`, `webhook-id` = `EventId` stable across retries), `Custom` (registered `IWebhookSigner` via `w.UseCustomSigner<T>()` — **declaring custom signing without a signer throws at `AddWebhooks` time, not send time**). **Secrets at rest** on the row are accepted for self-containment; **redacted on every read surface** (query service, endpoints, dashboard reduce `Secret` to a `HasSecret` flag, `Authorization`-class headers redacted — not caller-toggleable), never logged Info+ (§1.2); stricter hosts use `Signing = None` and sign in their own payload code. Exhaustion flips `Status = Exhausted` and invokes the host's `IWebhookDeliveryExhaustedHandler` **at-least-once, post-commit** with a redaction-safe snapshot (`ExhaustedCallbackPending` commits with the transition; the recovery check is **status-independent** so a `Redeliver` that flips the row back to `Pending` before the crash-recovery re-run still fires the prior exhaustion's callback) — a throwing callback is logged at Warning, never propagated (callbacks/instrumentation never out-throw). Host decides endpoint disable; Warp only signals. `IWebhookCommandService.Redeliver(id)` requeues a **settled** (`Delivered`/`Exhausted`) delivery to `Pending` + immediate job; `Pending`/unknown rejected with no side effects. **Stuck-delivery recovery (the one deliberate exception to no-timers/no-scans):** the executor's attempt claim and its outcome commit are two transactions — a fault on the second leaves the row `Pending` with no live job (the retry job was staged in the failed transaction). The claim therefore stamps `NextAttemptAt` even on a final attempt, and `StaleJobRecovery` sweeps `Pending` rows whose `NextAttemptAt` is more than `WarpConfiguration.WebhookStuckDeliveryGrace` (default 10 min) past. Duplicate-proof by construction: candidates that still have a live executor job on the webhooks queue are skipped (merely-backlogged workers ≠ lost job), and the guarded `NextAttemptAt` bump + the new job commit in ONE transaction on the scoped `TContext` via the `IWebhookRedeliveryEnqueuer` seam (the `Redeliver` pattern; no-op in processes without `AddWebhooks`) — a rollback undoes both, so no bumped-without-job or job-without-bump state exists. The recovered exhausted-callback reconstructs the exhaustion's `AttemptCount` from `RetrySchedule.Count + 1` on post-`Redeliver` rows (the live column was reset to 0). `IWebhookQueryService`/`IWebhookCommandService` live in `Warp.Core.Webhooks` and resolve in any `AddWarp` process (dashboard/publisher-only) reading on `TContext` (§2.14). `ExpirationCleanup` deletes deliveries past `ExpireAt` (`WebhookDeliveryRetention`, default 30d). **Adoption prerequisite: a Warp server (worker) must run somewhere** to drain `warp:webhooks` — coexistence with another job system (e.g. Hangfire) is a documented supported shape. Dashboard **Webhooks** nav gated on `GET {prefix}/api/addons` `webhooks` flag (true only where `AddWebhooks()` ran). Telemetry: `warp.webhooks.deliveries`/`attempts` (tag outcome) + `warp.webhooks.redeliveries`. See §8.19, `website/docs/features/webhooks.md`.

- **§8.21** **Inbound endpoint observability** (`Warp.Http`, opt-in via `opt.AddEndpointObservability(o => ...)` inside the `AddWarp`/`AddWarpServer` lambda + `app.UseWarpHttpObservability()` after `UseRouting`) is the **inbound mirror of adapters §8.19**: adapters observe calls the app *makes to* other services; this observes requests *made to* the app's **Warp HTTP endpoints** (handlers exposed via `MapWarpHttp`). Scope is Warp endpoints only — the middleware no-ops unless the matched endpoint carries the `WarpEndpointIdentity` metadata attached in `EndpointRouteBuilderExtensions.ApplyMetadata`, so it never observes the host's own controllers, the dashboard, health, or static files. **Identity = HTTP method + route TEMPLATE** (`GET /orders/{id}`) — already bounded (no runtime path-cardinality heuristic, unlike outbound's URL collapsing); inline constraints are normalized away (`{id:int}`→`{id}`) via `EndpointCounterKeys.NormalizeTemplate` so the colon-delimited counter key parses unambiguously, and the flusher stamps the SAME normalized method+template onto the `EndpointCallLog` row so the detail page joins log rows to aggregates. The route is the operation — counter dimensions are **Total + Group only** (no operation dimension); `group` is an optional low-cardinality caller key from `o.GroupSelector(HttpContext)` (channel/client/tenant — never raw IP/user id). Core is protocol-agnostic (`Warp.Core.Endpoints`: `EndpointCallLog` entity §8.13 always-in-schema §2.11, public `IEndpointCallRecorder`/`EndpointCallRecord` seam, `DbEndpointCallRecorder` bounded lossy channel, `EndpointCallFlusher<TContext>` drain→rows+`Counter`s, internal `EndpointCounterKeys`); the HTTP binding (`Warp.Http.Observability`) holds `WarpEndpointObservabilityOptions` (HttpContext-dependent), `WarpInboundObservabilityMiddleware`, and `AddEndpointObservability`/`UseWarpHttpObservability`. **Capture (§1.2 PII):** caller IP (`RemoteIpAddress`, or first `X-Forwarded-For` hop when `UseForwardedForIp`), user-agent, and `User.Identity.Name` are captured by default (the point of the feature) but are PII; request/response bodies + headers are each `None`/`OnFailure`/`Always` (default `OnFailure`), truncated (`MaxCapturedBodySize` 8 KB via a bounded pass-through `CaptureBodyStream` that never buffers a whole streaming/`IResult` response, `MaxCapturedHeaderSize` 4 KB) and redacted through the same user-owned `RedactedHeaders` denylist as adapters. Outcome `Failed` = status ≥ 500 or unhandled exception (4xx = client error, counted Success so error rate stays meaningful). `RecordCalls = FailuresOnly` skips success ROWS only (counters still written, error-rate denominator intact). **Recording is lossy + never blocks/fails the request** (full channel drops the record); `RecordAsync` swallows its own errors. **Metrics survive log deletion** (§ retention): counts/error-rate/avg-latency come from `Counter`→`Statistic` aggregates (a duration-sum `dur` token backs the average, same as adapters §2/Item 2); recent-calls + per-caller last-failure read raw rows and degrade to empty/null once swept. **Retention is GLOBAL** on `WarpConfiguration.EndpointCallLogRetention` (age, default 7d, stamped as `ExpireAt` by the middleware) + `EndpointCallLogRetentionCount` (count, null=off, keep newest N per method+route), both swept by `ExpirationCleanup` (`CleanupExpiredEndpointCallLogsAsync` + `CleanupEndpointCallLogsByCountAsync`) — no per-endpoint override (no definition table; endpoints are discovered from the aggregate keys, not a registry). `IEndpointQueryService` is registered by `AddWarp` itself (like `IAdapterQueryService`), so dashboard-only/publisher-only processes serve `/api/endpoints*` without the middleware; the detail id is a URL-safe base64 of the `{METHOD} {template}` route. Dashboard **Endpoints** nav gated on `GET {prefix}/api/addons` `endpoints` flag (true only where `AddEndpointObservability()` ran — keyed on `IEndpointCallRecorder` presence). Worker hot path untouched (§0.2/§6.1). See §2.15/§8.19, `website/docs/features/endpoint-observability.md`.

- **§8.22** **Log retention is age + count** (Item 1): adapter call logs, webhook deliveries, and endpoint call logs each cleaned on BOTH a time cap and a row-count cap, whichever trims first. Global defaults on `WarpConfiguration` (`AdapterCallLogRetentionCount`, `WebhookDeliveryRetentionCount`, `EndpointCallLogRetentionCount`, all `int?` null=off, beside the existing `*Retention` `TimeSpan`s); **adapters also take a per-adapter override** `WarpAdapterOptions.CallLogRetentionCount`, persisted onto `AdapterDefinition.CallLogRetentionCount` by the flusher so server-side `ExpirationCleanup` enforces it without the in-memory registry (webhooks/endpoints are global — a single source). Count sweeps keep the newest N (by `Timestamp`/`CreatedAt`), batched + `MaxSweepBatchesPerTick`-capped like the age sweeps; webhook count-trim excludes `Pending` (live work). **Aggregate metrics survive both sweeps** (Item 2): avg latency is now `Counter`→`Statistic`-backed via a per-dimension duration-sum counter (reserved `dur` token in `AdapterCounterKeys`/`EndpointCounterKeys`, folded into `OutcomeCounts.DurationSum`, never the call `Total`), so counts/error-rate/avg-latency all persist after raw call-log rows are deleted — only last-failure timestamps + recent-calls lists read raw rows and degrade gracefully.
