# Project-Specific Patterns

## Configuration

- **§8.1** `WarpConfiguration` via `IOptions<WarpConfiguration>`. All configurable values go through this pattern. The builder (`AddWarp<TContext>(opt => ...)`) inherits from `WarpConfiguration`, so config fields are set directly on `opt`.

## Job Lifecycle

- **§8.2** Failed jobs never auto-delete (`ExpireAt = null`). Only explicit user action (dashboard delete/requeue) or count-based cleanup (`MaxExpirableJobCount`, default null/disabled — deletes oldest by `ExpireAt` when threshold exceeded; failed jobs excluded).
- **§8.3** `ContinuationOptions` is generalized to all job kinds — any job with children can control child activation on parent failure.
- **§8.4** `RequeueJob` resets `ScheduleTime` to now. Requeued jobs always execute immediately.
- **§8.5** Cancellation uses `CancellationMode` enum (`None=0, Graceful=1`), not an immediate state change. `DeleteJob` sets `CancellationMode = Graceful`; `RunJobMonitor` detects this and cancels the handler's `CancellationToken`. If the handler ignores the token and completes, state stays `Completed` (work happened) and `CancellationMode` is cleared. Dashboard shows "Cancelling..." badge while waiting.

## Addons (Mutex, Semaphore, Timeout, RateLimit, CircuitBreaker, DB Push)

- **§8.6** Concurrency control is opt-in via `opt.AddConcurrency()`. `[Mutex("k")]` (limit fixed at 1) and `[Semaphore("k", N)]` (limit > 1) share `ConcurrencyPipelineBehavior`. Two policies via `ConcurrencyMode`: `Skip` (`[Mutex]` default — surplus → `Deleted`) and `Wait` (`[Semaphore]` default — surplus requeued). **Disjoint namespaces by design:** `[Mutex("k")]` uses `warp:concurrency:k`; `[Semaphore("k", N)]` uses `warp:concurrency:k:0..k:{N-1}`. Mixing both against the same key produces independent limits. Admin overrides via `IConcurrencyLimitManager` (precedence: `admin row > meta.Limit > 1`). Hide-on-404 dashboard nav.
- **§8.7** Timeout is opt-in via `opt.AddTimeout()`. `[Timeout(seconds: N)]` or `WithTimeout(TimeSpan)`. Two modes (`TimeoutMode`): `Delete` (default — pipeline sets `Deleted`, **not retried** by `AddRetry`) and `Fail` (throws `TimeoutException`, **caught** by `AddRetry`). Two scopes (`TimeoutScope`): `PerAttempt` (fresh budget per retry) and `Total` (`DeadlineUtc` stamped on publish). **Ordering: `AddRetry()` MUST come before `AddTimeout()`** (§2.12).
- **§8.8** Rate limiting is opt-in via `opt.AddRateLimit()`. Three styles (`Style`, from 1): `Fixed` (wall-clock window, floor-aligned to global UTC ticks), `Sliding` (rolling window over last N starts, defensively trimmed), and `TokenBucket` (**paces** rather than caps — tokens refill continuously at `count/perSeconds` per second up to a burst of `count`; each start consumes one; a fresh key starts full; when empty a `Wait`-mode start reschedules to the next token-refill instant, so a backlog trickles at the steady rate and never over-admits). `TokenBucket` stores the fractional token count + last-refill instant in `RateLimitBucket` (written only on accept); cross-style bucket-row reads degrade gracefully (bad/foreign payload → empty, never throws). Two policies (`Mode`): `Skip` (default — `Deleted`) and `Wait` (rescheduled via `JobOutcome.RescheduledState`). `perSeconds` capped at `MaxWindowSeconds` (7 days). Lock is released after check-and-increment — **not** held during handler execution (unlike Mutex). Live state in `RateLimitBucket` entity. Lock-contention reschedule has 100–500ms jitter. **DB push does NOT accelerate Wait-mode reschedules** — they land in `State.Scheduled` and depend on `ScheduledJobActivation` polling, so the effective release cadence (including `TokenBucket` refills) is floored at `ScheduledActivationInterval`. **Ordering: `AddConcurrency()` before `AddRateLimit()`** so mutex rejects don't waste tokens. **Attribute placement (#242):** `[RateLimit]`, `[Mutex]`, `[Semaphore]`, `[Timeout]` are read off the **request/job type**, never the handler impl — `AddWarp` throws a clear startup error if one is found on a handler class (self-handling jobs where request == handler are exempt).
- **§8.9** `RecurringJobScheduler` creates jobs with `ScheduleTime = now`. `AddOrUpdateRecurringJob` only registers/updates the definition — does **not** create jobs. Acquires a distributed lock on the recurring-job name and saves immediately (deliberate §5.7 exception). `RecurringJobLog` is the immutable audit trail; `ExpirationCleanup` retains the last 100 logs per recurring job.

## Conventions

- **§8.10** Source generators (`Warp.SourceGenerator`, `Warp.Http.SourceGenerator`) target `netstandard2.0` and provide zero-allocation mediator dispatch and HTTP endpoint generation. `[WarpHttpGet/Post/Put/Patch/Delete]` annotations on handler classes emit `RequestDelegate`s; `IJob` / `IMessage` rejected at compile time (`WHTTP001`). **Binary I/O:** a handler whose response is `Microsoft.AspNetCore.Http.IResult` (`IRequest<IResult>`) owns the full HTTP response — `JsonResponseWriter` detects `IResult` and calls `ExecuteAsync`, skipping the JSON envelope, so `Results.Stream/File/Bytes/NotFound/Ok` all work (used for file serving, bodyless status codes). **Multipart/form uploads:** request members typed `IFormFile`/`IFormFileCollection`/`IFormCollection` or carrying `[FromForm]` bind from the form (`BindingSource.Form`, emitted as a `Mixed` shape); `MapWarpHttp` sets `multipart/form-data` and `DisableAntiforgery()` on those endpoints. A request cannot bind both a form and a JSON `[FromBody]` (`WHTTP006`). Demo endpoints: `Warp.Test.Shared/HttpEndpoints.cs` — `/http/file-echo` (upload a file, echo its contents) and `/http/text-to-file` (send text, download it as a file).
- **§8.11** **Enums always start at 1, never 0.** `Skip = 1, Wait = 2`, never `Skip = 0`. Avoids `default(T)` collisions and forces explicit assignment. Applies to `JobKind`, `State`, `CancellationMode`, `ConcurrencyMode`, `RateLimitMode`, `RateLimitStyle`, `TimeoutMode`, `TimeoutScope`, etc.
- **§8.12** **Metadata properties are addon-prefixed**, not bare names. `IRateLimitMetadata.RateLimitKey` (not `Key`), `IRateLimitMetadata.RateLimitWindowSeconds` (not `WindowSeconds`), `IConcurrencyMetadata.ConcurrencyKey` / `ConcurrencyLimit` / `ConcurrencyMode`. Prevents dict-key collisions when a single job carries multiple metadata interfaces. Avoid `Dictionary<,>` names entirely — they're a red flag for collision-prone APIs.
- **§8.13** Entity namespaces are **split**: `Job` lives in `Warp.Core.Entities`; `JobLog`, `Server`, `Worker`, `ServerTask`, `ServerLog`, `RecurringJob`, `RecurringJobLog`, `RateLimitBucket`, `RateLimitOverride`, `ConcurrencyLimit` etc. live in `Warp.Core.Data.Entities`. Same folder, different namespaces — do not collapse them.
- **§8.14** **Routed `IMessage` jobs must keep `HandlerType` on requeue.** Addons that commit inside handler scope must capture-save-fire and clear-tracker-on-conflict (saga correctness pitfalls).
- **§8.15** Real-time log flushing: `RunJobMonitor` drains `JobLogCollector` every ~1s during handler execution and persists logs to the database. Logs visible in the dashboard while the job is still processing.
- **§8.16** `MetadataConvert` was string-only until the DateTime branch added 2026-05-12 — non-primitive `IJobMetadata` properties need explicit roundtrip tests.
- **§8.17** Sagas are an opt-in addon (`opt.AddSagas()` on the builder) in `Warp.Core.Sagas`. Subclass `Saga` (or `Saga<TKey>` for typed `string`/`Guid`/`int`/`long` keys), annotate the correlation property with `[Correlate]`, mark saga-starting messages with `[StartsSaga]`, implement `ISagaHandler<TSaga, TMessage>`, register handlers via `services.AddSagaHandler<H>()`. Storage: `SagaState` row per active saga + `SagaJobLink` extension table for the activity log with FK cascade. **Delete-on-completion** — `MarkCompleted()` removes the row in the same `SaveChanges`; the correlation key is immediately reusable. No auto-expiry; `ITimeoutMessage` self-schedules at `now + Delay`, and timeout-after-completion silently drops (`Outcome = Deleted`). Proxy serializes per correlation key on `warp:saga:{TSaga.FullName}:{key}` via `IWarpSemaphoreProvider`; optimistic `Version` concurrency is defense-in-depth. Both busy and version/unique conflict outcomes use jittered `ScheduleTime` (50–250ms) to avoid hot loops. `SagaCorrelationKeyConverter` trims strings, rejects empty-after-trim and `default(T)`, caps length at 200. `SagaPiiCheck` blocks `[Correlate]` properties matching common PII names (Email/Phone/SSN/etc.) at registration time; opt out with `[Correlate(IsAnonymized = true)]`. `ISagaCommandService.ForceComplete` acquires the saga mutex and emits a structured `LogInformation` audit. Dashboard at `/warp/sagas` and `/warp/sagas/{id}` with hide-on-404 nav; activity log query caps at 200 most-recent invocations with `IsTruncated` flag. Telemetry counters `warp.sagas.started`/`completed`/`requeued` (tagged `reason=busy|version|unique`). See `website/docs/features/sagas.md`.
- **§8.18** `WarpBackgroundService` is a base part of Warp (no addon opt-in) in `Warp.Core.BackgroundServices`. `AddWarp<TContext>` always contributes the four entities **and** registers `IBackgroundServiceQueryService` (so dashboard-only / publisher-only processes can serve `/api/services` without starting a server); `AddWarpServer<TContext>` adds the server-side host, lease coordinator, state service, and log store, plus the job worker by default. **The worker is a component of the server**: `opt.DisableWorker()` (sets `RunWorker = false`; `AddWarpServer` rejects `RunWorker = true` with zero total workers) yields a service-only server — background services + supporting server tasks (`Heartbeat`/`ServerCleanup`/`ExpirationCleanup`) without the job worker or job-only server tasks (provider still required). `WarpServerRegistration` creates no groups when `!RunWorker` (and skips `WorkerCount == 0` groups otherwise), so a service-only server leaves no `Worker`/`WorkerGroup` rows. `AddWarpWorker`/`WarpWorkerConfiguration`/`WarpWorkerBuilder` were removed in 2.0 (renamed to `AddWarpServer`/`WarpServerConfiguration`/`WarpServerBuilder`). Users register their own services with `opt.AddBackgroundService<T>()` (single type parameter on the non-generic `IWarpBuilder` receiver). Subclass `WarpBackgroundService`, override `Scope` (`PerServer = 1` — default, one instance per server; `Singleton = 2` — cluster-wide lease). Storage: `BackgroundServiceDefinition` (one row per service name), `BackgroundServiceInstance` (one per server-service pair), `BackgroundServiceLease` (singleton coordination, 30s TTL renewed in `Heartbeat`), `BackgroundServiceLog` (captured user + lifecycle events; FK cascade on instance delete). All in `Warp.Core.Data.Entities`. Worst-case singleton failover ~30s on hard-kill / ~0s on graceful shutdown (lease deleted in `StopAsync` before waiting on user code). Orphaned `Definition` rows (renamed/removed services with no live `Instance`) are deleted by `ExpirationCleanup` once `LastSeenAt > WarpConfiguration.BackgroundServiceDefinitionOrphanGrace` (default 2 min). **Captive-scoped-dependency foot-gun**: subclasses are singletons — inject `IServiceScopeFactory`, not `DbContext`; `ValidateScopes=true` catches it at startup. Log capture is auto-wired (`BackgroundServiceLoggerProvider`) with `MinLogLevel` (default Information), 100/s rate cap, 4KB message truncation, 1000-row/7-day retention. **§1.2 PII responsibility** applies to log output. Telemetry counters: `warp.background_services.started` (tag: `service_name`), `warp.background_services.faulted` (tags: `service_name`, `exception_type`), `warp.background_services.lease_lost` (tag: `service_name`), `warp.background_services.restarts` (tag: `service_name`). Worker hot path untouched (§0.2/§6.1) — separate `BackgroundServiceHost<TContext>`. See §2.13, `website/docs/features/background-services.md`.

- **§8.19** **Outbound adapters** are Warp's answer to observing calls the app *makes to* other services (contrast `Warp.Http` §8.10, which exposes Warp handlers *as* inbound endpoints — the naming `Warp.Adapters.Http` vs `Warp.Http` is inbound-vs-outbound and docs state it explicitly). Protocol-agnostic core in `Warp.Core.Adapters`; HTTP binding in `Warp.Adapters.Http`; Refit sugar in `Warp.Adapters.Refit` (only that package references Refit). **Three-axis identity — memorize the litmus test:** **adapter = policy + health boundary** (registration-time; retry/timeout/rate-limit config + SLO), **group = runtime who/where** (destination, tenant, shop, region — a *runtime value*, always explicit, never heuristic-derived, unbounded), **operation = what** (the API-contract axis — `GetOrders`, `payment.completed`; bounded, may be heuristic-derived). Litmus: if swapping the value changes the request's *structure* (route/verb/payload) → operation; if it only changes *where it goes or on whose behalf* → group. Diagnosis follows the axes: an operation red across all groups = caller-side bug (malformed payload, schema drift); a group red across all operations = counterparty problem (dead token, downed receiver); everything red = the adapter/vendor itself. Enums from 1 (§8.11): `CallRecording { All = 1, FailuresOnly = 2 }`, `CaptureMode { None = 1, OnFailure = 2, Always = 3 }`, `AdapterCallOutcome { Success = 1, Failed = 2, Throttled = 3, CircuitOpen = 4 }` (`CircuitOpen` reserved for the breaker fast-follow), `AdapterRateLimitOverflow { Wait = 1, FailFast = 2 }`. **Capture is opt-in and PII-owned (§1.2):** metadata always; request bodies, response bodies, and headers each independently `None`/`OnFailure`/`Always`, truncated (`MaxCapturedBodySize` 8 KB / `MaxCapturedHeaderSize` 4 KB) and passed through the user-owned `RedactedHeaders` denylist (case-insensitive, prepopulated with `Authorization`/`Proxy-Authorization`/`Cookie`/`Set-Cookie`/`X-Api-Key`; `Add`/`Remove`/`Clear` fully overridable — mandatory `Authorization` redaction was rejected, the denylist is a default not a lock). `RecordCalls = All` (default) writes a row per call — the volume knob for hot adapters is per-adapter `FailuresOnly`; capture modes control payload richness only, orthogonal to whether a row exists. **Cardinality guards:** `MaxDistinctOperations` (default 50) collapses *heuristic-derived* operation names beyond the cap to a literal `{other}` with a one-time warning (explicit names never collapse); `MaxDistinctGroups` (default 500) does the same for group values. `IncludeGroupInMetrics` (default false) keeps group off meter tags unless opted in (bounded group sets); group is always a span attribute + counter key regardless. **Shared rate limit = coordinated config:** `adapter name = cluster-wide identity` (same name ⇒ stats merge and limits share by design; genuinely different dependencies get different names). Shared-policy persistence is **first-writer-wins**: the first registration persists the policy onto `AdapterDefinition`, and later mismatching processes **enforce the persisted policy**, log a Warning, increment `warp.adapter.config_conflicts`, and set `HasPolicyConflict` (dashboard badge) — deterministic mid-rolling-deploy, and deploys alone never change the persisted limit (conflict is preserved, not overwritten, per SC13). Runtime precedence `RateLimitOverride` admin row > persisted definition > local code; **change a shared limit via a `RateLimitOverride` admin row (which takes precedence) or by clearing the persisted policy**, not by redeploying a new code value. **Adoption + rollout guidance:** adapters need only `AddWarp<TContext>` (no server/worker) — they run in any process, alongside other job systems; recording persists via the flusher on the user's `TContext`. **Observe-first is the recommended rollout:** register with no `UseResilience`/`UseSharedRateLimit` (the passive observing handler alone, zero behavioral change — same timeouts, single attempt, same exceptions), read the data, then add policy per adapter once it justifies the split. Telemetry: `warp.adapter.calls`, `warp.adapter.duration`, `warp.adapter.records_dropped`, `warp.adapter.config_conflicts`. See §2.15, `website/docs/features/adapters.md`.
- **§8.20** **Outbound webhooks** are **part of Core** (`Warp.Core.Webhooks`) and **always-on — there is no `AddWebhooks` gate on whether delivery runs**. `AddWarp` unconditionally wires the dispatcher, executor handler, redelivery enqueuer, and built-in signer; `AddWarpServer`'s default worker group polls `warp:webhooks` unconditionally, so **any server drains deliveries staged by any process — no per-process opt-in to forget** (the old two-process footgun is gone). Nothing runs until a caller invokes `IWebhookDispatcher.SendAsync`. `opt.AddWebhooks(...)` is now **optional config only** (custom `IWebhookSigner`, `IWebhookDeliveryExhaustedHandler`), not an enable switch. The `Moberg.Warp.Adapters.Webhooks` package was **removed** (folded into Core, which took a lightweight `Microsoft.Extensions.Http` dependency; the executor delivers via a bare `HttpClient` + a manual `IWarpAdapters` scope instead of the `Warp.Adapters.Http` binding). **Per-attempt `AdapterCallLog` rows require `AddAdapters()`** (recording opt-in, §8.19); without it the delivery state machine still works fully (dashboard, retries, exhaustion from the `WebhookDelivery` row) but the per-attempt HTTP call-log timeline is empty — consistent with §2.15 (telemetry unconditional, DB recording opt-in). Builds on adapters §8.19; makes durable webhook *delivery* a Warp feature. **Boundary: the host owns subscriptions + fan-out + payload building + endpoint enable/disable + its own secret tables; Warp owns everything after `SendAsync`** — delivery lifecycle, executor jobs, retry scheduling, exhaustion, signing, redelivery, dashboard. Warp models no subscriptions; the host calls `IWebhookDispatcher.SendAsync(WebhookSend)` once per destination. **The delivery, not the job, is the state machine:** the executor (`ExecuteWebhookDelivery`, an ordinary source-gen job on queue `warp:webhooks` — worker hot path untouched §0.2/§6.1) **always completes**; every attempt exception is caught and recorded as attempt failure, so webhook failures never surface as failed jobs or pollute the Jobs UI. State lives on the always-in-schema (§2.11) `WebhookDelivery` row (`Warp.Core.Data.Entities`, §8.13): `WebhookDeliveryStatus { Pending = 1, Delivered = 2, Exhausted = 3 }` (§8.11). **Self-contained row** — URL, headers, payload, schedule, success codes, signing mode + secret, group, reference all stamped at `SendAsync` time so a later config deploy never reshapes an in-flight delivery. **`SendAsync` persists `Pending` + enqueues the first attempt in the caller's transaction (outbox), returns the delivery id** (= adapter `CorrelationId`). **Attempts are adapter calls** through the auto-registered `warp-webhooks` adapter (group = endpoint, operation = event type, `CorrelationId` = delivery id; `RecordCalls = All`, response bodies always captured, request bodies never — payload already on the row; `CallLogRetention` aligned to `WebhookDeliveryRetention`) — the attempt timeline is `AdapterCallLog WHERE CorrelationId = deliveryId`, **no separate attempt table**. **No timers/scans:** each retry is a fresh executor job in `State.Scheduled` at `now + schedule[N-1]` riding `ScheduledJobActivation` (§2.8); `(RetrySchedule, AttemptCount)` fully determines the plan (schedule column never mutated), exhausted when `AttemptCount > schedule.Count`. `RetrySchedule` is per-send `IReadOnlyList<TimeSpan>` (§3 pillar: **no app-level schedule knob**): `null` = built-in `[1m,10m,1h,6h]`, `[]` = single attempt then `Exhausted`, N entries = N retries; persisted as a JSON seconds array (`"[60,600,3600,21600]"`/`"[]"`) via `RetryScheduleConverter` (§8.16 roundtrip tests mandated — empty/single/multi-hour on both providers). `SuccessCodes` `null` = any 2xx. **Cadence precision is delay + up to ~5s activation + worker pickup — a backoff, not a precision scheduler; document it.** Signing (`WebhookSigning { None = 1, StandardWebhooks = 2, Custom = 3 }`, §8.11): `None` (default, adds nothing — the legacy body-embedded-HMAC migration path), `StandardWebhooks` (HMAC-SHA256 over `{webhook-id}.{webhook-timestamp}.{payload}`, headers `webhook-id`/`webhook-timestamp`/`webhook-signature` `v1,<base64>`, `webhook-id` = `EventId` stable across retries), `Custom` (registered `IWebhookSigner` via `w.UseCustomSigner<T>()` — **declaring custom signing without a signer throws at `AddWebhooks` time, not send time**). **Secrets at rest** on the row are accepted for self-containment; **redacted on every read surface** (query service, endpoints, dashboard reduce `Secret` to a `HasSecret` flag, `Authorization`-class headers redacted — not caller-toggleable), never logged Info+ (§1.2); stricter hosts use `Signing = None` and sign in their own payload code. Exhaustion flips `Status = Exhausted` and invokes the host's `IWebhookDeliveryExhaustedHandler` **at-least-once, post-commit** with a redaction-safe snapshot (`ExhaustedCallbackPending` commits with the transition; the recovery check is **status-independent** so a `Redeliver` that flips the row back to `Pending` before the crash-recovery re-run still fires the prior exhaustion's callback) — a throwing callback is logged at Warning, never propagated (callbacks/instrumentation never out-throw). Host decides endpoint disable; Warp only signals. `IWebhookCommandService.Redeliver(id)` requeues a **settled** (`Delivered`/`Exhausted`) delivery to `Pending` + immediate job; `Pending`/unknown rejected with no side effects. **Stuck-delivery recovery (the one deliberate exception to no-timers/no-scans):** the executor's attempt claim and its outcome commit are two transactions — a fault on the second leaves the row `Pending` with no live job (the retry job was staged in the failed transaction). The claim therefore stamps `NextAttemptAt` even on a final attempt, and `StaleJobRecovery` sweeps `Pending` rows whose `NextAttemptAt` is more than `WarpConfiguration.WebhookStuckDeliveryGrace` (default 10 min) past. Duplicate-proof by construction: candidates that still have a live executor job on the webhooks queue are skipped (merely-backlogged workers ≠ lost job), and the guarded `NextAttemptAt` bump + the new job commit in ONE transaction on the scoped `TContext` via the `IWebhookRedeliveryEnqueuer` seam (the `Redeliver` pattern; registered by `AddWarp` always, so it works in any process) — a rollback undoes both, so no bumped-without-job or job-without-bump state exists. The recovered exhausted-callback reconstructs the exhaustion's `AttemptCount` from `RetrySchedule.Count + 1` on post-`Redeliver` rows (the live column was reset to 0). `IWebhookQueryService`/`IWebhookCommandService` live in `Warp.Core.Webhooks` and resolve in any `AddWarp` process (dashboard/publisher-only) reading on `TContext` (§2.14). `ExpirationCleanup` deletes deliveries past `ExpireAt` (`WebhookDeliveryRetention`, default 30d). **Adoption prerequisite: a Warp server (worker) must run somewhere** to drain `warp:webhooks` — but any `AddWarpServer` with a worker drains it (no `AddWebhooks` needed on that server); coexistence with another job system (e.g. Hangfire) is a documented supported shape. Dashboard **Webhooks** nav is **always shown** (webhooks is a Core feature) — the `GET {prefix}/api/addons` `webhooks` flag gates on the always-registered `IWebhookRedeliveryEnqueuer`. Telemetry: `warp.webhooks.deliveries`/`attempts` (tag outcome) + `warp.webhooks.redeliveries`. See §8.19, `website/docs/features/webhooks.md`.

- **§8.21** **Inbound endpoint observability** (`Warp.Http`, opt-in via `opt.AddEndpointObservability(o => ...)` inside the `AddWarp`/`AddWarpServer` lambda + `app.UseWarpHttpObservability()` after `UseRouting`) is the **inbound mirror of adapters §8.19**: adapters observe calls the app *makes to* other services; this observes requests *made to* the app's **Warp HTTP endpoints** (handlers exposed via `MapWarpHttp`). Scope is Warp endpoints only — the middleware no-ops unless the matched endpoint carries the `WarpEndpointIdentity` metadata attached in `EndpointRouteBuilderExtensions.ApplyMetadata`, so it never observes the host's own controllers, the dashboard, health, or static files. **Identity = HTTP method + route TEMPLATE** (`GET /orders/{id}`) — already bounded (no runtime path-cardinality heuristic, unlike outbound's URL collapsing); inline constraints are normalized away (`{id:int}`→`{id}`) via `EndpointCounterKeys.NormalizeTemplate` so the colon-delimited counter key parses unambiguously, and the flusher stamps the SAME normalized method+template onto the `EndpointCallLog` row so the detail page joins log rows to aggregates. The route is the operation — counter dimensions are **Total + Group only** (no operation dimension); `group` is an optional low-cardinality caller key from `o.GroupSelector(HttpContext)` (channel/client/tenant — never raw IP/user id). Core is protocol-agnostic (`Warp.Core.Endpoints`: `EndpointCallLog` entity §8.13 always-in-schema §2.11, public `IEndpointCallRecorder`/`EndpointCallRecord` seam, `DbEndpointCallRecorder` bounded lossy channel, `EndpointCallFlusher<TContext>` drain→rows+`Counter`s, internal `EndpointCounterKeys`); the HTTP binding (`Warp.Http.Observability`) holds `WarpEndpointObservabilityOptions` (HttpContext-dependent), `WarpInboundObservabilityMiddleware`, and `AddEndpointObservability`/`UseWarpHttpObservability`. **Capture (§1.2 PII):** caller IP (`RemoteIpAddress`, or first `X-Forwarded-For` hop when `UseForwardedForIp`), user-agent, and `User.Identity.Name` are captured by default (the point of the feature) but are PII; request/response bodies + headers are each `None`/`OnFailure`/`Always` (default `OnFailure`), truncated (`MaxCapturedBodySize` 8 KB via a bounded pass-through `CaptureBodyStream` that never buffers a whole streaming/`IResult` response, `MaxCapturedHeaderSize` 4 KB) and redacted through the same user-owned `RedactedHeaders` denylist as adapters. Outcome `Failed` = status ≥ 500 or unhandled exception (4xx = client error, counted Success so error rate stays meaningful). `RecordCalls = FailuresOnly` skips success ROWS only (counters still written, error-rate denominator intact). **Recording is lossy + never blocks/fails the request** (full channel drops the record); `RecordAsync` swallows its own errors. **Metrics survive log deletion** (§ retention): counts/error-rate/avg-latency come from `Counter`→`Statistic` aggregates (a duration-sum `dur` token backs the average, same as adapters §2/Item 2); recent-calls + per-caller last-failure read raw rows and degrade to empty/null once swept. **Retention is GLOBAL** on `WarpConfiguration.EndpointCallLogRetention` (age, default 7d, stamped as `ExpireAt` by the middleware) + `EndpointCallLogRetentionCount` (count, null=off, keep newest N per method+route), both swept by `ExpirationCleanup` (`CleanupExpiredEndpointCallLogsAsync` + `CleanupEndpointCallLogsByCountAsync`) — no per-endpoint override (no definition table; endpoints are discovered from the aggregate keys, not a registry). `IEndpointQueryService` is registered by `AddWarp` itself (like `IAdapterQueryService`), so dashboard-only/publisher-only processes serve `/api/endpoints*` without the middleware; the detail id is a URL-safe base64 of the `{METHOD} {template}` route. Dashboard **Endpoints** nav gated on `GET {prefix}/api/addons` `endpoints` flag (true only where `AddEndpointObservability()` ran — keyed on `IEndpointCallRecorder` presence). Worker hot path untouched (§0.2/§6.1). See §2.15/§8.19, `website/docs/features/endpoint-observability.md`.

- **§8.22** **Log retention is age + count** (Item 1): adapter call logs, webhook deliveries, and endpoint call logs each cleaned on BOTH a time cap and a row-count cap, whichever trims first. Global defaults on `WarpConfiguration` (`AdapterCallLogRetentionCount`, `WebhookDeliveryRetentionCount`, `EndpointCallLogRetentionCount`, all `int?` null=off, beside the existing `*Retention` `TimeSpan`s); **adapters also take a per-adapter override** `WarpAdapterOptions.CallLogRetentionCount`, persisted onto `AdapterDefinition.CallLogRetentionCount` by the flusher so server-side `ExpirationCleanup` enforces it without the in-memory registry (webhooks/endpoints are global — a single source). Count sweeps keep the newest N (by `Timestamp`/`CreatedAt`), batched + `MaxSweepBatchesPerTick`-capped like the age sweeps; webhook count-trim excludes `Pending` (live work). **Aggregate metrics survive both sweeps** (Item 2): avg latency is now `Counter`→`Statistic`-backed via a per-dimension duration-sum counter (reserved `dur` token in `AdapterCounterKeys`/`EndpointCounterKeys`, folded into `OutcomeCounts.DurationSum`, never the call `Total`), so counts/error-rate/avg-latency all persist after raw call-log rows are deleted — only last-failure timestamps + recent-calls lists read raw rows and degrade gracefully.

- **§8.23** **Multi-application observability** is Warp's answer to a **shared-database** deployment (many apps, one schema; all servers still pick up all jobs — execution/routing **unchanged**). It is NOT isolation — true isolation between independent apps is a **separate schema per app** (`opt.Schema`), documented not built here. **Opt-in trigger: `WarpConfiguration.ApplicationName` (`string?`, default `null`) gates ALL new runtime behavior** — `null` ⇒ today's behavior byte-for-byte. Plus optional self-reported `ApplicationVersion`/`ApplicationEnvironment` (per-instance, may differ mid rolling-deploy). `ApplicationName` = cluster-wide identity (same name ⇒ instances group + stats/metrics merge; different apps ⇒ different names) — same identity model as an adapter name (§8.19). **Sibling-table registry model** ("every server IS an application instance; not every instance is a server"): `Server` gains nullable `Application`/`Version`/`Environment` (stamped by the existing `Heartbeat` server task — no new loop for servers); non-server processes (`AddWarp`-only publisher/API/dashboard) write ONE `ApplicationInstance` row via a new lightweight heartbeat `IHostedService` (`ApplicationHeartbeatHost`) registered by `AddWarp` **only when `ApplicationName` set** — **a deliberate change to the "`AddWarp` is passive" contract** (§2.13), gated + no provider/lock (owns its row by `Id`) + deregisters on graceful `StopAsync`. Each process writes exactly one physical row (no double-writes). Entities `ApplicationInstance` + `ApplicationInstanceLog` live in `Warp.Core.Data.Entities` (§8.13), are **always-in-schema** (§2.11, `WarpModelCustomizer`) and mirrored by `WarpServerContext` (§2.14). `ApplicationInstanceEventType` enum from 1 (§8.11, namespace `Warp.Core.Enums`): `Registered=1, HeartbeatLost=2, Recovered=3, Stopped=4, StaleSwept=5` — unified lifecycle log for ALL instances (server ∪ non-server); `ServerLog` stays server-task-execution history (relabeled "Server tasks" in the UI). `ExpirationCleanup` sweeps stale `ApplicationInstance` rows past `ApplicationInstanceStaleGrace` (2m) + retains `ApplicationInstanceLog` by age (`ApplicationInstanceLogRetention` 7d) + count (`ApplicationInstanceLogRetentionCount` null=off) (§8.22). **Provenance** (nullable `Application` column, filter/display only): `Job.Application` (stamped at publish, **preserved on requeue**), `AdapterCallLog.Application`, `EndpointCallLog.Application`, `WebhookDelivery.Application`. **Provenance ≠ execution:** `Job.Application` = *publishing* app (filter/trace only) — jobs execute on a worker app, so per-**creator** job metrics are deliberately NOT provided; execution metrics are attributed to the **executor** app instead. **Per-app metrics under DISJOINT counter-key namespaces** (back-compat, first-segment-equality parsers reject them — existing keys byte-for-byte unchanged, old readers never see the new prefix, §8.6/§8.19): `adapter-app` (`AdapterCallFlusher.AppPrefix`), `endpoint-app` (`EndpointCounterKeys.AppPrefix` — `Application` also joins endpoint **identity** so the same route in two apps stays distinct), `jobstat`/`jobstat-app` (`JobStatsKeys` — per-job-**type** + per-**handler** execution count/duration/error, executor-app-sliced, folding via `Counter → CounterAggregator → Statistic` so they **survive raw-row cleanup**; hourly history auto-prunes at `HourlyStatisticsRetention` 7d, lifetime totals persist — no new aggregation/cleanup path). **Unified `InstanceView`** (`Warp.Core.Models`) merges `Server` ∪ `ApplicationInstance` into one dashboard roster. `IApplicationQueryService` + `ApplicationQueryService<TContext>` registered by **`AddWarp` itself** (like `IAdapterQueryService`/`IEndpointQueryService`), so dashboard-only/publisher-only processes resolve it. Dashboard **Applications** page = the renamed **Servers** page (`/servers` → `/applications` redirect), always shown; `WarpAddonsInfo.Applications` flag true iff `ApplicationName` set. API: `GET {prefix}/api/applications`, `/{id}`, `/{id}/instances/{instanceId}`, `/{id}/jobstats` (id = URL-safe base64 of the app NAME via `EndpointRouteId`); global `application` filter param on jobs/adapters/endpoints. `warp.application` OTel span attribute (`WarpTelemetryAttributes.WarpApplication`) when set, absent when null. **Migration 100% additive** — 2 new tables (`application_instance`, `application_instance_log`) + 7 nullable columns, picked up by the user's standard `dotnet ef migrations add / database update`; legacy `null`-application rows read as "(unassigned)"; rolling-deploy safe (old processes ignore new cols/tables, write null). Shared-DB "who owns migrations" is a pre-existing concern, unchanged. Worker hot path untouched (§0.2/§6.1 — Counter-writes only at the existing finalization site). See §2.15/§8.19, `website/docs/features/applications.md`.

- **§8.24** **Observability sinks** — everything Warp collects per-call/per-job can be routed to the DB (default), to **OTel**, or **Both**, so a high-throughput deployment can take the diagnostics firehose off its database. Two tracks: (a) **telemetry always emits** — `WarpTelemetry.ActivitySource`/`Meter` (both named `WarpTelemetry.ServiceName` = `"Warp"`, public const) fire spans + meters unconditionally (null-listener, zero cost without an exporter); wiring is `AddSource/AddMeter(WarpTelemetry.ServiceName)` + `AddOtlpExporter`. (b) **recording is the opt-in DB track**, now sink-selectable. `RecordingSink { Database=1, Otel=2, Both=3 }` (§8.11, `Warp.Core.Observability`), default `Database` ⇒ byte-for-byte current behavior. **Per-surface:** `opt.AddAdapters(o => o.Sink = …)` and `opt.AddEndpointObservability(o => o.Sink = …)` — `Database` wires the DB recorder + flusher; `Otel` wires **no recorder and no flusher** (so no call-log rows AND no per-app `Counter` writes) and instead **enriches the span Warp already emits** with the captured detail as span attributes (`warp.adapter.*` on the `Client` span via `AdapterCallScope.EnrichSpanDetail`; `warp.endpoint.*` on the ambient ASP.NET request span via `WarpInboundObservabilityMiddleware.EnrichSpan`); `Both` keeps the DB recorder + flusher **and** enriches the span. **No parallel OTel-log recorder exists** — the earlier `Otel*CallRecorder`/`Composite*CallRecorder`/`StructuredLogState` were removed: routing per-call payloads through `ILogger` fanned them to every log provider (console/file), a §1.2 leak, and duplicated the span. Span enrichment fires **only when `Activity.IsAllDataRequested`** (the span is sampled in), so a single consistent trace-sampling decision governs the whole call/request coherently — detail travels on the trace exporter only, never `ILogger`. Adapters carry the process-level enrich flag via the optional-marker seam (`AdapterRecordingSettings`, §2.9); endpoints read `WarpEndpointObservabilityOptions.Sink` in the middleware and take the recorder optionally (`IEnumerable<IEndpointCallRecorder>`, empty under Otel). The internal `IAdapterCallRecorder` **stays internal** (no public storage contract); under Otel-only it falls back to Core's `NullAdapterCallRecorder`. Dashboard nav flags stay keyed on presence markers registered regardless of sink (`IAdapterRecordingMarker`; new **`IEndpointObservabilityMarker`**, replacing the old `IEndpointCallRecorder`-presence gate which is absent under Otel). **Job-metrics:** `WarpConfiguration.JobMetricsSink` (`RecordingSink`, default `Database`) gates the per-type/handler `jobstat` `Counter` writes at the finalization sites — `Otel` skips them (perf win; §0.2/§6.1 hot path only gains `instrument.Record` calls + one config check), the meters carry the data. **Meters added/extended (always-on, low-cardinality tags only, `group` stays OFF meter tags §1.2):** `warp.adapter.calls`/`duration` (+`application`), `warp.endpoint.calls`/`duration` (`route`/`outcome`/`application`), `warp.job.execution.total`/`duration` (`job.type`/`job.handler`/`outcome`/executor-`application`). **Dashboard:** `Database`/`Both` → Warp dashboard works; `Otel`-only → those pages have no DB rows (use Grafana/Jaeger, or register a backend-backed impl behind the public `IAdapterQueryService`/`IEndpointQueryService` via `TryAdd`-before-`AddWarp`). Control-plane (jobs/servers/sagas/webhooks/app roster) stays in the DB regardless — it's state, not telemetry. See `website/docs/features/observability-sinks.md`.

- **§8.25** **Operational notifications** — a host seam (`IWarpNotifier { Task NotifyAsync(WarpOperationalEvent evt, CancellationToken ct); }`, `Warp.Core.Notifiers`) that hands Warp-detected operational events to the host, which decides what to do (Teams/Slack/email/page/log). **Warp ships no channel integrations** — pure seam, the `IWebhookDeliveryExhaustedHandler`/`IWebhookSigner`/`IWarpCredentialValidator` precedent. **Alerting ≠ webhooks:** a webhook is the host telling external subscribers about domain events (needs a subscriber URL); a notification is Warp telling the operator something is wrong (no URL) — reusing `IWebhookDispatcher` for self-alerting is the wrong abstraction. Register via `opt.AddNotifier<T>()` (non-generic `IWarpBuilder`, §2.13 `AddBackgroundService<T>` precedent); resolved as `IEnumerable<IWarpNotifier>` (optional-marker, §2.9) so **zero registered = inert**. **Contract:** invoked **post-commit** (the transition is durable) and a **throwing notifier is caught + logged at Warning + never propagated** (an alert sink can't take down what it observes; never fails/slows the worker). **Events are NOT persisted — no notification outbox.** Dispatch is in-process from an in-memory buffer, so **delivery to the sink is best-effort for every event**: a crash in the commit→dispatch window, or a notifier that's down/throwing (swallowed+logged, no retry), drops that alert. Convenience alerts, not an audit trail — the operator action / `WebhookDelivery` row / instance roster are the systems of record; don't build guaranteed-delivery accounting on them. **Per-source replay nuance:** only `WebhookDeliveryExhausted` is re-emitted after a crash-before-dispatch (the delivery's `Exhausted` state is persisted → executor re-run regenerates the event; may repeat, key on event id) — still lost if the sink is unreachable at call time. `SagaForceCompleted` + `InstanceDown` report a row deleted in the committing transaction, so a lost dispatch is gone for good. Don't overclaim at-least-once. §8.18 captive-dependency footgun applies — notifiers are singletons, inject `IServiceScopeFactory` not `DbContext`. Fan-out is centralised in the singleton **`WarpNotifierDispatcher`** (guarded loop over the set; empty-set no-op), registered by `AddWarp` (beside `ServerTaskSignals`) so every dispatch site resolves it in any process. **CRITICAL post-commit mechanism for server tasks:** `ExpirationCleanup`/`ServerCleanup` run INSIDE the server-task host's lock transaction (`IServerTask.LocksWithTransaction` default true → `ServerTaskLoop.RunUnderTransactionLockAsync` commits AFTER `ExecuteAsync` returns), so their `SaveChangesAsync` only **flushes** — a direct dispatch there fires **pre-commit** and could alert on a rollback-undone change. The seam is **`IServerTask.OnCommittedAsync(ct)`** — a **default-no-op post-commit hook** the `ServerTaskLoop` invokes after the transaction commits (both lock paths; **skipped on throw/rollback and when the lock wasn't held**). The two tasks **buffer** their `InstanceDown` events in a private field during `ExecuteAsync` and **dispatch from `OnCommittedAsync`** (`CancellationToken.None` so shutdown doesn't abandon a committed alert). Keeps `ServerTaskLoop` feature-agnostic (no `Notifiers` coupling). The webhook + saga sites are ordinary/​session-lock paths (genuinely post-commit) and dispatch inline via `WarpNotifierDispatcher` directly, also with `CancellationToken.None`. **New server-task authors: never dispatch in `ExecuteAsync` (pre-commit) — buffer + dispatch in `OnCommittedAsync`.** **Events are redaction-safe snapshots — identity/metadata only, never a payload body (§1.2).** Abstract `WarpOperationalEvent` base (`Type`/`Severity`/`TimestampUtc`/`MachineName`/`Application`/`Message`) + typed subtypes the host switches on. `WarpEventType` enum from 1 (§8.11, `Warp.Core.Enums`): `JobDeadLettered=1` (**RESERVED**, deferred — the payloadless finalization signal needs a claim mechanism), `WebhookDeliveryExhausted=2`, `SagaForceCompleted=3`, `InstanceDown=4`, `BacklogBreached=5` (**RESERVED**, needs queue-wait metrics). Plus `WarpEventSeverity { Info=1, Warning=2, Error=3 }`. **v1 dispatch sites (all pre-existing detections, worker hot path untouched §0.2/§6.1):** webhook exhaustion in `ExecuteWebhookDelivery` (post-commit, alongside the existing exhausted-handler — the two coexist), saga `ForceComplete` in `SagaCommandService` (after `SaveChanges`), and instance-down from BOTH the `ExpirationCleanup` stale `ApplicationInstance` sweep (`IsServer=false`) and the `ServerCleanup` stale-`Server` sweep (`IsServer=true`) — every server is an instance (§8.23). Dispatch sites take a **required** `WarpNotifierDispatcher` ctor param (§0.5 specific dep, no fallback). See `website/docs/features/operational-notifications.md`.

- **§8.26** **Queue metrics (queue-wait + backlog)** — the two job-system health signals beyond per-job execution time (§8.23/§8.24). **Always-on, no addon opt-in.** **(1) Queue-wait latency** measured at the worker claim site (`WarpWorkerService`/`WarpDispatcherWorker`, where `Enqueued → Processing` and the "Processing" `JobLog` is written): `waitMs = max(0, claimTime − Job.ScheduleTime)` (`ScheduleTime` advances on requeue, so wait is from requeue not original enqueue). **Hot path sacred (§0.2/§6.1):** the `Counter` rows are added to the **existing** claim-site `SaveChanges` — NO extra query, NO round-trip; the always-on `WarpTelemetry.RecordQueueWait` meter fires unconditionally. Folds `Counter → CounterAggregator → Statistic` via `QueueWaitKeys` (`Warp.Core.Services`, `internal static`, prefix `qwait` / per-app `qwait-app`, tokens `count`/`dur` + `pct:{bucket}` histogram, same buckets as `JobStatsKeys`) so **avg/p95/p99 survive raw-row cleanup**; per-app slice carries NO histogram (p95/p99 read 0) to bound volume. **(2) Backlog depth + oldest-age** sampled OFF the hot path by `BacklogSampler<TContext>` (`Warp.Worker.Services`, an `IServerTask` like `CounterAggregator`; `LockKey = "warp:backlog-sample"`, `DefaultInterval => WarpServerConfiguration.BacklogSampleInterval` default 15s): one EF-LINQ grouped query `GroupBy(Queue).Select(Count, Min(ScheduleTime))` filtered `Kind==Job && CurrentState==Enqueued && ScheduleTime<=now` — served by the **existing** `(Kind, CurrentState, Queue, ScheduleTime)` index (no new index, §5.x, no raw SQL). Writes always-on `WarpTelemetry.SetBacklogSnapshot` (drives `JobQueueDepth`/`JobQueueOldestAge` ObservableGauges, `queue` tag only) + `qbacklog:` gauge `Statistic` upserts (`QueueBacklogKeys`; overwrite each tick — NOT `Counter`, so `CounterAggregator` doesn't double them; drained queues reset to 0). **Backlog is queue-GLOBAL, deliberately NOT app-sliced** (there is no `qbacklog-app`): an eligible-but-unclaimed job has no executor, and slicing by the *publishing* app is the per-creator metric §8.23 omits — a single cluster-wide sampler (lock `warp:backlog-sample`) sees all apps' enqueued jobs, so the global count is correct. **Meters (always emit, low-cardinality tags `queue` + `application` when set — group/PII off §1.2):** `warp.job.queue.wait` (Histogram ms), `warp.job.queue.depth` + `warp.job.queue.oldest_age_seconds` (ObservableGauges). **Sink-respecting (§8.24):** both respect `WarpConfiguration.JobMetricsSink` — `Otel` SKIPS the Counter/Statistic writes (perf win), meters still carry the data. **Multi-app (§8.23):** queue-**wait** is sliced by **executor** application under a disjoint namespace (`qwait-app`, first-segment-equality parsers reject it, existing keys unchanged, §8.6/§8.19); **backlog stays global** (see above). `GetQueueMetrics(application)` returns that app's wait alongside the queue's global backlog. **Read side:** `IJobQueryService.GetQueueMetrics(string? application)` → `QueueMetricsModel`/`QueueMetricModel` (`Warp.Core.Models`) reads only the durable aggregates (resolves in any `AddWarp` process). API `GET {prefix}/api/queues/metrics` (`?application=` optional, no addons flag). Dashboard **Queues** page (`/queues`, `QueuesPage.tsx`) always shown in built-in nav (Core feature). See §2.15/§8.23/§8.24, `website/docs/features/queue-metrics.md`.

- **§8.27** **Client (frontend) observability** is the **browser-side** complement to server-side observability (adapters §8.19 outbound, endpoints §8.21 inbound-to-Warp): a public **ingest endpoint** a frontend app posts to, attributed to an **application** (§8.23). One `ClientEvent` primitive discriminated by `ClientEventType { Error=1, Vital=2, Log=3, Event=4 }` (§8.11, `Warp.Core.Enums`) — `log()`/`track()` sugar + auto-captured errors/vitals are the SAME row (no second subsystem). Same pipeline as adapters/endpoints: bounded lossy channel (`DbClientEventRecorder`) → `ClientEventFlusher<TContext>` (drains to `ClientEventLog` rows + the durable `clientevent:` Counter fold, stamps `ReceivedAt`/`ExpireAt`, §0.5 scope) → `Counter → CounterAggregator → Statistic`. **Two-tier storage (never inflate the DB):** raw `ClientEventLog` rows (`Warp.Core.Data.Entities`, always-in-schema §2.11, mirrored by `WarpServerContext` §2.14) are trimmed on age (`ClientEventLogRetention` 7d) AND count (`ClientEventLogRetentionCount` 100k/app) by `ExpirationCleanup`; trend data (`ClientEventKeys`, `Warp.Core.ClientObservability`, disjoint prefixes `clientevent`/`clientevent-app`, §8.6/§8.19) — per-type count + hourly history, per-name total, per-vital count+dur+**p75 histogram** — **survives raw-row cleanup** (§8.22). **Cardinality guard (the difference from endpoints, whose routes are bounded) — NOTHING client-sent is trusted bounded on a public endpoint:** error/event names AND log **levels** collapse to `{other}` beyond a per-type cap (`ClientEventCardinality`, §8.19); **vital names go through a fixed allowlist** (`ClientEventCardinality.KnownVitals` = LCP/CLS/INP/FCP/TTFB → else `{other}`) for BOTH the counter key and the `warp.client.vitals` meter tag — a raw client vital name is never a metric dimension. Counter-only; the raw row keeps the real name. Logs fold by `Level` (§8.27 "logs count per level"), not the free name. CLS is folded ×1000 into the shared integer histogram and unscaled ÷1000 on read. **Web vitals follow Google: p75** (their good/needs-improvement/poor threshold percentile), NOT p95/p99. **Public endpoint (hostile client):** auth is a public write-only **DSN key** (`o.AddIngestKey(app, key)` → **trusted** app name, never client-declared; unknown → 401), a CORS **origin allowlist** (else 403; same-origin — `Origin == scheme://host` — bypasses the allowlist), an **in-memory per-caller-IP** rate limit (`ClientIngestRateLimiter` — keyed on IP not the public key, checked BEFORE the body read so floods/bad-key/empty posts are bounded cheaply; NEVER DB-backed), and hard size/batch caps. A crafted out-of-range `ts` is caught (never faults the request). Key travels in `x-warp-key` header OR body (a `sendBeacon` caller can't set headers). Recording is lossy (full channel drops + `warp.client.events.dropped`; an unrecognized event `type` is also dropped-and-counted, never silent; browser never blocked). **PII (§1.2):** IP off by default; property maps redacted via a denylist + truncated; never logged Info+; **consent/GDPR is the host's job**. **Sink-respecting (§8.24):** `Database`/`Both` write rows; `Otel` skips the DB, meters carry it (`warp.client.events`/`vitals`/`events.dropped`, always-on). Core (`Warp.Core.ClientObservability`) holds the sink-free pipeline + options + `AddClientObservability(IWarpBuilder)` + the query service (registered by `AddWarp` itself, resolves in dashboard-only processes); the HTTP binding (`Warp.Http.ClientObservability`) holds `MapWarpClientObservability()` (the ingest endpoint + `GET {IngestPath}/client.js` serving the shipped self-contained browser script — error hooks, web vitals via PerformanceObserver, breadcrumbs, `sendBeacon`/`fetch(keepalive)` batching, per-session sampling). Dashboard **Client** page (`/client`, `ClientPage.tsx`) gated on `WarpAddonsInfo.Client` (keyed on `IClientObservabilityMarker`). API `GET {prefix}/api/client/summary|events|events/{id}|applications`. Worker hot path untouched (§0.2/§6.1). See §2.15/§8.19/§8.21, `website/docs/features/client-observability.md`.
