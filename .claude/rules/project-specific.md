# Project-Specific Patterns

## Configuration

- **§8.1** `WarpConfiguration` via `IOptions<WarpConfiguration>`. All configurable values go through this pattern. The builder (`AddWarp<TContext>(opt => ...)`) inherits from `WarpConfiguration`, so config fields are set directly on `opt`.

## Job Lifecycle

- **§8.2** Failed jobs never auto-delete (`ExpireAt = null`). Only explicit user action (dashboard delete/requeue) or count-based cleanup (`MaxExpirableJobCount`, default null/disabled — deletes oldest by `ExpireAt` when threshold exceeded; failed jobs excluded).
- **§8.3** `ContinuationOptions` is generalized to all job kinds — any job with children can control child activation on parent failure.
- **§8.4** `RequeueJob` resets `ScheduleTime` to now. Requeued jobs always execute immediately.
- **§8.5** Cancellation uses `CancellationMode` enum (`None=0, Graceful=1`), not an immediate state change. `DeleteJob` sets `CancellationMode = Graceful`; `RunJobMonitor` detects this and cancels the handler's `CancellationToken`. If the handler ignores the token and completes, state stays `Completed` (work happened) and `CancellationMode` is cleared. Dashboard shows "Cancelling..." badge while waiting.

## Addons (Mutex, Semaphore, Timeout, RateLimit, CircuitBreaker, DB Push)

- **§8.6** Concurrency control is opt-in via `opt.AddConcurrency()`. `[Mutex("k")]` (limit fixed at 1) and `[Semaphore("k", N)]` (limit > 1) share `ConcurrencyPipelineBehavior`. Two policies via `ConcurrencyMode`: `Skip` (`[Mutex]` default — surplus → `Deleted`) and `Wait` (`[Semaphore]` default — surplus requeued). **Disjoint namespaces by design:** `[Mutex("k")]` uses `warp:concurrency:k`; `[Semaphore("k", N)]` uses `warp:concurrency:k:0..k:{N-1}`. Mixing both against the same key produces independent limits. Admin overrides via `IConcurrencyLimitManager` (precedence: `admin row > meta.Limit > 1`). Hide-on-404 dashboard nav.
- **§8.7** Timeout is opt-in via `opt.AddTimeout()`. `[Timeout(seconds: N)]` or `WithTimeout(TimeSpan)`. Two modes (`TimeoutMode`): `Delete` (default — pipeline sets `Deleted`, **not retried** by `AddRetry`) and `Fail` (throws `TimeoutException`, **caught** by `AddRetry`). Two scopes (`TimeoutScope`): `PerAttempt` (fresh budget per retry) and `Total` (`DeadlineUtc` stamped on publish). **Ordering: `AddRetry()` MUST come before `AddTimeout()`** (§2.12).
- **§8.8** Rate limiting is opt-in via `opt.AddRateLimit()`. Three styles (`Style`, from 1): `Fixed` (wall-clock window, floor-aligned to global UTC ticks), `Sliding` (rolling window over last N starts, defensively trimmed), and `TokenBucket` (**paces** rather than caps — tokens refill continuously at `count/perSeconds` per second up to a burst of `count`; each start consumes one; a fresh key starts full; when empty a `Wait`-mode start reschedules to the next token-refill instant, so a backlog trickles at the steady rate and never over-admits). `TokenBucket` stores the fractional token count + last-refill instant in `RateLimitBucket` (written only on accept); cross-style bucket-row reads degrade gracefully (bad/foreign payload → empty, never throws). Two policies (`Mode`): `Skip` (default — `Deleted`) and `Wait` (rescheduled via `JobOutcome.RescheduledState`). `perSeconds` capped at `MaxWindowSeconds` (7 days). Lock is released after check-and-increment — **not** held during handler execution (unlike Mutex). Live state in `RateLimitBucket` entity. Lock-contention reschedule has 100–500ms jitter. **DB push does NOT accelerate Wait-mode reschedules** — they land in `State.Scheduled` and depend on `ScheduledJobActivation` polling, so the effective release cadence (including `TokenBucket` refills) is floored at `ScheduledActivationInterval`. **Ordering: `AddConcurrency()` before `AddRateLimit()`** so mutex rejects don't waste tokens. **Attribute placement — the policy axis (supersedes #242):** `[RateLimit]`, `[Mutex]`, `[Semaphore]`, `[Timeout]`, `[Retry]`, `[CircuitBreaker]` are legal on the request/job/message **contract**, on a job/message **handler** class, or on **both** — precedence is **ranked, not forbidden**, and resolution happens in exactly ONE place: `PolicyResolver` (`Warp.Core.Policies`), called from each pipeline behaviour at execution. Rungs: **explicit metadata already on the row** (a publish-time `WithMutex`/`WithRetry`/…, or what a previous attempt stamped) → **handler class** → **contract** → **global options**. Resolution is **rung-major, not attribute-major** — the handler rung is searched for the whole FAMILY before the contract rung, so a handler `[Semaphore]` beats a contract `[Mutex]` (they share one metadata slot); within a rung the family order is fixed (`Mutex` before `Semaphore`). **The winner is stamped into the job's metadata and never re-resolved** (`meta.X != null` ⇒ return): whatever the row says is what executes. The stamp reaches the DB with the attempt's finalizing write (no extra hot-path round-trip, §0.2/§6.1), so an `Enqueued` row is blank and a `Processing` row has resolved but not yet persisted — assertions must read after finalization. A requeue/retry therefore cannot change policy mid-flight and a redeploy never reshapes bound jobs — the debugging contract is "open the job, read its policy". Stamp-once is **per family, not per job**: a short-circuiting behaviour (Skip/Wait concurrency, a throttled rate limit) returns before the behaviours nested inside it resolve, so a requeued row carries the family that decided its fate and resolves the rest at the next attempt — do not read "stamped" as "the whole policy is frozen". Both worker paths persist metadata on the FAILURE path too, not just when an outcome was set, or a stamp made on a throwing attempt would be lost and the next attempt would re-resolve. **Global defaults are deliberately NOT stamped** (process config, read live, identical for every job — absent metadata reads as "the default applies"). **Publish stamps nothing except `Timeout(Scope = Total)`** — `ConcurrencyPublishBehavior`/`RateLimitPublishBehavior`/`RetryPublishBehavior` were DELETED; stamping the contract at publish is exactly what made the handler rung unreachable (#236's shape). Total is the one carve-out: a wall-clock budget from enqueue whose `DeadlineUtc` must exist before any handler is known (§8.31 reads it pre-execution), so it stays **contract-only** and publish-stamped, a handler `[Timeout]` under a Total-scoped global default is **inert** (logged once per request type), and `Scope = Total` on a handler fails the BUILD (`WARP002`) and is **inert at runtime** (`TimeoutStamp.TotalOnHandler`, logged once per request type) for handlers the generator cannot see — never a throw: the resolver runs inside the pipeline, where an outer Retry reads the exception as a handler failure and burns the whole budget on a static misconfiguration. Every policy behaviour shares one prologue, `PolicyResolver.Bypasses(request, jobContext)`: non-job/message shapes, **`JobId == Guid.Empty`** (an in-memory `Send` of an `IJob`-shaped type — no row to skip/reschedule, so gating it would return a silent `default!`), and `IPolicyExemptHandler` all pass straight through. A retry policy is **atomic per rung** — `StampRetry` takes `MaxRetries` AND `RetryDelays` from whichever rung wins and never merges fields across rungs, so `WithRetry(5)` at publish claims the whole policy and the global schedule applies beneath it rather than the attribute's. The sentinel is **either explicit field** (`MaxRetries != null || RetryDelays != null`), symmetrically — an explicit schedule claims the rung and takes the global count beneath it just as an explicit count takes the global schedule. Keying it on `MaxRetries` alone let the attribute overwrite a caller's explicit `RetryDelays`: a delays-only row is **reachable** — `JobParameters.Configure<IRetryMetadata>` and `JobParameters.Metadata` are public, so `WithRetry` is not the only way in. **Concurrency and RateLimit deliberately do NOT take that symmetric sentinel** — they key on `ConcurrencyKey` / `RateLimitKey` alone and stamp all-fields-or-none. Retry has a global default for both of its fields, so a delays-only row is a working policy that must claim its rung; concurrency and rate limit have no global default, so a keyless partial row is inert and honouring it as a rung would mean "no policy" rather than "this limit". The key is identity, and merging an attribute's key onto a caller's count would put two jobs on one key disagreeing about its size. **A cancelled attempt is not a spent retry:** `RetryPipelineBehavior` rethrows an `OperationCanceledException` whose incoming token is cancelled (a graceful `DeleteJob` mid-flight) BEFORE any retry bookkeeping, because the worker's cancel arm now persists `Metadata` to keep the stamp and a `RetriedTimes` bump would otherwise survive on the `Deleted` row and start a later `RequeueJob` one attempt down. The circuit breaker's default group for a routed message child is its **handler** type (a job's stays the request type). The stamp is persisted by **all three** worker finalizing arms — success, `catch (Exception)`, and the graceful-cancel arm — in both `WarpWorkerService` and `WarpDispatcherWorker` (§8.33 lockstep). **There is NO startup validation** — `ValidateAddonAttributesOnHandlers` and `TimeoutStartupDefaults` were removed; a misconfigured policy fails its own job, not the process. Build-time diagnostics keep only what no execution path can honour: `WARP001` (policy attribute on a stream / in-memory-request handler) and `WARP002` (handler `Scope = Total`). **Messages behave exactly like jobs**: the router copies only explicit metadata to children, and each child resolves handler-then-contract at its OWN first execution — so a contract declaration is the shared default across the fan-out (children that declare nothing contend on the one key) and a handler declaration overrides it for that handler's children alone. **`CircuitBreaker` is resolved but never stamped** — its threshold/duration describe a shared dependency GROUP whose live state is a DB row, and two jobs in one group must not disagree about when the circuit opens. **Trap:** `IJobContext.GetMetadata<T>()` COPIES the backing dictionary and re-points `IJobContext.Metadata` at the copy, so a proxy held across `next()` is orphaned and writes to it vanish (this silently disabled `RetriedTimes` and produced infinite retries) — re-read after the inner call, never cache across it. Self-handling jobs (request == handler) stay exempt. Handlers implementing `IPolicyExemptHandler` (saga proxies) are skipped by ALL policy behaviours — attributes, metadata and global defaults alike. A Skip-mode deletion of a routed child counts as SETTLED for parent finalization (`Orchestrator` readiness treats `Deleted` like `Completed`/`Failed`; skipped work is not failed work).
- **§8.9** `RecurringJobScheduler` creates jobs with `ScheduleTime = now`. `AddOrUpdateRecurringJob` only registers/updates the definition — does **not** create jobs. Acquires a distributed lock on the recurring-job name and saves immediately (deliberate §5.7 exception). A firing lands in `State.Enqueued`, so the scheduler **must announce it like every other enqueue site** — it captures `NotificationDispatch.CapturePending` before its `SaveChanges` and dispatches from `OnCommittedAsync` (post-commit per §8.25, since `ExecuteAsync` runs inside the task host's lock transaction). Missing that wake was a real bug: firings were only found by the next backoff poll, up to `MaxPollingInterval` later — which `UseDatabasePush()` raises from 30s to **5 minutes** — and it poisoned the queue-wait SLI (§8.26) with multi-minute samples on otherwise-idle queues. **Disabled definitions are still visited** (the candidate query filters only on `NextExecution <= now`) and take a skip branch that writes a `Skipped` `RecurringJobLog` and creates no `Job` — so a disabled recurring job never executes. That branch must **not** advance `LastExecution`: it names the last occurrence that actually ran, and advancing it on a skip was a real bug — a disabled definition read as if it were still firing on the dashboard while `AttachLastRun` (which filters `!Skipped`) correctly showed no last run beside it. It **does** advance `NextExecution`, deliberately: freezing it would leave the row permanently due and write one skip log per scheduler tick instead of one per cron occurrence, so the dashboard hides the column while disabled (renders `—`) rather than relying on it standing still. `ExecuteAsync` reports the two outcomes separately (`Scheduled X recurring jobs, skipped Y disabled`) — a skip is not scheduled work — while `scheduled + skipped > 0` gates the `SaveChanges`, since a skip does mutate rows. `TriggerRecurringJob` deliberately ignores `DisabledAt` (explicit operator override). **Every single-definition method on `IRecurringJobService` keys on the registered NAME, not the surrogate `Id` (6.0 hard rename, compile error on the old signatures)** — `Trigger`/`Enable`/`Disable`/`DeleteRecurringJob`, `GetRecurringJob` (was `GetRecurringJobById`), `GetRecurringJobHistory`. The name is what a caller already holds, is unique-indexed, and is **stable across a delete-and-re-register** while the identity column is not (a stored/bookmarked id could land on a different definition). `RecurringJobName.Normalize` (internal, shared by the publisher and the service so a lookup can never miss over whitespace) trims, rejects empty, and caps at 200 — the cap is the distributed-lock name `warp:recurring:{name}`, deliberately NOT a column facet, so there is no migration. Commands throw `ArgumentException` for an unknown name; the two queries read as not-found (null / empty page) since a definition can be deleted while its detail page is open. The dashboard routes keep `{prefix}/api/recurring/{id}` but `{id}` is the **URL-safe base64 of the name** (`UrlSafeId`, the codec the endpoints/applications routes share, since a name may hold `/` and spaces); `WarpEndpoints.RecurringAction` decodes it and maps a bad id / unknown name to **404** rather than the old 500. `RecurringJobLog` is the immutable audit trail; `ExpirationCleanup` retains the last 100 logs per recurring job. **A firing's OUTCOME outlives its `Job` row:** `JobExpirationTimeout` is 1 day, so for anything less frequent than daily the job is swept long before the next firing and `DeleteBehavior.SetNull` nulls `RecurringJobLog.JobId` — which left the dashboard able to say only "Cleaned up" for every run a monthly definition ever made, and worse, conflated a `Deleted` run (a skip-mode concurrency/rate-limit refusal, a graceful cancel) with a success, since failed jobs never auto-expire (§8.2) so everything swept was `Completed` or `Deleted`. `ExpirationCleanup` therefore **stamps `RecurringJobLog.FinalState` immediately before the delete, in BOTH delete paths** (`RunCleanupAsync` and `RunCountBasedCleanupAsync` — a new delete path must follow, or `MaxExpirableJobCount` silently loses what the age sweep preserves). Bounded by construction: the expired ids are already in hand, `RecurringJobLog.JobId` is indexed, one grouped `ExecuteUpdateAsync` per distinct state, and **zero UPDATEs on a tick with no recurring firing among its expired jobs**. Stamped at cleanup rather than at finalization deliberately — the worker would need a lookup mid-finalization (§0.2/§6.1). Read side: `AttachLastRun` and the history query read `Job.CurrentState` while the row exists and fall back to `FinalState`, with `RecurringJobModel.LastRunCleanedUp` telling the dashboard the outcome is known but unopenable (renders `Completed (cleaned up)`, never a link into a 404). `FinalState` stays null for a skipped firing (nothing ran) and for runs swept pre-upgrade, which keep degrading to the bare `Cleaned up`. Migration is one additive nullable column.

## Conventions

- **§8.10** Source generators (`Warp.SourceGenerator`, `Warp.Http.SourceGenerator`) target `netstandard2.0` and provide zero-allocation mediator dispatch and HTTP endpoint generation. `[WarpHttpGet/Post/Put/Patch/Delete]` annotations on handler classes emit `RequestDelegate`s; `IJob` / `IMessage` rejected at compile time (`WHTTP001`). **Binary I/O:** a handler whose response is `Microsoft.AspNetCore.Http.IResult` (`IRequest<IResult>`) owns the full HTTP response — `JsonResponseWriter` detects `IResult` and calls `ExecuteAsync`, skipping the JSON envelope, so `Results.Stream/File/Bytes/NotFound/Ok` all work (used for file serving, bodyless status codes). **Multipart/form uploads:** request members typed `IFormFile`/`IFormFileCollection`/`IFormCollection` or carrying `[FromForm]` bind from the form (`BindingSource.Form`, emitted as a `Mixed` shape); `MapWarpHttp` sets `multipart/form-data` and `DisableAntiforgery()` on those endpoints. A request cannot bind both a form and a JSON `[FromBody]` (`WHTTP006`). Demo endpoints: `Warp.Test.Shared/HttpEndpoints.cs` — `/http/file-echo` (upload a file, echo its contents) and `/http/text-to-file` (send text, download it as a file). **`WARP003` — a contract nothing handles** (`UnhandledJobValidator`, prior art PA-05): the mediator generator already knows every `IJob`/`IMessage` and every handler beside it, and a contract missing from that map fails only when a worker picks the row up (`No handler registered for X`) — §8.8's criterion ("what no execution path can honour") covers it. **Warning, never error, and the exemptions are the whole design:** a compilation cannot see an assembly that references it, so a project declaring **no** job-family handler at all is a contracts project and is skipped wholesale (the shared-contract layout stays silent); saga messages count as handled via `ISagaHandler<TSaga, TMessage>` (the user's handler never implements `IMessageHandler<T>` — `AddSagaHandler` registers a proxy, so the message is absent from the dispatch map); self-handling jobs are already their own map entry; open generics are skipped (the map keys a closed type); and referenced contracts are never this compilation's to report. Unhandled `IRequest<T>`/`IStreamRequest<T>` are deliberately **out of scope** — they throw on the calling thread at `Send`/`CreateStream`, and the asymmetry the diagnostic exists for is that a job fails later, elsewhere. What survives suppresses with `#pragma warning disable WARP003`. `Warp.Tests` carries a project-level `NoWarn` because its fixtures are handler-less by design; `UnhandledJobDiagnosticTests` drives the generator in-process and is unaffected.
- **§8.11** **Enums always start at 1, never 0.** `Skip = 1, Wait = 2`, never `Skip = 0`. Avoids `default(T)` collisions and forces explicit assignment. Applies to `JobKind`, `State`, `CancellationMode`, `ConcurrencyMode`, `RateLimitMode`, `RateLimitStyle`, `TimeoutMode`, `TimeoutScope`, etc.
- **§8.12** **Metadata properties are addon-prefixed**, not bare names. `IRateLimitMetadata.RateLimitKey` (not `Key`), `IRateLimitMetadata.RateLimitWindowSeconds` (not `WindowSeconds`), `IConcurrencyMetadata.ConcurrencyKey` / `ConcurrencyLimit` / `ConcurrencyMode`. Prevents dict-key collisions when a single job carries multiple metadata interfaces. Avoid `Dictionary<,>` names entirely — they're a red flag for collision-prone APIs.
- **§8.13** Entity namespaces are **split**: `Job` lives in `Warp.Core.Entities`; `JobLog`, `Server`, `Worker`, `ServerTask`, `ServerLog`, `RecurringJob`, `RecurringJobLog`, `RateLimitBucket`, `RateLimitOverride`, `ConcurrencyLimit` etc. live in `Warp.Core.Data.Entities`. Same folder, different namespaces — do not collapse them.
- **§8.14** **Routed `IMessage` jobs must keep `HandlerType` on requeue** — it IS the routing decision; clearing it sends re-dispatch to `IJobHandler<T>` discovery, which finds nothing for a message type. Enforcement moved from *compile-time-constraint-excludes-messages* to **conditional `ClearHandlerType = request is not IMessage` in every requeue-outcome site** (Concurrency, RateLimit ×2, Retry) when the policy behaviours were widened to messages — a new behaviour that requeues MUST follow it (`MessagePolicyTests.WaitModeHandlerMutex_RoutedChildKeepsHandlerTypeAndCompletes` is the guard). Addons that commit inside handler scope must capture-save-fire and clear-tracker-on-conflict (saga correctness pitfalls).
- **§8.15** Real-time log flushing: `RunJobMonitor` drains `JobLogCollector` every ~1s during handler execution and persists logs to the database. Logs visible in the dashboard while the job is still processing.
- **§8.16** `MetadataConvert` was string-only until the DateTime branch added 2026-05-12 — non-primitive `IJobMetadata` properties need explicit roundtrip tests.
- **§8.17** Sagas are an opt-in addon (`opt.AddSagas()` on the builder) in `Warp.Core.Sagas`. Subclass `Saga` (or `Saga<TKey>` for typed `string`/`Guid`/`int`/`long` keys), annotate the correlation property with `[Correlate]`, mark saga-starting messages with `[StartsSaga]`, implement `ISagaHandler<TSaga, TMessage>`, register handlers via `services.AddSagaHandler<H>()`. Storage: `SagaState` row per active saga + `SagaJobLink` extension table for the activity log with FK cascade. **Delete-on-completion** — `MarkCompleted()` removes the row in the same `SaveChanges`; the correlation key is immediately reusable. No auto-expiry; `ITimeoutMessage` self-schedules at `now + Delay`, and timeout-after-completion silently drops (`Outcome = Deleted`). Proxy serializes per correlation key on `warp:saga:{TSaga.FullName}:{key}` via `IWarpSemaphoreProvider`; optimistic `Version` concurrency is defense-in-depth. Both busy and version/unique conflict outcomes use jittered `ScheduleTime` (50–250ms) to avoid hot loops. `SagaCorrelationKeyConverter` trims strings, rejects empty-after-trim and `default(T)`, caps length at 200. `SagaPiiCheck` blocks `[Correlate]` properties matching common PII names (Email/Phone/SSN/etc.) at registration time; opt out with `[Correlate(IsAnonymized = true)]`. `ISagaCommandService.ForceComplete` acquires the saga mutex and emits a structured `LogInformation` audit. Dashboard at `/warp/sagas` and `/warp/sagas/{id}` with hide-on-404 nav; activity log query caps at 200 most-recent invocations with `IsTruncated` flag. Telemetry counters `warp.sagas.started`/`completed`/`requeued` (tagged `reason=busy|version|unique`). See `website/docs/features/sagas.md`.
- **§8.18** `WarpBackgroundService` is a base part of Warp (no addon opt-in) in `Warp.Core.BackgroundServices`. `AddWarp<TContext>` always contributes the four entities **and** registers `IBackgroundServiceQueryService` (so dashboard-only / publisher-only processes can serve `/api/services` without starting a server); `AddWarpServer<TContext>` adds the server-side host, lease coordinator, state service, and log store, plus the job worker by default. **The worker is a component of the server**: `opt.DisableWorker()` (sets `RunWorker = false`; `AddWarpServer` rejects `RunWorker = true` with zero total workers) yields a service-only server — background services + supporting server tasks (`Heartbeat`/`ServerCleanup`/`ExpirationCleanup`) plus the cluster-locked aggregation folds (`StatisticRollup`/`MetricRollup`/`CounterAggregator`/`ErrorGroupAggregator`/`SloEvaluator`, all registered in `AddServerHostCore` — since 7.5.0; before that the last three ran only with a worker, so a `DisableWorker()` server now runs them: a release-note behaviour change, no data change) without the job worker or the six job-only tasks (`StaleJobRecovery`/`BacklogSampler`/`RecurringJobScheduler`/`ScheduledJobActivation`/`Orchestrator`/`MessageRouter`, registered by `AddWarpServerCore` after the `!runWorker` return), so it claims no job (provider still required). `WarpServerRegistration` creates no groups when `!RunWorker` (and skips `WorkerCount == 0` groups otherwise), so a service-only server leaves no `Worker`/`WorkerGroup` rows. `AddWarpWorker`/`WarpWorkerConfiguration`/`WarpWorkerBuilder` were removed in 2.0 (renamed to `AddWarpServer`/`WarpServerConfiguration`/`WarpServerBuilder`). Users register their own services with `opt.AddBackgroundService<T>()` (single type parameter on the non-generic `IWarpBuilder` receiver). Subclass `WarpBackgroundService`, override `Scope` (`PerServer = 1` — default, one instance per server; `Singleton = 2` — cluster-wide lease). Storage: `BackgroundServiceDefinition` (one row per service name), `BackgroundServiceInstance` (one per server-service pair), `BackgroundServiceLease` (singleton coordination, 30s TTL renewed in `Heartbeat`), `BackgroundServiceLog` (captured user + lifecycle events; FK cascade on instance delete). All in `Warp.Core.Data.Entities`. Worst-case singleton failover ~30s on hard-kill / ~0s on graceful shutdown (lease deleted in `StopAsync` before waiting on user code). Orphaned `Definition` rows (renamed/removed services with no live `Instance`) are deleted by `ExpirationCleanup` once `LastSeenAt > WarpConfiguration.BackgroundServiceDefinitionOrphanGrace` (default 2 min). **Captive-scoped-dependency foot-gun**: subclasses are singletons — inject `IServiceScopeFactory`, not `DbContext`; `ValidateScopes=true` catches it at startup. Log capture is auto-wired (`BackgroundServiceLoggerProvider`) with `MinLogLevel` (default Information), 100/s rate cap, 4KB message truncation, 1000-row/7-day retention. **§1.2 PII responsibility** applies to log output. Telemetry counters: `warp.background_services.started` (tag: `service_name`), `warp.background_services.faulted` (tags: `service_name`, `exception_type`), `warp.background_services.lease_lost` (tag: `service_name`), `warp.background_services.restarts` (tag: `service_name`). Worker hot path untouched (§0.2/§6.1) — separate `BackgroundServiceHost<TContext>`. See §2.13, `website/docs/features/background-services.md`.

- **§8.19** **Outbound adapters** are Warp's answer to observing calls the app *makes to* other services (contrast `Warp.Http` §8.10, which exposes Warp handlers *as* inbound endpoints — the naming `Warp.Adapters.Http` vs `Warp.Http` is inbound-vs-outbound and docs state it explicitly). Protocol-agnostic core in `Warp.Core.Adapters`; HTTP binding in `Warp.Adapters.Http`; Refit sugar in `Warp.Adapters.Refit` (only that package references Refit). **Three-axis identity — memorize the litmus test:** **adapter = policy + health boundary** (registration-time; retry/timeout/rate-limit config + SLO), **group = runtime who/where** (destination, tenant, shop, region — a *runtime value*, always explicit, never heuristic-derived, unbounded), **operation = what** (the API-contract axis — `GetOrders`, `payment.completed`; bounded, may be heuristic-derived). Litmus: if swapping the value changes the request's *structure* (route/verb/payload) → operation; if it only changes *where it goes or on whose behalf* → group. Diagnosis follows the axes: an operation red across all groups = caller-side bug (malformed payload, schema drift); a group red across all operations = counterparty problem (dead token, downed receiver); everything red = the adapter/vendor itself. Enums from 1 (§8.11): `CallRecording { All = 1, FailuresOnly = 2 }`, `CaptureMode { None = 1, OnFailure = 2, Always = 3 }`, `AdapterCallOutcome { Success = 1, Failed = 2, Throttled = 3, CircuitOpen = 4 }` (`CircuitOpen` reserved for the breaker fast-follow), `AdapterRateLimitOverflow { Wait = 1, FailFast = 2, Respond429 = 3 }`. **Capture is opt-in and PII-owned (§1.2):** metadata always; request bodies, response bodies, and headers each independently `None`/`OnFailure`/`Always`, truncated (`MaxCapturedBodySize` 8 KB / `MaxCapturedHeaderSize` 4 KB) and passed through the user-owned `RedactedHeaders` denylist (case-insensitive, prepopulated with `Authorization`/`Proxy-Authorization`/`Cookie`/`Set-Cookie`/`X-Api-Key`; `Add`/`Remove`/`Clear` fully overridable — mandatory `Authorization` redaction was rejected, the denylist is a default not a lock). `RecordCalls = All` (default) writes a row per call — the volume knob for hot adapters is per-adapter `FailuresOnly`; capture modes control payload richness only, orthogonal to whether a row exists. **Cardinality guards:** `MaxDistinctOperations` (default 50) collapses *heuristic-derived* operation names beyond the cap to a literal `{other}` with a one-time warning (explicit names never collapse); `MaxDistinctGroups` (default 500) does the same for group values. `IncludeGroupInMetrics` (default false) keeps group off meter tags unless opted in (bounded group sets); group is always a span attribute + counter key regardless. **Shared rate limit = coordinated config:** `adapter name = cluster-wide identity` (same name ⇒ stats merge and limits share by design; genuinely different dependencies get different names). Shared-policy persistence is **first-writer-wins**: the first registration persists the policy onto `AdapterDefinition`, and later mismatching processes **enforce the persisted policy**, log a Warning, increment `warp.adapter.config_conflicts`, and set `HasPolicyConflict` (dashboard badge) — deterministic mid-rolling-deploy, and deploys alone never change the persisted limit (conflict is preserved, not overwritten, per SC13). Runtime precedence `RateLimitOverride` admin row > persisted definition > local code; **change a shared limit via a `RateLimitOverride` admin row (which takes precedence) or by clearing the persisted policy**, not by redeploying a new code value. **Refit wraps pipeline exceptions (#284):** Refit hands the caller `ApiRequestException` for EVERY exception escaping the `HttpClient` pipeline (and an `ApiResponse<T>` method never throws at all), so `catch (AdapterRateLimitedException)` silently never fires on the Refit binding and `RefitSettings`' response-driven exception factory cannot undo it. Three additive answers, all shipped: `Respond429` waits like `Wait` then answers with a **synthetic 429** (`WarpThrottledResponse`, `Retry-After` + `x-warp-retry-after-ms`) instead of throwing — **recognised by TYPE, not status, in `WarpAdapterHandler.CompleteOutcome` so it records `Throttled` while a REAL vendor 429 keeps recording `Failed`** (a bare status check would both mis-record Warp's own refusal and silently move every existing 429's classification), and **synthesised in the OUTERMOST `WarpAdapterHandler`, never in the rate-limit handler that raised it** — a 429 born innermost is an ordinary retryable status to the user's resilience handler nesting between them (`AddStandardResilienceHandler` treats 429 as transient for BOTH retry and breaker), which would retry Warp's own self-throttle straight back into the limiter and open the breaker on calls the limiter would have admitted; thrown, it passes user handlers untouched (not an `HttpRequestException`), so `Respond429` is byte-for-byte `Wait` inside the pipeline and differs only at the caller; `AdapterRateLimitedException.RetryAfter` carries the window remainder the limiter already computed and used to discard; and `AdapterRateLimitExtensions.IsAdapterRateLimited/GetAdapterRetryAfter/FindAdapterRateLimited` walk `InnerException` + every `AggregateException` branch for callers staying on the throwing modes. The limiter itself is unchanged for the new mode — only `FailFast` short-circuits, so `Respond429` waits and throws like `Wait`, and the HTTP binding converts. **Adoption + rollout guidance:** adapters need only `AddWarp<TContext>` (no server/worker) — they run in any process, alongside other job systems; recording persists via the flusher on the user's `TContext`. **Observe-first is the recommended rollout:** register with no retry handler and no `UseSharedRateLimit` (the passive observing handler alone, zero behavioral change — same timeouts, single attempt, same exceptions), read the data, then add policy per adapter once it justifies the split. Telemetry: `warp.adapter.calls`, `warp.adapter.duration`, `warp.adapter.records_dropped`, `warp.adapter.config_conflicts`. See §2.15, `website/docs/features/adapters.md`.
- **§8.20** **Outbound webhooks** are **part of Core** (`Warp.Core.Webhooks`) and **always-on — there is no `AddWebhooks` gate on whether delivery runs**. `AddWarp` unconditionally wires the dispatcher, executor handler, redelivery enqueuer, and built-in signer; `AddWarpServer`'s default worker group polls `warp:webhooks` unconditionally, so **any server drains deliveries staged by any process — no per-process opt-in to forget** (the old two-process footgun is gone). Nothing runs until a caller invokes `IWebhookDispatcher.SendAsync`. `opt.AddWebhooks(...)` is now **optional config only** (custom `IWebhookSigner`, `IWebhookDeliveryExhaustedHandler`), not an enable switch. The `Moberg.Warp.Adapters.Webhooks` package was **removed** (folded into Core, which took a lightweight `Microsoft.Extensions.Http` dependency; the executor delivers via a bare `HttpClient` + a manual `IWarpAdapters` scope instead of the `Warp.Adapters.Http` binding). **Per-attempt `AdapterCallLog` rows require `AddAdapters()`** (recording opt-in, §8.19); without it the delivery state machine still works fully (dashboard, retries, exhaustion from the `WebhookDelivery` row) but the per-attempt HTTP call-log timeline is empty — consistent with §2.15 (telemetry unconditional, DB recording opt-in). Builds on adapters §8.19; makes durable webhook *delivery* a Warp feature. **Boundary: the host owns subscriptions + fan-out + payload building + endpoint enable/disable + its own secret tables; Warp owns everything after `SendAsync`** — delivery lifecycle, executor jobs, retry scheduling, exhaustion, signing, redelivery, dashboard. Warp models no subscriptions; the host calls `IWebhookDispatcher.SendAsync(WebhookSend)` once per destination. **The delivery, not the job, is the state machine:** the executor (`ExecuteWebhookDelivery`, an ordinary source-gen job on queue `warp:webhooks` — worker hot path untouched §0.2/§6.1) **always completes**; every attempt exception is caught and recorded as attempt failure, so webhook failures never surface as failed jobs or pollute the Jobs UI. State lives on the always-in-schema (§2.11) `WebhookDelivery` row (`Warp.Core.Data.Entities`, §8.13): `WebhookDeliveryStatus { Pending = 1, Delivered = 2, Exhausted = 3 }` (§8.11). **Self-contained row** — URL, headers, payload, schedule, success codes, signing mode + secret, group, reference all stamped at `SendAsync` time so a later config deploy never reshapes an in-flight delivery. **`SendAsync` persists `Pending` + enqueues the first attempt in the caller's transaction (outbox), returns the delivery id** (= adapter `CorrelationId`). **Attempts are adapter calls** through the auto-registered `warp-webhooks` adapter (group = endpoint, operation = event type, `CorrelationId` = delivery id; `RecordCalls = All`, response bodies always captured, request bodies never — payload already on the row; `CallLogRetention` aligned to `WebhookDeliveryRetention`) — the attempt timeline is `AdapterCallLog WHERE CorrelationId = deliveryId`, **no separate attempt table**. **No timers/scans:** each retry is a fresh executor job in `State.Scheduled` at `now + schedule[N-1]` riding `ScheduledJobActivation` (§2.8); `(RetrySchedule, AttemptCount)` fully determines the plan (schedule column never mutated), exhausted when `AttemptCount > schedule.Count`. `RetrySchedule` is per-send `IReadOnlyList<TimeSpan>` (§3 pillar: **no app-level schedule knob**): `null` = built-in `[1m,10m,1h,6h]`, `[]` = single attempt then `Exhausted`, N entries = N retries; persisted as a JSON seconds array (`"[60,600,3600,21600]"`/`"[]"`) via `RetryScheduleConverter` (§8.16 roundtrip tests mandated — empty/single/multi-hour on both providers). `SuccessCodes` `null` = any 2xx. **Cadence precision is delay + up to ~5s activation + worker pickup — a backoff, not a precision scheduler; document it.** Signing (`WebhookSigning { None = 1, StandardWebhooks = 2, Custom = 3 }`, §8.11): `None` (default, adds nothing — the legacy body-embedded-HMAC migration path), `StandardWebhooks` (HMAC-SHA256 over `{webhook-id}.{webhook-timestamp}.{payload}`, headers `webhook-id`/`webhook-timestamp`/`webhook-signature` `v1,<base64>`, `webhook-id` = `EventId` stable across retries), `Custom` (registered `IWebhookSigner` via `w.UseCustomSigner<T>()` — **declaring custom signing without a signer throws at `AddWebhooks` time, not send time**). **Secrets at rest** on the row are accepted for self-containment; **redacted on every read surface** (query service, endpoints, dashboard reduce `Secret` to a `HasSecret` flag, `Authorization`-class headers redacted — not caller-toggleable), never logged Info+ (§1.2); stricter hosts use `Signing = None` and sign in their own payload code. Exhaustion flips `Status = Exhausted` and invokes the host's `IWebhookDeliveryExhaustedHandler` **at-least-once, post-commit** with a redaction-safe snapshot (`ExhaustedCallbackPending` commits with the transition; the recovery check is **status-independent** so a `Redeliver` that flips the row back to `Pending` before the crash-recovery re-run still fires the prior exhaustion's callback) — a throwing callback is logged at Warning, never propagated (callbacks/instrumentation never out-throw). Host decides endpoint disable; Warp only signals. `IWebhookCommandService.Redeliver(id)` requeues a **settled** (`Delivered`/`Exhausted`) delivery to `Pending` + immediate job; `Pending`/unknown rejected with no side effects. **Stuck-delivery recovery (the one deliberate exception to no-timers/no-scans):** the executor's attempt claim and its outcome commit are two transactions — a fault on the second leaves the row `Pending` with no live job (the retry job was staged in the failed transaction). The claim therefore stamps `NextAttemptAt` even on a final attempt, and `StaleJobRecovery` sweeps `Pending` rows whose `NextAttemptAt` is more than `WarpConfiguration.WebhookStuckDeliveryGrace` (default 10 min) past. Duplicate-proof by construction: candidates that still have a live executor job on the webhooks queue are skipped (merely-backlogged workers ≠ lost job), and the guarded `NextAttemptAt` bump + the new job commit in ONE transaction — a rollback undoes both, so no bumped-without-job or job-without-bump state exists. **That sweep runs on the SERVER context like every other server task (§2.14), staging the executor job directly (`JobHelper.CreateJob` + a `Created` `JobLog` + `NotificationDispatch.CapturePending` → `OnCommittedAsync`, the `RecurringJobScheduler`/`MessageRouter` pattern) rather than through the `TContext`-bound `IPublisher`.** It once went through the `IWebhookRedeliveryEnqueuer` seam on `TContext`, which put the bump and the job on a SECOND connection: they could no longer commit with the task host's lock transaction, and the live-job probe waited on the `Job` row locks the stale-job sweep in the same tick still held — under read-committed locking (**SQL Server without RCSI**) a self-block on a transaction that cannot commit until the sweep returns, killed by the command timeout every tick. The enqueuer seam stays for `WebhookCommandService.Redeliver`, which is genuinely user-context outbox work. Staging directly also bypasses `NoRestartPublishBehavior`, so the sweep stamps `ICanBeRestartedMetadata.CanBeRestarted = true` itself — `[Restart]` on `ExecuteWebhookDelivery` is otherwise only honored when the host called `AddNoRestart()`, and the delivery-completes guarantee must not depend on an addon or on `RestartStaleJobsByDefault`. The recovered exhausted-callback reconstructs the exhaustion's `AttemptCount` from `RetrySchedule.Count + 1` on post-`Redeliver` rows (the live column was reset to 0). `IWebhookQueryService`/`IWebhookCommandService` live in `Warp.Core.Webhooks` and resolve in any `AddWarp` process (dashboard/publisher-only) reading on `TContext` (§2.14). `ExpirationCleanup` deletes deliveries past `ExpireAt` (`WebhookDeliveryRetention`, default 30d). **Adoption prerequisite: a Warp server (worker) must run somewhere** to drain `warp:webhooks` — but any `AddWarpServer` with a worker drains it (no `AddWebhooks` needed on that server); coexistence with another job system (e.g. Hangfire) is a documented supported shape. Dashboard **Webhooks** nav is **always shown** (webhooks is a Core feature) — the `GET {prefix}/api/addons` `webhooks` flag gates on the always-registered `IWebhookRedeliveryEnqueuer`. Telemetry: `warp.webhooks.deliveries`/`attempts` (tag outcome) + `warp.webhooks.redeliveries`. See §8.19, `website/docs/features/webhooks.md`.

- **§8.21** **Inbound endpoint observability** (`Warp.Http`, opt-in via `opt.AddEndpointObservability(o => ...)` inside the `AddWarp`/`AddWarpServer` lambda + `app.UseWarpHttpObservability()` after `UseRouting`) is the **inbound mirror of adapters §8.19**: adapters observe calls the app *makes to* other services; this observes requests *made to* the app's **Warp HTTP endpoints** (handlers exposed via `MapWarpHttp`). ONE builder, `WarpEndpointIdentityFactory`, serves both: method from `HttpMethodMetadata` (several/none → `*`, `EndpointCallLog.Method` is 16 chars), template RENDERED from `RoutePattern` segments (never the request path; constraints dropped; required values substituted so a conventional `{controller}/{action}` route gets the action's own template), operation = explicit name (innermost marker) > endpoint name > route name > `Controller.Action` > display name; truncated to the column bounds (1024/200). Rot guards: `HostEndpointObservabilityTestsBase` (both DBs: real MVC + minimal API, Issues, FailuresOnly, Otel, dashboard, Warp-in-group), `WarpEndpointIdentityFactoryTests`, `HostEndpointPipelineOrderTests`. **Identity = HTTP method + route TEMPLATE** (`GET /orders/{id}`) — already bounded (no runtime path-cardinality heuristic, unlike outbound's URL collapsing); inline constraints are normalized away (`{id:int}`→`{id}`) via `EndpointCounterKeys.NormalizeTemplate` so the colon-delimited counter key parses unambiguously, and the flusher stamps the SAME normalized method+template onto the `EndpointCallLog` row so the detail page joins log rows to aggregates. The route is the operation — counter dimensions are **Total + Group only** (no operation dimension); `group` is an optional low-cardinality caller key from `o.GroupSelector(HttpContext)` (channel/client/tenant — never raw IP/user id). Core is protocol-agnostic (`Warp.Core.Endpoints`: `EndpointCallLog` entity §8.13 always-in-schema §2.11, public `IEndpointCallRecorder`/`EndpointCallRecord` seam, `DbEndpointCallRecorder` bounded lossy channel, `EndpointCallFlusher<TContext>` drain→rows+`Counter`s, internal `EndpointCounterKeys`); the HTTP binding (`Warp.Http.Observability`) holds `WarpEndpointObservabilityOptions` (HttpContext-dependent), `WarpInboundObservabilityMiddleware`, and `AddEndpointObservability`/`UseWarpHttpObservability`. **Capture (§1.2 PII):** caller IP (`RemoteIpAddress`, or first `X-Forwarded-For` hop when `UseForwardedForIp`), user-agent, and `User.Identity.Name` are captured by default (the point of the feature) but are PII; request/response bodies + headers are each `None`/`OnFailure`/`Always` (default `OnFailure`), truncated (`MaxCapturedBodySize` 8 KB via a bounded pass-through `CaptureBodyStream` that never buffers a whole streaming/`IResult` response, `MaxCapturedHeaderSize` 4 KB) and redacted through the same user-owned `RedactedHeaders` denylist as adapters. Outcome `Failed` = **final wire status** ≥ 500, or an exception after the response started (truncated 2xx). - **§8.24** **Observability sinks** — everything Warp collects per-call/per-job can be routed to the DB (default), to **OTel**, or **Both**, so a high-throughput deployment can take the diagnostics firehose off its database. Two tracks: (a) **telemetry always emits** — `WarpTelemetry.ActivitySource`/`Meter` (both named `WarpTelemetry.ServiceName` = `"Warp"`, public const) fire spans + meters unconditionally (null-listener, zero cost without an exporter); wiring is `AddSource/AddMeter(WarpTelemetry.ServiceName)` + `AddOtlpExporter`. (b) **recording is the opt-in DB track**, now sink-selectable. `RecordingSink { Database=1, Otel=2, Both=3 }` (§8.11, `Warp.Core.Observability`), default `Database` ⇒ byte-for-byte current behavior. **Per-surface:** `opt.AddAdapters(o => o.Sink = …)` and `opt.AddEndpointObservability(o => o.Sink = …)` — `Database` wires the DB recorder + flusher; `Otel` wires **no recorder and no flusher** (so no call-log rows AND no per-app `Counter` writes) and instead **enriches the span Warp already emits** with the captured detail as span attributes (`warp.adapter.*` on the `Client` span via `AdapterCallScope.EnrichSpanDetail`; `warp.endpoint.*` on the ambient ASP.NET request span via `WarpInboundObservabilityMiddleware.EnrichSpan` — for Warp endpoints and opted-in host endpoints alike, §8.21); `Both` keeps the DB recorder + flusher **and** enriches the span. **No parallel OTel-log recorder exists** — the earlier `Otel*CallRecorder`/`Composite*CallRecorder`/`StructuredLogState` were removed: routing per-call payloads through `ILogger` fanned them to every log provider (console/file), a §1.2 leak, and duplicated the span. Span enrichment fires **only when `Activity.IsAllDataRequested`** (the span is sampled in), so a single consistent trace-sampling decision governs the whole call/request coherently — detail travels on the trace exporter only, never `ILogger`. Adapters carry the process-level enrich flag via the optional-marker seam (`AdapterRecordingSettings`, §2.9). **Repeated `AddAdapters` calls merge** into one options bag (`AdapterRecordingRegistration`), and the implicit `AddAdapters()` inside `AddAdapter`/`AddAdapter<TApi>` sets no sink, so an explicit `Sink` wins in either call order: every call re-syncs the DB recorder + flusher descriptors to the merged sink (registered once, for the final choice), and `AdapterRecordingSettings` is ONE factory registration read from it. Before, `AddAdapter` registered the DB pair with the default sink and a later `AddAdapters(o => o.Sink = Otel)` could not take it back (rows were still written), and with `AddAdapter` first the span enrichment was lost too (`WarpAdapters` read the first of two settings); `RecordingSinkWiringTests` covers both orders on HTTP and Refit; endpoints read `WarpEndpointObservabilityOptions.Sink` in the middleware and take the recorder optionally (`IEnumerable<IEndpointCallRecorder>`, empty under Otel). The internal `IAdapterCallRecorder` **stays internal** (no public storage contract); under Otel-only it falls back to Core's `NullAdapterCallRecorder`. Dashboard nav flags stay keyed on presence markers registered regardless of sink (`IAdapterRecordingMarker`; new **`IEndpointObservabilityMarker`**, replacing the old `IEndpointCallRecorder`-presence gate which is absent under Otel). **Job-metrics:** `WarpConfiguration.JobMetricsSink` (`RecordingSink`, default `Database`) gates the per-type/handler `jobstat` counter increments at the finalization sites (buffer entries, §6.2 — not rows) — `Otel` skips them (perf win; §0.2/§6.1 hot path only gains `instrument.Record` calls + one config check), the meters carry the data. **Meters added/extended (always-on, low-cardinality tags only, `group` stays OFF meter tags §1.2):** `warp.adapter.calls`/`duration` (+`application`), `warp.endpoint.calls`/`duration` (`route`/`outcome`/`application`), `warp.job.execution.total`/`duration` (`job.type`/`job.handler`/`outcome`/executor-`application`). **Dashboard:** `Database`/`Both` → Warp dashboard works; `Otel`-only → those pages have no DB rows (use Grafana/Jaeger, or register a backend-backed impl behind the public `IAdapterQueryService`/`IEndpointQueryService` via `TryAdd`-before-`AddWarp`). Control-plane (jobs/servers/sagas/webhooks/app roster) stays in the DB regardless — it's state, not telemetry. See `website/docs/features/observability-sinks.md`.

- **§8.25** **Operational notifications** — a host seam (`IWarpNotifier { Task NotifyAsync(WarpOperationalEvent evt, CancellationToken ct); }`, `Warp.Core.Notifiers`) that hands Warp-detected operational events to the host, which decides what to do (Teams/Slack/email/page/log). **Warp ships no channel integrations** — pure seam, the `IWebhookDeliveryExhaustedHandler`/`IWebhookSigner`/`IWarpCredentialValidator` precedent. **Alerting ≠ webhooks:** a webhook is the host telling external subscribers about domain events (needs a subscriber URL); a notification is Warp telling the operator something is wrong (no URL) — reusing `IWebhookDispatcher` for self-alerting is the wrong abstraction. Register via `opt.AddNotifier<T>()` (non-generic `IWarpBuilder`, §2.13 `AddBackgroundService<T>` precedent); resolved as `IEnumerable<IWarpNotifier>` (optional-marker, §2.9) so **zero registered = inert**. **Contract:** invoked **post-commit** (the transition is durable) and a **throwing notifier is caught + logged at Warning + never propagated** (an alert sink can't take down what it observes; never fails/slows the worker). **Events are NOT persisted — no notification outbox.** Dispatch is in-process from an in-memory buffer, so **delivery to the sink is best-effort for every event**: a crash in the commit→dispatch window, or a notifier that's down/throwing (swallowed+logged, no retry), drops that alert. Convenience alerts, not an audit trail — the operator action / `WebhookDelivery` row / instance roster are the systems of record; don't build guaranteed-delivery accounting on them. **Per-source replay nuance:** only `WebhookDeliveryExhausted` is re-emitted after a crash-before-dispatch (the delivery's `Exhausted` state is persisted → executor re-run regenerates the event; may repeat, key on event id) — still lost if the sink is unreachable at call time. `SagaForceCompleted` + `InstanceDown` report a row deleted in the committing transaction, so a lost dispatch is gone for good. Don't overclaim at-least-once. §8.18 captive-dependency footgun applies — notifiers are singletons, inject `IServiceScopeFactory` not `DbContext`. Fan-out is centralised in the singleton **`WarpNotifierDispatcher`** (guarded loop over the set; empty-set no-op), registered by `AddWarp` (beside `ServerTaskSignals`) so every dispatch site resolves it in any process. **CRITICAL post-commit mechanism for server tasks:** `ExpirationCleanup`/`ServerCleanup` run INSIDE the server-task host's lock transaction (`IServerTask.LocksWithTransaction` default true → `ServerTaskLoop.RunUnderTransactionLockAsync` commits AFTER `ExecuteAsync` returns), so their `SaveChangesAsync` only **flushes** — a direct dispatch there fires **pre-commit** and could alert on a rollback-undone change. The seam is **`IServerTask.OnCommittedAsync(ct)`** — a **default-no-op post-commit hook** the `ServerTaskLoop` invokes after the transaction commits (both lock paths; **skipped on throw/rollback and when the lock wasn't held**). The two tasks **buffer** their `InstanceDown` events in a private field during `ExecuteAsync` and **dispatch from `OnCommittedAsync`** (`CancellationToken.None` so shutdown doesn't abandon a committed alert). Keeps `ServerTaskLoop` feature-agnostic (no `Notifiers` coupling). The webhook + saga sites are ordinary/​session-lock paths (genuinely post-commit) and dispatch inline via `WarpNotifierDispatcher` directly, also with `CancellationToken.None`. **New server-task authors: never dispatch in `ExecuteAsync` (pre-commit) — buffer + dispatch in `OnCommittedAsync`.** **Events are redaction-safe snapshots — identity/metadata only, never a payload body (§1.2).** Abstract `WarpOperationalEvent` base (`Type`/`Severity`/`TimestampUtc`/`MachineName`/`Application`/`Message`) + typed subtypes the host switches on. `WarpEventType` enum from 1 (§8.11, `Warp.Core.Enums`): `JobDeadLettered=1` (**RESERVED**, deferred — the payloadless finalization signal needs a claim mechanism), `WebhookDeliveryExhausted=2`, `SagaForceCompleted=3`, `InstanceDown=4`, `BacklogBreached=5` (**RESERVED**, needs queue-wait metrics). Plus `WarpEventSeverity { Info=1, Warning=2, Error=3 }`. **v1 dispatch sites (all pre-existing detections, worker hot path untouched §0.2/§6.1):** webhook exhaustion in `ExecuteWebhookDelivery` (post-commit, alongside the existing exhausted-handler — the two coexist), saga `ForceComplete` in `SagaCommandService` (after `SaveChanges`), and instance-down from BOTH the `ExpirationCleanup` stale `ApplicationInstance` sweep (`IsServer=false`) and the `ServerCleanup` stale-`Server` sweep (`IsServer=true`) — every server is an instance (§8.23). Dispatch sites take a **required** `WarpNotifierDispatcher` ctor param (§0.5 specific dep, no fallback). See `website/docs/features/operational-notifications.md`.

- **§8.26** **Queue metrics (queue-wait + backlog)** — the two job-system health signals beyond per-job execution time (§8.23/§8.24). **Always-on, no addon opt-in.** **(1) Queue-wait latency** measured at the worker claim site (`WarpWorkerService`/`WarpDispatcherWorker`, where `Enqueued → Processing` and the "Processing" `JobLog` is written): `waitMs = max(0, claimTime − Job.ScheduleTime)` (`ScheduleTime` advances on requeue, so wait is from requeue not original enqueue). **Hot path sacred (§0.2/§6.1):** the increments are **staged on the worker and handed to the process-wide `WarpCounterBuffer` once the claim commits** — NO row, NO extra query, NO round-trip (they used to be `Counter` rows added to the existing claim-site `SaveChanges`; `CounterBufferFlusher` now writes one row per distinct key per `CounterBufferFlushInterval`, default 2s, and an UNGRACEFUL exit loses at most that window — a graceful stop flushes). Staging, not buffering directly, is what makes a rolled-back attempt contribute nothing: `BeginFinalizingTransactionAsync` clears the staging list, so an arm that re-finalizes after a failed commit cannot hand across the abandoned attempt's increments as well as its own. The always-on `WarpTelemetry.RecordQueueWait` meter fires unconditionally. Folds `Counter → CounterAggregator → Statistic` via `QueueWaitKeys` (`Warp.Core.Services`, `internal static`, prefix `qwait` / per-app `qwait-app`, tokens `count`/`dur` + `pct:{bucket}` histogram, same buckets as `JobStatsKeys`) so **avg/p95/p99 survive raw-row cleanup**; per-app slice carries NO histogram (p95/p99 read 0) to bound volume. **(2) Backlog depth + oldest-age** sampled OFF the hot path by `BacklogSampler<TContext>` (`Warp.Worker.Services`, an `IServerTask` like `CounterAggregator`; `LockKey = "warp:backlog-sample"`, `DefaultInterval => WarpServerConfiguration.BacklogSampleInterval` default 60s): one EF-LINQ grouped query `GroupBy(Queue).Select(Count, Min(ScheduleTime))` filtered `Kind==Job && CurrentState==Enqueued && ScheduleTime<=now` — served by the **existing** `(Kind, CurrentState, Queue, ScheduleTime)` index (no new index, §5.x, no raw SQL). Writes always-on `WarpTelemetry.SetBacklogSnapshot` (drives `JobQueueDepth`/`JobQueueOldestAge` ObservableGauges, `queue` tag only) + `qbacklog:` gauge `Statistic` upserts (`QueueBacklogKeys`; overwrite each tick — NOT `Counter`, so `CounterAggregator` doesn't double them; drained queues reset to 0). **Backlog is queue-GLOBAL, deliberately NOT app-sliced** (there is no `qbacklog-app`): an eligible-but-unclaimed job has no executor, and slicing by the *publishing* app is the per-creator metric §8.23 omits — a single cluster-wide sampler (lock `warp:backlog-sample`) sees all apps' enqueued jobs, so the global count is correct. **Meters (always emit, low-cardinality tags `queue` + `application` when set — group/PII off §1.2):** `warp.job.queue.wait` (Histogram ms), `warp.job.queue.depth` + `warp.job.queue.oldest_age_seconds` (ObservableGauges). **Sink-respecting (§8.24):** both respect `WarpConfiguration.JobMetricsSink` — `Otel` SKIPS the Counter/Statistic writes (perf win), meters still carry the data. **Multi-app (§8.23):** queue-**wait** is sliced by **executor** application under a disjoint namespace (`qwait-app`, first-segment-equality parsers reject it, existing keys unchanged, §8.6/§8.19); **backlog stays global** (see above). `GetQueueMetrics(application)` returns that app's wait alongside the queue's global backlog. **Read side:** `IJobQueryService.GetQueueMetrics(string? application)` → `QueueMetricsModel`/`QueueMetricModel` (`Warp.Core.Models`) reads only the durable aggregates (resolves in any `AddWarp` process). API `GET {prefix}/api/queues/metrics` (`?application=` optional, no addons flag) — **retained as public read API, but the dashboard no longer consumes it**. The standalone **Queues** page was REMOVED in 6.x: `counterModel` already routed `qwait`/`qwait-app` AND `qbacklog` into one `queues` counter family, deliberately merging depth/oldest-age onto the same row as that queue's wait latency, so the page was a second rendering of the same two folds. The one thing it had that the family lacked — p99 — moved over: `FamilyDef.percentiles` is now a LIST (default `[0.95]`, client vitals `[0.75]`, queues `[0.95, 0.99]`), so a family can report several percentiles off one histogram. Do not reintroduce the page; add to the family instead. See §2.15/§8.23/§8.24, `website/docs/features/queue-metrics.md`.

- **§8.27** **Client (frontend) observability** is the **browser-side** complement to server-side observability (adapters §8.19 outbound, endpoints §8.21 inbound-to-Warp): a public **ingest endpoint** a frontend app posts to, attributed to an **application** (§8.23). One `ClientEvent` primitive discriminated by `ClientEventType { Error=1, Vital=2, Log=3, Event=4 }` (§8.11, `Warp.Core.Enums`) — `log()`/`track()` sugar + auto-captured errors/vitals are the SAME row (no second subsystem). Same pipeline as adapters/endpoints: bounded lossy channel (`DbClientEventRecorder`) → `ClientEventFlusher<TContext>` (drains to `ClientEventLog` rows + the durable `clientevent:` Counter fold, stamps `ReceivedAt`/`ExpireAt`, §0.5 scope) → `Counter → CounterAggregator → Statistic`. **Two-tier storage (never inflate the DB):** raw `ClientEventLog` rows (`Warp.Core.Data.Entities`, always-in-schema §2.11, mirrored by `WarpServerContext` §2.14) are trimmed on age (`ClientEventLogRetention` 7d) AND count (`ClientEventLogRetentionCount` 100k/app) by `ExpirationCleanup`; trend data (`ClientEventKeys`, `Warp.Core.ClientObservability`, disjoint prefixes `clientevent`/`clientevent-app`, §8.6/§8.19) — per-type count + hourly history, per-name total, per-vital count+dur+**p75 histogram** — **survives raw-row cleanup** (§8.22). **Cardinality guard (the difference from endpoints, whose routes are bounded) — NOTHING client-sent is trusted bounded on a public endpoint:** error/event names AND log **levels** collapse to `{other}` beyond a per-type cap (`ClientEventCardinality`, §8.19); **vital names go through a fixed allowlist** (`ClientEventCardinality.KnownVitals` = LCP/CLS/INP/FCP/TTFB → else `{other}`) for BOTH the counter key and the `warp.client.vitals` meter tag — a raw client vital name is never a metric dimension. Counter-only; the raw row keeps the real name. Logs fold by `Level` (§8.27 "logs count per level"), not the free name. CLS is folded ×1000 into the shared integer histogram and unscaled ÷1000 on read. **Web vitals follow Google: p75** (their good/needs-improvement/poor threshold percentile), NOT p95/p99. **Public endpoint (hostile client):** auth is a public write-only **DSN key** (`o.AddIngestKey(app, key)` → **trusted** app name, never client-declared; unknown → 401), a CORS **origin allowlist** (else 403; same-origin — `Origin == scheme://host` — bypasses the allowlist), an **in-memory per-caller-IP** rate limit (`ClientIngestRateLimiter` — keyed on IP not the public key, checked BEFORE the body read so floods/bad-key/empty posts are bounded cheaply; NEVER DB-backed), and hard size/batch caps. A crafted out-of-range `ts` is caught (never faults the request). Key travels in `x-warp-key` header OR body (a `sendBeacon` caller can't set headers). Recording is lossy (full channel drops + `warp.client.events.dropped`; an unrecognized event `type` is also dropped-and-counted, never silent; browser never blocked). **PII (§1.2):** IP off by default; property maps redacted via a denylist + truncated; never logged Info+; **consent/GDPR is the host's job**. **Sink-respecting (§8.24):** `Database`/`Both` write rows; `Otel` skips the DB, meters carry it (`warp.client.events`/`vitals`/`events.dropped`, always-on). Core (`Warp.Core.ClientObservability`) holds the sink-free pipeline + options + `AddClientObservability(IWarpBuilder)` + the query service (registered by `AddWarp` itself, resolves in dashboard-only processes); the HTTP binding (`Warp.Http.ClientObservability`) holds `MapWarpClientObservability()` (the ingest endpoint + `GET {IngestPath}/client.js` serving the shipped self-contained browser script — error hooks, web vitals via PerformanceObserver, breadcrumbs, `sendBeacon`/`fetch(keepalive)` batching, per-session sampling). Dashboard **Client** page (`/client`, `ClientPage.tsx`) gated on `WarpAddonsInfo.Client` (keyed on `IClientObservabilityMarker`). API `GET {prefix}/api/client/summary|events|events/{id}|applications`. Worker hot path untouched (§0.2/§6.1). **Client↔server correlation (unified session timeline):** the shipped script propagates TWO W3C headers on same-origin calls — `traceparent` (per-request **trace id**, already adopted into `EndpointCallLog.TraceId`/`Job.TraceId`) and `baggage: session.id=…` (the OTel `session.id` for the whole session). The middleware reads the session baggage onto `EndpointCallLog.Session` (via `Activity.Current.GetBaggageItem`, `WarpTelemetryAttributes.SessionId = "session.id"`) and sets it as the `session.id` span attribute on the request span so OTel backends slice by session. **Jobs are NOT stamped with session** — a `Job.Session` column was built and then dropped as redundant: a job already carries a `TraceId`, and the trace id ties it back to the originating request, which carries the session. Session is a request/endpoint-level dimension; the job↔request link is the trace id (the join key the unified trace view uses, §8.28). `ClientEventType.Request = 5` + `ClientEventLog.TraceId` (Guid, "N"-form join key). `IClientEventQueryService.GetSession(sessionId)` merges the session's client events with the `EndpointCallLog` rows stamped with that session (direct column join) into one chronological timeline; `GET {prefix}/api/client/sessions/{id}`, `ClientSessionPage.tsx` at `/client/sessions/:id`, request/server rows link to `/trace/{traceId}` (the unified trace view §8.28). Trace id = one action end-to-end; session id = all actions in a visit — both propagated. See §2.15/§8.19/§8.21/§8.28, `website/docs/features/client-observability.md`.

- **§8.28** **Unified trace view** — a single screen showing *everything* that happened for one trace id: the browser request, the server endpoint call it hit, the jobs that endpoint spawned, and the outbound adapter calls those jobs made — a local, DB-backed Jaeger/Tempo-lite for the rows Warp already persists. **The key insight: Warp already stores spans.** A `Job` is a span (`TraceId`, `SpawnedByJobId` = parent, `CreateTime`, terminal state), an `EndpointCallLog` is a span (`TraceId`, `Timestamp`, `DurationMs`, `Outcome`), an `AdapterCallLog` is a span (`TraceId` — **string**, `"N"`-form — `Timestamp`, `DurationMs`, `Outcome`), and a `ClientEventLog` of `Type = Request` is a span (`TraceId`, `Timestamp`, `Value` = client-measured duration). So the unified trace view is built by **unioning those existing rows on their shared trace id — NO new `Span` table, NO `ActivityListener` collector, NO hot-path span capture** (an earlier "local tracing" batch that added a `Span` entity + `SpanKind`/`SpanStatus` enums + retention was deliberately reverted once this was understood — do not reintroduce it). **`ITraceQueryService.GetTrace(Guid traceId)` → `TraceOverviewModel?`** (`Warp.Core.Services` / `Warp.Core.Models`, registered by `AddWarp` itself like `IAdapterQueryService`/`IEndpointQueryService`, so it resolves in dashboard-only/publisher-only processes) fetches each source with `AsNoTracking` `.Select()` projections (§5.3/§6.4), maps each to a `TraceSpanModel { Source ("client"|"endpoint"|"job"|"adapter"), Id, Name, StartTime, DurationMs?, Status, IsError, ParentId? }`, and returns them ordered by `StartTime` (null if the trace has no rows). Adapter rows join on `traceId.ToString("N")` (their `TraceId` is a string); only jobs carry a `ParentId` (`SpawnedByJobId`) — the other sources are roots. **Job execution timing comes from `JobLog`, not the `Job` row:** the `Job` row has no execution-duration column, but the worker already persists per-attempt timing — each terminal `JobLog` (Completed/Failed/Cancelled, via `FinalizationLogs`) carries the handler's `DurationMs` at its `Timestamp`. `GetTrace` does a two-step fetch (job ids → their `DurationMs != null` logs, §5.2 — no subquery-in-projection) and maps the **latest** such log per job (retries: last execution wins) to `DurationMs = log.DurationMs`, `StartTime = log.Timestamp − DurationMs` (the real execution window, so a job bar nests over the adapter calls it made). Falls back to the `CreateTime` marker (`DurationMs = null`, a placeholder `—`) when the logs have aged out (`JobLog` retention) or the job hasn't finished — graceful degradation, same stance as the other sources. Endpoint/adapter/client spans have precise timing from their own rows. Read-only union — no writes, no new schema, worker hot path untouched (§0.2/§6.1). **Dashboard:** `TraceWaterfall.tsx` renders the spans as a time-ordered Gantt (source badges — client=green, server=slate, job=blue, outbound=purple; bars positioned on a shared min-start→max-end axis; job indentation via `ParentId`; error bars in `bg-destructive`; per-span detail links — job→`/detail/{id}`, client→`/client/events/{id}`), injected **above the existing job-DAG ReactFlow graph on `/trace/{traceId}`** (`TracePage.tsx`) — the DAG shows job parent/child structure, the waterfall shows the cross-source timeline. `GET {prefix}/api/traces/{traceId}` (distinct from the pre-existing `trace/{traceId}` job-DAG endpoint). Reachable from the session timeline (§8.27, request/server rows link to `/trace/{traceId}`) and any job/endpoint/adapter detail page. **Rollout stance (the user's framing):** save it all locally for near-Jaeger experience on your own DB; switch to an external collector (OTel is always emitting, §8.24) once data volume makes the DB too slow. See §2.15/§8.19/§8.21/§8.27, `website/docs/features/client-observability.md`.

- **§8.29** **Error grouping / "Issues"** turns raw error rows from the four already-persisted surfaces — failed-job `JobLog`, endpoint 5xx `EndpointCallLog`, adapter-call `AdapterCallLog`, browser `ClientEventLog` — into durable **`ErrorGroup` "issues"** (Sentry-lite: one row per real problem, not per occurrence, with count/first-last-seen/trend/sample and an `Unresolved/Resolved/Ignored` lifecycle). **Always-on Core feature** (no addon opt-in, like queue metrics §8.26); `WarpConfiguration.ErrorGroupingInterval = null` disables it (byte-for-byte today's behavior). **Write path is inbox-drain, zero hot-path cost (§0.2/§6.1):** `JobLog`/`*CallLog` have no `(discriminator, Timestamp)` index and scanning them would write-amplify hot inserts, so instead each source **appends one `ErrorOccurrence` inbox row** (transient, write-optimized, self-clearing — the `Counter` pattern): **jobs** append in the **existing finalization `SaveChanges`** (no fingerprint CPU on the worker, no round-trip). NOTE it is a ROW and stays one — unlike the queue-wait counter §8.26, which moved into the in-memory buffer: an occurrence must survive the process, so it cannot follow the counter. **Endpoint** occurrences — from Warp endpoints AND host endpoints opted in via `WithWarpObservability()`/`[WarpObserved]` (§8.21; their identity is the same bounded `METHOD /template`) — are appended by `EndpointCallFlusher` (NOT `WarpInboundObservabilityMiddleware`, which only hands the record to the recorder) — in the same `SaveChanges` that drains the call, gated on `ErrorGroupingInterval`, and independent of whether the call-log ROW is written, so 4xx groups still exist under `RecordCalls=FailuresOnly`. The corollary: an `Otel`-only endpoint sink registers no recorder and no flusher, so it produces **no endpoint issues** (§8.24). **Adapter/client** append in their flushers too. **`ErrorGroupAggregator<TContext>`** is an `IServerTask` (§2.3, like `CounterAggregator`; `LockKey="warp:error-grouping"`, cadence `WarpConfiguration.ErrorGroupingInterval` default **60s**) that **drains-and-deletes** the inbox (exactly-once by construction — no cursor), computes fingerprints **off the hot path**, and **upserts** `ErrorGroup` (`Count += n`, `LastSeenAt`, `LastSample`, `SampleTraceId`; `FirstSeenAt`/`Title`/`Culprit` on insert) + folds an hourly `errorgroup:{fingerprint}:count` **Counter** (trend → `Statistic`, §6.2, **survives raw-row cleanup** §8.22). **Fingerprint** (`ErrorFingerprint`, `Warp.Core.ErrorGrouping`, pure + unit-tested) = `hash(source + exception-type + locus)` → 32-hex; **message is normalized OUT of identity** (digits/GUIDs/hex/quoted literals → `<num>/<guid>/<hex>/<str>`) so message-varying occurrences group and the normalized message is the **PII-safe `Title` (§1.2)**. **Fine (stack-frame) grouping:** stack-bearing sources (job, client) use the **top in-app stack frame** (first frame not matching the `InAppNamespaceDenylist` — `Warp.*`/`System.*`/`Microsoft.*`/`Npgsql.*`, editable — so two bugs in one handler are two issues); stackless sources (endpoint, adapter) use route/operation; **`Source` is part of identity** (a browser `TypeError` ≠ a server exception). **What counts per source:** **jobs** count **every** caught exception — retry attempts AND terminal (`FinalizeJobState` has `e` either way, so flaky handlers are visible); **endpoints** count `Outcome=Failed` (5xx/unhandled: type+route) **and any 4xx** (`status + route` groups, `Kind=StatusCode`) — 4xx are **default-filtered** in the UI and **kept OFF the reliability SLI** (§8.21 stays 5xx-only; issue membership ≠ error rate); **adapters** count `Failed` only (Throttled/CircuitOpen excluded — expected backpressure); **client** counts `Type=Error` only. **Entities** (`Warp.Core.Data.Entities`, §8.13; **always-in-schema §2.11**; mirrored by `WarpServerContext` §2.14): `ErrorGroup` (`Fingerprint` unique, `Source` `ErrorSource {Job=1,Endpoint=2,Adapter=3,Client=4}`, `Kind` `ErrorKind {Exception=1,StatusCode=2}`, `ExceptionType`, `Title`, `Culprit`, `StatusCode?`, `Application?`, `FirstSeenAt`, `LastSeenAt`, `Count`, `LastSample` raw+truncated §1.2, `SampleTraceId?`, `Status` `ErrorGroupStatus {Unresolved=1,Resolved=2,Ignored=3}`, `StatusChangedAt?`; enums from 1 §8.11) + `ErrorOccurrence` (the transient inbox; drained+deleted each tick — a defensive orphan sweep in `ExpirationCleanup` clears any past a grace, like the webhook stuck-recovery). **Lifecycle (Sentry-lite):** **new** issue = a UI **"new" badge** only (not an alert — a fresh deploy mints many new types, paging on each is noise); **Resolve/Ignore** via `IErrorGroupCommandService.SetStatus(fingerprint, status)` (mutex + structured `LogInformation` audit, mirrors `SagaCommandService.ForceComplete`; `Ignored` still counts, hidden from the default view); **regression** — a `Resolved` group re-opens (→`Unresolved` + "regressed" badge) **ONLY** on an occurrence with `Timestamp > StatusChangedAt` (so pre-resolve inbox backlog can't false-reopen) and that fires **`WarpEventType.IssueRegressed`** (`Warp.Core.Enums`, from 1 §8.11) dispatched **post-commit from the aggregator's `OnCommittedAsync`** (§8.25 — never `ExecuteAsync`; opt-in/inert notifier seam, zero registered = no-op); **`Ignored` never auto-re-opens**. **Cardinality guard** (§8.19/§8.27 — critical because the client source is fed from the public ingest endpoint, hostile input): `MaxDistinctErrorGroups` (default **2000**, per source + app when app-sliced) collapses overflow into a per-source `{other}` group (still counted, keeps a sample; one-time warning). **Read/UI:** `IErrorGroupQueryService` registered by **`AddWarp` itself** (resolves dashboard-only/publisher-only, §8.27/§8.28); metrics from durable aggregates survive raw-row cleanup, recent occurrences degrade to empty once swept. Always-shown built-in **Issues** page (`/issues` — grouped list: source badge, count, trend sparkline, status chip, new/regressed badges, filters source/status/application + a 4xx toggle) + detail (`/issues/:fingerprint`: title, raw sample stack, hourly trend chart, occurrences → trace, Resolve/Ignore). **Diagnostic detail:** `FromException` **unwraps** `TargetInvocationException`/`AggregateException` to the real inner cause (the mediator invokes handlers via reflection, so the raw type is the wrapper — group on the cause, keep the full wrapper as the sample); the job **culprit is the short type name** (`WarpTelemetry.GetShortTypeName`), not the assembly-qualified string; occurrences carry `Version`/`Environment` (`ApplicationVersion`/`ApplicationEnvironment`) and the group records `FirstSeenVersion`/`LastSeenVersion`/`Environment` (tie an issue to a deploy); and `ErrorGroup.RecentSamples` is a rolling capped-10 JSON list (`{traceId,timestamp,message,version}`, newest-first, gated on `CaptureErrorSamples`) the detail renders as a walkable per-occurrence timeline. **Both worker paths feed the inbox** — `WarpWorkerService.FinalizeJobState` AND `WarpDispatcherWorker` (via `PendingCompletion.Occurrence` → `CompletionBatch`); a dispatcher-mode integration test (`UseDispatcher=true` → failed job → group) guards the second path. **Navigation:** forward is shipped — issue→trace via a stored `SampleTraceId` linking into the unified trace view (§8.28), where every span (job/endpoint/adapter/client) already links to its own detail, so an issue reaches all of its related surfaces. **Reverse nav (a source detail page → its issue) is a planned follow-up** — the fingerprint is a pure function of the already-loaded row, so a detail page can recompute it on-read (no stored `Fingerprint` column, no hot-path change) and show a "Part of issue" chip; not built in the 3.9 slice. API `GET {prefix}/api/issues`, `GET .../issues/{fingerprint}`, `POST .../issues/{fingerprint}/status`. **Config:** `WarpConfiguration.ErrorGroupingInterval` (60s, null=off), `ErrorGroupRetention` (age by `LastSeenAt`, 30d), `ErrorGroupRetentionCount` (count, null=off), `MaxDistinctErrorGroups` (2000), `CaptureErrorSamples` (true — raw truncated sample; Title stays normalized/PII-safe), `InAppNamespaceDenylist`. **Retention (§8.22)** swept by `ExpirationCleanup` (age + count + the orphan-occurrence sweep); trend `Statistic`s outlive the groups. **Multi-app (§8.23):** `ErrorGroup.Application` = **executor** app for jobs (execution attribution), source app otherwise; disjoint counter namespace `errorgroup`/`errorgroup-app` (first-segment-equality safe, §8.6/§8.19); `?application=` filter. **Sink (§8.24):** Otel-only sources write no rows → no inbox rows → no issues from them (jobs always feed — they always persist `JobLog`; disable via `ErrorGroupingInterval = null`). Worker hot path untouched (§0.2/§6.1). See §2.15/§8.19/§8.21/§8.27, `website/docs/features/error-grouping.md`.
- **§8.30** **Metrics retention tiers** make every time-bucketed `Statistic` series multi-resolution: **fine (5-min) → hourly → daily**, downsampled by rollup instead of the old delete-only prune. **Explicit tier marker** `MetricTiers` (`Warp.Core.Services`, `internal`): trailing suffix `:{m5|h1|d1}:{stamp}` (`yyyy-MM-dd-HH-mm` / `-HH` / day) — chosen over inferring resolution from stamp shape so per-family parsers stay fixed-length + disjoint (§8.6/§8.19). Applies to the hist/pcth families with a windowed consumer or latency histogram — **`jobstat` + `qwait` emit the fine tier** (fine `hist` + a new tiered **`pcth`** latency histogram alongside the untouched lifetime `pct`, for windowed percentiles); **`stats:`/adapter/endpoint/clientevent/errorgroup keep emitting unmarked hourly** and are rolled to daily by the generic pass (no emit change, strictly more history retained than the old delete). **Lifetime totals (`…:{token}`, no date) and lifetime `pct` are untouched.** **Emit change is inside each `*Keys.Build()`** (worker call sites just pass `MetricTiers.Suffix(Fine, now, FineResolutionMinutes)` instead of an hour string) — **zero `CounterAggregator` change** (it folds any key). **`StatisticRollup<TContext>`** is an `IServerTask` (§2.3, registered in `AddServerHostCore` beside `ExpirationCleanup`, `LockKey="warp:stat-rollup"`, cadence `WarpServerConfiguration.StatisticRollupInterval` default **10m**) — **family-agnostic**: `MetricTiers.TryClassifyKey` splits any key into (base, tier, bucket) from the trailing suffix (marked **or** legacy unmarked `:yyyy-MM-dd-HH`, so **pre-3.10 rows migrate to daily automatically**), then per pass it **sums-then-deletes** fine→hourly (older than `FineResolutionRetention` 6h) and hourly→daily (older than `HourlyStatisticsRetention` 7d — repurposed from a delete age), and prunes daily (older than `DailyStatisticsRetention` 90d, `null`=keep forever). **Crash-idempotent** inside the task lock transaction (source gone once its value lands in the parent); retention ordering (fine≪hourly≪daily) keeps targets/sources disjoint, with a guard that drops a colliding target so a pass can never update-then-delete the same row (only reachable if rollup was disabled past the hourly window). The **old delete-only hourly prune** in `ExpirationCleanup` (+ its `TryParseHourlySuffix`) is **removed**. **Readers (all history readers are tier-aware — daily is retained *and* read, not just stored):** `MetricTiers.TryClassifyKey` backs `DashboardStatsService.GetStatsHistory`/`GetCountersHistory`/`GetCounters` (tiered keys stay out of the counters *table*; fine buckets **down-bin to their hour**, grouped by base-key + hour), and each per-family chart parser — `AdapterCounterKeys`/`EndpointCounterKeys`/`ClientEventKeys.TryParseHistory` — accepts the marked tiers **and** legacy unmarked hourly and down-bins to the hour, so a rolled-to-daily window past the hourly retention still charts. Lifetime/`pct` reads untouched. **Config** on `WarpConfiguration`: `FineResolutionMinutes` (5; **must be >= 1**, validated fail-fast in `AddWarpServer` along with `fine < hourly < daily` ordering), `FineResolutionRetention`, `HourlyStatisticsRetention`, `DailyStatisticsRetention`; `StatisticRollupInterval` on `WarpServerConfiguration` (the rollup is the **only** pruner of time-bucketed rows now — `null` lets them accumulate). **No schema migration** — all tiers are new rows in the existing `Statistic`/`Counter` tables. This is the storage foundation SLO fast-burn reads its short window from. See `website/docs/features/metrics-retention.md`.

- **§8.32** **Dropped-record visibility.** The lossy recording pipelines (adapters §8.19, endpoints §8.21, client §8.27) drop records when their bounded channel is full and increment an always-on OTel meter (`warp.{adapter|endpoint|client}.records_dropped`) — reliable because the drop signal never rides the lossy channel it reports on, but only observable through an OTel backend. To make a saturated pipeline visible **in-box** (the whole point of the dashboard): each drop site also calls `DroppedRecordCounters.Track(DropPipeline, n)` (a single interlocked add — safe on the recording-failure path) into a process-global counter; a per-process `DroppedRecordReporter<TContext>` (`BackgroundService`, **not** a locked `IServerTask` — the counters are per-process, each process reports its own; 30s cadence, **no DB work when nothing dropped** so it's a good neighbour) drains them and folds each delta to the durable tiered stat `warpsys:records-dropped:{pipeline}` (`DroppedRecordKeys`, disjoint `warpsys` first-segment namespace §8.6/§8.19; classified/rolled by the generic `MetricTiers` reader §8.30). `DashboardStatsService` sums the last-24h buckets (windowed, so the tile self-clears) into `DashboardStatistics.{Adapter|Endpoint|Client}RecordsDropped`, surfaced as a red-when-nonzero **Dropped (24h)** tile on the dashboard. The reporter also raises a **throttled** (per-pipeline 5-min cooldown) `WarpEventType.RecordsDropped`=8 (`RecordsDroppedEvent`, Warning) post-commit through the notifier seam (§8.25), so a saturated pipeline is alertable in Slack/email **without OTel**. Enums from 1 (`DropPipeline {Adapter=1, Endpoint=2, Client=3}`).
- **§8.33** **Outcome metrics taxonomy (append-only `stats:`, reason-attributed breakdown).** Governing principle: **a metric records an event; current state is a query.** Every `stats:` key is now **append-only** — `JobCommandService.DecrementStatForState` and the decrement arm of `ApplyRequeueAccounting` are **removed, do not reintroduce them**: restating `succeeded`/`failed`/`deleted` on requeue caused four distinct defects — (1) the decrement wrote the *lifetime* key only, so a lifetime total silently disagreed with the sum of its own hourly buckets, (2) the dashboard's realtime rate chart deltas the total and clamped the resulting negative to 0 (`stores/dashboard.ts`), under-reporting the tick, (3) it destroyed the counter's only unique information — failed jobs never auto-expire (§8.2), so the `Job` query already answers "currently failed" and the counter's one added value is "ever failed", which is exactly what the decrement removed, and (4) nothing stores which reason produced a job's *previous* terminal state, so a restated total can never reconcile with an append-only breakdown. Consequence to state in release notes: `stats:succeeded`/`failed`/`deleted` mean **ever**, not *latest outcome was*, and grow for anyone who requeues; the live tiles and nav badges are unaffected because they query `Job`. **Three levels, and the umbrella is DERIVED not stored:** per-state totals (`stats:{succeeded|failed|deleted|requeued}`) + per-reason breakdown (`stats:{state}-{reason}`) + the not-Completed umbrella computed **on read** as `failed + deleted` (`counterModel.buildOutcomeRows`, the pure read-side model behind the Counters page). A stored `stats:unsuccessful` row was built and reverted: it was maintained at the 2 worker finalization sites while `failed`/`deleted` also move at 6 others (`DeleteJob`, `BulkDeleteJobs`, both crash-recovery arms, both worker cancellation paths), so it under-reported from the first delete and the page drew a child larger than its parent — **a pure function of two stored values must not be a third stored value**; `OutcomeMetricsTestsBase.AssertUmbrellaIsNotStored` pins it.
