# Project-Specific Patterns

> Rules only. Rationale, history, measurements and full rot-guard lists live in `.claude/references/design-notes/<section>-*.md` — read the note before changing a section's area.
> Observability features (§8.19–§8.24, §8.26–§8.32, §8.34) are in `observability.md`, which loads only when you touch those areas.

## Configuration

- **§8.1** `WarpConfiguration` via `IOptions<WarpConfiguration>`. All configurable values go through this pattern. The builder (`AddWarp<TContext>(opt => ...)`) inherits from `WarpConfiguration`, so config fields are set directly on `opt`.

## Job Lifecycle

- **§8.2** Failed jobs never auto-delete (`ExpireAt = null`). Only explicit user action (dashboard delete/requeue) or count-based cleanup (`MaxExpirableJobCount`, default null/disabled — deletes oldest by `ExpireAt` when threshold exceeded; failed jobs excluded).
- **§8.3** `ContinuationOptions` is generalized to all job kinds — any job with children can control child activation on parent failure.
- **§8.4** `RequeueJob` resets `ScheduleTime` to now. Requeued jobs always execute immediately.
- **§8.5** Cancellation uses `CancellationMode` enum (`None=0, Graceful=1`), not an immediate state change. `DeleteJob` sets `CancellationMode = Graceful`; the worker group's `RunningJobMonitor` (§6.14) reads it back from its keep-alive renewal, once per `CancellationCheckInterval`, and cancels the handler's `CancellationToken`. If the handler ignores the token and completes, state stays `Completed` (work happened) and `CancellationMode` is cleared. Dashboard shows "Cancelling..." badge while waiting.

## Addons (Mutex, Semaphore, Timeout, RateLimit, CircuitBreaker, DB Push)

- **§8.6** Concurrency control is opt-in via `opt.AddConcurrency()`. `[Mutex("k")]` (limit fixed at 1) and `[Semaphore("k", N)]` (limit > 1) share `ConcurrencyPipelineBehavior`. Two policies via `ConcurrencyMode`: `Skip` (`[Mutex]` default — surplus → `Deleted`) and `Wait` (`[Semaphore]` default — surplus requeued). **Disjoint namespaces by design, on both providers (`ConcurrencyLockName`):** effective limit 1 uses `warp:concurrency:k` (unchanged since 8.0, so a mutex stays exclusive through rolling upgrades); limit N uses semaphore name `warp:concurrency-semaphore:k` (PG slots `k:0..k:{N-1}`; moved in 8.1). Different prefixes so a mutex key can never name a slot (`[Mutex("tenantA:0")]` once took slot 0 of `[Semaphore("tenantA", N)]`, fixed 8.1). Slot names never collide across semaphore keys on either DB (guard: `SemaphoreSlotNameTestsBase`). Mixing both against the same key produces independent limits. Admin overrides via `IConcurrencyLimitManager` (precedence: `admin row > meta.Limit > 1`). Hide-on-404 dashboard nav.
- **§8.7** Timeout is opt-in via `opt.AddTimeout()`. `[Timeout(seconds: N)]` or `WithTimeout(TimeSpan)`. Two modes (`TimeoutMode`): `Delete` (default — pipeline sets `Deleted`, **not retried** by `AddRetry`) and `Fail` (throws `TimeoutException`, **caught** by `AddRetry`). Two scopes (`TimeoutScope`): `PerAttempt` (fresh budget per retry) and `Total` (`DeadlineUtc` stamped on publish). **Ordering: `AddRetry()` MUST come before `AddTimeout()`** (§2.12).

## Conventions

- **§8.11** **Enums always start at 1, never 0.** `Skip = 1, Wait = 2`, never `Skip = 0`. Avoids `default(T)` collisions and forces explicit assignment. Applies to `JobKind`, `State`, `CancellationMode`, `ConcurrencyMode`, `RateLimitMode`, `RateLimitStyle`, `TimeoutMode`, `TimeoutScope`, etc.
- **§8.12** **Metadata properties are addon-prefixed**, not bare names. `IRateLimitMetadata.RateLimitKey` (not `Key`), `IRateLimitMetadata.RateLimitWindowSeconds` (not `WindowSeconds`), `IConcurrencyMetadata.ConcurrencyKey` / `ConcurrencyLimit` / `ConcurrencyMode`. Prevents dict-key collisions when a single job carries multiple metadata interfaces. Avoid `Dictionary<,>` names entirely — they're a red flag for collision-prone APIs.
- **§8.13** Entity namespaces are **split**: `Job` lives in `Warp.Core.Entities`; `JobLog`, `Server`, `Worker`, `ServerTask`, `ServerLog`, `RecurringJob`, `RecurringJobLog`, `RateLimitBucket`, `RateLimitOverride`, `ConcurrencyLimit` etc. live in `Warp.Core.Data.Entities`. Same folder, different namespaces — do not collapse them.
- **§8.14** **Routed `IMessage` jobs must keep `HandlerType` on requeue** — it IS the routing decision. Every requeue-outcome site sets `ClearHandlerType = request is not IMessage` (Concurrency, RateLimit ×2, Retry); a new behaviour that requeues MUST follow it (guard: `MessagePolicyTests.WaitModeHandlerMutex_RoutedChildKeepsHandlerTypeAndCompletes`). Addons that commit inside handler scope must capture-save-fire and clear-tracker-on-conflict.
- **§8.15** Real-time log flushing: the worker group's `RunningJobMonitor` (§6.14; one loop per group, not one per job) drains every running job's `JobLogCollector` each `LogFlushInterval` (~1s) during handler execution and persists the logs in one save. Logs visible in the dashboard while the job is still processing.
- **§8.16** `MetadataConvert` was string-only until the DateTime branch added 2026-05-12 — non-primitive `IJobMetadata` properties need explicit roundtrip tests.

## Cross-Cutting (kept always-loaded; numbered with the observability set)

- **§8.25** **Operational notifications** (`IWarpNotifier`, `Warp.Core.Notifiers`, `opt.AddNotifier<T>()`): a pure host seam — Warp ships no channel integrations; zero registered = inert. Not webhooks (webhooks = domain events to subscribers). Fan-out through the singleton `WarpNotifierDispatcher` (registered by `AddWarp`; dispatch sites take it as a required ctor param). **Contract: post-commit, and a throwing notifier is caught + logged at Warning, never propagated.** Events are not persisted — delivery is best-effort; do not build guaranteed-delivery accounting on them. Events are redaction-safe snapshots (identity/metadata, never payloads, §1.2). `WarpEventType`/`WarpEventSeverity` from 1. Notifiers are singletons — inject `IServiceScopeFactory`. **Server-task rule (applies to every server task, not just notifiers):** `ExecuteAsync` runs inside the task host's lock transaction, so anything that must happen after commit (notifier dispatch, enqueue wakes, post-commit meters) is buffered in a field and fired from `IServerTask.OnCommittedAsync` with `CancellationToken.None` — **never dispatch from `ExecuteAsync`**. Ordinary (non-task) sites dispatch inline after their save. See `website/docs/features/operational-notifications.md`.
- **§8.33** **Outcome metrics: `stats:` keys are append-only.** A metric records an event; current state is a query. `DecrementStatForState` and the decrement arm of `ApplyRequeueAccounting` were removed — **do not reintroduce them**; `stats:succeeded`/`failed`/`deleted` mean *ever*. Levels: per-state totals (`stats:{succeeded|failed|deleted|requeued}`) + per-reason breakdown (`stats:{state}-{reason}`) written independently, and the not-Completed umbrella is **derived on read** (`counterModel.buildOutcomeRows`), never stored (`AssertUmbrellaIsNotStored`). `OutcomeReason` is a **closed enum** (from 1) on `JobOutcome`; `OutcomeReasonTokens.For` is a `switch` that returns `"unknown"` rather than throwing (it runs inside finalization's catch). `stats:retried-jobs` counts distinct jobs (first retry = incoming `RetriedTimes == 0`), no new column. Manual and crash-recovery requeues write the state total + reason key, one increment per `Requeued` log row; their meter emissions are post-commit (§8.25). `warp.job.requeued` meter carries no key tags (§1.2). `willRetry` tests `State.Enqueued or State.Scheduled`. Circuit breaker counts `Failed` (incl. `RetryExhausted`) but not reschedule/delete outcomes; `RetryExhausted` only when `maxRetries > 0`. **Worker lockstep:** `WarpWorkerService.FinalizeJobState` and `WarpDispatcherWorker`'s `CompletionBatch` each compose finalization separately — any change to outcome stats, counter-buffer increments (§8.26), error occurrences (§8.29) or policy stamps (§8.8) goes into BOTH. Guards: `StatSurfaceTestsBase`, `RetryStatusDispatcherIntegrationTestsBase`, `WorkerPathLockstepTests`.
