# Security & Data Integrity

- **§1.1** No secrets, connection strings, or credentials in source code. Use `appsettings.Development.json` (gitignored) or environment variables for local dev. The `Warp.TestApp` / `Warp.TestWorker` demo projects ship `appsettings.json` with non-secret defaults only.
- **§1.2** No PII or sensitive data in log output. Job payloads (`Job.Message`) may contain user data — never log payload contents at Info level or above. Keys for `[Mutex]`, `[Semaphore]`, `[RateLimit]` appear in `JobLog.Message` and the dashboard — keep tenant identifiers tokenised/hashed, not raw PII.
- **§1.3** All multi-step database mutations use explicit transactions (`BeginTransactionAsync`). Single-`SaveChanges` mutations rely on EF Core's implicit transaction. See `JobCommandService.DeleteJob` for the canonical pattern.
- **§1.4** Row-level locking via `IWarpSqlQueries.LockXAsync` methods. Provider implementations translate to `FOR NO KEY UPDATE` (Postgres) / `WITH (UPDLOCK, ROWLOCK)` (SQL Server). Examples: `LockJobByIdWaitAsync`, `LockAllServersAsync`, `LockLeaseByServiceNameAsync`, `LockDefinitionByServiceNameAsync`. When adding a row-locked fetch on a new table, add a corresponding `LockXByYAsync` method to both `PostgresWarpSqlQueries` and `SqlServerWarpSqlQueries`. The interceptor-based `TagWith(InterceptorConstants.RowLockTable*)` pattern was refactored away.
- **§1.5** Dashboard authorization defaults to **open access**. The dashboard is routed endpoints: `MapWarpUI` returns a `WarpUIEndpointConventionBuilder` spanning the SPA shell, the REST API group and the SignalR hub, so the host gates it with ASP.NET Core authorization — `RequireAuthorization(policy)` for a host identity system, `AddWarpDashboard().AddBuiltInLogin<TValidator>()` + `RequireWarpDashboardLogin()` for the built-in cookie login (a real `AddCookie` scheme, HTTP-only, `SameSite=Strict`, server-enforced expiry), or `RequireLocalRequests()` for loopback-only. Authorization is the right primitive over endpoint filters because filters do not run for hub endpoints. `IWarpAuthorizationFilter` / `LocalRequestsOnlyAuthorizationFilter` / `UnauthorizedRedirectUrl` were **removed in 4.0** — a bool filter could not separate challenge (anonymous) from forbid (unpermitted), so both rendered as a bare 401 and the redirect option bounced unpermitted users to sign-in forever. **Everything under the route prefix is an endpoint**, including the SPA's embedded assets and extension JS: `WarpSpaEndpoints` serves them from the `EmbeddedFileProvider` itself rather than `UseStaticFiles`, because `StaticFileMiddleware` stands down once routing matched an endpoint and the shell catch-all matches every asset path — leaving them on middleware 404s every asset and renders the dashboard blank (regression-tested by `StaticAssets_AreServed`). Gating is therefore uniform, and **Warp owns every path under the prefix** (host middleware content under it is unreachable — a documented 4.0 break). **Registering `AddBuiltInLogin<T>()` gates the dashboard on its own** (`MapWarpUI` applies the login policy when the marker is present, through an `IEndpointConventionBuilder.Finally` convention so it can see the host's own conventions and **step aside** rather than stack — a host policy REPLACES the login gate and flips the SPA's `hasBuiltInLogin` off via `WarpDashboardGate`, read per request; `RequireWarpDashboardLogin()` is explicit-but-optional and idempotent) — the half-configured shape must never leave the API anonymous behind a rendered login page. `{prefix}/api/auth/status` is mapped **only** with the built-in login (it is necessarily `AllowAnonymous`, so mapping it always would bypass the host's gate and report a constant `true`); unmatched `{prefix}/api/**` paths are claimed by an in-group catch-all so they inherit the group's authorization (an anonymous 404 beside a 401 is an addon-enumeration oracle); `RoutePrefix` is normalized (`'/' + trim('/')`, root rejected); and every API response carries `X-Warp-Api` so the SPA can tell a real API answer from a followed sign-in redirect.
- **§1.6** Provider packages (`Warp.Provider.PostgreSql`, `Warp.Provider.SqlServer`) are the *only* places allowed to use provider-native SQL APIs (`NpgsqlConnection.WaitAsync`, `SqlConnection` Service Broker, `FromSqlRaw` for row-locks). `Warp.Core` must stay provider-agnostic.
