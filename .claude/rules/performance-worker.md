# Performance — worker internals (§6.9–§6.26)

> Loaded only when touching the paths above. Rules only — rationale, history, measurements and full rot-guard lists live in `.claude/references/design-notes/<section>-*.md`; **read the note before changing a section's area**.

## Claiming jobs

- **§6.9** **The claim's queue predicate is a SCALAR equality, and the worker issues ONE statement per queue** (`ClaimEnqueuedJobsAsync`, both providers). `queue = ANY(@queues)` / `IN (...)` collapses to a full sort over the wrong index when statistics go stale (720x, reachable in ordinary workloads; the old form is bimodal, so compare distributions, not medians). **Do NOT re-collapse the loop into one multi-value statement.** Deliberate consequences to preserve: cross-queue starvation is reproduced, not fixed (budget spent queue by queue); queue order is `StringComparer.Ordinal`; each statement is its own implicit transaction. **Rows a claim RETURNS are sorted by `ScheduleTime` in memory** (`ClaimFromQueueAsync`, skipped for one row). Guard: `ConcurrentClaimTests.ClaimEnqueuedJobs_BatchClaim_ReturnsTheOldestJobsOldestFirst`.
- **§6.15** **The job table's claim, scheduled, parent and expiry indexes are partial** (`WarpPartialIndexes`, end of `ApplyWarpModel`): claim `(Kind, CurrentState, Queue, ScheduleTime)` only `Enqueued`; `(CurrentState, ScheduleTime)` only `Scheduled`; `(ParentJobId, CurrentState)` only rows with a parent; `(ExpireAt)` only rows with an expiry. The dashboard listing index `(Kind, CurrentState, CreateTime)` stays whole. **Readers must keep stating the predicate the index needs**: compare `CurrentState` to a LITERAL (a parameter stops SQL Server using a filtered index), parent/expiry lookups with `=`/`<`. Filters are SQL with double-quoted column names (§5.1 exception). Hosts recreate the indexes without a lock via `migrationBuilder.RecreateWarpJobIndexesOnline(TargetModel)`. Guards: `JobPartialIndexTests`, `OnlineJobIndexStatementsTests`, `OnlineJobIndexMigrationTestsBase`.
- **§6.16** **A dispatcher's claim starts at a watermark while its claims come back full** (`ClaimWatermark`, one per `WarpDispatcher`; single-worker passes `null`): after a FULL claim the next adds `ScheduleTime >= <newest taken>`; a SHORT claim, or any claim once `HeadClaimInterval` (1 s) has passed, reads from the head (catches rows that became claimable behind the watermark). No margin before the watermark. Guard: `ConcurrentClaimTests.ClaimEnqueuedJobs_WithAWatermark_SkipsTheEmptiedHeadAndStillReachesAnOlderJob`.
- **§6.19** **A dispatcher whose group is full waits for a worker to free a slot; it does not poll** (`DispatcherWorkerAvailability.WaitForFreeSlotAsync`, 1 s backstop). Before sizing a claim it **settles** (yields while free capacity keeps growing, at most 8 yields). The claim is still capped at the free capacity. Guard: `DispatcherWorkerAvailabilityTests.WaitForFreeSlotAsync_*`.
- **§6.20** **The dispatcher claims on a no-tracking context** (`WarpDispatcher.FetchAndDistribute`); nothing writes claimed jobs back through EF. Single-worker mode still tracks (it finalizes through EF). Dispatcher tests that mock the claim use `InMemoryServerContext`. Guard: `ConcurrentClaimTests.ClaimEnqueuedJobs_OnANoTrackingContext_ReturnsTheClaimedRowsUntracked`.
- **§6.21** **PostgreSQL job claims turn `enable_sort` off for their own command** (`PostgresWarpSqlQueries.ClaimPlanGuard`: a `DO` block calling `set_config('enable_sort', 'off', true)`, prepended to both claim forms). **Not `SET LOCAL`** (it warns outside a transaction block, one server-log line per claim) and it must not return a result set before the claim's own. Changes the plan, never the result. Guards: `ClaimPlanStabilityTests` (`..._BurstIntoAQueueTheStatisticsSayIsEmpty_UsesTheClaimIndexWithoutSorting`, `..._EmptyQueue_RaisesNoServerNotice`, `SetLocalInAMultiStatementCommand_LastsForThatCommandOnly`).

## Running and finalizing jobs

- **§6.10** **Finalization writes ONLY the nine columns it assigns**: `CurrentState`, `CancellationMode`, `CurrentWorkerId`, `LastKeepAlive`, `ExpireAt`, `HandlerType`, `ScheduleTime`, `Metadata`, `RunId` (cleared). In dispatcher mode the list lives in the two provider completion statements (§6.13) and moves in lockstep with `WarpDispatcherWorker.BuildFinalization`. **A new field assigned at finalization and not added to BOTH statements is silently never persisted.** Single-worker mode diffs a tracked entity, so a column another writer changed on the row (`CancellationMode`) must be marked modified explicitly (`ClearCancellationMode`). Guard: `WorkerPathLockstepTests` (every mapped column, both modes).
- **§6.12** **Nothing is written for a job between its claim and its handler.** The "Processing" `JobLog` is deferred (`DeferredJobLog`): the job monitor's first flush writes it, otherwise it rides the finalizing write — written once. The dispatcher's ownership check is skipped for a fresh claim (`ConfirmOwnership`: received within `InvisibilityTimeout / 2 - CancellationCheckInterval`); an older one gets the guarded `RenewClaim`. Accepted: a short job's "Processing" row appears at completion; in dispatcher mode several running jobs can share one `CurrentWorkerId` — **never key a dictionary on it**. Do not move either write back in front of the handler. Guards: `WorkerExecutionIntegrationTests.GivenLongRunningHandler_*` / `GivenShortHandler_*`, `DispatcherPrefetchTests`, `ServerQueryTests.GetServers_SeveralRunningJobsUnderOneId_StillLoads`.
- **§6.13** **Dispatcher completions are flushed per worker GROUP, in one set-based statement** (`IWarpSqlQueries.CompleteJobsAsync`; one `CompletionBatch` + one `CompletionFlusher` per group, built by `WarpDispatcherHost`).
  - **Triggers:** buffer full (`CompletionBatchSize`), oldest entry waited `CompletionFlushInterval`, or the group has nothing left claimed — decided from the count `DispatcherWorkerAvailability.Release()` returns (`SlotReleased(remaining)`), never a live read of `Outstanding`. Do not put back a flush on "this worker is idle". **A timer flushes only the buffer it was started for** (generation; `Holds(generation)`), not by `IsTimeElapsed`.
  - **Workers never write the flush**; they add and return to their channel. The flusher's final flush has its own budget (`FinalFlushBudgetSeconds`, 5 s), not the host's shutdown token. At most `4 × CompletionBatchSize` jobs per statement.
  - **Backpressure (#348):** at `BackpressureThreshold` (4 × batch size, never below `MinBackpressureThreshold` = 200) `AddAsync` makes the adding worker wait for the write in flight; the wait ends on the worker's stopping token.
  - **Every completion is guarded by its run** (`JobRunOwner`): still `Processing` AND (stamped by the run's worker OR exactly as the claim left it) AND `RunId` equal (null-safe). Every claim stamps a fresh `Job.RunId`; **every exit from `Processing` must clear `RunId`**. Keep the worker/keep-alive pair (rolling deploys). A skipped completion counts nothing and writes no logs.
  - **`RunId` is an EF concurrency token on `WarpServerContext` only — never on the application's `TContext` model.** A single-worker conflict discards the attempt (`CommitFinalizationAsync`), it is not re-finalized as a handler failure.
  - **SQL Server: `INNER LOOP JOIN` with the JSON rows outermost and `ROWLOCK` are load-bearing**, in the update AND the log-row insert (`FROM OPENJSON(@logs) ... INNER LOOP JOIN @done`, not `IN (SELECT ...)`).
  - `SaveChanges` inside the worker's finalizing transactions runs with `AutoSavepointsEnabled = false`. A transient `DbException` gets the deadlock retry then the split.
  - Guards: `CompletionBatchTests`, `BatchedCompletionIntegrationTests`, `JobRunOwnershipTests`, `RunIdConcurrencyTokenTests`, `CompletionPlanStabilityTests`, `FailedFinalizationCounterTestsBase`, `WorkerPathLockstepTests`.
- **§6.14** **A worker group watches all its running jobs in one loop** (`RunningJobMonitor`, one per group). Each tick drains every job's handler logs, progress rows and deferred "Processing" row into one save; every `CancellationCheckInterval` ONE statement (`IWarpSqlQueries.RenewRunningJobsAsync`) renews `LastKeepAlive`, touches only rows still `Processing` and still that run's (§6.13 predicate), and returns the jobs to cancel. Cancellations are started, not awaited. The statement runs through `SqlQueryRaw` (rows aliased `beat`) so EF interceptors see it. **Anything that renews or flushes for a job goes through the monitor — never a per-job loop again.** Guards: `WorkerExecutionIntegrationTests.GivenTwoLongRunningHandlersInOneGroup_*`, `GivenOneKeepAliveRenewalFails_*`, `JobRunOwnershipTests`.
- **§6.17** **The worker never resolves or saves the application's DbContext** (8.0, both modes). A handler saves its own work; a job staged without saving is discarded with its scope. Do not reintroduce a worker-side resolve or save of `TContext`, not even to check for unsaved changes. The addon pipeline stores (concurrency resolver, rate-limit store/resolver, circuit-breaker store) use `DeferredWarpContext` (server context, opened on first use), never `TContext`; admin managers run on the Warp context (§2.14). Sagas: the proxy saves for the saga handler (§8.17). Guards: `PolicyBehaviorContextTests`, `WorkerExecutionIntegrationTests.GivenAHandlerThatStagesAJobWithoutSaving_*`.

## Orchestrator

- **§6.11** **The Orchestrator's query shapes are load-bearing** (§6.9's lesson again; PostgreSQL only — SQL Server never had the problem).
  - `FinalizeParentsAsync` finds ready parents with **one branch per kind** (`Kind = Message` UNION ALL `Kind = Batch`), each `ORDER BY CurrentState, CreateTime` + `Take`. A scalar `Kind` alone is not enough; it needs the `ORDER BY` only `(Kind, CurrentState, CreateTime)` can supply.
  - "Which awaiting rows can move?" is **three steps** (`AwaitedParentIdsQuery` → `AwaitedParentStatesQuery` → `AwaitingChildrenOfQuery`), each DISTINCT parent read once — never one `WHERE EXISTS(parent ...)` statement.
  - Past 1,000 awaited parents (`ServerTaskSignals.ManyAwaitedParents`) a pass asks only about jobs a wake named (`AwaitedParentIdsAmongQuery`) and reads the whole set only on a sweep, 5,000 parents at a time (`NextSweepSlice`).
  - **A wake names the parents to check** (`SignalJobFinalized(Guid?)` / `SignalJobsFinalized`; push payload `parents[;settled]` after `F:`, `FinalizedParentsPayload`); the worker passes the claimed row's `ParentJobId` (no query, §0.2). Hinted passes find children by parent id alone (`ChildStatesOfQuery`), decide readiness in memory (`ParentsWithSettledChildren`) and load the ready parents by primary key (`ParentsByIdQuery`) — never kind/state predicates on the children in SQL (the planner found them through `(kind, state, create_time)`: 325 to 25,208 pages per call on identical code); the full `ReadyParentsQuery` runs only on a **sweep** (first pass, every scheduled run via the internal `IScheduledRunAware.BeginRun`, after the no-argument `SignalJobFinalized()`, on hint overflow).
  - **Every site that puts a child into a terminal state names its parent** (`DeleteJob`/`BulkDeleteJobs`, `StaleJobRecovery` from `OnCommittedAsync`); a new one must too. **Do not remove the sweep, and do not make a wake-only signal request one.** A pass that throws or is rolled back returns its work (`ReturnFinalizedParents`).
  - Guards: `OrchestratorReadyParentsPlanTests`, `FinalizedParentHintsTests`, `OrchestrationTaskTests`, `MessageIntegrationTests.GivenNoParentSweepDue_*`.

## Server tasks

- **§6.18** **A signal-woken server task runs at most once per `ServerTaskSignalInterval`** (default 500 ms; `ClusterTaskTimings.HoldAfterRun`, cluster-wide, §6.23). The hold is measured from the START of the run, never longer than the task's own interval, applies only to tasks with signals, and is skipped after work on a `RerunImmediately` task; a wake arriving meanwhile stays pending, none is lost. `WarpTestServer` sets it to zero. Guards: `ClusterTaskSchedulerTests.PassAsync_SignalsElsewhereWhileASignaledRunHolds_FoldIntoOneRerun`, `PassAsync_RunOnSchedule_DoesNotHold`.
- **§6.22** **On PostgreSQL the server context opens on Warp's own pool, without the connection reset** (`BuildServerConnectionString`: `Application Name` suffixed `:warp-server`, `No Reset On Close`, `MinPoolSize` 0). **Do not add session state to server-context connections without restoring the reset.** Raises peak connections; not applied to a host's own `NpgsqlDataSource`. Guard: `ServerConnectionPoolTests`.
- **§6.23** **Server tasks: one lease scheduler for cluster-wide tasks, one plain loop for the heartbeat.** Spec: `docs/specs/2026-11-23-cluster-server-tasks.md`. What must stay true:
  - **Who runs a task is decided by a lease row** (`ClusterTask`), claimed for every due task in ONE statement by one `ClusterTaskScheduler` per server (`ClaimClusterTasksAsync`, `SKIP LOCKED` / `READPAST`). Do not reintroduce a per-task loop or a per-server lock attempt.
  - **The heartbeat is not a cluster task**: no `LockKey` → `PerServerTaskLoop`, writes nothing on success. The `ServerTask` table stays in the schema, unused.
  - **One way to execute a task: `ServerTaskRunner`** (transaction, `OnCommittedAsync` after commit, no hook on a throw; in-memory work taken for a pass is given back when the scope is disposed without the hook).
  - **Every time is the database's own**; a server's clock only decides how long it sleeps.
  - **An idle run writes nothing, except on a task with signals** (`Orchestrator`, `MessageRouter`), which writes its completion after every run to free the lease — only while another server is alive (`ClusterTaskClaims.OtherServersAlive`). Do not remove that release, and do not add it to tasks without signals.
  - **Due times sit on a grid**; a renewal only ever extends a lease. The claim is sent only when a task is due (`Entry.DueAt`).
  - **A long run renews its lease every third of its interval; a renewal that finds another holder cancels the run.** A failed renewal is retried at the next one (catch inside the loop).
  - **Signals** claim the task at once (`RequestClusterTaskRunAsync`) or set `RunRequestedAt` for the holder's completion; a signal arriving while a run finishes, or whose request failed, is put back, never lost.
  - **No startup delay.**
  - **At most `ClusterTaskTimings.TimerTaskConcurrency` (2) timer-only tasks run at once per server; signal-driven ones (Orchestrator, MessageRouter) never wait.** Each run takes its own connection and the grid makes the tasks fall due together, so starting everything a claim won at once held about 14 connections on an idle server, kept for good by the pool. The slot is taken after the lease renewal starts and released before the signal hold; the wait is not part of the recorded duration. Do not lift the cap to "run them all". Guards: `ClusterTaskSchedulerTests.PassAsync_MoreTimerTasksDueThanSlots_RunsTwoAtATime` (fails without the cap), `PassAsync_TimerSlotsFull_SignalDrivenTaskStillRuns`.
  - **Rolling deploys:** while a server without `Server.CoordinationVersion` is alive, each run also takes the old lock (`LegacyTaskLock`, the only call site; remove in the release after 8.x). Assumed alive until the first claim says otherwise.
  - **Registration is one insert-if-absent statement** (`RegisterClusterTasksAsync`), not an EF insert caught on `DbUpdateException`.
  - **Both providers implement the five statements** (`PostgresClusterTaskSql`, `SqlServerClusterTaskSql`); a change to one goes into both. They read result rows by position, not `SqlQueryRaw`.
  - Guards (both DBs): `ClusterTaskQueriesTests`, `ClusterTaskSchedulerTests`, `ServerTaskRunnerTests`, `PerServerTaskLoopTests`, `ClusterTaskDashboardTests`.

## Perf CI

- **§6.24** **Report-only perf-CI gates (TODO, until calibrated by three no-op runs)** in `PerfCompare.RenderScenario`: (1) every SQL Server per-job row, (2) the `TwoServersUnderLoad`, `RecurringJobs` and `BackgroundLoad` scenarios (`[CiScenario(Calibrated = false)]`), (3) DB ms/job on both providers. After calibration switch each back on and update "How to read this" in `.github/workflows/perf.yml`. Validity checks (a missing measurement; a two-server case where one server completed under 20% of the jobs) are NOT report-only.
- **§6.25** **The Performance workflow runs only when someone starts it** (`workflow_dispatch`: Actions > Performance > Run workflow, or `gh workflow run perf.yml --ref <branch> [-f base_ref=7.7.0]`), plus a published release. Not on pull requests, no nightly run. **Do not put it back on `pull_request`** without first making a red check mean a confirmed regression. Run it before a release and after a change to the worker, the claim, the completion or the server tasks; read the count columns (statements, commands, transactions, WAL per job) — timings on shared runners are for the ratio within one run only. The bench PostgreSQL runs with `full_page_writes=off` (`WAL FPI/job` should read 0). **`-f repeats=N` (1 to 5)** measures every case N times in one run and adds a medians table (`medians-bdn`, `PerfCompare.Medians`) that marks a case whose repeats were apart: 1 to check a change, 3 or more for numbers that will be published or for any timing.

## Failure path

- **§6.26** **A failed job's stored stack trace ends where Warp called the handler** (`HandlerStackTrace.Trim`, applied in `FinalizationLogs.Build` and `ErrorOccurrenceFactory.FromException`). The frames from `GeneratedJobDispatcher` down (the generated call, every pipeline behaviour, the worker's `ExecuteJob`) are dropped per exception; untrimmed, 8.0 stored 1,302 characters where 7.7 stored 529 and retries wrote 6% more WAL per job than 7.7. **Do not store `error.ToString()` for a job failure anywhere else without the trim.** Guard: `HandlerStackTraceTests`.
