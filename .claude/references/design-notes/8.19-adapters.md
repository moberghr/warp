# §8.19 — design notes (adapters)

> Full rationale, history, measurements and rot guards behind the condensed rule §8.19 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `project-specific.md` (2026-11-24).

**§8.19** **Outbound adapters** are Warp's answer to observing calls the app *makes to* other services (contrast `Warp.Http` §8.10, which exposes Warp handlers *as* inbound endpoints — the naming `Warp.Adapters.Http` vs `Warp.Http` is inbound-vs-outbound and docs state it explicitly). Protocol-agnostic core in `Warp.Core.Adapters`; HTTP binding in `Warp.Adapters.Http`; Refit sugar in `Warp.Adapters.Refit` (only that package references Refit).

**Three-axis identity — memorize the litmus test:** **adapter = policy + health boundary** (registration-time; retry/timeout/rate-limit config + SLO), **group = runtime who/where** (destination, tenant, shop, region — a *runtime value*, always explicit, never heuristic-derived, unbounded), **operation = what** (the API-contract axis — `GetOrders`, `payment.completed`; bounded, may be heuristic-derived). Litmus: if swapping the value changes the request's *structure* (route/verb/payload) → operation; if it only changes *where it goes or on whose behalf* → group. Diagnosis follows the axes: an operation red across all groups = caller-side bug (malformed payload, schema drift); a group red across all operations = counterparty problem (dead token, downed receiver); everything red = the adapter/vendor itself. Enums from 1 (§8.11): `CallRecording { All = 1, FailuresOnly = 2 }`, `CaptureMode { None = 1, OnFailure = 2, Always = 3 }`, `AdapterCallOutcome { Success = 1, Failed = 2, Throttled = 3, CircuitOpen = 4 }` (`CircuitOpen` reserved for the breaker fast-follow), `AdapterRateLimitOverflow { Wait = 1, FailFast = 2, Respond429 = 3 }`.

**Capture is opt-in and PII-owned (§1.2):** metadata always; request bodies, response bodies, and headers each independently `None`/`OnFailure`/`Always`, truncated (`MaxCapturedBodySize` 8 KB / `MaxCapturedHeaderSize` 4 KB) and passed through the user-owned `RedactedHeaders` denylist (case-insensitive, prepopulated with `Authorization`/`Proxy-Authorization`/`Cookie`/`Set-Cookie`/`X-Api-Key`; `Add`/`Remove`/`Clear` fully overridable — mandatory `Authorization` redaction was rejected, the denylist is a default not a lock). `RecordCalls = All` (default) writes a row per call — the volume knob for hot adapters is per-adapter `FailuresOnly`; capture modes control payload richness only, orthogonal to whether a row exists.

**Cardinality guards:** `MaxDistinctOperations` (default 50) collapses *heuristic-derived* operation names beyond the cap to a literal `{other}` with a one-time warning (explicit names never collapse); `MaxDistinctGroups` (default 500) does the same for group values. `IncludeGroupInMetrics` (default false) keeps group off meter tags unless opted in (bounded group sets); group is always a span attribute + counter key regardless.

**Shared rate limit = coordinated config:** `adapter name = cluster-wide identity` (same name ⇒ stats merge and limits share by design; genuinely different dependencies get different names). Shared-policy persistence is **first-writer-wins**: the first registration persists the policy onto `AdapterDefinition`, and later mismatching processes **enforce the persisted policy**, log a Warning, increment `warp.adapter.config_conflicts`, and set `HasPolicyConflict` (dashboard badge) — deterministic mid-rolling-deploy, and deploys alone never change the persisted limit (conflict is preserved, not overwritten, per SC13). Runtime precedence `RateLimitOverride` admin row > persisted definition > local code; **change a shared limit via a `RateLimitOverride` admin row (which takes precedence) or by clearing the persisted policy**, not by redeploying a new code value.

**Refit wraps pipeline exceptions (#284):** Refit hands the caller `ApiRequestException` for EVERY exception escaping the `HttpClient` pipeline (and an `ApiResponse<T>` method never throws at all), so `catch (AdapterRateLimitedException)` silently never fires on the Refit binding and `RefitSettings`' response-driven exception factory cannot undo it. Three additive answers, all shipped: `Respond429` waits like `Wait` then answers with a **synthetic 429** (`WarpThrottledResponse`, `Retry-After` + `x-warp-retry-after-ms`) instead of throwing — **recognised by TYPE, not status, in `WarpAdapterHandler.CompleteOutcome` so it records `Throttled` while a REAL vendor 429 keeps recording `Failed`** (a bare status check would both mis-record Warp's own refusal and silently move every existing 429's classification), and **synthesised in the OUTERMOST `WarpAdapterHandler`, never in the rate-limit handler that raised it** — a 429 born innermost is an ordinary retryable status to the user's resilience handler nesting between them (`AddStandardResilienceHandler` treats 429 as transient for BOTH retry and breaker), which would retry Warp's own self-throttle straight back into the limiter and open the breaker on calls the limiter would have admitted; thrown, it passes user handlers untouched (not an `HttpRequestException`), so `Respond429` is byte-for-byte `Wait` inside the pipeline and differs only at the caller; `AdapterRateLimitedException.RetryAfter` carries the window remainder the limiter already computed and used to discard; and `AdapterRateLimitExtensions.IsAdapterRateLimited/GetAdapterRetryAfter/FindAdapterRateLimited` walk `InnerException` + every `AggregateException` branch for callers staying on the throwing modes. The limiter itself is unchanged for the new mode — only `FailFast` short-circuits, so `Respond429` waits and throws like `Wait`, and the HTTP binding converts.

**Adoption + rollout guidance:** adapters need only `AddWarp<TContext>` (no server/worker) — they run in any process, alongside other job systems; recording persists via the flusher on the user's `TContext`.

**Observe-first is the recommended rollout:** register with no retry handler and no `UseSharedRateLimit` (the passive observing handler alone, zero behavioral change — same timeouts, single attempt, same exceptions), read the data, then add policy per adapter once it justifies the split. Telemetry: `warp.adapter.calls`, `warp.adapter.duration`, `warp.adapter.records_dropped`, `warp.adapter.config_conflicts`. See §2.15, `website/docs/features/adapters.md`.
