# §2.8 — design notes (scheduled activation)

> Full rationale, history, measurements and rot guards behind the condensed rule §2.8 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `architecture.md` (2026-11-25).

**§2.8** Future-dated jobs land in `State.Scheduled`. `ScheduledJobActivation` flips them to `Enqueued` when `ScheduleTime <= now`. Cadence is `WarpServerConfiguration.ScheduledActivationInterval` (default 10s) — this is the worst-case latency between `ScheduleTime` and pickup eligibility. The task is time-driven and does **not** participate in DB-push wake-up; push only accelerates what happens *after* activation. It does **emit** one, though — an activated row is an enqueue site, and since the flip is a Modified row `NotificationDispatch.CapturePending` cannot see it, so the task builds the `Notification` itself and dispatches it from `OnCommittedAsync` (§6.3/§8.25). Worker fetch queries always filter by `CurrentState == Enqueued` with a defensive `ScheduleTime <= now` predicate for pre-upgrade legacy rows. Adding new query sites that filter on `Enqueued` without the time predicate is a latent bug on upgraded deployments.
