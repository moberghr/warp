# §2.17 — design notes (lock release never throws)

> Full rationale, history, measurements and rot guards behind the condensed rule §2.17 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `architecture.md` (2026-11-25).

**§2.17** **Releasing a lock never throws.** Every DB-backed provider (`PostgresLockProvider`, `SqlServerLockProvider`, `PostgresSemaphoreProvider`, `SqlServerSemaphoreProvider`) wraps its handle in **`SafeReleaseLockHandle`** (`Warp.Core.Locking`, public because the provider packages compose against Core's public API only, §0.5/§2.11), which catches on `DisposeAsync` and logs at Warning with the lock name. The contract is set **at the provider**, not at the five call sites, so a new lock consumer cannot miss it. Why: release runs in a `finally` / `await using` AFTER the guarded work committed, so a throw cannot un-commit anything — it can only fail a completed operation (`AddOrUpdateRecurringJob` taking down host startup) or **replace** the guarded body's real exception, which is exactly what `SagaHandlerProxy` and the old per-task loop's `finally` did (a handler failure surfaced as a lock error). Swallowing does not change the lock's fate: throwing releases nothing either, and a lock stranded on a pooled backend cannot be reclaimed by anyone. On `PostgresSemaphoreProvider` the wrap sits **outside** `SlotHandle` so a throwing release still frees the in-process slot via `SlotHandle`'s own `finally` first. Do NOT re-add a rethrow to "surface the problem" — the Warning is the surface, and `SafeReleaseLockHandleTests` (including the exception-masking case) is the rot guard. Operator-facing detail lives in `website/docs/operations/connection-pooling.md`.
