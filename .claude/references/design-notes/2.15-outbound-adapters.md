# §2.15 — design notes (outbound adapters)

> Full rationale, history, measurements and rot guards behind the condensed rule §2.15 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `architecture.md` (2026-11-25).

**§2.15** **Outbound** service-call observability is the mirror of the **inbound** `Warp.Http` binding: `Warp.Http` exposes Warp handlers *as* HTTP endpoints; `Warp.Adapters.Http` observes calls Warp *makes to* other services. The protocol-agnostic core lives in `Warp.Core.Adapters`: `IWarpAdapters.BeginCall(adapter, operation, group?)` returns an `AdapterCallScope` (`Succeed`/`Fail`/`SetGroup`/`SetCorrelation`/`SetTag`) usable for any transport (SOAP proxies, vendor SDKs) via manual scopes. **Telemetry is unconditional** (null-listener pattern, zero cost without a listener): every completed scope emits a `Client`-kind Activity named `{adapter}.{operation}` plus `warp.adapter.calls`/`warp.adapter.duration` meters regardless of `AddAdapters()`. **Only DB recording is gated by `opt.AddAdapters()`** — it registers the bounded-channel `DbAdapterCallRecorder` and the `AdapterCallFlusher` `IHostedService` (drains batches on an `IServiceScopeFactory`-created `TContext` scope, §0.5). Recording is **lossy-by-design**: a full channel drops the record + increments `warp.adapter.records_dropped` — user calls are never blocked or failed (call logs are diagnostics, not an audit trail — same stance as `JobLog`). The two entities (`AdapterDefinition`, `AdapterCallLog`, both in `Warp.Core.Data.Entities` §8.13) are added **unconditionally** by `WarpModelCustomizer` (§2.11) and mirrored by `WarpServerContext` (§2.14), so the schema is stable whichever hosts opt in. `AddAdapters()` uses the non-generic `IWarpBuilder` receiver (mirrors `AddBackgroundService<T>` §2.13). Adapter stats write `Counter` rows collapsed by `CounterAggregator` (never direct `Statistic` writes, §6.2); `ExpirationCleanup` (a server task) gains two bounded deletes (expired `AdapterCallLog` rows, orphaned `AdapterDefinition` rows past `AdapterDefinitionOrphanGrace`) — the worker hot path is untouched (§0.2/§6.1). `IAdapterQueryService` is registered by `AddWarp` itself (like `IBackgroundServiceQueryService`), so **dashboard-only / publisher-only / `AddWarp`-only** processes resolve it and serve `/api/adapters*` without running a server or calling `AddAdapters()`. The **cluster-shared rate limiter** reuses the `RateLimitBucket` entity (key `warp:adapter:{name}`, disjoint namespace §8.6) with DB-backed token leasing — a differentiator a per-process limiter cannot provide; the one row-lock need goes through `IWarpSqlQueries` (§1.4), no raw SQL in Core (§5.1). Shared-policy persistence is **first-writer-wins**: the first registration writes the policy onto `AdapterDefinition`; a later process whose local policy differs **enforces the persisted policy**, logs a Warning, increments `warp.adapter.config_conflicts`, and sets `HasPolicyConflict` (dashboard badge) — deploys alone never rewrite it. Runtime precedence `RateLimitOverride` admin row > persisted definition > local code; **change a shared limit via a `RateLimitOverride` admin row (which takes precedence) or by clearing the persisted policy**, not by redeploying. Two thin binding packages compose against Core's public API only (no `InternalsVisibleTo`, §0.5): `Warp.Adapters.Http` (a `DelegatingHandler` that auto-scopes `IHttpClientFactory` clients; **no retry dependency** — `UseResilience` and the `Microsoft.Extensions.Http.Resilience` package reference were removed in 4.1, resilience is a user handler added via `ConfigureHttpClientBuilder`, which lands in the same slot in the fixed chain) and `Warp.Adapters.Refit` (operation names from `RestMethodInfo`; the only package referencing Refit). See `website/docs/features/adapters.md`.
