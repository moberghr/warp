# §6.2.1 — design notes (bounded aggregation drains)

> Full rationale, history, measurements and rot guards behind the condensed rule §6.2.1 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `performance.md` (2026-11-25).

**§6.2.1** `CounterAggregator`, `ErrorGroupAggregator` and `StatisticRollup` drain a BOUNDED slice per tick (`MaxBatchesPerTick` = 20 batches on the first two, `MaxRollupRowsPerTick` = 20,000 source rows on the rollup, shared across BOTH of its passes) and set `RerunImmediately`. **Never remove the cap to "drain faster."** `IServerTask.LocksWithTransaction` defaults true, so the task host wraps the whole of `ExecuteAsync` in ONE transaction and the per-batch `SaveChanges` only flush — an unbounded drain holds a single transaction open until the table empties (measured: 51 minutes against a 500k-job backlog). That pins the vacuum horizon, so autovacuum cannot reclaim any tuple newer than its snapshot; the job table measured 43% dead tuples (`CurrentState` is in the worker's fetch index, so every transition orphans index entries and no update is HOT), the claim scan degraded from 3.3ms to 253ms, and throughput fell from 567 to 27 jobs/sec WHILE the queue was still draining — the aggregator running longer made the bloat worse, which made it slower. **On `StatisticRollup` the WRITE is what costs, not the scan** — 43 ms to read a 500,000-row `Statistic` table against 3,472 ms / 317,259 buffers for a 300,000-key `ExecuteDeleteAsync`, where the capped 20,000-key delete is 462 ms / 34,727 (PostgreSQL 18, re-measured for 7.1.0) — and its worst tick is the FIRST after an upgrade, when every legacy unmarked hourly key rolls to daily at once, or any tick after the rollup has been disabled past the hourly window. Capping it is safe only because the passes DEFER rather than drop: a fine row held back by the cap whose hourly parent pass 2 then rolls away re-creates that hourly key next tick with its own value and rolls on the tick after, so the summed value is preserved across ticks (`StatisticRollupTestsBase` asserts exactly that, and was confirmed to fail against the uncapped version). `RerunImmediately` is safe to pair with a cap because the scheduler re-runs only when `ExecuteAsync` returned a message and these tasks return null when they rolled nothing — an idle tick does not spin.
