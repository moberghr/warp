# §8.20 — design notes (webhooks)

> Full rationale, history, measurements and rot guards behind the condensed rule §8.20 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `project-specific.md` (2026-11-24).

**§8.20** **Outbound webhooks** are **part of Core** (`Warp.Core.Webhooks`) and **always-on — there is no `AddWebhooks` gate on whether delivery runs**. `AddWarp` unconditionally wires the dispatcher, executor handler, redelivery enqueuer, and built-in signer; an executor job is an ordinary job on an ordinary queue (`DefaultQueue` by default, see *Webhook queue* below), so **any server whose workers drain that queue runs deliveries staged by any process — no per-process opt-in to forget** (the old two-process footgun is gone). Nothing runs until a caller invokes `IWebhookDispatcher.SendAsync`. `opt.AddWebhooks(...)` is now **optional config only** (custom `IWebhookSigner`, `IWebhookDeliveryExhaustedHandler`), not an enable switch. The `Moberg.Warp.Adapters.Webhooks` package was **removed** (folded into Core, which took a lightweight `Microsoft.Extensions.Http` dependency; the executor delivers via a bare `HttpClient` + a manual `IWarpAdapters` scope instead of the `Warp.Adapters.Http` binding). **Per-attempt `AdapterCallLog` rows require `AddAdapters()`** (recording opt-in, §8.19); without it the delivery state machine still works fully (dashboard, retries, exhaustion from the `WebhookDelivery` row) but the per-attempt HTTP call-log timeline is empty — consistent with §2.15 (telemetry unconditional, DB recording opt-in). Builds on adapters §8.19; makes durable webhook *delivery* a Warp feature. **Boundary: the host owns subscriptions + fan-out + payload building + endpoint enable/disable + its own secret tables; Warp owns everything after `SendAsync`** — delivery lifecycle, executor jobs, retry scheduling, exhaustion, signing, redelivery, dashboard. Warp models no subscriptions; the host calls `IWebhookDispatcher.SendAsync(WebhookSend)` once per destination.

**The delivery, not the job, is the state machine:** the executor (`ExecuteWebhookDelivery`, an ordinary source-gen job on the delivery's queue — worker hot path untouched §0.2/§6.1) **always completes**; every attempt exception is caught and recorded as attempt failure, so webhook failures never surface as failed jobs or pollute the Jobs UI. State lives on the always-in-schema (§2.11) `WebhookDelivery` row (`Warp.Core.Data.Entities`, §8.13): `WebhookDeliveryStatus { Pending = 1, Delivered = 2, Exhausted = 3 }` (§8.11). **Self-contained row** — URL, headers, payload, schedule, success codes, signing mode + secret, group, reference all stamped at `SendAsync` time so a later config deploy never reshapes an in-flight delivery. **`SendAsync` persists `Pending` + enqueues the first attempt in the caller's transaction (outbox), returns the delivery id** (= adapter `CorrelationId`). **Attempts are adapter calls** through the auto-registered `warp-webhooks` adapter (group = endpoint, operation = event type, `CorrelationId` = delivery id; `RecordCalls = All`, response bodies always captured, request bodies never — payload already on the row; `CallLogRetention` aligned to `WebhookDeliveryRetention`) — the attempt timeline is `AdapterCallLog WHERE CorrelationId = deliveryId`, **no separate attempt table**.

**No timers/scans:** each retry is a fresh executor job in `State.Scheduled` at `now + schedule[N-1]` riding `ScheduledJobActivation` (§2.8); `(RetrySchedule, AttemptCount)` fully determines the plan (schedule column never mutated), exhausted when `AttemptCount > schedule.Count`. `RetrySchedule` is per-send `IReadOnlyList<TimeSpan>` (§3 pillar: **no app-level schedule knob**): `null` = built-in `[1m,10m,1h,6h]`, `[]` = single attempt then `Exhausted`, N entries = N retries; persisted as a JSON seconds array (`"[60,600,3600,21600]"`/`"[]"`) via `RetryScheduleConverter` (§8.16 roundtrip tests mandated — empty/single/multi-hour on both providers). `SuccessCodes` `null` = any 2xx. **Cadence precision is delay + up to ~5s activation + worker pickup — a backoff, not a precision scheduler; document it.** Signing (`WebhookSigning { None = 1, StandardWebhooks = 2, Custom = 3 }`, §8.11): `None` (default, adds nothing — the legacy body-embedded-HMAC migration path), `StandardWebhooks` (HMAC-SHA256 over `{webhook-id}.{webhook-timestamp}.{payload}`, headers `webhook-id`/`webhook-timestamp`/`webhook-signature` `v1,<base64>`, `webhook-id` = `EventId` stable across retries), `Custom` (registered `IWebhookSigner` via `w.UseCustomSigner<T>()` — **declaring custom signing without a signer throws at `AddWebhooks` time, not send time**). **Secrets at rest** on the row are accepted for self-containment; **redacted on every read surface** (query service, endpoints, dashboard reduce `Secret` to a `HasSecret` flag, `Authorization`-class headers redacted — not caller-toggleable), never logged Info+ (§1.2); stricter hosts use `Signing = None` and sign in their own payload code. Exhaustion flips `Status = Exhausted` and invokes the host's `IWebhookDeliveryExhaustedHandler` **at-least-once, post-commit** with a redaction-safe snapshot (`ExhaustedCallbackPending` commits with the transition; the recovery check is **status-independent** so a `Redeliver` that flips the row back to `Pending` before the crash-recovery re-run still fires the prior exhaustion's callback) — a throwing callback is logged at Warning, never propagated (callbacks/instrumentation never out-throw). Host decides endpoint disable; Warp only signals. `IWebhookCommandService.Redeliver(id)` requeues a **settled** (`Delivered`/`Exhausted`) delivery to `Pending` + immediate job; `Pending`/unknown rejected with no side effects.

**Stuck-delivery recovery (the one deliberate exception to no-timers/no-scans):** the executor's attempt claim and its outcome commit are two transactions — a fault on the second leaves the row `Pending` with no live job (the retry job was staged in the failed transaction). The claim therefore stamps `NextAttemptAt` even on a final attempt, and `StaleJobRecovery` sweeps `Pending` rows whose `NextAttemptAt` is more than `WarpConfiguration.WebhookStuckDeliveryGrace` (default 10 min) past. Duplicate-proof by construction: candidates that still have a live executor job on the webhooks queue are skipped (merely-backlogged workers ≠ lost job), and the guarded `NextAttemptAt` bump + the new job commit in ONE transaction — a rollback undoes both, so no bumped-without-job or job-without-bump state exists. **That sweep runs on the SERVER context like every other server task (§2.14), staging the executor job directly (`JobHelper.CreateJob` + a `Created` `JobLog` + `NotificationDispatch.CapturePending` → `OnCommittedAsync`, the `RecurringJobScheduler`/`MessageRouter` pattern) rather than through the `TContext`-bound `IPublisher`.** It once went through the `IWebhookRedeliveryEnqueuer` seam on `TContext`, which put the bump and the job on a SECOND connection: they could no longer commit with the task host's lock transaction, and the live-job probe waited on the `Job` row locks the stale-job sweep in the same tick still held — under read-committed locking (**SQL Server without RCSI**) a self-block on a transaction that cannot commit until the sweep returns, killed by the command timeout every tick. The enqueuer seam stays for `WebhookCommandService.Redeliver`, which is genuinely user-context outbox work. Staging directly also bypasses `NoRestartPublishBehavior`, so the sweep stamps `ICanBeRestartedMetadata.CanBeRestarted = true` itself — `[Restart]` on `ExecuteWebhookDelivery` is otherwise only honored when the host called `AddNoRestart()`, and the delivery-completes guarantee must not depend on an addon or on `RestartStaleJobsByDefault`. The recovered exhausted-callback reconstructs the exhaustion's `AttemptCount` from `RetrySchedule.Count + 1` on post-`Redeliver` rows (the live column was reset to 0). `IWebhookQueryService`/`IWebhookCommandService` live in `Warp.Core.Webhooks` and resolve in any `AddWarp` process (dashboard/publisher-only) reading on `TContext` (§2.14). `ExpirationCleanup` deletes deliveries past `ExpireAt` (`WebhookDeliveryRetention`, default 30d). **Adoption prerequisite: a Warp server (worker) must run somewhere** that drains the webhook queue (no `AddWebhooks` needed on that server); coexistence with another job system (e.g. Hangfire) is a documented supported shape. Dashboard **Webhooks** nav is **always shown** (webhooks is a Core feature) — the `GET {prefix}/api/addons` `webhooks` flag gates on the always-registered `IWebhookRedeliveryEnqueuer`. Telemetry: `warp.webhooks.deliveries`/`attempts` (tag outcome) + `warp.webhooks.redeliveries`. See §8.19, `website/docs/features/webhooks.md`.

**Endpoint health, cancel, dedupe, last attempt (8.1).** *Why the endpoint is the `GroupName`, not the URL:* the host decides what an endpoint is (a subscription, a tenant's URL); two subscriptions on one URL can have different secrets or headers, so one group succeeding must never mark another healthy. Deliveries without a group are untracked. *Why the opt-in is stamped on the row (`TrackEndpointHealth`), not read from the executing server's config:* the attempt runs on whichever server claims the job, and per-process config would make the same delivery park on one server and exhaust on another — the self-contained-row pillar applied to behaviour. (`PublicAddressesOnly` is the opposite case: it is a property of the network the attempt leaves from, so it is per process.) *Why the delivery that turns a group Failing is `Exhausted`, not parked:* it is the signal (exhausted callback + `WebhookEndpointFailing`), as the feature spec asks; only deliveries running out while the group is already failing park. A failing group with nothing parked has nothing to probe and recovers on its next success. *Why recovery and release are split:* the executor flips Failing→Healthy in its own outcome transaction (atomic with the delivered row), but releasing thousands of parked rows there would make one delivery's commit unbounded; the `WebhookEndpointMonitor` releases at most 200 per run, oldest first, re-running while full, with staged schedule times ascending so the claim order follows creation order. Released rows go through the normal queue, so recovery never adds a herd beyond the workers' own concurrency. *Why the endpoint row is inserted in a separate scope before the outcome transaction:* a duplicate-key insert inside it would abort the whole outcome transaction on PostgreSQL; EF Core has no provider-neutral insert-if-absent and Core may not carry provider SQL (§5.1). *Probe = "release with one attempt left"* (`AttemptCount = RetrySchedule.Count`): it reuses the existing claim/outcome state machine, so a failed probe parks again with no special case and the stuck-delivery sweep still covers a probe whose outcome commit faulted. *Cancel* is enforced by the outcome commit's `ExecuteUpdate … WHERE Status = Pending` (which also stamps the #357 fields): a row cancelled mid-attempt is never overwritten and schedules no retry; a live executor job's claim already skips non-Pending rows. *Dedupe* hashes the length-prefixed event id + URL (a 2048-char URL exceeds SQL Server's index key limit); the unique index on a nullable column is filtered to non-null by EF Core's SQL Server convention and PostgreSQL treats nulls as distinct, so no provider SQL is needed; the check is read-before-insert, and a concurrent duplicate loses on the index (documented, not retried — the dispatcher saves inside the caller's unit of work). *The webhook SLO kind reads delivery rows, not counters:* deliveries are durable (not lossy) within retention, and the in-time test needs both timestamps of one row.

**Secure by default (8.1, security review).** *`PublicAddressesOnly` is on by default* because the URL is tenant-chosen: off by default meant a customer could make a server POST to `10.x`, `localhost` or cloud metadata. The guard therefore moved into `AddWarp` (`WebhookHttpClientSetup.AddDefaultClient`), gated by `WebhookAddressPolicy` (default true), registered once per service collection; only an EXPLICIT `PublicAddressesOnly` assignment configures the policy (a nullable backing field), so a second `AddWebhooks` for another option cannot undo a local-dev opt-out. The guard is still per process (it lives on the client of the process that runs the attempt). `SendAsync` adds an up-front `ArgumentException` for what is certain at send time — non-public IP literals and `localhost`/`*.localhost` (RFC 6761) — never for host names, whose DNS answer can change. The startup check swallows (Debug log) a handler that cannot be built yet: a host routing `warp-webhooks` to an in-process test server failed to start otherwise. The repo's own `WarpTestServer` and demos opt out (stubs and localhost receivers); the tests that cover the guard opt back in.

**Webhook queue (8.2).** An executor job is an ordinary job on an ordinary queue: `WebhookSend.Queue` ?? `AddWebhooks(w => w.Queue)` ?? `DefaultQueue`, resolved once at `SendAsync` and stamped on `WebhookDelivery.Queue` (nullable, unbounded like `Job.Queue`, declared in `AddWebhookDeliveryEntity` so §5.12 pins it). Every later enqueue of the delivery reads the row: the executor's retry `Schedule`, `WebhookRedeliveryEnqueuer<TContext>` (redeliver and "Retry now" probe; it reads the row's queue on the same scoped context inside the caller's transaction, so the public `IWebhookRedeliveryEnqueuer.EnqueueAsync(id)` signature is unchanged), the stuck sweep and the endpoint monitor (`WebhookExecutorJobs.Stage(..., queue, ...)`, `WebhookParkedRelease.ProbeOldestAsync` returns `ParkedDelivery(Id, Queue)`). A delivery therefore stays on its queue for life, whichever process enqueues it. A null column is a row written before 8.2 and resolves through `WebhookSendBehavior.ResolveQueue` to the enqueuing process's default. The stuck sweep's live-job probe filters on that same resolved queue. Why no special worker-group logic: a slow receiver holds a worker for up to `WebhookAttemptTimeout` per attempt, and the host decides how much of that it will tolerate — isolation is the host's own `AddWorkerGroup` on the webhook queue (`PrefetchCount = 0` recommended: attempts are slow and prefetched ones would wait behind them on one server). `WebhookSendBehavior` is public with internal setters only because the public server tasks (`StaleJobRecovery`, `WebhookEndpointMonitor`) take `IOptions<WebhookSendBehavior>` in their constructors.

**Legacy-queue bridge (REMOVE in 9.0, issue #367).** Through 8.1 every executor job ran on the literal `warp:webhooks`, which every server drained by itself; 8.2 drains nothing by name, so jobs still Enqueued/Scheduled there would be stranded silently. `StaleJobRecovery.MoveLegacyWebhookJobsAsync` (every run) moves the Enqueued ones with one `ExecuteUpdate` (`Kind = Job`, `CurrentState = Enqueued` as literals: the claim partial index) to the server's resolved webhook queue, and buffers one `JobEnqueued` wake for `OnCommittedAsync` when it moved any. **Only Enqueued, deliberately:** a legacy retry still `Scheduled` there is flipped to `Enqueued` by `ScheduledJobActivation` when due and moved by the next run (at most one `StaleJobRecoveryInterval` late); a Scheduled update would read the whole Scheduled partial index every 30 s, a cost that grows with every scheduled job in the deployment. Idempotent (a moved row no longer matches); it also catches rows an 8.1 publisher still writes during a rolling deploy. Guards: `CrashRecoveryTestsBase.MoveLegacyWebhookJobs_*`.

**Decisions after review (8.1).** *A host's non-Sockets primary handler is kept and fails closed* rather than being replaced: replacing silently dropped a proxy or mTLS certificate on upgrade (deliveries then left without them, or bypassed a corporate proxy). `WebhookGuardUnavailableHandler` wraps the kept handler and throws on every send, with a message naming both fixes (`UseSocketsHttpHandler`, or `PublicAddressesOnly = false`); the same text is logged once at Warning, at startup on worker servers. *The first failure parks too:* the delivery that turns a tracked group Failing is `Parked`, not `Exhausted`, so every delivery sent during an outage is eventually probed or released; the `WebhookEndpointFailing` signal replaces the exhausted callback as the alert. *`RateLimitBucket.UpdatedAt` is indexed* in the same 8.1 migration, for the stale-bucket sweep added on the security-hardening branch.
