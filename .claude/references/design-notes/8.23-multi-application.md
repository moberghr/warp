# §8.23 — design notes (multi application)

> Full rationale, history, measurements and rot guards behind the condensed rule §8.23 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `project-specific.md` (2026-11-24).

**§8.23** **Multi-application observability** is Warp's answer to a **shared-database** deployment (many apps, one schema; all servers still pick up all jobs — execution/routing **unchanged**). It is NOT isolation — true isolation between independent apps is a **separate schema per app** (`opt.Schema`), documented not built here. **Opt-in trigger: `WarpConfiguration.ApplicationName` (`string?`, default `null`) gates ALL new runtime behavior** — `null` ⇒ today's behavior byte-for-byte. Plus optional self-reported `ApplicationVersion`/`ApplicationEnvironment` (per-instance, may differ mid rolling-deploy). `ApplicationName` = cluster-wide identity (same name ⇒ instances group + stats/metrics merge; different apps ⇒ different names) — same identity model as an adapter name (§8.19). **Sibling-table registry model** ("every server IS an application instance; not every instance is a server"): `Server` gains nullable `Application`/`Version`/`Environment` (stamped by the existing `Heartbeat` server task — no new loop for servers); non-server processes (`AddWarp`-only publisher/API/dashboard) write ONE `ApplicationInstance` row via a new lightweight heartbeat `IHostedService` (`ApplicationHeartbeatHost`) registered by `AddWarp` **only when `ApplicationName` set** — **a deliberate change to the "`AddWarp` is passive" contract** (§2.13), gated + no provider/lock (owns its row by `Id`) + deregisters on graceful `StopAsync`. Each process writes exactly one physical row (no double-writes). Entities `ApplicationInstance` + `ApplicationInstanceLog` live in `Warp.Core.Data.Entities` (§8.13), are **always-in-schema** (§2.11, `WarpModelCustomizer`) and mirrored by `WarpServerContext` (§2.14). `ApplicationInstanceEventType` enum from 1 (§8.11, namespace `Warp.Core.Enums`): `Registered=1, HeartbeatLost=2, Recovered=3, Stopped=4, StaleSwept=5` — unified lifecycle log for ALL instances (server ∪ non-server); `ServerLog` stays server-task-execution history (relabeled "Server tasks" in the UI). `ExpirationCleanup` sweeps stale `ApplicationInstance` rows past `ApplicationInstanceStaleGrace` (2m) + retains `ApplicationInstanceLog` by age (`ApplicationInstanceLogRetention` 7d) + count (`ApplicationInstanceLogRetentionCount` null=off) (§8.22). **Provenance** (nullable `Application` column, filter/display only): `Job.Application` (stamped at publish, **preserved on requeue**), `AdapterCallLog.Application`, `EndpointCallLog.Application`, `WebhookDelivery.Application`.

**Provenance ≠ execution:** `Job.Application` = *publishing* app (filter/trace only) — jobs execute on a worker app, so per-**creator** job metrics are deliberately NOT provided; execution metrics are attributed to the **executor** app instead. **Per-app metrics under DISJOINT counter-key namespaces** (back-compat, first-segment-equality parsers reject them — existing keys byte-for-byte unchanged, old readers never see the new prefix, §8.6/§8.19): `adapter-app` (`AdapterCallFlusher.AppPrefix`), `endpoint-app` (`EndpointCounterKeys.AppPrefix` — `Application` also joins endpoint **identity** so the same route in two apps stays distinct), `jobstat`/`jobstat-app` (`JobStatsKeys` — per-job-**type** + per-**handler** execution count/duration/error, executor-app-sliced, folding via `Counter → CounterAggregator → Statistic` so they **survive raw-row cleanup**; hourly history auto-prunes at `HourlyStatisticsRetention` 7d, lifetime totals persist — no new aggregation/cleanup path). **Unified `InstanceView`** (`Warp.Core.Models`) merges `Server` ∪ `ApplicationInstance` into one dashboard roster. `IApplicationQueryService` + `ApplicationQueryService<TContext>` registered by **`AddWarp` itself** (like `IAdapterQueryService`/`IEndpointQueryService`), so dashboard-only/publisher-only processes resolve it. Dashboard **Applications** page = the renamed **Servers** page (`/servers` → `/applications` redirect), always shown; `WarpAddonsInfo.Applications` flag true iff `ApplicationName` set. API: `GET {prefix}/api/applications`, `/{id}`, `/{id}/instances/{instanceId}`, `/{id}/jobstats` (id = URL-safe base64 of the app NAME via `EndpointRouteId`); global `application` filter param on jobs/adapters/endpoints. `warp.application` OTel span attribute (`WarpTelemetryAttributes.WarpApplication`) when set, absent when null. **Migration 100% additive** — 2 new tables (`application_instance`, `application_instance_log`) + 7 nullable columns, picked up by the user's standard `dotnet ef migrations add / database update`; legacy `null`-application rows read as "(unassigned)"; rolling-deploy safe (old processes ignore new cols/tables, write null). Shared-DB "who owns migrations" is a pre-existing concern, unchanged. Worker hot path untouched (§0.2/§6.1 — counter increments only, into the in-memory buffer at the existing finalization site, §6.2).

**Deploy history (#325):** `ApplicationDeploy` (`Warp.Core.Data.Entities`, always-in-schema, mirrored; Application/Version/Environment/FirstSeenAt/InstanceId (soft ref)/InstanceName) = the first instance of an application to register with a version not seen before for that (application, environment). Recorded by the internal `ApplicationDeployRecorder.RecordAsync` at REGISTRATION only — `WarpServerRegistration.StartAsync` (servers, after the `Server` row commits, own `SaveChanges`) and `ApplicationHeartbeatHost.RegisterAsync` (non-server) — never per heartbeat (the version is static per process) and never on the worker path. Gated on `ApplicationName` AND a non-blank `ApplicationVersion`. **Unique index (Application, Environment, Version)** settles the N-instance race: probe → insert → on `DbUpdateException` clear the tracker and re-probe; present ⇒ "already recorded" (provider-agnostic on purpose — an `AddWarp`-only process may have no `IDatabaseExceptionClassifier`). **`Environment` is stored NON-NULL with `""` = none** — a NULL in a unique index is distinct on PostgreSQL and EF's SQL Server convention filters NULLs out of a unique index, so a nullable column would let two "no environment" rows of one version in; the read model maps `""` back to null. A rollback to an already-recorded version is not a new deploy. Recording is best effort (any non-cancel failure → Warning, registration still succeeds; the next instance of that version retries). Retention is SEPARATE from the instance sweeps: `ApplicationDeployRetention` (`TimeSpan?`, default null = keep forever), swept by `ExpirationCleanup.CleanupExpiredApplicationDeploysAsync`, which never deletes the newest deploy per (application, environment) — deleting it would make the next start of that long-running version record a fresh deploy. Read: `IApplicationDeployQueryService.GetDeploys(application?, since?, until?)` newest first, capped at `IApplicationDeployQueryService.MaxDeploys` 500 — its OWN interface (implemented by `ApplicationQueryService<TContext>`, `TryAddScoped` by `AddWarp`), NOT a member of `IApplicationQueryService`: that interface is `TryAdd`-registered, so a host may implement it before `AddWarp` (the §8.24 seam) and adding a member would break its build; a default interface implementation would have had to return an empty list and silently 404 the verdict. `DeployVerdictService` and the two deploy routes take the new interface; API `GET {prefix}/api/applications/{id}/deploys` and `GET {prefix}/api/applications/deploys?application=<name>` (`from`/`to` optional, the UTC-converted `from >= to` → 400, a bare instant read as UTC and an offset one converted; a malformed `{id}` → 404); Applications detail page "Deploys" card (`deployModel.withPreviousVersion`). Migration: one additive table `application_deploy`. Rot guard: `ApplicationDeployTestsBase` (N=2 `BarrierSignal` race, both registration paths, retention keeps newest, instance sweep leaves history).

**Post-deploy verdict:** `GET {prefix}/api/applications/verdict?application=<name>[&version=][&environment=][&minWindowMinutes=0..1440, default 5][&minCoverage=0..1, default 0][&board=<name>]` answers "is this release healthy?" for a CI step — `verdict` = `pass`/`warn`/`fail`/`pending`/`noData` (string tokens, `DeployVerdicts`) + `summary` + `checksWithData`/`checksTotal` + the deploy (with `previousVersion`/`supersededBy`) + the window + one check per tile/SLO (source, state token, acknowledged, value/baseline/target/threshold, reason). **An SLO check's `value` and `target` share one scale** (`DeployVerdictMath.SloTarget`): `value` is the attainment, and for `MetricLatency`/`MetricGaugeThreshold` — whose attainment is a SHARE (events within the threshold / observed time compliant) — `target` is the required share `percentile / 100` and the threshold moves to the additive `threshold` field (null on every other check); it once reported the threshold as `target` (`observed 0.9917 vs target 600`). The reason mirrors `sloDisplay.formatObserved`/`formatTarget` (`DeployVerdictMath.SloObserved`/`SloTargetText`: `observed 99.17% compliant vs target max ≤ 600 in 95%`, `observed 98.74% ≤ 2 vs target p95 ≤ 2`, rate kinds as %, counts rounded, job latency in ms, a baseline ratio as a drop in points, a volume floor as a share of baseline) with the budget as a whole percentage; the demo verdict builds its reason from those same `sloDisplay` helpers, so the two cannot drift apart silently. `IDeployVerdictService`/`DeployVerdictService` (non-generic, registered by `AddWarp` — dashboard-only hosts serve it) **composes the existing read services and adds no query**: `IApplicationDeployQueryService.GetDeploys(app)` (deploy read) → pure `DeployVerdictMath.Resolve` (newest match on version/environment, neighbours in the SAME environment) → the clean window `DeployVerdictMath.Window` (`FirstSeenAt` rounded UP to a fine bucket → the board's cut, or the next deploy in that environment rounded down when superseded; see Aggregation below), clamped to 90 d → ONE batched board read (skipped for an empty window): **`GetAllBoards` without `board`** (the tiles of EVERY named board, resolved question 2 of the 2026-11-17 named boards spec: counting only Default would silently drop a tile from an existing CI check the moment a team moves it), or that board's read with `board=<name>` (matched OrdinalIgnoreCase in memory via `GetBoards` by the CURRENT name; when no board has that name, `Default` (ignoring case) resolves to the `IsDefault` board whatever it is called — the seeder's meaning of `AddMetricBoard("Default", …)`, so one rule for both and a CI step pinned to `board=Default` survives a rename; a board currently NAMED Default wins; rot guards `GetVerdict_BoardDefaultAfterTheDefaultBoardWasRenamed_*` / `GetVerdict_BoardDefaultWhileAnotherBoardIsNamedDefault_IsThatBoard`, resolved BEFORE the deploy and whatever the window; an unknown name throws `MetricBoardNotFoundException` → route **404** `{ error }`, never an empty check set that reads as a pass) → the SLOs (skipped when superseded — current SLO state describes the newer release): **without `board`, ONE `GetObjectives` (every SLO of the application) — so the all-boards read skips its own SLO-tile join through the internal `IMetricBoardVerdictReader.GetAllBoardsWithoutObjectives` (implemented by `MetricBoardQueryService`; the public `GetAllBoards` keeps the join, and a host's own `IMetricBoardQueryService` falls back to it), pinned by `GetVerdict_WithSloTilesOnTheBoards_ReadsTheObjectivesOnce` (one `slo_evaluation` statement, with and without `board`, full and empty window); with `board=<name>`, ONLY the objectives that have an SLO tile on that board** (resolved question 1 of the 2026-11-19 chart/SLO tiles spec — a board with no SLO tile counts no SLO; still application-scoped + `Enabled`), taken from the board read already made, which joins its SLO tiles to its own single `GetObjectives` (no extra query; with an empty window, where no board read is made, `GetTiles` lists the board's SLO tiles and `GetObjectives` runs only when one exists). A behaviour change from the boards batch on this branch: a CI step pinned to `board=` reads a different check set (release notes). Counts tiles **with a status rule** scoped to the app or unscoped (`MetricPointQueries.NormalizeApplication`, ordinal) and **enabled** SLOs scoped the same way; an SLO never evaluated or last evaluated before the clean window's start `window.From` is NoData (no evaluation history exists, so no before/after SLO comparison). Aggregation (`DeployVerdictMath.Aggregate`): **the window holds only complete fine buckets that start after the deploy** (`DeployVerdictMath.Window`, fed `FineResolutionMinutes` + `MetricFlushInterval`): `From` = `FirstSeenAt` rounded UP to a bucket boundary (the mixed bucket holding the deploy is never counted, so no pre-deploy traffic), `To` = the board's cut (fine `BucketStart(now − flush)`), or for a superseded deploy the next deploy's `FirstSeenAt` rounded DOWN when earlier; the LATEST deploy is `pending` until that clean window is ≥ `minWindow` (and ≥ one bucket) of complete data, regardless of checks (checks still returned) — `settlesAt` = `CeilToBucket(From + minWindow)` + flush (defaults: a deploy at 10:00:00 settles 10:05:30, one at 10:00:10 or 10:04:50 settles 10:10:30); **a superseded deploy keeps the settled-over-its-lifetime rule** (its window can never grow, so it never waits for `minWindow` — it was once `pending` forever with a past `settlesAt`): `settlesAt` = its last bucket's completion (next deploy rounded down + flush, so at most one flush interval of `pending` right after the replacement), and with no whole bucket between the two deploys it is `noData` with a "superseded … before a complete metric bucket" summary, never `pending`; SLO checks take the same clean start only as far as possible — `LastEvaluatedAt < window.From` ⇒ NoData — since an SLO's state covers its own rolling window, which the verdict cannot re-cut; the coverage bar compares the SHARE `withData / count >= minCoverage − 1e-9` (not `withData >= minCoverage × count`, which rounds 0.56 × 25 past 14); else any Breaching ⇒ fail, share of checks with data below `minCoverage` ⇒ noData (a would-be pass/warn only — **a fail is never downgraded**), any Warning ⇒ warn, any Healthy/Acknowledged ⇒ pass, else noData — **Acknowledged never fails**. Sparse data stays `pass` at the default `minCoverage=0`; `checksWithData`/`checksTotal` (JSON names consumed by the UI) and the `summary` prefix `pass (2 of 9 checks had data): …` make it visible. 400 = missing app / > 200 chars (board too) / bad minWindow / bad minCoverage (`DeployVerdictQuery.TryCreate`, the board overload); 404 = no matching deploy. Auth = the dashboard group gate (§1.5), no new scheme; CI uses the host policy (bearer/API-key) or the built-in login cookie. Non-finite values serialize as null. No schema change. UI: "Latest deploy verdict" card on the Applications detail page (`verdictModel.ts`), demo `demoDeployVerdict`. Rot guards: `DeployVerdictTestsBase` (both DBs), `DeployVerdictMathTests`/`DeployVerdictQueryTests` (NoDb), topology, `verdictModel.test.ts`. See §2.15/§8.19, `website/docs/features/applications.md`.
