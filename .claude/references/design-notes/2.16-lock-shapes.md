# §2.16 — design notes (lock shapes)

> Full rationale, history, measurements and rot guards behind the condensed rule §2.16 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `architecture.md` (2026-11-25).

**§2.16** Two lock shapes, and **the difference is a deployment contract, not an implementation detail**. **Transaction-scoped** (`IWarpSqlQueries.RunUnderTransactionLockAsync`, `pg_try_advisory_xact_lock` / `sp_getapplock`, released by `COMMIT`) is what `IServerTask.LocksWithTransaction` (default **true**) selects, and it is safe through any connection-pooling mode. **Session-scoped** (`IWarpLockProvider.TryAcquireAsync` → Medallion, released by an explicit unlock on the SAME backend session) is required only where the guarded work spans multiple transactions, and it is **broken by a pooler in transaction mode** — the acquire and release land on different backends, so `pg_advisory_unlock` returns false and, far worse, the acquire never provided mutual exclusion. The five session-lock sites are `RecurringJobPublisher.AddOrUpdateRecurringJob`, `MessageRouter` (the only server task with `LocksWithTransaction => false`; under cluster task leases it takes the lock only while a server from before the lease is alive, §6.23), `SagaHandlerProxy`, `SagaCommandService.ForceComplete`, `RateLimitPipelineBehavior`, plus the `ConcurrencyPipelineBehavior` semaphore. **Prefer the transaction-scoped lock for anything new**; reach for the session lock only when per-item commits inside the guarded region genuinely require it, and say why in a comment. The asymmetry is also the diagnostic signature: a transaction-pooled deployment looks mostly healthy (jobs run, heartbeat ticks) while message routing silently stops and sagas requeue forever.
