# §2.18 — design notes (postgres lock pool)

> Full rationale, history, measurements and rot guards behind the condensed rule §2.18 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `architecture.md` (2026-11-25).

**§2.18** **On PostgreSQL the lock providers get their own Npgsql pool**, via `ResolveLockConnectionString` — `TContext`'s connection string with `Application Name` suffixed `:warp-locks` (part of Npgsql's pool key) and `MinPoolSize` pinned to 0. NOT tidiness: Npgsql resets a pooled connection with one `DISCARD ALL`, but a connector carrying PREPARED STATEMENTS must use a seven-statement sequence instead (`CLOSE ALL`/`UNLISTEN *`/`pg_advisory_unlock_all()`/`RESET ALL`/`DISCARD TEMP`/`DISCARD SEQUENCES`/`SET SESSION AUTHORIZATION DEFAULT`) because `DISCARD ALL` would deallocate them — and Medallion prepares its lock statements, so ONE shared pool flipped every EF connector in the process. Measured (re-measured for 7.1.0, two interleaved passes): 51.18 -> 25.10 statements/job on the no-contention concurrency arm, 379.88 -> 181.10 at full mutex contention (1 group / 16 workers), and **17.00 -> 13.71 on a workload with no concurrency keys at all** (the server tasks take advisory locks too). Throughput unchanged (interleaved, 5 pairs: within noise on every arm); this is database load, not latency. **The connection string is read from `TContext` — through `WarpDatabaseConnection<TContext>` (registered by `AddWarp`; the application's options BEFORE Warp's interceptors, resolved once and cached, so reading a connection string never constructs Warp's interceptors: building them from a singleton factory is what deadlocked the push transport against the enqueue interceptor, #322) — never `IWarpServerContext`** — §2.14 governs which DbContext EXECUTES server-internal work, while these are raw Npgsql sessions off any context (§2.16), and `IWarpLockProvider` must resolve in `AddWarp`-only processes (`RecurringJobPublisher.AddOrUpdateRecurringJob`, `SagaCommandService.ForceComplete`) where the server context does not exist. **The DATA-SOURCE path is deliberately not split** — an `NpgsqlDataSource`'s password provider / certificate callbacks / type mappings are write-only on the builder and unreadable from the built object, so forking one would silently drop the host's auth; those hosts pass their own via the `UsePostgreSql(lockDataSource)` overload (two overloads, not an optional parameter, to keep binary compatibility). **Two pools RAISE peak connection use, they do not re-divide it** — measured 30-31 peak backends on one pool vs 46 on two (per-pool maxima 30 DbContext and 17 lock, sampled independently, so they need not sum to the overall peak) on the contended mutex arm; the DbContext peak does not fall, because each pool sizes to its own demand and an idle connector in one cannot serve the other. Budget `peak(TContext) + peak(locks)`, where the lock pool tends toward WorkerCount: it sizes to concurrent lock ATTEMPTS, not holds (17 against 8 holdable locks — a rejected attempt opens a connection, and Medallion allocates a fresh shareable connection when its multiplexed one cannot take an acquire instantly, so multiplexing does NOT bound this). Ceilings are inherited, deliberately NOT capped at an invented number (too low blocks acquisition rather than degrading it); `MinPoolSize` pinned to 0 so the IDLE cost is not doubled. SQL Server has no equivalent (one `sp_reset_connection`). Rot guards: `LockConnectionPoolIsolationTests` (the pure `BuildLockConnectionString`) + `LockConnectionPoolWiringTests` (BOTH call sites, each verified to fail alone under mutation).
