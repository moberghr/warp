# §6.9 — design notes (claim scalar queue predicate)

> Full rationale, history, measurements and rot guards behind the condensed rule §6.9 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `performance.md` (2026-11-25).

**§6.9** **The claim's queue predicate is a SCALAR equality, and the worker issues ONE statement per queue** (`ClaimEnqueuedJobsAsync`, both providers). It was `queue = ANY(@queues)` with `ORDER BY Queue, ScheduleTime`, which returns the same rows but collapses the moment the planner's row estimate goes stale: with 54,000 claimable rows in a 300k table and stale statistics, `ANY(array)` sorted (external merge, 2,584 kB to disk) over the WRONG index with `queue` demoted to a Filter — 5,139 buffers + 584 temp / 44.6 ms — where the scalar form was an Index Cond on `(Kind, CurrentState, Queue, ScheduleTime)` at 26 buffers / 0.062 ms (720x, and `LIMIT 1` single-worker mode is hit identically at 42.1 ms). Both spellings estimate `rows=1` there; only the scalar one does not NEED the estimate to be right, because with `queue` fixed that index supplies the ordering for free, so there is no Sort and `LIMIT` stops at the first rows — a Sort must consume its entire input before emitting anything, which is why `LIMIT` bought nothing and the claim read the whole enqueued range to return one job. **Not parameter opacity** — a literal `ANY(ARRAY[...])` (40.8 ms) and `IN (...)` (40.2 ms) are just as bad, and fresh statistics "fix" it only by winning a race against a backlog that swings empty-to-full between autovacuum ticks. Do NOT re-collapse the loop into one multi-value statement to "save a round trip": the loop costs nothing measurable (statements/job within noise of the old form at 120k jobs), and a single queue — the common shape — still issues exactly one statement. **The bad plan is reachable in an ordinary workload, not just under a pinned `EXPLAIN`** — re-measured for 7.1.0 at 120k jobs published-then-drained, the old predicate took it in **2 of 6 runs** (claim 78-85M blocks and ~910 jobs/sec, against 6.9M and ~1,170 on its good runs) while the scalar form took it in **0 of 12** (6.5-7.1M blocks, 1,179-1,254 jobs/sec). The two have similar MEDIANS, so a median-to-median comparison reads as "no change" and is the wrong instrument: the old predicate is bimodal and the new one is not. An earlier session concluded the lab never reproduces the bad state; that conclusion did not survive re-measurement. Three consequences are deliberate and must be preserved: cross-queue **starvation is reproduced, not fixed** (the budget is spent down queue by queue, the same drain-the-first-queue-completely behaviour the old `ORDER BY Queue` gave, and the default group binds `{DefaultQueue, warp:webhooks}` so webhooks already wait for the default queue); ordering moved from the database collation to **`StringComparer.Ordinal`** (identical for the ASCII queue names Warp produces); and each statement is its own implicit transaction where one was atomic across queues — nothing depends on cross-queue atomicity, and a failure partway leaves claimed rows `Processing` with no worker, the crash-mid-claim case `StaleJobRecovery` already repairs. **The rows a claim RETURNS are sorted by `ScheduleTime` in memory** (`ClaimFromQueueAsync`, both providers, skipped for a single row, so single-worker mode pays nothing): the inner `SELECT` picks the oldest rows, but `UPDATE ... RETURNING` / `OUTPUT` hands them back in no particular order (id order on PostgreSQL), and the dispatcher starts a claimed batch in list order, so a newer job of the batch could start before an older one. Rot guard: `ConcurrentClaimTests.ClaimEnqueuedJobs_BatchClaim_ReturnsTheOldestJobsOldestFirst` (fails on PostgreSQL without the sort).
