# §8.25 — design notes (operational notifications)

> Full rationale, history, measurements and rot guards behind the condensed rule §8.25 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `project-specific.md` (2026-11-24).

**§8.25** **Operational notifications** — a host seam (`IWarpNotifier { Task NotifyAsync(WarpOperationalEvent evt, CancellationToken ct); }`, `Warp.Core.Notifiers`) that hands Warp-detected operational events to the host, which decides what to do (Teams/Slack/email/page/log). **Warp ships no channel integrations** — pure seam, the `IWebhookDeliveryExhaustedHandler`/`IWebhookSigner`/`IWarpCredentialValidator` precedent.

**Alerting ≠ webhooks:** a webhook is the host telling external subscribers about domain events (needs a subscriber URL); a notification is Warp telling the operator something is wrong (no URL) — reusing `IWebhookDispatcher` for self-alerting is the wrong abstraction. Register via `opt.AddNotifier<T>()` (non-generic `IWarpBuilder`, §2.13 `AddBackgroundService<T>` precedent); resolved as `IEnumerable<IWarpNotifier>` (optional-marker, §2.9) so **zero registered = inert**.

**Contract:** invoked **post-commit** (the transition is durable) and a **throwing notifier is caught + logged at Warning + never propagated** (an alert sink can't take down what it observes; never fails/slows the worker). **Events are NOT persisted — no notification outbox.** Dispatch is in-process from an in-memory buffer, so **delivery to the sink is best-effort for every event**: a crash in the commit→dispatch window, or a notifier that's down/throwing (swallowed+logged, no retry), drops that alert. Convenience alerts, not an audit trail — the operator action / `WebhookDelivery` row / instance roster are the systems of record; don't build guaranteed-delivery accounting on them.

**Per-source replay nuance:** only `WebhookDeliveryExhausted` is re-emitted after a crash-before-dispatch (the delivery's `Exhausted` state is persisted → executor re-run regenerates the event; may repeat, key on event id) — still lost if the sink is unreachable at call time. `SagaForceCompleted` + `InstanceDown` report a row deleted in the committing transaction, so a lost dispatch is gone for good. Don't overclaim at-least-once. §8.18 captive-dependency footgun applies — notifiers are singletons, inject `IServiceScopeFactory` not `DbContext`. Fan-out is centralised in the singleton **`WarpNotifierDispatcher`** (guarded loop over the set; empty-set no-op), registered by `AddWarp` (beside `ServerTaskSignals`) so every dispatch site resolves it in any process.

**CRITICAL post-commit mechanism for server tasks:** `ExpirationCleanup`/`ServerCleanup` run INSIDE the server-task host's lock transaction (`IServerTask.LocksWithTransaction` default true → `ServerTaskRunner.RunUnderTransactionLockAsync` commits AFTER `ExecuteAsync` returns), so their `SaveChangesAsync` only **flushes** — a direct dispatch there fires **pre-commit** and could alert on a rollback-undone change. The seam is **`IServerTask.OnCommittedAsync(ct)`** — a **default-no-op post-commit hook** the `ServerTaskRunner` invokes after the transaction commits (every execution path; **skipped on throw/rollback and when the lock wasn't held**). The two tasks **buffer** their `InstanceDown` events in a private field during `ExecuteAsync` and **dispatch from `OnCommittedAsync`** (`CancellationToken.None` so shutdown doesn't abandon a committed alert). Keeps `ServerTaskRunner` feature-agnostic (no `Notifiers` coupling). The webhook + saga sites are ordinary/​session-lock paths (genuinely post-commit) and dispatch inline via `WarpNotifierDispatcher` directly, also with `CancellationToken.None`. **New server-task authors: never dispatch in `ExecuteAsync` (pre-commit) — buffer + dispatch in `OnCommittedAsync`.** **Events are redaction-safe snapshots — identity/metadata only, never a payload body (§1.2).** Abstract `WarpOperationalEvent` base (`Type`/`Severity`/`TimestampUtc`/`MachineName`/`Application`/`Message`) + typed subtypes the host switches on. `WarpEventType` enum from 1 (§8.11, `Warp.Core.Enums`): `JobDeadLettered=1` (**RESERVED**, deferred — the payloadless finalization signal needs a claim mechanism), `WebhookDeliveryExhausted=2`, `SagaForceCompleted=3`, `InstanceDown=4`, `BacklogBreached=5` (**RESERVED**, needs queue-wait metrics). Plus `WarpEventSeverity { Info=1, Warning=2, Error=3 }`. **v1 dispatch sites (all pre-existing detections, worker hot path untouched §0.2/§6.1):** webhook exhaustion in `ExecuteWebhookDelivery` (post-commit, alongside the existing exhausted-handler — the two coexist), saga `ForceComplete` in `SagaCommandService` (after `SaveChanges`), and instance-down from BOTH the `ExpirationCleanup` stale `ApplicationInstance` sweep (`IsServer=false`) and the `ServerCleanup` stale-`Server` sweep (`IsServer=true`) — every server is an instance (§8.23). Dispatch sites take a **required** `WarpNotifierDispatcher` ctor param (§0.5 specific dep, no fallback). See `website/docs/features/operational-notifications.md`.
