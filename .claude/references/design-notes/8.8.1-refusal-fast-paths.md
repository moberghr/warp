# §8.8.1 — design notes (refusal fast paths)

> Full rationale, history, measurements and rot guards behind the condensed rule §8.8.1 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `project-specific.md` (2026-11-24).

**§8.8.1** **Refusal fast paths (rate limit + concurrency), both process-wide singletons registered by the addon, both EXACT — they may only refuse what the database would refuse.** `RateLimitGate` remembers, per key, the instant an authoritative check said the key reopens; until then a job on that key is refused from memory (no lock, no override lookup, no bucket read). Sound across servers because other processes can only CONSUME capacity, so the reopening instant is a lower bound everywhere — the one exception (an admin raising/removing an override) is bounded by `RateLimitGate.MaxClosedAge` (5s) and cleared at once on the process that made the change (`RateLimitManager` invalidates after its `SaveChanges`). A cached entry is keyed by the job's DECLARED (count, window, style) — a job declaring a different shape on the same key goes to the database.

**Wait mode spreads the backlog:** each throttled job takes its own slot from the cluster-wide cursor `RateLimitBucket.NextSlotUtc` (advanced under the key's lock, one position per `window / count`; a `Fixed` job is scheduled at the START of the window its position falls in — the window admits its count at once, and spreading across it delayed a backlog's drain by up to a window, measured 42s -> 52s; `Sliding`/`TokenBucket` use the position as-is), leased in blocks of at most `MaxLeaseSize` (20) AND at most `LeaseHorizon` (5s) of capacity — the time cap is what stops one process reserving an hour of a `20/hour` key for one job. Before this every refused job was rescheduled onto the SAME reopening instant, so a backlog of B at C per window re-executed ~B²/2C times; do not reintroduce a shared reschedule time. Slots are not FIFO (fresh arrivals that find capacity run first). **A window shorter than `ScheduledActivationInterval` steps the cursor by the activation interval with `count` jobs per step** (`IScheduledActivationCadence`, registered by the worker from `WarpServerConfiguration.ScheduledActivationInterval`, injected into the gate as an optional `IEnumerable`; none ⇒ no stepping): a batch released on one tick is consumed in well under a second and only meets the window open then. Measured on 50/2 s, 500 jobs, 10 s ticks: `count` per step = 62 statements/job, ~0.9 refused runs/job, 92 s drain; the review's `count × interval / window` per step = 90 statements/job, 2.4 refused runs/job, 73 s drain — the team chose lower DB load, and the docs tell short-window users to lower `ScheduledActivationInterval` for the full rate. `ConcurrencyLocalHolds` counts the slots THIS process holds per **(lock name, limit)** — the exact acquire request, never the name alone; when they alone reach the effective limit the DB acquire is skipped (it cannot succeed). Keyed per name it broke the exactness rule: on PostgreSQL a mutex locks `name` and a semaphore of N locks `name:0..N-1` (independent caps, §8.6), so N held semaphore slots refused a `[Mutex]` on the same key whose lock was free — deleting it in Skip mode; per request, mixed shapes and a limit an admin changes mid-run simply go to the database (`SemaphoreSlotsHeldByThisProcess_MutexOnSameKey_StillAcquires` is the guard). Release order is load-bearing: the local count is decremented BEFORE the DB lock is released — the reverse leaves a moment where the key is free in the DB but counted here, and a Skip-mode job arriving in it would be deleted although it could have run. The behaviours' PUBLIC constructors build private, instance-scoped instances (gate lease size 1) so direct construction stays correct; only the internal DI shims share the singletons. **Mutex Wait mode still requeues with `ScheduleTime = now`** and is NOT given a backoff: a future-dated `Enqueued` row is forbidden (`JobOutcome.RescheduledState`), and a future `Scheduled` row waits up to `ScheduledActivationInterval` (10s) per hop, which would serialize a key's jobs 10s apart. **The rate-limit lock is released BEFORE the handler runs** (`await using (lockHandle) { evaluate }` then `next()`): it was an `await using var` spanning `next()`, so admitted jobs on a key ran one at a time and other workers queued on the lock for the handler's whole duration; `AdmittedJob_LockReleasedBeforeHandlerRuns` is the guard. Rot guards: `RateLimitGateTests`, `ConcurrencyLocalHoldsTests` (NoDb), the cache/slot/two-server tests in `RateLimitTestsBase`, and the local-hold tests in `MutexTestsBase`; `LoadLab --scenario=RateLimit|Mutex` measures it.
