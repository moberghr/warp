# §8.26 — design notes (queue metrics)

> Full rationale, history, measurements and rot guards behind the condensed rule §8.26 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `project-specific.md` (2026-11-24).

**§8.26** **Queue metrics (queue-wait + backlog)** — the two job-system health signals beyond per-job execution time (§8.23/§8.24). **Always-on, no addon opt-in.** **(1) Queue-wait latency** measured at the worker claim site (`WarpWorkerService`/`WarpDispatcherWorker`, where `Enqueued → Processing` and the "Processing" `JobLog` is written): `waitMs = max(0, claimTime − Job.ScheduleTime)` (`ScheduleTime` advances on requeue, so wait is from requeue not original enqueue).

**Hot path sacred (§0.2/§6.1):** the increments are **staged on the worker and handed to the process-wide `WarpCounterBuffer` once the claim commits** — NO row, NO extra query, NO round-trip (they used to be `Counter` rows added to the existing claim-site `SaveChanges`; `CounterBufferFlusher` now writes one row per distinct key per `CounterBufferFlushInterval`, default 2s, and an UNGRACEFUL exit loses at most that window — a graceful stop flushes). Staging, not buffering directly, is what makes a rolled-back attempt contribute nothing: `BeginFinalizingTransactionAsync` clears the staging list, so an arm that re-finalizes after a failed commit cannot hand across the abandoned attempt's increments as well as its own. The always-on `WarpTelemetry.RecordQueueWait` meter fires unconditionally. Folds `Counter → CounterAggregator → Statistic` via `QueueWaitKeys` (`Warp.Core.Services`, `internal static`, prefix `qwait` / per-app `qwait-app`, tokens `count`/`dur` + `pct:{bucket}` histogram, same buckets as `JobStatsKeys`) so **avg/p95/p99 survive raw-row cleanup**; per-app slice carries NO histogram (p95/p99 read 0) to bound volume. **(2) Backlog depth + oldest-age** sampled OFF the hot path by `BacklogSampler<TContext>` (`Warp.Worker.Services`, an `IServerTask` like `CounterAggregator`; `LockKey = "warp:backlog-sample"`, `DefaultInterval => WarpServerConfiguration.BacklogSampleInterval` default 60s): one EF-LINQ grouped query `GroupBy(Queue).Select(Count, Min(ScheduleTime))` filtered `Kind==Job && CurrentState==Enqueued && ScheduleTime<=now` — served by the **existing** `(Kind, CurrentState, Queue, ScheduleTime)` index (no new index, §5.x, no raw SQL). Writes always-on `WarpTelemetry.SetBacklogSnapshot` (drives `JobQueueDepth`/`JobQueueOldestAge` ObservableGauges, `queue` tag only) + `qbacklog:` gauge `Statistic` upserts (`QueueBacklogKeys`; overwrite each tick — NOT `Counter`, so `CounterAggregator` doesn't double them; drained queues reset to 0). **Backlog is queue-GLOBAL, deliberately NOT app-sliced** (there is no `qbacklog-app`): an eligible-but-unclaimed job has no executor, and slicing by the *publishing* app is the per-creator metric §8.23 omits — a single cluster-wide sampler (lock `warp:backlog-sample`) sees all apps' enqueued jobs, so the global count is correct. **Meters (always emit, low-cardinality tags `queue` + `application` when set — group/PII off §1.2):** `warp.job.queue.wait` (Histogram ms), `warp.job.queue.depth` + `warp.job.queue.oldest_age_seconds` (ObservableGauges).

**Sink-respecting (§8.24):** both respect `WarpConfiguration.JobMetricsSink` — `Otel` SKIPS the Counter/Statistic writes (perf win), meters still carry the data.

**Multi-app (§8.23):** queue-**wait** is sliced by **executor** application under a disjoint namespace (`qwait-app`, first-segment-equality parsers reject it, existing keys unchanged, §8.6/§8.19); **backlog stays global** (see above). `GetQueueMetrics(application)` returns that app's wait alongside the queue's global backlog.

**Read side:** `IJobQueryService.GetQueueMetrics(string? application)` → `QueueMetricsModel`/`QueueMetricModel` (`Warp.Core.Models`) reads only the durable aggregates (resolves in any `AddWarp` process). API `GET {prefix}/api/queues/metrics` (`?application=` optional, no addons flag) — **retained as public read API, but the dashboard no longer consumes it**. The standalone **Queues** page was REMOVED in 6.x: `counterModel` already routed `qwait`/`qwait-app` AND `qbacklog` into one `queues` counter family, deliberately merging depth/oldest-age onto the same row as that queue's wait latency, so the page was a second rendering of the same two folds. The one thing it had that the family lacked — p99 — moved over: `FamilyDef.percentiles` is now a LIST (default `[0.95]`, client vitals `[0.75]`, queues `[0.95, 0.99]`), so a family can report several percentiles off one histogram. Do not reintroduce the page; add to the family instead. See §2.15/§8.23/§8.24, `website/docs/features/queue-metrics.md`.
