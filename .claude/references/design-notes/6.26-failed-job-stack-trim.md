# §6.26 — design notes (failed job's stored stack trace)

> Full rationale, history, measurements and rot guards behind the condensed rule §6.26 in `.claude/rules/`. Read on demand when changing this area.

**§6.26** **A failed job's stored stack trace ends where Warp called the handler** (`HandlerStackTrace.Trim`, applied in `FinalizationLogs.Build` and `ErrorOccurrenceFactory.FromException`, the two places the text is stored for every failed attempt). Under the generated dispatch an exception carries the whole chain below the handler: the generated call with the job type's full name (when the handler throws synchronously), every pipeline behaviour and the worker's `ExecuteJob`, each with a file path. 7.7's reflection call ended the trace at the handler, so 8.0 stored 1,302 characters where 7.7 stored 529 on the retry benchmark, and retries wrote 6% MORE WAL per job than 7.7 although every other write was smaller (`job_log` insert 732 -> 1,006 bytes of WAL per call, `error_occurrence` 985 -> 2,205). The frames from `GeneratedJobDispatcher` down are dropped per exception, so an inner exception keeps its own frames and the outer one its own; a trace with no generated frame (a handler the generator did not see) is stored whole. The error fingerprint is unaffected: it reads the top in-app frame, which is the first one. Do not store `error.ToString()` for a job failure anywhere else without the trim. Rot guard: `HandlerStackTraceTests` (NoDb; `Build_FailureThroughAPipelineBehaviour_StoresNoFrameBelowTheHandler` runs a real failure through the generated dispatch with a behaviour).
