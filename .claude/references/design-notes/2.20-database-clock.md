# §2.20 — design notes (database clock)

> Full rationale, history, measurements and rot guards behind the condensed rule §2.20 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `architecture.md` (2026-11-25).

**§2.20** **Cross-server times are the database's (#350).** Every DI-resolved `Warp.Worker` component takes its `TimeProvider` as `[FromKeyedServices(DatabaseClock.Key)]` (`DatabaseClock`, `Warp.Core`, registered in `AddServerHostCore` around the host's `TimeProvider`); host-built pieces (workers, dispatcher, flusher, monitor, task loops) get it from their host. Only `GetUtcNow` is corrected (local clock + the offset); timers and `GetTimestamp` stay local. The heartbeat statement writes `statement_timestamp()` / `SYSUTCDATETIME()` for the server's heartbeat, its instances and its lease renewals, stores `Server.ClockOffsetMs` (database minus the `now` the server passed) and returns the database time, which `Heartbeat` records into the clock (round-trip midpoint); `WarpServerRegistration` does one heartbeat right after inserting the row so the first tasks are already corrected. **Measured only while the periodic heartbeat is on** (`HealthCheckInterval != null`) — fake-time tests run with it off, and correcting would undo their clock. Past `ClockSkewWarningThreshold` (1 s): Warning + `ClockSkewDetected` (= 9) once per excursion (`ClockSkewState`). A new server component that takes a plain `TimeProvider` compares other servers' times on its own clock — `DatabaseClockTests.Constructors_EveryDiResolvedServerComponent_TakesTheDatabaseClock` fails on it; add host-built types to its allowlist only. **Mixed 7.7/8.0 clusters (REMOVE in the release after 8.x, with `LegacyTaskLock`):** a 7.7 server writes and compares its LOCAL clock, so while one is alive an 8.0 server does too — mixing the two was worse than pure 7.7 (a singleton lease written on one clock looked expired on the other). `LegacyServerPresence` (`Warp.Core`, internal singleton, starts **alive = true**) is reported by `WarpServerRegistration` before any task or worker runs (an EF `Any` over `Server` rows without `CoordinationVersion`, the claim's own question) and then by every `ClusterTaskScheduler` claim (`ClusterTaskClaims.LegacyServersAlive`); `DatabaseClock` reads it through its internal ctor/`LegacyServers` property. While alive: `GetUtcNow` applies NO offset (the offset is still measured, stored as `ClockOffsetMs` and warned on), and `HeartbeatAsync(..., writeLocalTime: true, ...)` writes the passed `now` for `LastHeartbeatTime`, instance heartbeats and lease renewal (and compares lease expiry with it), as 7.7 did — a second cached statement per provider rather than a CASE, so each keeps one plan and the 7.7 variant deletes cleanly. The public `DatabaseClock(TimeProvider)` ctor knows no legacy servers and always corrects. **A 7.7 row counts for as long as it EXISTS; its heartbeat is never compared** — it is written on the 7.7 host's clock, and judged against the database's a database ahead of the hosts by `HealthCheckTimeout` read every live 7.7 server as gone: the legacy lock was dropped, the correction applied, `StaleJobRecovery` requeued jobs running on 7.7 and `ServerCleanup` deleted the live rows. A dead one's row is removed by `ServerCleanup` (on the hosts' clock while this holds). Rot guard: `ClusterTaskQueriesTests.ClaimClusterTasks_ServerFromBeforeTheLeaseWithAnOldHeartbeat_IsAliveUntilItsRowIsGone`. **`AddWarp`-only processes:** with a provider registered (`IWarpSqlQueries<TContext>` resolvable) `ApplicationHeartbeatHost` writes `ApplicationInstance.LastHeartbeatAt` in ONE `ExecuteUpdate` (was SELECT + UPDATE) whose value is `CASE WHEN EXISTS(Server without CoordinationVersion) THEN <local now> ELSE <database now> END` (`DateTime.UtcNow` inside the LINQ is translated to `GETUTCDATE()`/`now()`), right after registering and on every beat — never worse than 7.7, whose sweeper compares its own clock. Without a provider (EF only) it writes local time. It has no `DatabaseClock` (that would take a second statement per beat). Still not covered: a publisher's `ScheduleTime`. Guards: `ClockSkewIntegrationTests` (both DBs, a server 3 h ahead: no requeue, no server removed, no early activation, offset stored; with a 7.7 server alive: no correction, own row carries its local time), `DatabaseClockTests`, `HeartbeatSqlQueryTests.HeartbeatAsync_DatabaseTime_*`/`HeartbeatAsync_LocalTimeWhileAServerFromBefore80IsAlive_*`, `ApplicationRegistryTests.Heartbeat_ClockHoursBehind*`. **The corrected clock carries the measurement's error** (up to half the heartbeat's round trip, re-measured every beat), so a test that compares a time a server component stamped (a claim, a "Processing" log row) with the test's own `DateTime.UtcNow` runs with `HealthCheckInterval = null` and drives the heartbeat by hand, which leaves the correction off: `PauseIntegrationTests.PauseServer_Resume_JobsGetProcessed` read a claim stamp 31 ms before its own resume on CI SQL Server.
