# §6.22 — design notes (postgres server pool)

> Full rationale, history, measurements and rot guards behind the condensed rule §6.22 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `performance.md` (2026-11-25).

**§6.22** **On PostgreSQL the server context opens on Warp's own pool, without the connection reset** (`PostgreSqlServiceConfiguration.BuildServerConnectionString`: the DbContext's connection string with `Application Name` suffixed `:warp-server`, `No Reset On Close`, `MinPoolSize` 0). Every server-task run, claim, completion and keep-alive opens a scope, and on the shared pool each checkout cost a `DISCARD ALL`: measured with the idle probe (1 server, 5 workers, 120 s), 389 statements a minute with the shared pool against 271 with Warp's own (-30%); every `DISCARD ALL` was gone. The reset clears nothing on these connections: Warp sets no session state on them (no `SET`, temp tables or prepared statements; advisory locks are transaction-scoped, and the session-scoped ones live in the lock pool, §2.18), and Npgsql rolls back a transaction left open on a returned connection regardless. Do not add session state to server-context connections without restoring the reset. Like the lock pool, it RAISES peak connections (a second pool sizes to its own demand) and is not applied to a host's own `NpgsqlDataSource`, which cannot be forked; those hosts keep the shared pool and its reset. SQL Server has no equivalent statement (its reset rides the next request). Rot guard: `ServerConnectionPoolTests` (the derived string and the wiring).
