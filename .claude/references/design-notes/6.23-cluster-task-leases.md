# §6.23 — design notes (cluster task leases)

> Full rationale, history, measurements and rot guards behind the condensed rule §6.23 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `performance.md` (2026-11-25).

**§6.23** **Server tasks: one lease scheduler for cluster-wide tasks, one plain loop for the heartbeat.** Design, history and measurements: `docs/specs/2026-11-23-cluster-server-tasks.md`. What must stay true:
  - **Who runs a task is decided by a lease row, never by a lock attempt on every server.** A task with a `LockKey` has one `ClusterTask` row; `ClusterTaskScheduler` (one per server) claims every due task in ONE statement (`ClaimClusterTasksAsync`, `FOR UPDATE SKIP LOCKED` / `READPAST`) and runs what it won. Measured idle load (PostgreSQL, 5 workers): 389 statements a minute per server before; 161 for one server and 210 for two after. Do not reintroduce a per-task loop or a lock attempt for cluster-wide tasks.
  - **The heartbeat is not a cluster task.** A task without a `LockKey` runs on its own `PerServerTaskLoop`: wait the interval, run, log a failure. It writes nothing on success (`Server.LastHeartbeatTime` is its record) and has no dashboard task row. The `ServerTask` table is kept in the schema but no longer read or written (dropping it would be a breaking migration).
  - **One way to execute a task:** `ServerTaskRunner`. A `LocksWithTransaction` task runs in one transaction and `OnCommittedAsync` runs after the commit; a throw skips the hook. A task that took in-memory work for a pass gives it back when its scope is disposed without the hook having run (the `Orchestrator`'s finalized-parent hints: a failed commit or a run cancelled for a lost lease comes after `ExecuteAsync` returned). Rot guard: `ServerTaskRunnerTests.RunAsync_WorkRolledBackAfterTheOrchestratorReturned_GivesItsParentsBack`.
  - **Every time is the database's own** (`now()` / `SYSUTCDATETIME()`); a server's clock only decides how long it sleeps.
  - **An idle run writes nothing, except on a task that signals run.** The lease lasts until the task's next run, so it lapses on its own. A run that did work, failed, changed status, or was not recorded for a minute writes one completion (`CompleteClusterTaskAsync`), which frees the lease. A task with signals (`Orchestrator`, `MessageRouter`) writes that completion after every run, idle ones included: a signal on another server can claim the task only while the lease is free, and that server cannot tell a lease an idle run left behind from a run in progress, so a held lease turned the signal into a request nobody read until the lease lapsed (10–15 s at defaults, where 7.7 ran at once). One `UPDATE` per idle run of those two tasks for the whole cluster, whatever the server count (about +12 statements a minute at default intervals; the idle benchmark read it as +5.9% statements/s on PostgreSQL, past its gate). **Only while another server is alive**: the claim statement also returns whether a server other than the claimer heartbeated within the live window (`ClusterTaskClaims.OtherServersAlive`, both providers), and the scheduler skips the release when the last claim said no — no other server could claim the lease, and a signal on the lone server claims a lease of its own outright. A server that starts meanwhile waits at most one interval, until the holder's next claim sees it. The completion returns whether the task is then due at once; a release that left the next run where the claim put it resets nothing and wakes nobody, so no claim follows it. Do not remove the release to save the write, and do not add it to tasks without signals. Rot guards: `ClusterTaskSchedulerTests.PassAsync_SignalOnAnotherServerAfterAnIdleScheduledRun_RunsTheTaskThereAtOnce`, `RunningTask_IdleRunOfASignalTaskThatOnlyFreesItsLease_DoesNotWakeTheLoop`, `RunningTask_IdleRunOfASignalTaskOnALoneServer_KeepsItsLease`, `ClusterTaskQueriesTests.ClaimClusterTasks_OtherLiveServer_ReportsItButNotTheClaimingServerItself`.
  - **Due times sit on a grid:** the next run is the next multiple of the interval at least half an interval away, so tasks fall due together and one claim covers them. A renewal only ever extends a lease.
  - **The claim is sent only when a task is due** by what the last claim reported (`Entry.DueAt`); a pass woken by a signal or a finished run does not ask about the others. A pass that claims every task still returns a sleep until the next due time.
  - **A long run renews its lease every third of its interval; a renewal that finds another holder cancels the run.** A server that dies mid-run delays the task by at most one interval. A renewal that fails is retried at the next one (the catch is inside the loop: one transient failure used to end renewals for the rest of the run). On both providers a renewal never shortens or clears a lease: a task disabled mid-run (NULL interval) renews by the second, and intervals of any length are supported (`ClusterTaskQueriesTests.RenewClusterTaskLease_IntervalClearedWhileTheTaskRuns_NeverShortensOrClearsTheLease`, `..._IntervalLongerThanAMonth_ExtendsTheLease`).
  - **Signals** claim the task at once (`RequestClusterTaskRunAsync`, at most once per `ServerTaskSignalInterval` per task per server) or, when another server holds it, set `RunRequestedAt` for the holder's completion. A request from the server that holds the lease claims it outright: the scheduler asks only for a task it is not running, so that lease is one whose completion was not written (a failed write), and it must not hold the run back until the next tick. A signal that arrives while a run is finishing (after the completion read the rerun flag) is turned back into a signal for the next pass, and a signal whose request statement failed is put back; both used to be lost until the task's next run, which with a distant sweep left a message `Processing` (`MessageIntegrationTests.GivenNoParentSweepDue_*` failed on CI on it). A signal for a task running here reruns it after the run with no extra write.
  - **The signal hold (§6.18) is cluster-wide:** a run a signal started holds its lease for the rest of `ServerTaskSignalInterval` (renewal still running) before it completes, so signals on any server meanwhile fold into one rerun; that completion is always written, so a request from elsewhere is not left behind the lease. A run on schedule does not hold, and a run that did work on a `RerunImmediately` task skips the hold (`ClusterTaskTimings.HoldAfterRun`). The recorded duration excludes the hold.
  - **No startup delay.** Tasks are claimed from the first pass; #346 measured the random startup delay as moving work into the drain rather than removing it.
  - **Rolling deploys:** while a server without `Server.CoordinationVersion` is alive, each run also takes the task's old lock (`LegacyTaskLock`, the only call site). Remove it in the release after 8.x. The scheduler assumes such a server is alive until its first claim says otherwise, because the first pass honours pending signals before it claims (`PassAsync_SignalBeforeTheFirstClaimWhileAnOldServerHoldsTheOldLock_TaskDoesNotRun`).
  - **Registration is one insert-if-absent statement** (`RegisterClusterTasksAsync`: `INSERT ... ON CONFLICT DO UPDATE` on PostgreSQL, `MERGE ... WITH (HOLDLOCK)` under a transaction-scoped `sp_getapplock` on SQL Server): servers starting together each register every task, and the loser of an insert updates the interval. It was an EF insert caught on `DbUpdateException` and retried, and EF logged every lost insert at Error. Guard: `ClusterTaskQueriesTests.RegisterClusterTasks_AnotherServerInsertsTheRowMeanwhile_UpdatesItInsteadOfFailing` (both providers; fails with a plain insert).
  - **Both providers implement the five statements** (`PostgresClusterTaskSql`, `SqlServerClusterTaskSql`; required members of `IWarpSqlQueries`). A change to one goes into both. They read result rows by position, not `SqlQueryRaw`, which maps columns through the calling context's naming convention.
  - Rot guards, both databases: `ClusterTaskQueriesTests` (each statement, the grid, a renewal never shortens, a request claims its own idle lease), `ClusterTaskSchedulerTests` (one server per tick with N=2, idle runs stay on their interval and wake nobody, a lost lease cancels the run, the legacy lock, signals folded during a hold, no hold on schedule), `ServerTaskRunnerTests` (transaction, hook after commit, no hook on a throw, the legacy lock skips the body when held), `PerServerTaskLoopTests` (nothing written on success, a failure logged, a signal ends the interval wait), `ClusterTaskDashboardTests`.
