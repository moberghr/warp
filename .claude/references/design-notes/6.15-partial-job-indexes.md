# §6.15 — design notes (partial job indexes)

> Full rationale, history, measurements and rot guards behind the condensed rule §6.15 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `performance.md` (2026-11-25).

**§6.15** **The job table's claim, scheduled, parent and expiry indexes are partial** (`WarpPartialIndexes`, applied at the end of `ApplyWarpModel`): the claim index `(Kind, CurrentState, Queue, ScheduleTime)` holds only `CurrentState = Enqueued`, `(CurrentState, ScheduleTime)` only `Scheduled`, `(ParentJobId, CurrentState)` only rows with a parent, `(ExpireAt)` only rows with an expiry. A non-HOT update (every state transition is one: `CurrentState` is indexed) writes a new entry into EVERY index of the table unless the index is partial and the new row falls outside it, so a job's insert, claim and completion wrote 21 index entries, most of which no reader ever looked at. Measured on the load lab (10,000 jobs, dispatcher, PostgreSQL): 3,777 to 2,938 WAL bytes per job and 78 to 61 buffer hits per job; the `--tune=partial` lab lever reproduces it against whole indexes. The filters are SQL naming the columns as the host's naming convention spells them, quoted with double quotes (PostgreSQL always accepts them; SQL Server does with QUOTED_IDENTIFIER on, which a filtered index requires anyway). Readers must keep stating the predicate the index needs: the claim and scheduled activation compare `CurrentState` to a LITERAL (a parameter would stop SQL Server using a filtered index, and a PostgreSQL generic plan too), and the parent and expiry lookups compare with `=`/`<`, which imply `IS NOT NULL`. The dashboard listing index `(Kind, CurrentState, CreateTime)` stays whole: it lists every state. Upgrading recreates four indexes, which locks a large job table while it runs; release note. Hosts avoid the lock with `migrationBuilder.RecreateWarpJobIndexesOnline(TargetModel)` (`WarpMigrationBuilderExtensions` in each provider package: `CREATE/DROP INDEX CONCURRENTLY` + rename on PostgreSQL, `DROP_EXISTING = ON, ONLINE = ON` on SQL Server with an `ONLINE = OFF` fallback by engine edition), which reads names, columns and filters from the migration's model through the public `WarpJobIndexes.FindPartial` (by entity NAME, so a snapshot-built model works); `WarpPartialIndexes` and it share one property list. Guards: `OnlineJobIndexStatementsTests` (NoDb), `OnlineJobIndexMigrationTestsBase` (both databases, populated table with the 7.7 indexes). Rot guard: `JobPartialIndexTests` (both namings); the plan tests (`ClaimPlanStabilityTests`, `OrchestratorReadyParentsPlanTests`) run against the partial schema.
