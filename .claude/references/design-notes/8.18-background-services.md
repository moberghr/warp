# §8.18 — design notes (background services)

> Full rationale, history, measurements and rot guards behind the condensed rule §8.18 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `project-specific.md` (2026-11-24).

**§8.18** `WarpBackgroundService` is a base part of Warp (no addon opt-in) in `Warp.Core.BackgroundServices`. `AddWarp<TContext>` always contributes the four entities **and** registers `IBackgroundServiceQueryService` (so dashboard-only / publisher-only processes can serve `/api/services` without starting a server); `AddWarpServer<TContext>` adds the server-side host, lease coordinator, state service, and log store, plus the job worker by default. **The worker is a component of the server**: `opt.DisableWorker()` (sets `RunWorker = false`; `AddWarpServer` rejects `RunWorker = true` with zero total workers) yields a service-only server — background services + supporting server tasks (`Heartbeat`/`ServerCleanup`/`ExpirationCleanup`) plus the cluster-locked aggregation folds (`StatisticRollup`/`MetricRollup`/`CounterAggregator`/`ErrorGroupAggregator`/`SloEvaluator`, all registered in `AddServerHostCore` — since 7.5.0; before that the last three ran only with a worker, so a `DisableWorker()` server now runs them: a release-note behaviour change, no data change) without the job worker or the six job-only tasks (`StaleJobRecovery`/`BacklogSampler`/`RecurringJobScheduler`/`ScheduledJobActivation`/`Orchestrator`/`MessageRouter`, registered by `AddWarpServerCore` after the `!runWorker` return), so it claims no job (provider still required). `WarpServerRegistration` creates no groups when `!RunWorker` (and skips `WorkerCount == 0` groups otherwise), so a service-only server leaves no `Worker`/`WorkerGroup` rows. `AddWarpWorker`/`WarpWorkerConfiguration`/`WarpWorkerBuilder` were removed in 2.0 (renamed to `AddWarpServer`/`WarpServerConfiguration`/`WarpServerBuilder`). Users register their own services with `opt.AddBackgroundService<T>()` (single type parameter on the non-generic `IWarpBuilder` receiver). Subclass `WarpBackgroundService`, override `Scope` (`PerServer = 1` — default, one instance per server; `Singleton = 2` — cluster-wide lease). Storage: `BackgroundServiceDefinition` (one row per service name), `BackgroundServiceInstance` (one per server-service pair), `BackgroundServiceLease` (singleton coordination, 30s TTL renewed in `Heartbeat`), `BackgroundServiceLog` (captured user + lifecycle events; FK cascade on instance delete). All in `Warp.Core.Data.Entities`. Worst-case singleton failover ~30s on hard-kill / ~0s on graceful shutdown (lease deleted in `StopAsync` before waiting on user code). Orphaned `Definition` rows (renamed/removed services with no live `Instance`) are deleted by `ExpirationCleanup` once `LastSeenAt > WarpConfiguration.BackgroundServiceDefinitionOrphanGrace` (default 2 min). **Captive-scoped-dependency foot-gun**: subclasses are singletons — inject `IServiceScopeFactory`, not `DbContext`; `ValidateScopes=true` catches it at startup. Log capture is auto-wired (`BackgroundServiceLoggerProvider`) with `MinLogLevel` (default Information), 100/s rate cap, 4KB message truncation, 1000-row/7-day retention. **§1.2 PII responsibility** applies to log output. Telemetry counters: `warp.background_services.started` (tag: `service_name`), `warp.background_services.faulted` (tags: `service_name`, `exception_type`), `warp.background_services.lease_lost` (tag: `service_name`), `warp.background_services.restarts` (tag: `service_name`). Worker hot path untouched (§0.2/§6.1) — separate `BackgroundServiceHost<TContext>`. See §2.13, `website/docs/features/background-services.md`.
