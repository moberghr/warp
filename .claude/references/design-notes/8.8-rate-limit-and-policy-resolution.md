# §8.8 — design notes (rate limit and policy resolution)

> Full rationale, history, measurements and rot guards behind the condensed rule §8.8 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `project-specific.md` (2026-11-24).

**§8.8** Rate limiting is opt-in via `opt.AddRateLimit()`. Three styles (`Style`, from 1): `Fixed` (wall-clock window, floor-aligned to global UTC ticks), `Sliding` (rolling window over last N starts, defensively trimmed), and `TokenBucket` (**paces** rather than caps — tokens refill continuously at `count/perSeconds` per second up to a burst of `count`; each start consumes one; a fresh key starts full; when empty a `Wait`-mode start reschedules to the next token-refill instant, so a backlog trickles at the steady rate and never over-admits). `TokenBucket` stores the fractional token count + last-refill instant in `RateLimitBucket` (written only on accept); cross-style bucket-row reads degrade gracefully (bad/foreign payload → empty, never throws). Two policies (`Mode`): `Skip` (default — `Deleted`) and `Wait` (rescheduled via `JobOutcome.RescheduledState`). `perSeconds` capped at `MaxWindowSeconds` (7 days). Lock is released after check-and-increment — **not** held during handler execution (unlike Mutex). Live state in `RateLimitBucket` entity. Lock-contention reschedule has 100–500ms jitter. **DB push does NOT accelerate Wait-mode reschedules** — they land in `State.Scheduled` and depend on `ScheduledJobActivation` polling, so the effective release cadence (including `TokenBucket` refills) is floored at `ScheduledActivationInterval`. **Ordering: `AddConcurrency()` before `AddRateLimit()`** so mutex rejects don't waste tokens.

**Attribute placement — the policy axis (supersedes #242):** `[RateLimit]`, `[Mutex]`, `[Semaphore]`, `[Timeout]`, `[Retry]`, `[CircuitBreaker]` are legal on the request/job/message **contract**, on a job/message **handler** class, or on **both** — precedence is **ranked, not forbidden**, and resolution happens in exactly ONE place: `PolicyResolver` (`Warp.Core.Policies`), called from each pipeline behaviour at execution. Rungs: **explicit metadata already on the row** (a publish-time `WithMutex`/`WithRetry`/…, or what a previous attempt stamped) → **handler class** → **contract** → **global options**. Resolution is **rung-major, not attribute-major** — the handler rung is searched for the whole FAMILY before the contract rung, so a handler `[Semaphore]` beats a contract `[Mutex]` (they share one metadata slot); within a rung the family order is fixed (`Mutex` before `Semaphore`). **The winner is stamped into the job's metadata and never re-resolved** (`meta.X != null` ⇒ return): whatever the row says is what executes. The stamp reaches the DB with the attempt's finalizing write (no extra hot-path round-trip, §0.2/§6.1), so an `Enqueued` row is blank and a `Processing` row has resolved but not yet persisted — assertions must read after finalization. A requeue/retry therefore cannot change policy mid-flight and a redeploy never reshapes bound jobs — the debugging contract is "open the job, read its policy". Stamp-once is **per family, not per job**: a short-circuiting behaviour (Skip/Wait concurrency, a throttled rate limit) returns before the behaviours nested inside it resolve, so a requeued row carries the family that decided its fate and resolves the rest at the next attempt — do not read "stamped" as "the whole policy is frozen". Both worker paths persist metadata on the FAILURE path too, not just when an outcome was set, or a stamp made on a throwing attempt would be lost and the next attempt would re-resolve. **Global defaults are deliberately NOT stamped** (process config, read live, identical for every job — absent metadata reads as "the default applies"). **Publish stamps nothing except `Timeout(Scope = Total)`** — `ConcurrencyPublishBehavior`/`RateLimitPublishBehavior`/`RetryPublishBehavior` were DELETED; stamping the contract at publish is exactly what made the handler rung unreachable (#236's shape). Total is the one carve-out: a wall-clock budget from enqueue whose `DeadlineUtc` must exist before any handler is known (§8.31 reads it pre-execution), so it stays **contract-only** and publish-stamped, a handler `[Timeout]` under a Total-scoped global default is **inert** (logged once per request type), and `Scope = Total` on a handler fails the BUILD (`WARP002`) and is **inert at runtime** (`TimeoutStamp.TotalOnHandler`, logged once per request type) for handlers the generator cannot see — never a throw: the resolver runs inside the pipeline, where an outer Retry reads the exception as a handler failure and burns the whole budget on a static misconfiguration. Every policy behaviour shares one prologue, `PolicyResolver.Bypasses(request, jobContext)`: non-job/message shapes, **`JobId == Guid.Empty`** (an in-memory `Send` of an `IJob`-shaped type — no row to skip/reschedule, so gating it would return a silent `default!`), and `IPolicyExemptHandler` all pass straight through. A retry policy is **atomic per rung** — `StampRetry` takes `MaxRetries` AND `RetryDelays` from whichever rung wins and never merges fields across rungs, so `WithRetry(5)` at publish claims the whole policy and the global schedule applies beneath it rather than the attribute's. The sentinel is **either explicit field** (`MaxRetries != null || RetryDelays != null`), symmetrically — an explicit schedule claims the rung and takes the global count beneath it just as an explicit count takes the global schedule. Keying it on `MaxRetries` alone let the attribute overwrite a caller's explicit `RetryDelays`: a delays-only row is **reachable** — `JobParameters.Configure<IRetryMetadata>` and `JobParameters.Metadata` are public, so `WithRetry` is not the only way in. **Concurrency and RateLimit deliberately do NOT take that symmetric sentinel** — they key on `ConcurrencyKey` / `RateLimitKey` alone and stamp all-fields-or-none. Retry has a global default for both of its fields, so a delays-only row is a working policy that must claim its rung; concurrency and rate limit have no global default, so a keyless partial row is inert and honouring it as a rung would mean "no policy" rather than "this limit". The key is identity, and merging an attribute's key onto a caller's count would put two jobs on one key disagreeing about its size.

**A cancelled attempt is not a spent retry:** `RetryPipelineBehavior` rethrows an `OperationCanceledException` whose incoming token is cancelled (a graceful `DeleteJob` mid-flight) BEFORE any retry bookkeeping, because the worker's cancel arm now persists `Metadata` to keep the stamp and a `RetriedTimes` bump would otherwise survive on the `Deleted` row and start a later `RequeueJob` one attempt down. The circuit breaker's default group for a routed message child is its **handler** type (a job's stays the request type). The stamp is persisted by **all three** worker finalizing arms — success, `catch (Exception)`, and the graceful-cancel arm — in both `WarpWorkerService` and `WarpDispatcherWorker` (§8.33 lockstep). **There is NO startup validation** — `ValidateAddonAttributesOnHandlers` and `TimeoutStartupDefaults` were removed; a misconfigured policy fails its own job, not the process. Build-time diagnostics keep only what no execution path can honour: `WARP001` (policy attribute on a stream / in-memory-request handler) and `WARP002` (handler `Scope = Total`). **Messages behave exactly like jobs**: the router copies only explicit metadata to children, and each child resolves handler-then-contract at its OWN first execution — so a contract declaration is the shared default across the fan-out (children that declare nothing contend on the one key) and a handler declaration overrides it for that handler's children alone. **`CircuitBreaker` is resolved but never stamped** — its threshold/duration describe a shared dependency GROUP whose live state is a DB row, and two jobs in one group must not disagree about when the circuit opens.

**Trap:** `IJobContext.GetMetadata<T>()` COPIES the backing dictionary and re-points `IJobContext.Metadata` at the copy, so a proxy held across `next()` is orphaned and writes to it vanish (this silently disabled `RetriedTimes` and produced infinite retries) — re-read after the inner call, never cache across it. Self-handling jobs (request == handler) stay exempt. Handlers implementing `IPolicyExemptHandler` (saga proxies) are skipped by ALL policy behaviours — attributes, metadata and global defaults alike. A Skip-mode deletion of a routed child counts as SETTLED for parent finalization (`Orchestrator` readiness treats `Deleted` like `Completed`/`Failed`; skipped work is not failed work).
