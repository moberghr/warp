# §8.29 — design notes (error grouping)

> Full rationale, history, measurements and rot guards behind the condensed rule §8.29 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `project-specific.md` (2026-11-24).

**§8.29** **Error grouping / "Issues"** turns raw error rows from the four already-persisted surfaces — failed-job `JobLog`, endpoint 5xx `EndpointCallLog`, adapter-call `AdapterCallLog`, browser `ClientEventLog` — into durable **`ErrorGroup` "issues"** (Sentry-lite: one row per real problem, not per occurrence, with count/first-last-seen/trend/sample and an `Unresolved/Resolved/Ignored` lifecycle). **Always-on Core feature** (no addon opt-in, like queue metrics §8.26); `WarpConfiguration.ErrorGroupingInterval = null` disables it (byte-for-byte today's behavior).

**Write path is inbox-drain, zero hot-path cost (§0.2/§6.1):** `JobLog`/`*CallLog` have no `(discriminator, Timestamp)` index and scanning them would write-amplify hot inserts, so instead each source **appends one `ErrorOccurrence` inbox row** (transient, write-optimized, self-clearing — the `Counter` pattern): **jobs** append in the **existing finalization `SaveChanges`** (no fingerprint CPU on the worker, no round-trip). NOTE it is a ROW and stays one — unlike the queue-wait counter §8.26, which moved into the in-memory buffer: an occurrence must survive the process, so it cannot follow the counter. **Endpoint** occurrences — from Warp endpoints AND host endpoints opted in via `WithWarpObservability()`/`[WarpObserved]` (§8.21; their identity is the same bounded `METHOD /template`) — are appended by `EndpointCallFlusher` (NOT `WarpInboundObservabilityMiddleware`, which only hands the record to the recorder) — in the same `SaveChanges` that drains the call, gated on `ErrorGroupingInterval`, and independent of whether the call-log ROW is written, so 4xx groups still exist under `RecordCalls=FailuresOnly`. The corollary: an `Otel`-only endpoint sink registers no recorder and no flusher, so it produces **no endpoint issues** (§8.24). **Adapter/client** append in their flushers too. **`ErrorGroupAggregator<TContext>`** is an `IServerTask` (§2.3, like `CounterAggregator`; `LockKey="warp:error-grouping"`, cadence `WarpConfiguration.ErrorGroupingInterval` default **60s**) that **drains-and-deletes** the inbox (exactly-once by construction — no cursor), computes fingerprints **off the hot path**, and **upserts** `ErrorGroup` (`Count += n`, `LastSeenAt`, `LastSample`, `SampleTraceId`; `FirstSeenAt`/`Title`/`Culprit` on insert) + folds an hourly `errorgroup:{fingerprint}:count` **Counter** (trend → `Statistic`, §6.2, **survives raw-row cleanup** §8.22). **Fingerprint** (`ErrorFingerprint`, `Warp.Core.ErrorGrouping`, pure + unit-tested) = `hash(source + exception-type + locus)` → 32-hex; **message is normalized OUT of identity** (digits/GUIDs/hex/quoted literals → `<num>/<guid>/<hex>/<str>`) so message-varying occurrences group and the normalized message is the **PII-safe `Title` (§1.2)**.

**Fine (stack-frame) grouping:** stack-bearing sources (job, client) use the **top in-app stack frame** (first frame not matching the `InAppNamespaceDenylist` — `Warp.*`/`System.*`/`Microsoft.*`/`Npgsql.*`, editable — so two bugs in one handler are two issues); stackless sources (endpoint, adapter) use route/operation; **`Source` is part of identity** (a browser `TypeError` ≠ a server exception).

**What counts per source:** **jobs** count **every** caught exception — retry attempts AND terminal (`FinalizeJobState` has `e` either way, so flaky handlers are visible); **endpoints** count `Outcome=Failed` (5xx/unhandled: type+route) **and any 4xx** (`status + route` groups, `Kind=StatusCode`) — 4xx are **default-filtered** in the UI and **kept OFF the reliability SLI** (§8.21 stays 5xx-only; issue membership ≠ error rate); **adapters** count `Failed` only (Throttled/CircuitOpen excluded — expected backpressure); **client** counts `Type=Error` only. **Entities** (`Warp.Core.Data.Entities`, §8.13; **always-in-schema §2.11**; mirrored by `WarpServerContext` §2.14): `ErrorGroup` (`Fingerprint` unique, `Source` `ErrorSource {Job=1,Endpoint=2,Adapter=3,Client=4}`, `Kind` `ErrorKind {Exception=1,StatusCode=2}`, `ExceptionType`, `Title`, `Culprit`, `StatusCode?`, `Application?`, `FirstSeenAt`, `LastSeenAt`, `Count`, `LastSample` raw+truncated §1.2, `SampleTraceId?`, `Status` `ErrorGroupStatus {Unresolved=1,Resolved=2,Ignored=3}`, `StatusChangedAt?`; enums from 1 §8.11) + `ErrorOccurrence` (the transient inbox; drained+deleted each tick — a defensive orphan sweep in `ExpirationCleanup` clears any past a grace, like the webhook stuck-recovery).

**Lifecycle (Sentry-lite):** **new** issue = a UI **"new" badge** only (not an alert — a fresh deploy mints many new types, paging on each is noise); **Resolve/Ignore** via `IErrorGroupCommandService.SetStatus(fingerprint, status)` (mutex + structured `LogInformation` audit, mirrors `SagaCommandService.ForceComplete`; `Ignored` still counts, hidden from the default view); **regression** — a `Resolved` group re-opens (→`Unresolved` + "regressed" badge) **ONLY** on an occurrence with `Timestamp > StatusChangedAt` (so pre-resolve inbox backlog can't false-reopen) and that fires **`WarpEventType.IssueRegressed`** (`Warp.Core.Enums`, from 1 §8.11) dispatched **post-commit from the aggregator's `OnCommittedAsync`** (§8.25 — never `ExecuteAsync`; opt-in/inert notifier seam, zero registered = no-op); **`Ignored` never auto-re-opens**. **Cardinality guard** (§8.19/§8.27 — critical because the client source is fed from the public ingest endpoint, hostile input): `MaxDistinctErrorGroups` (default **2000**, per source + app when app-sliced) collapses overflow into a per-source `{other}` group (still counted, keeps a sample; one-time warning).

**Read/UI:** `IErrorGroupQueryService` registered by **`AddWarp` itself** (resolves dashboard-only/publisher-only, §8.27/§8.28); metrics from durable aggregates survive raw-row cleanup, recent occurrences degrade to empty once swept. Always-shown built-in **Issues** page (`/issues` — grouped list: source badge, count, trend sparkline, status chip, new/regressed badges, filters source/status/application + a 4xx toggle) + detail (`/issues/:fingerprint`: title, raw sample stack, hourly trend chart, occurrences → trace, Resolve/Ignore).

**Diagnostic detail:** `FromException` **unwraps** `TargetInvocationException`/`AggregateException` to the real inner cause (the mediator invokes handlers via reflection, so the raw type is the wrapper — group on the cause, keep the full wrapper as the sample); the job **culprit is the short type name** (`WarpTelemetry.GetShortTypeName`), not the assembly-qualified string; occurrences carry `Version`/`Environment` (`ApplicationVersion`/`ApplicationEnvironment`) and the group records `FirstSeenVersion`/`LastSeenVersion`/`Environment` (tie an issue to a deploy); and `ErrorGroup.RecentSamples` is a rolling capped-10 JSON list (`{traceId,timestamp,message,version}`, newest-first, gated on `CaptureErrorSamples`) the detail renders as a walkable per-occurrence timeline. **Both worker paths feed the inbox** — `WarpWorkerService.FinalizeJobState` AND `WarpDispatcherWorker` (via `PendingCompletion.Occurrence` → `CompletionBatch`); a dispatcher-mode integration test (`UseDispatcher=true` → failed job → group) guards the second path.

**Navigation:** forward is shipped — issue→trace via a stored `SampleTraceId` linking into the unified trace view (§8.28), where every span (job/endpoint/adapter/client) already links to its own detail, so an issue reaches all of its related surfaces. **Reverse nav (a source detail page → its issue) is a planned follow-up** — the fingerprint is a pure function of the already-loaded row, so a detail page can recompute it on-read (no stored `Fingerprint` column, no hot-path change) and show a "Part of issue" chip; not built in the 3.9 slice. API `GET {prefix}/api/issues`, `GET .../issues/{fingerprint}`, `POST .../issues/{fingerprint}/status`.

**Config:** `WarpConfiguration.ErrorGroupingInterval` (60s, null=off), `ErrorGroupRetention` (age by `LastSeenAt`, 30d), `ErrorGroupRetentionCount` (count, null=off), `MaxDistinctErrorGroups` (2000), `CaptureErrorSamples` (true — raw truncated sample; Title stays normalized/PII-safe), `InAppNamespaceDenylist`. **Retention (§8.22)** swept by `ExpirationCleanup` (age + count + the orphan-occurrence sweep); trend `Statistic`s outlive the groups.

**Multi-app (§8.23):** `ErrorGroup.Application` = **executor** app for jobs (execution attribution), source app otherwise; disjoint counter namespace `errorgroup`/`errorgroup-app` (first-segment-equality safe, §8.6/§8.19); `?application=` filter.

**Sink (§8.24):** Otel-only sources write no rows → no inbox rows → no issues from them (jobs always feed — they always persist `JobLog`; disable via `ErrorGroupingInterval = null`). Worker hot path untouched (§0.2/§6.1). See §2.15/§8.19/§8.21/§8.27, `website/docs/features/error-grouping.md`.
