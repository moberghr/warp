# §8.28 — design notes (unified trace)

> Full rationale, history, measurements and rot guards behind the condensed rule §8.28 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `project-specific.md` (2026-11-24).

**§8.28** **Unified trace view** — a single screen showing *everything* that happened for one trace id: the browser request, the server endpoint call it hit, the jobs that endpoint spawned, and the outbound adapter calls those jobs made — a local, DB-backed Jaeger/Tempo-lite for the rows Warp already persists. **The key insight: Warp already stores spans.** A `Job` is a span (`TraceId`, `SpawnedByJobId` = parent, `CreateTime`, terminal state), an `EndpointCallLog` is a span (`TraceId`, `Timestamp`, `DurationMs`, `Outcome`), an `AdapterCallLog` is a span (`TraceId` — **string**, `"N"`-form — `Timestamp`, `DurationMs`, `Outcome`), and a `ClientEventLog` of `Type = Request` is a span (`TraceId`, `Timestamp`, `Value` = client-measured duration). So the unified trace view is built by **unioning those existing rows on their shared trace id — NO new `Span` table, NO `ActivityListener` collector, NO hot-path span capture** (an earlier "local tracing" batch that added a `Span` entity + `SpanKind`/`SpanStatus` enums + retention was deliberately reverted once this was understood — do not reintroduce it). **`ITraceQueryService.GetTrace(Guid traceId)` → `TraceOverviewModel?`** (`Warp.Core.Services` / `Warp.Core.Models`, registered by `AddWarp` itself like `IAdapterQueryService`/`IEndpointQueryService`, so it resolves in dashboard-only/publisher-only processes) fetches each source with `AsNoTracking` `.Select()` projections (§5.3/§6.4), maps each to a `TraceSpanModel { Source ("client"|"endpoint"|"job"|"adapter"), Id, Name, StartTime, DurationMs?, Status, IsError, ParentId? }`, and returns them ordered by `StartTime` (null if the trace has no rows). Adapter rows join on `traceId.ToString("N")` (their `TraceId` is a string); only jobs carry a `ParentId` (`SpawnedByJobId`) — the other sources are roots.

**Job execution timing comes from `JobLog`, not the `Job` row:** the `Job` row has no execution-duration column, but the worker already persists per-attempt timing — each terminal `JobLog` (Completed/Failed/Cancelled, via `FinalizationLogs`) carries the handler's `DurationMs` at its `Timestamp`. `GetTrace` does a two-step fetch (job ids → their `DurationMs != null` logs, §5.2 — no subquery-in-projection) and maps the **latest** such log per job (retries: last execution wins) to `DurationMs = log.DurationMs`, `StartTime = log.Timestamp − DurationMs` (the real execution window, so a job bar nests over the adapter calls it made). Falls back to the `CreateTime` marker (`DurationMs = null`, a placeholder `—`) when the logs have aged out (`JobLog` retention) or the job hasn't finished — graceful degradation, same stance as the other sources. Endpoint/adapter/client spans have precise timing from their own rows. Read-only union — no writes, no new schema, worker hot path untouched (§0.2/§6.1).

**Dashboard:** `TraceWaterfall.tsx` renders the spans as a time-ordered Gantt (source badges — client=green, server=slate, job=blue, outbound=purple; bars positioned on a shared min-start→max-end axis; job indentation via `ParentId`; error bars in `bg-destructive`; per-span detail links — job→`/detail/{id}`, client→`/client/events/{id}`), injected **above the existing job-DAG ReactFlow graph on `/trace/{traceId}`** (`TracePage.tsx`) — the DAG shows job parent/child structure, the waterfall shows the cross-source timeline. `GET {prefix}/api/traces/{traceId}` (distinct from the pre-existing `trace/{traceId}` job-DAG endpoint). Reachable from the session timeline (§8.27, request/server rows link to `/trace/{traceId}`) and any job/endpoint/adapter detail page.

**Rollout stance (the user's framing):** save it all locally for near-Jaeger experience on your own DB; switch to an external collector (OTel is always emitting, §8.24) once data volume makes the DB too slow. See §2.15/§8.19/§8.21/§8.27, `website/docs/features/client-observability.md`.
