# §2.7.1 — design notes (scope per send)

> Full rationale, history, measurements and rot guards behind the condensed rule §2.7.1 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `architecture.md` (2026-11-25).

**§2.7.1** **Scope per send (#321, opt-in `opt.Mediator.ScopePerSend`, default off).** `AddWarp` registers `IMediator` through a factory that reads the merged `WarpConfiguration.Mediator` (`WarpMediatorOptions`, a record so `WarpConfigurationMerge` compares it by value) at resolve time and returns either `Mediator` or the internal `ScopePerSendMediator`. The latter creates an async scope per `Send`, runs every `ISendScopeInitializer(parent, child)`, dispatches through `MediatorDispatcher` in the child and disposes it; `CreateStream` is an async iterator, so the scope is created when enumeration starts and disposed when it ends or is abandoned. Nested sends get their own scope (the handler's `IMediator` is another `ScopePerSendMediator` bound to the child). For hosts whose ambient scope is long-lived (Blazor Server circuits). `Warp.Http` dispatches in the REQUEST scope regardless, through the public `ISendScopeBypass.InCurrentScope` seam (public because `Warp.Http` composes against Core's public API, §0.5). Workers never go through `IMediator`, so job execution is untouched (§0.2). Rot guard: `ScopePerSendMediatorTests` (NoDb).
