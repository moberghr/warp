# §8.27 — design notes (client observability)

> Full rationale, history, measurements and rot guards behind the condensed rule §8.27 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `project-specific.md` (2026-11-24).

**§8.27** **Client (frontend) observability** is the **browser-side** complement to server-side observability (adapters §8.19 outbound, endpoints §8.21 inbound-to-Warp): a public **ingest endpoint** a frontend app posts to, attributed to an **application** (§8.23). One `ClientEvent` primitive discriminated by `ClientEventType { Error=1, Vital=2, Log=3, Event=4 }` (§8.11, `Warp.Core.Enums`) — `log()`/`track()` sugar + auto-captured errors/vitals are the SAME row (no second subsystem). Same pipeline as adapters/endpoints: bounded lossy channel (`DbClientEventRecorder`) → `ClientEventFlusher<TContext>` (drains to `ClientEventLog` rows + the durable `clientevent:` Counter fold, stamps `ReceivedAt`/`ExpireAt`, §0.5 scope) → `Counter → CounterAggregator → Statistic`.

**Two-tier storage (never inflate the DB):** raw `ClientEventLog` rows (`Warp.Core.Data.Entities`, always-in-schema §2.11, mirrored by `WarpServerContext` §2.14) are trimmed on age (`ClientEventLogRetention` 7d) AND count (`ClientEventLogRetentionCount` 100k/app) by `ExpirationCleanup`; trend data (`ClientEventKeys`, `Warp.Core.ClientObservability`, disjoint prefixes `clientevent`/`clientevent-app`, §8.6/§8.19) — per-type count + hourly history, per-name total, per-vital count+dur+**p75 histogram** — **survives raw-row cleanup** (§8.22). **Cardinality guard (the difference from endpoints, whose routes are bounded) — NOTHING client-sent is trusted bounded on a public endpoint:** error/event names AND log **levels** collapse to `{other}` beyond a per-type cap (`ClientEventCardinality`, §8.19); **vital names go through a fixed allowlist** (`ClientEventCardinality.KnownVitals` = LCP/CLS/INP/FCP/TTFB → else `{other}`) for BOTH the counter key and the `warp.client.vitals` meter tag — a raw client vital name is never a metric dimension. Counter-only; the raw row keeps the real name. Logs fold by `Level` (§8.27 "logs count per level"), not the free name. CLS is folded ×1000 into the shared integer histogram and unscaled ÷1000 on read. **Web vitals follow Google: p75** (their good/needs-improvement/poor threshold percentile), NOT p95/p99.

**Public endpoint (hostile client):** auth is a public write-only **DSN key** (`o.AddIngestKey(app, key)` → **trusted** app name, never client-declared; unknown → 401), a CORS **origin allowlist** (else 403; same-origin — `Origin == scheme://host` — bypasses the allowlist), an **in-memory per-caller-IP** rate limit (`ClientIngestRateLimiter` — keyed on IP not the public key, checked BEFORE the body read so floods/bad-key/empty posts are bounded cheaply; NEVER DB-backed), and hard size/batch caps. A crafted out-of-range `ts` is caught (never faults the request). Key travels in `x-warp-key` header OR body (a `sendBeacon` caller can't set headers). Recording is lossy (full channel drops + `warp.client.events.dropped`; an unrecognized event `type` is also dropped-and-counted, never silent; browser never blocked).

**PII (§1.2):** IP off by default; property maps redacted via a denylist + truncated; never logged Info+; **consent/GDPR is the host's job**.

**Sink-respecting (§8.24):** `Database`/`Both` write rows; `Otel` skips the DB, meters carry it (`warp.client.events`/`vitals`/`events.dropped`, always-on). Core (`Warp.Core.ClientObservability`) holds the sink-free pipeline + options + `AddClientObservability(IWarpBuilder)` + the query service (registered by `AddWarp` itself, resolves in dashboard-only processes); the HTTP binding (`Warp.Http.ClientObservability`) holds `MapWarpClientObservability()` (the ingest endpoint + `GET {IngestPath}/client.js` serving the shipped self-contained browser script — error hooks, web vitals via PerformanceObserver, breadcrumbs, `sendBeacon`/`fetch(keepalive)` batching, per-session sampling). Dashboard **Client** page (`/client`, `ClientPage.tsx`) gated on `WarpAddonsInfo.Client` (keyed on `IClientObservabilityMarker`). API `GET {prefix}/api/client/summary|events|events/{id}|applications`. Worker hot path untouched (§0.2/§6.1).

**Client↔server correlation (unified session timeline):** the shipped script propagates TWO W3C headers on same-origin calls — `traceparent` (per-request **trace id**, already adopted into `EndpointCallLog.TraceId`/`Job.TraceId`) and `baggage: session.id=…` (the OTel `session.id` for the whole session). The middleware reads the session baggage onto `EndpointCallLog.Session` (via `Activity.Current.GetBaggageItem`, `WarpTelemetryAttributes.SessionId = "session.id"`) and sets it as the `session.id` span attribute on the request span so OTel backends slice by session. **Jobs are NOT stamped with session** — a `Job.Session` column was built and then dropped as redundant: a job already carries a `TraceId`, and the trace id ties it back to the originating request, which carries the session. Session is a request/endpoint-level dimension; the job↔request link is the trace id (the join key the unified trace view uses, §8.28). `ClientEventType.Request = 5` + `ClientEventLog.TraceId` (Guid, "N"-form join key). `IClientEventQueryService.GetSession(sessionId)` merges the session's client events with the `EndpointCallLog` rows stamped with that session (direct column join) into one chronological timeline; `GET {prefix}/api/client/sessions/{id}`, `ClientSessionPage.tsx` at `/client/sessions/:id`, request/server rows link to `/trace/{traceId}` (the unified trace view §8.28). Trace id = one action end-to-end; session id = all actions in a visit — both propagated. See §2.15/§8.19/§8.21/§8.28, `website/docs/features/client-observability.md`.
