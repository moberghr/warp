# §6.17 — design notes (worker never touches tcontext)

> Full rationale, history, measurements and rot guards behind the condensed rule §6.17 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `performance.md` (2026-11-25).

**§6.17** **The worker never resolves or saves the application's DbContext** (8.0; both worker modes). A handler owns its context and its pipeline: it calls `SaveChangesAsync` (or `IPublisher`/`IBatchPublisher.SaveChangesAsync`) for its own work, and a job it stages without saving is discarded with its scope, like anywhere else; the `WarnOnUnsavedStagedJobs` warning now covers handler scopes too. Until 7.x the worker resolved `TContext` in every handler scope and called `SaveChangesAsync` after the handler, so every job built a full EF context (options, EF's per-context services) even when the handler never touched the database: measured on the load lab, ~0.94 application contexts initialized per empty job and most of the ~94 KB the worker allocated per job. Do not reintroduce a worker-side resolve or save of `TContext`, not even to check for unsaved changes. **The same holds for the addon pipeline stores**: the concurrency resolver, the rate-limit store and resolver and the circuit-breaker store read and write Warp's own tables through `DeferredWarpContext` (Warp's server context, opened on first use and disposed with the job's scope), never `TContext`; their behaviours are built for every job, so a job with no `[Mutex]`/`[Semaphore]`/`[RateLimit]`/circuit-breaker state to touch builds no context at all. Their caches are allocated on first use for the same reason. The admin managers (`ConcurrencyLimitManager<TContext>`, `RateLimitManager<TContext>`) run on the Warp context that `AddWarp` registers in every process (#344, §2.14). Rot guard: `PolicyBehaviorContextTests` (resolving the pipeline with all three addons constructs no `TContext`). Sagas are separate: the saga proxy saves for the saga handler (§8.17). Release note: breaking for handlers that relied on the worker's save. Rot guard: `WorkerExecutionIntegrationTests.GivenAHandlerThatStagesAJobWithoutSaving_WhenItCompletes_ThenTheStagedJobIsNotCommitted` (both modes).
