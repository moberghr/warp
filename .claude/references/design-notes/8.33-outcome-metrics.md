# §8.33 — design notes (outcome metrics)

> Full rationale, history, measurements and rot guards behind the condensed rule §8.33 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `project-specific.md` (2026-11-24).

**§8.33** **Outcome metrics taxonomy (append-only `stats:`, reason-attributed breakdown).** Governing principle: **a metric records an event; current state is a query.** Every `stats:` key is now **append-only** — `JobCommandService.DecrementStatForState` and the decrement arm of `ApplyRequeueAccounting` are **removed, do not reintroduce them**: restating `succeeded`/`failed`/`deleted` on requeue caused four distinct defects — (1) the decrement wrote the *lifetime* key only, so a lifetime total silently disagreed with the sum of its own hourly buckets, (2) the dashboard's realtime rate chart deltas the total and clamped the resulting negative to 0 (`stores/dashboard.ts`), under-reporting the tick, (3) it destroyed the counter's only unique information — failed jobs never auto-expire (§8.2), so the `Job` query already answers "currently failed" and the counter's one added value is "ever failed", which is exactly what the decrement removed, and (4) nothing stores which reason produced a job's *previous* terminal state, so a restated total can never reconcile with an append-only breakdown. Consequence to state in release notes: `stats:succeeded`/`failed`/`deleted` mean **ever**, not *latest outcome was*, and grow for anyone who requeues; the live tiles and nav badges are unaffected because they query `Job`.

**Three levels, and the umbrella is DERIVED not stored:** per-state totals (`stats:{succeeded|failed|deleted|requeued}`) + per-reason breakdown (`stats:{state}-{reason}`) + the not-Completed umbrella computed **on read** as `failed + deleted` (`counterModel.buildOutcomeRows`, the pure read-side model behind the Counters page). A stored `stats:unsuccessful` row was built and reverted: it was maintained at the 2 worker finalization sites while `failed`/`deleted` also move at 6 others (`DeleteJob`, `BulkDeleteJobs`, both crash-recovery arms, both worker cancellation paths), so it under-reported from the first delete and the page drew a child larger than its parent — **a pure function of two stored values must not be a third stored value**; `OutcomeMetricsTestsBase.AssertUmbrellaIsNotStored` pins it. Breakdown rows are written **independently of** the state total, never derived from it, so an outcome no addon claimed still lands in the total and shows as the **unattributed remainder** (surfaced in the UI, including the impossible `attributed > total` direction). **`OutcomeReason` is a closed enum** (`Warp.Core.Enums`, from 1 §8.11: `Retry=1, RetryExhausted=2, Concurrency=3, RateLimit=4, Timeout=5, Saga=6, Manual=7, Recovery=8, CircuitBreaker=9`) stamped on the `JobOutcome` each behaviour already constructs (13 sites) — **boundedness is the cost model, not a style choice**: `JobOutcome` is public API and a free-string reason would let any caller mint unbounded `Statistic` rows, turning a fixed ~14-key family into keys-per-value. **`OutcomeReasonTokens.For` is a `switch` expression, never `ToString().ToLowerInvariant()`** — it allocates nothing per finalization and pins the wire format so an enum rename cannot silently orphan every historical row under the old key; it **returns the literal `"unknown"` rather than throwing** because every caller runs inside the job's own `catch (Exception e)` at finalization, where a throw is laundered into a fake handler failure, re-enters finalization, throws again and escapes before `SaveChangesAsync` — leaving the job `Processing` for `StaleJobRecovery` to requeue and re-poison forever (instrumentation never out-throws, §8.19/§8.25). A guard test asserts every member maps to a distinct token that is not `unknown`. **Both worker paths must move in lockstep** (§0.2/§6.1) — `WarpWorkerService.FinalizeJobState` and `WarpDispatcherWorker`'s `CompletionBatch` keep separate copies of the composition, §8.29 records the dispatcher path being missed once, and `RetryStatusDispatcherIntegrationTestsBase` (`UseDispatcher=true`) is the guard. Same lockstep applies to the `willRetry` label: it tests `State.Enqueued or State.Scheduled`, because `JobOutcome.RescheduledState` returns `Scheduled` for any future target and `RetryOptions.Delays` defaults to `[15,60,300]` — testing `Enqueued` alone labelled every default retry `status=failed` on `warp.job.completed`. **`stats:retried-jobs` counts DISTINCT jobs that entered retry, not retry events**, and adds **no schema column**: it reuses `Job.Metadata.RetriedTimes`, already read **before** handler execution via the pinned `WarpTelemetryAttributes.RetryMetadataRetriedTimesKey` constant (so the worker keeps no dependency on the Retry addon), where an incoming count of `0` on a `Retry` outcome is exactly "this job's first retry". Manual (`RequeueJob`/`BulkRequeueJobs`) and crash-recovery (`StaleJobRecovery`) requeues write the **state total AND the reason key** with hourly buckets, counted from the same in-transaction re-query that writes the `Requeued` `JobLog` rows — one counter increment per log row is the invariant. Always-on meter `warp.job.requeued{queue, type, reason, application}` fires for EVERY requeue — both worker finalization paths (beside the state total, `unknown` token for a reasonless user outcome), manual, and crash recovery; the manual/recovery emissions are POST-COMMIT (buffered via `OnCommittedAsync` in `StaleJobRecovery`, per §8.25 — an inline emission under the task-host lock transaction records requeues a rollback undoes). **no key tags**, `ConcurrencyKey`/`RateLimitKey` are unbounded and PII-adjacent (§1.2) and stay on spans.

**Interlocking behaviours (learned via review, keep them):** the circuit breaker counts a `Failed` outcome as a dependency failure (retry EXHAUSTION stamps `Failed`/`RetryExhausted`; skipping all outcome-bearing attempts made the breaker blind in the documented breaker-outer order) but never reschedule/delete outcomes; `RetryExhausted` is stamped only when `maxRetries > 0` (the behaviour runs for every job once `AddRetry()` is called and `MaxRetries` defaults to 0 — unguarded, every attribute-less type's first failure read "exhausted"); an untouched `WarpServerConfiguration.Queues` follows the RESOLVED `DefaultQueue` (`WarpServerRegistration` passes it — the server builder's copy is wrong in the AddWarp-first two-builder shape), with the explicitness flag guarded against `ConfigurationBinder` invoking setters for absent keys; `AddWarpServer` validates `BackgroundServiceLeaseTtl` (or its 30s default — `DefaultBackgroundServiceLeaseTtl`, one shared constant) ≥ 3× `HealthCheckInterval` at startup. Keys stay lifetime + **unmarked hourly**, so `CounterAggregator` and `StatisticRollup` (§8.30) need zero changes. `StatSurfaceTestsBase` is the cross-key guard — one mixed workload, the complete key/value map asserted exactly on both providers. See `website/docs/features/queue-metrics.md`.
