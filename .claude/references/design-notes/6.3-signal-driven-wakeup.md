# §6.3 — design notes (signal driven wakeup)

> Full rationale, history, measurements and rot guards behind the condensed rule §6.3 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `performance.md` (2026-11-25).

**§6.3** Signal-driven wake-up. `ServerTaskSignals<TContext>` has three channels (`ServerTaskSignal`, numbered from 1): `SignalJobFinalized` wakes `Orchestrator`; `SignalMessageEnqueued` wakes `MessageRouter`; `SignalJobEnqueued(queue)` shortcuts the backoff of the local worker groups that drain that queue, so a same-server `Enqueued` `Kind=Job` row is picked up without waiting for the poll interval or a DB round-trip (§2.9). **The wake is queue-scoped (8.1.x):** `WarpDispatcher` and `WarpWorker` subscribe with their group's effective queues (`ServerTaskSignals.SubscribeJobEnqueued`, `DispatcherRegistry.Register(signal, queues)`, the cross-process path through `IDispatcherWake.Signal(queue)`, whose default falls back to `SignalAll`), matched exactly and ordinally; a signal with no queue (the listener's reconnect drain) wakes everyone, and the plain `Subscribe(JobEnqueued, ...)` still hears every queue. Why: with one group a wake is never wasted, but with a second group on another queue a wake-all made every handler-staged child also wake that group, which ran one claim against its empty queue. Perf CI run 45829375927 (main vs 8.0.0, a server with a second, single-queue group) failed the PostgreSQL statements gate on every fan-out case: 13.18 statements / 3.82 commands / 3.92 transactions per job against 10.62 / 2.55 / 2.12, and 299 MB allocated against 218 MB; removing the second group restored the 8.0 numbers exactly. A queue no local group drains wakes nobody, which is correct: no local group could claim it. **Don't reduce poll intervals** as a performance hack — register/fire a signal instead. **Every site that puts a row into `Enqueued` must announce it, including the ones that MODIFY an existing row** — `NotificationDispatch.CapturePending` only walks the change tracker for **Added** `Job` entries, so a `Scheduled→Enqueued` activation or a `Processing→Enqueued` requeue is invisible to it and has to build its own `Notification` from the flip (`ScheduledJobActivation`, `StaleJobRecovery`). Both then **buffer it and dispatch from `OnCommittedAsync`** whenever there is an ambient transaction (§8.25) — under the task host `ExecuteAsync` runs inside the lock transaction, so an inline dispatch wakes a worker onto a row it cannot see yet and it sleeps again having found nothing; with no ambient transaction (a direct caller — test, admin trigger) the `SaveChanges` already committed, so the wake fires inline because nothing will call the hook for it. Missing that wake is silent: the row is correct and simply waits out a worker's backoff, up to `MaxPollingInterval` — which `UseDatabasePush()` raises from 30s to **5 minutes** — and it poisons the queue-wait SLI (§8.26) the same way the recurring-scheduler bug did (§8.9). Crash-recovery requeues shipped without it.
