# §6.14 — design notes (running job monitor)

> Full rationale, history, measurements and rot guards behind the condensed rule §6.14 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `performance.md` (2026-11-25).

**§6.14** **A worker group watches all its running jobs in one loop** (`RunningJobMonitor`, one per group, built by `WarpDispatcherHost` and `WarpSingleWorkerHost`; a `WarpWorkerService` built on its own, as tests do, gets a private one). Each running job used to have a monitor of its own: every `CancellationCheckInterval` a cancellation `SELECT` and a keep-alive `UPDATE` per job, and a save per job per `LogFlushInterval` for any job that logged, so a group running N long jobs paid 2N statements per check. Now each tick drains every registered job's handler logs, progress rows and (once the job has run a whole tick) its deferred "Processing" row (§6.12) into one save, and every `CancellationCheckInterval` ONE statement (`IWarpSqlQueries.RenewRunningJobsAsync`: `unnest` on PostgreSQL, `OPENJSON` with `INNER LOOP JOIN`/`ROWLOCK` on SQL Server, jobs in id order like the completion) renews `LastKeepAlive`, stamps each job's worker, touches only rows still `Processing` (so a renewal racing a completion writes nothing to the finished row) and returns the jobs whose `CancellationMode` asks for cancellation, which are cancelled after their logs are saved. The loop runs only while something is registered, so an idle group costs nothing; a worker whose stopping token fired is no longer watched. A failed renewal is logged and retried at the next check, separately from the log save. A failed log save puts the rows it took back on their entries, for the next tick or the job's finalizing write; the rows are taken per entry under its own lock, so a job whose worker has let go gives up nothing, and the "Processing" row is taken only for that entry's own job (`DeferredJobLog.TakeFor`). Cancellations are started and not awaited: `CancelAsync` returns only once the job token's callbacks have run, and one that blocked held the whole group's tick. The renewal carries each job's run (`JobRunOwner`) and touches a row only while it is still that run's, with the completion's predicate (§6.13): renewing a row another claim now holds kept a dead run's job from recovery and stamped the wrong worker on the live one (`JobRunOwnershipTests`). The statement runs through EF's `SqlQueryRaw`, not a bare command, so EF command interceptors see it (its rows are aliased `beat`, which is how `FailFirstKeepAliveInterceptor` finds it). A worker disposes its registration before finalizing a job; anything that renews or flushes for a job must go through the monitor, never a per-job loop again. Rot guards: `WorkerExecutionIntegrationTests.GivenTwoLongRunningHandlersInOneGroup_WhileTheyRun_ThenOneRenewalStampsBoth` (one statement renews both, so they carry the same instant), `GivenOneKeepAliveRenewalFails_WhileTheHandlerRuns_ThenLaterRenewalsStillHappen`, the cancellation tests, both modes.
