# §6.11 — design notes (orchestrator parent queries)

> Full rationale, history, measurements and rot guards behind the condensed rule §6.11 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `performance.md` (2026-11-25).

**§6.11** **`Orchestrator.FinalizeParentsAsync` finds ready parents with one branch per kind (`Kind = Message` UNION ALL `Kind = Batch`), each `ORDER BY CurrentState, CreateTime` + `Take`, and that shape is load-bearing** (the §6.9 lesson on a second query). As one `Kind IN (...) AND CurrentState IN (Awaiting, Processing)` predicate the planner estimated one row either way and chose `(CurrentState, ScheduleTime)` with `Kind` as a Filter. Every job passes through `Processing`, so until vacuum catches up that index range holds an entry for every row that has since left it, and the query walked all of them and visited the heap for each to return nothing: **10,004 pages per call against 6**, reproduced on a table with no batch or message in it, and 1,147,074 pages across a 10,000-job lab run against 4,008 after (the task ticks on almost every finalization, so that was up to ~100 pages per job). A scalar `Kind` alone is NOT enough (the two index costs tie and the wrong one still wins); it takes the scalar `Kind` AND an `ORDER BY` only the `(Kind, CurrentState, CreateTime)` index can supply. Statement count is unchanged (one statement). **Rot guard: `OrchestratorReadyParentsPlanTests`** measures the pages the real query reads (PostgreSQL `EXPLAIN (ANALYZE, BUFFERS)`, SQL Server `STATISTICS IO`) with 3,000 rows that have just left `Processing` and no batch or message, and fails above 200: the old shape reads 2,949 on PostgreSQL, the new one 4. **SQL Server never had the problem** (8 logical reads with either shape), so the change costs it nothing. This was also the swing behind the perf workflow's bimodal Buffers/job column; the two sides of that comparison now each get a fresh PostgreSQL container (`.github/scripts/start-bench-postgres.sh`), since sharing one, head first, read ~50 buffers per job higher on "head" for identical code. **The "which awaiting rows can move?" half had its own version of this, and is now three steps that can each be served only one way** (`AwaitedParentIdsQuery` -> `AwaitedParentStatesQuery` -> `AwaitingChildrenOfQuery`, shared by the activation and the deleted-parent sweep). It was one statement per question, awaiting rows `WHERE EXISTS(parent WHERE id = the row's parent AND state = Completed)`, measured at 2 and 12 pages on a table with no continuation in it, which is the wrong table to measure on: in a batch workload PostgreSQL found the parent through the STATE index and checked the id afterwards, so for each awaiting row it read every Completed row in the table and discarded all but one (505 awaiting rows, 250 completed: 126,250 rows discarded, **5,063 pages per call**, cost = awaiting rows x completed rows, on almost every job completion). A scalar subquery on the parent's id is deterministic but still two key lookups per awaiting ROW (3,042 pages, and it made SQL Server worse: 2 -> 1,083). The three steps read each DISTINCT parent once: 500 jobs in five continuation batches wait on ten parents, **13 + 15 pages per pass, plus 46 when something is ready**; SQL Server is level (42 against 41). Statements per pass do not go up: one when nothing is awaiting (was two), two when rows wait but none can move (was two), one more for each of ready and deleted. **Past 1,000 awaited parents the pass stops reading them all** (`ServerTaskSignals.ManyAwaitedParents`, set and cleared by the Orchestrator from the size of the set it last read): 100,000 single-job continuations on 100,000 parents was a scan of every awaiting row plus 100 lookup statements on every job completion. In that mode a pass asks only about the jobs a wake said reached a terminal state (`AwaitedParentIdsAmongQuery`, the `(ParentJobId, CurrentState)` index with both columns bound) and the whole set is read on a sweep alone, 5,000 parents at a time, each sweep carrying on from the last one's cursor (`NextSweepSlice`) so nothing is starved. That is why a wake carries a second id list, the SETTLED jobs: the worker sends the job's own id once it is at rest (never for a requeue), `DeleteJob`/`BulkDeleteJobs`/`StaleJobRecovery` send theirs, `NotificationDispatch.CapturePending` names the parent of every ADDED `Awaiting` row (a continuation published after its parent finished has nothing else to wake for it), and the Orchestrator adds the parents it finalizes and the rows it fails, plus anything it could not finish in one pass (`NoteFinalized`). Below the threshold nothing changes: the settled ids are taken and ignored, because one scan of a small awaiting range (2 to 13 pages) is cheaper than an index probe per finished job. Push payload grammar: `parents[;settled]`, at most 128 ids. Rot guards: `OrchestrationTaskTests.RunOrchestration_MoreAwaitedParentsThanOnePassReads_ChecksNamedJobsAndSweepsTheRest`, `OrchestratorReadyParentsPlanTests.AwaitedParentIdsAmongQuery_ThousandsOfAwaitingRows_ReadsOnlyTheNamedJobs`, `FinalizedParentHintsTests.NextSweepSlice_*`. This was the swing behind the batch scenario reading 2,948 buffers per job in one CI run and about 165 in the others. Rot guard: `OrchestratorReadyParentsPlanTests.AwaitingRowQueries_BatchWorkloadAmongManyCompletedJobs_EachReadAHandfulOfPages`. **A wake names the parents to check; every parent in flight is checked only on a sweep.** Even with the right plan, the ready-parents query reads each in-flight parent (about 11 pages each on PostgreSQL: 10,924 per pass with 1,000 messages in flight and none ready, 10 on SQL Server) and it ran on every job completion, so message routing cost passes x in-flight parents and read anywhere from 164 to 1,643 pages per job on identical code. The worker now passes the finished job's `ParentJobId` (already on the claimed row: no query, §0.2) with its wake, `ServerTaskSignals.SignalJobFinalized(Guid?)` / `SignalJobsFinalized` for a dispatcher flush, and the same ids travel in the push payload after `F:` (`FinalizedParentsPayload`: ids, `-` for no parent, nothing for unknown, at most 64 per notification). `Orchestrator` takes them with `TakeFinalizedParents` and checks them in two statements that can each be served only one way, `ChildStatesOfQuery` (the children's kind and state, by parent id and nothing else) then `ParentsByIdQuery` (the ready parents, by primary key and nothing else), with readiness decided in memory between them (`ParentsWithSettledChildren`), and runs the full `ReadyParentsQuery` only on a **sweep**: the first pass of the process, **every run its schedule started** (the claim reports `ClusterTaskState.Scheduled` when it took the task because `NextRunAt` had come, not only for a run request; the scheduler hands that to the task through the INTERNAL `IScheduledRunAware.BeginRun`, set by `ServerTaskRunner`, so `IServerTask` is unchanged: `ClusterTaskSchedulerTests.PassAsync_RunClaimedOnItsSchedule_TellsTheTaskItIsAScheduledRun`, `ClusterTaskQueriesTests.ClaimClusterTasks_DueBySchedule_ReportsAScheduledClaim`, `FinalizedParentHintsTests.TakeFinalizedParents_ScheduledRunRightAfterASweep_SweepsAgain`), on a signal run once 90% of `OrchestrationInterval` has passed since the last sweep (stopwatch, not `TimeProvider`: `TakeFinalizedParents_ScheduledRunAMomentSoonerAfterItsTickThanTheLast_StillSweeps`), after the public no-argument `SignalJobFinalized()` (a reconnect drain, a bare `F:` from a pre-8.0 server), after a full sweep slice, and when the bounded hint set (10,000) overflows. A pass that throws, or whose work is rolled back after it returned (the scope is disposed without `OnCommittedAsync`), returns its work (`ReturnFinalizedParents`). **Every site that puts a child into a terminal state names its parent, not only the worker**: `JobCommandService.DeleteJob` / `BulkDeleteJobs` (so `CancelBatch` too) dispatch after their commit, and `StaleJobRecovery`'s deleted and failed arms buffer theirs for `OnCommittedAsync`; a new site that finishes a child must do the same, or its parent waits for the sweep. The sweep remains the backstop for what cannot name a parent or cannot reach the Orchestrator (a wake lost with a crashed process, a delete from a dashboard-only process without `UseDatabasePush()`), up to `OrchestrationInterval` (10 s; 1 min with push): do not remove it, and do not make a wake-only signal request one (with push, every completion echoes back through the listener). **The named check was one statement** (parents by id, kind and state, `NOT EXISTS` a pending child with `kind = Job`, `EXISTS` a child with `kind = Job` in a settled state), and every extra predicate offered PostgreSQL another index: after a burst the statistics said each matched one row, so it found the settled child through `(kind, state, create_time)`, every finished job in the table once per named parent, and the pending child through a BitmapAnd with `kind = Job`. Measured on the message-routing benchmark: 28,608 pages for 26 named parents and 177,258 for 60, 25,208 pages per call over a run, on almost every completion; message routing read 110 to 1,317 pages per job on identical code. The children's states that `FinalizeParentsAsync` read with its own kind-and-state statement (1,239 pages a call) come from the same `ChildStatesOfQuery` result now. Do not add a kind or state predicate back to either statement; filter in memory. The sweep's `ReadyParentsQuery` still runs `WhereChildrenSettled` in SQL. Rot guards: `OrchestratorReadyParentsPlanTests.HintedReadiness_ThousandMessagesInFlight_ReadsOnlyTheNamedParents` and `HintedReadiness_BurstOfFinishedJobsTheStatisticsNeverSaw_ReadsOnlyTheNamedParents` (the old statement reads 22,065 pages there on PostgreSQL, the two new ones 71 and 15), `FinalizedParentHintsTests` (NoDb), `OrchestrationTaskTests.RunOrchestration_ParentNamedByAFinishedJob_OnlyThatParentIsFinalized`, `MessageIntegrationTests.GivenNoParentSweepDue_WhenHandlersFinish_ThenWorkerNamesTheMessageAndItCompletes` in both worker modes, `JobCommandServiceTests.DeleteJob_ChildOfAMessage_NamesTheParentForTheOrchestrator`, and `NoRestartCrashRecoveryTests.RequeueStaleJobs_FailedChildOfAMessage_NamesTheParentForTheOrchestrator`.
