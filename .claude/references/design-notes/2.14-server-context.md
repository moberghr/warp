# §2.14 — design notes (server context)

> Full rationale, history, measurements and rot guards behind the condensed rule §2.14 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `architecture.md` (2026-11-25).

**§2.14** Autonomous server-internal DB work runs on an internal **`WarpServerContext<TContext>`** (`Warp.Core`, registered by `AddServerHostCore`), not the user's `TContext`. It's a runtime-only mirror of the Warp model: `ApplyWarpModel` + `WarpConfiguration.EntityConfigurators` (so it mirrors `TContext`'s full model) + table/column/schema names pinned via **`IWarpServerModelNames`** + `ExcludeFromMigrations` (TContext stays the schema owner). **`WarpServerContext` never resolves `TContext`** — and it mirrors NAMES only, never the consumer's `ConfigureConventions`: the two contexts can only agree on the physical columns because §5.12's ownership pass guarantees no consumer convention retypes a Warp column on `TContext` in the first place (and a runtime convention that does is a startup error). The names come from the `IWarpServerModelNames` abstraction (non-generic; default impl `WarpServerModelNames<TContext>` reads `TContext`'s model once via `IServiceScopeFactory` and caches it — the *single* place `TContext` is touched, swappable for another name source). Its connection comes from the provider via `IWarpServerContextConfigurator` (pulled from `TContext`'s options); its options demote EF's command-executed event to `Debug` (quiet logging) unless `opt.EnableServerCommandLogging`. Components depend on the **`IWarpServerContext`** abstraction (exposes `DbContext Context`) and extract the context once — never the concrete generic type (keeps them decoupled + testable; tests wrap any `DbContext`). **On the server context (all autonomous server-internal DB work):** the **job worker** fetch/execute path (`WarpWorkerService` / `WarpDispatcher*` — claim, processing log, completion, the job monitor), the 14 server tasks of §2.3 (on every server: `Heartbeat`, `ServerCleanup`, `ExpirationCleanup`, `StatisticRollup`, `MetricRollup`, `CounterAggregator`, `ErrorGroupAggregator`, `SloEvaluator`; job-only: `StaleJobRecovery`, `BacklogSampler`, `RecurringJobScheduler`, `ScheduledJobActivation`, `MessageRouter`, `Orchestrator`), the background-service host + its write services (state/lease/log), and the addon pipeline stores (`ConcurrencyLimitResolver`, `RateLimitStore`, `RateLimitResolver`, `CircuitBreakerStore` — through `DeferredWarpContext`, opened on first use, §6.17). **Stays on `TContext` — only the outbox + user code:** `Publisher`/`BatchPublisher` staging job rows in the caller's transaction, the **handler scope** (handler code + its outbox, which the handler saves itself — the worker never resolves or saves `TContext`, §6.17), the addon admin managers (`ConcurrencyLimitManager<TContext>`, `RateLimitManager<TContext>`), and the dashboard query services / `IBackgroundServiceQueryService` (must resolve in `AddWarp`-only processes). `IWarpSqlQueries<TContext>` method params are `DbContext` so the queries accept either context (worker-fetch passes the server context; cold-path commands like `JobCommandService.DeleteJob` pass `TContext`). **A server task must not mix the two.** Every sweep inside one `ExecuteAsync` shares the task host's lock transaction on the server-context connection; reaching for `TContext` mid-task puts that work on a second connection, where it cannot commit atomically with the rest and — under read-committed locking (SQL Server without RCSI) — blocks on the row locks the same task is still holding, waiting on a transaction that only commits once `ExecuteAsync` returns. A task that needs to enqueue a job stages it directly (`JobHelper.CreateJob` + `NotificationDispatch.CapturePending` → dispatch from `OnCommittedAsync`, per `RecurringJobScheduler`/`MessageRouter`/`StaleJobRecovery`) instead of through the `TContext`-bound `IPublisher`. Worker hot path: only the resolved context type changed — no orchestration added (§0.2/§6.1). Tests that wait on worker-written `JobLog` rows poll the committed row (a `TContext`-scoped EF interceptor can't observe server-context writes).

**The Warp context (8.2, #344).** Until 8.2 the dashboard query services, the dashboard command services and the admin managers ran on `TContext`, because they must resolve in `AddWarp`-only processes and the server context was registered by `AddServerHostCore` only. Warp's reads then depended on the application's context (interceptors, logging, retry strategy, pool) and added to its cost. `AddWarp` now registers **`WarpContext<TContext>`**, a sibling of the server context built by the same `WarpMirrorModel.Apply` and opened through the same `IWarpServerContextConfigurator` (which `UsePostgreSql()`/`UseSqlServer()` register in any process; it reads `WarpDatabaseConnection<TContext>`, also an `AddWarp` registration). `IWarpServerModelNames` moved to `AddWarp`. **Why a sibling, not the server context itself:** the server context makes `Job.RunId` a concurrency token for single-worker finalization (#347); `JobCommandService` saves tracked jobs, and with the token on its context two concurrent bulk requeues deadlocked on SQL Server — the reason #347 kept it off `TContext`. Services depend on the internal **`IWarpContext`**, a scoped handle chosen once per process by `WarpContextSelection<TContext>`: the Warp context when a configurator is registered AND `IWarpServerContextConfigurator.Supports(TContext's options)` (a default interface member; PostgreSQL answers on `NpgsqlOptionsExtension`, SQL Server on `SqlServerOptionsExtension`), otherwise the scoped `TContext`. **The fallback is for an application's tests (#359)**: they keep `UsePostgreSql()` from `Program.cs` and swap the context to EF in-memory, so the Warp context would open PostgreSQL against a connection string that is not there, and a separate in-memory context would not see the rows the test published. The Warp context copies `TContext`'s command timeout (nothing else: no interceptors, no retry strategy, no query splitting), logs its commands at Debug unless `EnableServerCommandLogging` (via the internal `WarpCommandLogging`, registered by `AddWarpServer`), and its `DbContextOptions` forwarder is removed like the server context's (`WarpContextOptions.Register`, so `dotnet ef` never counts it). The 28 services keep their public `TContext` constructors (no API break); `AddWarp` builds them through internal `DbContext` constructors. **Webhook redelivery and probes** commit the delivery's reset and the executor job in one transaction: on the Warp context Warp's own enqueuer (which publishes through the `TContext`-bound `IPublisher`, another connection) is bypassed and the job is staged with `WebhookExecutorJobs` (moved to Core) on the same context, its wake dispatched after the commit; a host-registered `IWebhookRedeliveryEnqueuer` is still called. `ConcurrencyLimitManager` is registered through a factory, so `ReplacedRegistration` recognises Warp's own registration by the factory instance (§8.8.1). Not moved yet (follow-up): the `AddWarp` background writers (flushers, `ContextMetricPointSink`, `ApplicationHeartbeatHost`, `DroppedRecordReporter`) and the seeders. Behaviour changes are in the 8.2.0 release notes (not part of the caller's transaction; `TransactionScope` escalation; `TContext` configuration no longer applies). Guards: `WarpContextSelectionTests` (NoDb: every moved service holds the Warp context on both providers, falls back on in-memory, builds no `TContext`; the #359 shape end to end; design-time forwarders; `Supports`; pool and command timeout; `RunId` token only on the server context) and `WarpOwnedContextTestsBase` (both DBs: an `AddWarp`-only host's reads, requeue, admin-manager writes and redelivery reach the database through the Warp context and never the application's command interceptor, snake_case on PostgreSQL).
