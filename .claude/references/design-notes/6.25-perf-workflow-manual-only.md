# §6.25 — design notes (perf workflow manual only)

> Full rationale, history, measurements and rot guards behind the condensed rule §6.25 in `.claude/rules/`. Read on demand when changing this area. Verbatim from `performance.md` as committed in e3181df0 (2026-11-25).

**§6.25** **The Performance workflow runs only when someone starts it** (`workflow_dispatch`: Actions > Performance > Run workflow, or `gh workflow run perf.yml --ref <branch> [-f base_ref=7.7.0]`), plus a published release, which records that release's results. It does not run on pull requests and there is no nightly run. On every push it was 38 cells with several gates each, and it was red on most pushes for reasons that were not regressions: a harness query picked as a SQL Server deadlock victim, WAL per job moved by where PostgreSQL's checkpoints fell (the bench servers now run with `full_page_writes=off`; `WAL FPI/job` should read 0), one flaky cell among 38, and each push cancelling the run before it. Do not put it back on `pull_request` without first making a red check mean a confirmed regression (a small count-only gate, a cell with no measurement reported as inconclusive, a crossed gate re-run before it fails). Run it before a release and after a change to the worker, the claim, the completion or the server tasks, and read the count columns (statements, commands, transactions, WAL per job); timings on shared runners are for the ratio within one run only.
