# §8.21 — design notes (endpoint observability)

> Full rationale, history, measurements and rot guards behind the condensed rule §8.21 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `project-specific.md` (2026-11-24).

**§8.21** **Inbound endpoint observability** (`Warp.Http`, opt-in via `opt.AddEndpointObservability(o => ...)` inside the `AddWarp`/`AddWarpServer` lambda + `app.UseWarpHttpObservability()` after `UseRouting`) is the **inbound mirror of adapters §8.19**: adapters observe calls the app *makes to* other services; this observes requests *made to* the app's **Warp HTTP endpoints** (handlers exposed via `MapWarpHttp`). Scope is Warp endpoints **plus host endpoints the host explicitly opts in** — the middleware no-ops unless the matched endpoint carries a `WarpEndpointIdentity` (attached to Warp endpoints in `EndpointRouteBuilderExtensions.ApplyMetadata`) or the `WarpObservedAttribute` marker.

**Host opt-in (no global switch):** `WithWarpObservability(string? operation = null)` on any `IEndpointConventionBuilder` (`MapControllers()`, `MapGet(...)`, a group) adds the marker via `Add` and builds a **per-endpoint** identity in `Finally` (so it sees every other convention, never overwrites an existing identity — a Warp endpoint in an opted-in group keeps its own — and steps aside for an exclusion); `[WarpObserved]` on a controller/action is the attribute path, whose identity the middleware builds once per endpoint and caches (`ConditionalWeakTable`). ONE builder, `WarpEndpointIdentityFactory`, serves both: method from `HttpMethodMetadata` (several/none → `*`, `EndpointCallLog.Method` is 16 chars), template RENDERED from `RoutePattern` segments (never the request path; constraints dropped; required values substituted so a conventional `{controller}/{action}` route gets the action's own template), operation = explicit name (innermost marker) > endpoint name > route name > `Controller.Action` > display name; truncated to the column bounds (1024/200). Opted-in endpoints behave **identically** to Warp endpoints — same options/defaults, capture tiers, sinks, meters, Issues, dashboard; no handler lookup anywhere in the Endpoints/Issues UI, so host endpoints need no UI change. **`ExcludeFromWarpObservabilityAttribute`** (`Warp.Core.Endpoints`, Core so the dashboard can stamp it without a `Warp.Http` reference) always wins over an opt-in; `MapWarpDashboard` and `MapWarpApiEndpoints` stamp it on every dashboard endpoint, so the dashboard is never observed even when the host calls `WithWarpObservability()` on it. Order: `UseRouting()` → `UseWarpHttpObservability()` → endpoints (a `WebApplication` without an explicit `UseRouting` is fine — the implicit routing step runs first); middleware before an explicit `UseRouting` observes nothing. Health/static files are never observed unless opted in. Rot guards: `HostEndpointObservabilityTestsBase` (both DBs: real MVC + minimal API, Issues, FailuresOnly, Otel, dashboard, Warp-in-group), `WarpEndpointIdentityFactoryTests`, `HostEndpointPipelineOrderTests`. **Identity = HTTP method + route TEMPLATE** (`GET /orders/{id}`) — already bounded (no runtime path-cardinality heuristic, unlike outbound's URL collapsing); inline constraints are normalized away (`{id:int}`→`{id}`) via `EndpointCounterKeys.NormalizeTemplate` so the colon-delimited counter key parses unambiguously, and the flusher stamps the SAME normalized method+template onto the `EndpointCallLog` row so the detail page joins log rows to aggregates. The route is the operation — counter dimensions are **Total + Group only** (no operation dimension); `group` is an optional low-cardinality caller key from `o.GroupSelector(HttpContext)` (channel/client/tenant — never raw IP/user id). Core is protocol-agnostic (`Warp.Core.Endpoints`: `EndpointCallLog` entity §8.13 always-in-schema §2.11, public `IEndpointCallRecorder`/`EndpointCallRecord` seam, `DbEndpointCallRecorder` bounded lossy channel, `EndpointCallFlusher<TContext>` drain→rows+`Counter`s, internal `EndpointCounterKeys`); the HTTP binding (`Warp.Http.Observability`) holds `WarpEndpointObservabilityOptions` (HttpContext-dependent), `WarpInboundObservabilityMiddleware`, and `AddEndpointObservability`/`UseWarpHttpObservability`.

**Capture (§1.2 PII):** caller IP (`RemoteIpAddress`, or first `X-Forwarded-For` hop when `UseForwardedForIp`), user-agent, and `User.Identity.Name` are captured by default (the point of the feature) but are PII; request/response bodies + headers are each `None`/`OnFailure`/`Always` (default `OnFailure`), truncated (`MaxCapturedBodySize` 8 KB via a bounded pass-through `CaptureBodyStream` that never buffers a whole streaming/`IResult` response, `MaxCapturedHeaderSize` 4 KB) and redacted through the same user-owned `RedactedHeaders` denylist as adapters. Outcome `Failed` = **final wire status** ≥ 500, or an exception after the response started (truncated 2xx). An exception escaping BEFORE the response starts defers recording to `Response.OnCompleted` — the real status is written by an upstream host exception middleware AFTER Warp's frame unwinds, so reading it inline records the never-written 200 default. An exception a host maps to 4xx counts like any 4xx (client error, counted Success so error rate stays meaningful) with the exception kept on the row; exception-bearing rows are never suppressed (`FailuresOnly`/sampling) and are capture-worthy under `OnFailure` tiers. `RecordCalls = FailuresOnly` skips success ROWS only (counters still written, error-rate denominator intact). **Recording is lossy + never blocks/fails the request** (full channel drops the record); `RecordAsync` swallows its own errors. **Metrics survive log deletion** (§ retention): counts/error-rate/avg-latency come from `Counter`→`Statistic` aggregates (a duration-sum `dur` token backs the average, same as adapters §2/Item 2); recent-calls + per-caller last-failure read raw rows and degrade to empty/null once swept. **Retention is GLOBAL** on `WarpConfiguration.EndpointCallLogRetention` (age, default 7d, stamped as `ExpireAt` by the middleware) + `EndpointCallLogRetentionCount` (count, null=off, keep newest N per method+route), both swept by `ExpirationCleanup` (`CleanupExpiredEndpointCallLogsAsync` + `CleanupEndpointCallLogsByCountAsync`) — no per-endpoint override (no definition table; endpoints are discovered from the aggregate keys, not a registry). `IEndpointQueryService` is registered by `AddWarp` itself (like `IAdapterQueryService`), so dashboard-only/publisher-only processes serve `/api/endpoints*` without the middleware; the detail id is a URL-safe base64 of the `{METHOD} {template}` route. Dashboard **Endpoints** nav gated on `GET {prefix}/api/addons` `endpoints` flag (true only where `AddEndpointObservability()` ran — keyed on `IEndpointCallRecorder` presence). Worker hot path untouched (§0.2/§6.1). See §2.15/§8.19, `website/docs/features/endpoint-observability.md`.
