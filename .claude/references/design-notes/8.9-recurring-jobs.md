# §8.9 — design notes (recurring jobs)

> Full rationale, history, measurements and rot guards behind the condensed rule §8.9 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `project-specific.md` (2026-11-24).

**§8.9** `RecurringJobScheduler` creates jobs with `ScheduleTime = now`. `AddOrUpdateRecurringJob` only registers/updates the definition — does **not** create jobs. Acquires a distributed lock on the recurring-job name and saves immediately (deliberate §5.7 exception). A firing lands in `State.Enqueued`, so the scheduler **must announce it like every other enqueue site** — it captures `NotificationDispatch.CapturePending` before its `SaveChanges` and dispatches from `OnCommittedAsync` (post-commit per §8.25, since `ExecuteAsync` runs inside the task host's lock transaction). Missing that wake was a real bug: firings were only found by the next backoff poll, up to `MaxPollingInterval` later — which `UseDatabasePush()` raises from 30s to **5 minutes** — and it poisoned the queue-wait SLI (§8.26) with multi-minute samples on otherwise-idle queues. **Disabled definitions are still visited** (the candidate query filters only on `NextExecution <= now`) and take a skip branch that writes a `Skipped` `RecurringJobLog` and creates no `Job` — so a disabled recurring job never executes. That branch must **not** advance `LastExecution`: it names the last occurrence that actually ran, and advancing it on a skip was a real bug — a disabled definition read as if it were still firing on the dashboard while `AttachLastRun` (which filters `!Skipped`) correctly showed no last run beside it. It **does** advance `NextExecution`, deliberately: freezing it would leave the row permanently due and write one skip log per scheduler tick instead of one per cron occurrence, so the dashboard hides the column while disabled (renders `—`) rather than relying on it standing still. `ExecuteAsync` reports the two outcomes separately (`Scheduled X recurring jobs, skipped Y disabled`) — a skip is not scheduled work — while `scheduled + skipped > 0` gates the `SaveChanges`, since a skip does mutate rows. `TriggerRecurringJob` deliberately ignores `DisabledAt` (explicit operator override). **Every single-definition method on `IRecurringJobService` keys on the registered NAME, not the surrogate `Id` (6.0 hard rename, compile error on the old signatures)** — `Trigger`/`Enable`/`Disable`/`DeleteRecurringJob`, `GetRecurringJob` (was `GetRecurringJobById`), `GetRecurringJobHistory`. The name is what a caller already holds, is unique-indexed, and is **stable across a delete-and-re-register** while the identity column is not (a stored/bookmarked id could land on a different definition). `RecurringJobName.Normalize` (internal, shared by the publisher and the service so a lookup can never miss over whitespace) trims, rejects empty, and caps at 200 — the cap is the distributed-lock name `warp:recurring:{name}`, deliberately NOT a column facet, so there is no migration. Commands throw `ArgumentException` for an unknown name; the two queries read as not-found (null / empty page) since a definition can be deleted while its detail page is open. The dashboard routes keep `{prefix}/api/recurring/{id}` but `{id}` is the **URL-safe base64 of the name** (`UrlSafeId`, the codec the endpoints/applications routes share, since a name may hold `/` and spaces); `WarpEndpoints.RecurringAction` decodes it and maps a bad id / unknown name to **404** rather than the old 500. `RecurringJobLog` is the immutable audit trail; `ExpirationCleanup` retains the last 100 logs per recurring job.

**A firing's OUTCOME outlives its `Job` row:** `JobExpirationTimeout` is 1 day, so for anything less frequent than daily the job is swept long before the next firing and `DeleteBehavior.SetNull` nulls `RecurringJobLog.JobId` — which left the dashboard able to say only "Cleaned up" for every run a monthly definition ever made, and worse, conflated a `Deleted` run (a skip-mode concurrency/rate-limit refusal, a graceful cancel) with a success, since failed jobs never auto-expire (§8.2) so everything swept was `Completed` or `Deleted`. `ExpirationCleanup` therefore **stamps `RecurringJobLog.FinalState` immediately before the delete, in BOTH delete paths** (`RunCleanupAsync` and `RunCountBasedCleanupAsync` — a new delete path must follow, or `MaxExpirableJobCount` silently loses what the age sweep preserves). Bounded by construction: the expired ids are already in hand, `RecurringJobLog.JobId` is indexed, one grouped `ExecuteUpdateAsync` per distinct state, and **zero UPDATEs on a tick with no recurring firing among its expired jobs**. Stamped at cleanup rather than at finalization deliberately — the worker would need a lookup mid-finalization (§0.2/§6.1). Read side: `AttachLastRun` and the history query read `Job.CurrentState` while the row exists and fall back to `FinalState`, with `RecurringJobModel.LastRunCleanedUp` telling the dashboard the outcome is known but unopenable (renders `Completed (cleaned up)`, never a link into a 404). `FinalState` stays null for a skipped firing (nothing ran) and for runs swept pre-upgrade, which keep degrading to the bare `Cleaned up`. Migration is one additive nullable column.
