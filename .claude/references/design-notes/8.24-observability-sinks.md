# §8.24 — design notes (observability sinks)

> Full rationale, history, measurements and rot guards behind the condensed rule §8.24 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `project-specific.md` (2026-11-24).

**§8.24** **Observability sinks** — everything Warp collects per-call/per-job can be routed to the DB (default), to **OTel**, or **Both**, so a high-throughput deployment can take the diagnostics firehose off its database. Two tracks: (a) **telemetry always emits** — `WarpTelemetry.ActivitySource`/`Meter` (both named `WarpTelemetry.ServiceName` = `"Warp"`, public const) fire spans + meters unconditionally (null-listener, zero cost without an exporter); wiring is `AddSource/AddMeter(WarpTelemetry.ServiceName)` + `AddOtlpExporter`. (b) **recording is the opt-in DB track**, now sink-selectable. `RecordingSink { Database=1, Otel=2, Both=3 }` (§8.11, `Warp.Core.Observability`), default `Database` ⇒ byte-for-byte current behavior.

**Per-surface:** `opt.AddAdapters(o => o.Sink = …)` and `opt.AddEndpointObservability(o => o.Sink = …)` — `Database` wires the DB recorder + flusher; `Otel` wires **no recorder and no flusher** (so no call-log rows AND no per-app `Counter` writes) and instead **enriches the span Warp already emits** with the captured detail as span attributes (`warp.adapter.*` on the `Client` span via `AdapterCallScope.EnrichSpanDetail`; `warp.endpoint.*` on the ambient ASP.NET request span via `WarpInboundObservabilityMiddleware.EnrichSpan` — for Warp endpoints and opted-in host endpoints alike, §8.21); `Both` keeps the DB recorder + flusher **and** enriches the span. **No parallel OTel-log recorder exists** — the earlier `Otel*CallRecorder`/`Composite*CallRecorder`/`StructuredLogState` were removed: routing per-call payloads through `ILogger` fanned them to every log provider (console/file), a §1.2 leak, and duplicated the span. Span enrichment fires **only when `Activity.IsAllDataRequested`** (the span is sampled in), so a single consistent trace-sampling decision governs the whole call/request coherently — detail travels on the trace exporter only, never `ILogger`. Adapters carry the process-level enrich flag via the optional-marker seam (`AdapterRecordingSettings`, §2.9). **Repeated `AddAdapters` calls merge** into one options bag (`AdapterRecordingRegistration`), and the implicit `AddAdapters()` inside `AddAdapter`/`AddAdapter<TApi>` sets no sink, so an explicit `Sink` wins in either call order: every call re-syncs the DB recorder + flusher descriptors to the merged sink (registered once, for the final choice), and `AdapterRecordingSettings` is ONE factory registration read from it. Before, `AddAdapter` registered the DB pair with the default sink and a later `AddAdapters(o => o.Sink = Otel)` could not take it back (rows were still written), and with `AddAdapter` first the span enrichment was lost too (`WarpAdapters` read the first of two settings); `RecordingSinkWiringTests` covers both orders on HTTP and Refit; endpoints read `WarpEndpointObservabilityOptions.Sink` in the middleware and take the recorder optionally (`IEnumerable<IEndpointCallRecorder>`, empty under Otel). The internal `IAdapterCallRecorder` **stays internal** (no public storage contract); under Otel-only it falls back to Core's `NullAdapterCallRecorder`. Dashboard nav flags stay keyed on presence markers registered regardless of sink (`IAdapterRecordingMarker`; new **`IEndpointObservabilityMarker`**, replacing the old `IEndpointCallRecorder`-presence gate which is absent under Otel).

**Job-metrics:** `WarpConfiguration.JobMetricsSink` (`RecordingSink`, default `Database`) gates the per-type/handler `jobstat` counter increments at the finalization sites (buffer entries, §6.2 — not rows) — `Otel` skips them (perf win; §0.2/§6.1 hot path only gains `instrument.Record` calls + one config check), the meters carry the data. **Meters added/extended (always-on, low-cardinality tags only, `group` stays OFF meter tags §1.2):** `warp.adapter.calls`/`duration` (+`application`), `warp.endpoint.calls`/`duration` (`route`/`outcome`/`application`), `warp.job.execution.total`/`duration` (`job.type`/`job.handler`/`outcome`/executor-`application`).

**Dashboard:** `Database`/`Both` → Warp dashboard works; `Otel`-only → those pages have no DB rows (use Grafana/Jaeger, or register a backend-backed impl behind the public `IAdapterQueryService`/`IEndpointQueryService` via `TryAdd`-before-`AddWarp`). Control-plane (jobs/servers/sagas/webhooks/app roster) stays in the DB regardless — it's state, not telemetry. See `website/docs/features/observability-sinks.md`.
