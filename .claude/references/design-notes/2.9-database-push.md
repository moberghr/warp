# §2.9 — design notes (database push)

> Full rationale, history, measurements and rot guards behind the condensed rule §2.9 in `.claude/rules/`. Read on demand when changing this area. Verbatim from the pre-split `architecture.md` (2026-11-25).

**§2.9** DB push is an opt-in addon. `opt.UseDatabasePush()` replaces the default `NullNotificationTransport` with a provider-specific one (Postgres LISTEN/NOTIFY or SQL Server Service Broker) and registers `NotificationListenerTask`. **Every listening process receives every notification on both providers.** PostgreSQL NOTIFY broadcasts by nature; a Service Broker queue hands each message to ONE receiver, so `SqlServerNotificationTransport` gives each listening process its own queue and service (`{channel}/queue/{id}`, `{channel}/service/{id}`, created when it starts listening, dropped when it stops) and `PublishAsync` sends to every `{channel}/service/` service in one batch (dialog `LIFETIME = 60`, so a message to a service dropped in between expires instead of sitting in the transmission queue). It had one shared queue, which woke one random process per notification and lost the wake whenever that process had no workers (a publisher or dashboard host). Queues of processes that died without dropping theirs are swept by the other listeners once their oldest message is older than five minutes (a live listener drains continuously); the listener ends each conversation it receives in the same batch (the old one never did, leaking an endpoint per notification); setup is serialized per channel with `sp_getapplock` (processes starting together raced on IF NOT EXISTS and the loser's transport was disabled). **A stopping listener wakes its own queue** (`SendWakeAsync`, from a cancellation callback, off the cancelling thread, awaited before the queue is dropped): SQL Server 2025 ignores a cancel that reaches a `WAITFOR (RECEIVE)` as it starts until the WAITFOR times out (measured: the full 30 s in about 40% of stops, against 0 on 2022; a second cancel does not help), and a message arriving in the queue ends it at once. The relay does the same on 7.7's shared queue, only while it is waiting there, repeating (at most 25 wakes, 200 ms apart) because another receiver may take a wake. The wake is a `{channel}/msg` with NO body, sent from the sender service: the listener skips a body-less message, the relay keeps only bodies a 7.7 process sent, and 7.7 skips a body-less message too, so it is never delivered or relayed. Not a message type of its own, which would need a contract on 7.7's shared service. Nothing is sent while a listener runs (idle cost unchanged). Rot guards: `SqlServerNotificationTransportTests.Stop_AsTheNextWaitStarts_EndsAtOnce` (fails on 2025 without the wake) and `Wake_SentToTheListenerAndToThe77SharedQueue_IsNeitherDeliveredNorRelayed`. **Rolling-deploy bridge (REMOVE in the release after 8.x, with `LegacyTaskLock`):** 7.7 sends to and listens on ONE shared service/queue (`{channel}/service`, `{channel}/queue`), which only a 7.7 process creates; 8.0 sends from its own `{channel}/sender/service` (on `{channel}/sender/queue`) and never creates the shared objects. While the shared service exists, `PublishAsync` also sends to it (the same cursor, `OR name = @legacy`) so 7.7 listeners wake, and every 8.0 listener runs `RelayLegacyQueueAsync` on a connection of its own: a `WAITFOR (RECEIVE)` on the shared queue that keeps only messages whose conversation's `far_service` is the shared service (sent by 7.7; 8.0's own copies come from the sender service, already reached every listener, and are dropped), ends every conversation, and re-sends the kept messages to every `{channel}/service/` service — never back to the shared one, so nothing loops. Several 8.0 relays drain the queue concurrently; each message goes to one, which re-sends to all. 8.0 relays compete with 7.7 listeners for 7.7's messages, so 7.7 processes get some wakes, not all (7.7 already woke one random process per message). With no shared queue the relay checks for it every `LegacyQueueCheckInterval` (1 min) and does nothing else. After the last 7.7 process, operators may drop the shared service/queue to end the bridge. Rot guards: `SqlServerNotificationTransportTests.Publish_SharedQueueCreatedBy77_*`, `Listen_77PublisherSendsToTheSharedQueue_*`, `Listen_TwoListenersAndOne77Message_*`, `Listen_80PublishWhileTheSharedQueueExists_IsDeliveredOnce`, `PublishListen_No77SharedQueue_CreatesNothingAndStillDelivers`. Rot guards: `SqlServerNotificationTransportTests.Publish_TwoListeningProcesses_BothReceiveIt`, `Listen_QueueLeftByADeadProcess_IsSweptAndItsOwnQueueIsDroppedWhenItStops`, `DatabasePushIntegrationTests.JobEnqueuedByAnotherHost_WithDispatcherPlusPush_DispatcherPicksUpWithoutPolling` (both providers). The transport is resolved via `IWarpNotificationTransportFactory`, registered by the provider package (`opt.UsePostgreSql()` / `opt.UseSqlServer()`) — **call the provider first, push second**. A cross-process `JobEnqueued` push wakes both worker modes: the listener calls the dispatcher wake (`IDispatcherWake`) **and** `ServerTaskSignals.SignalJobEnqueued`, which every bare `WarpWorker` subscribes to, so `UseDispatcher = false` is not "push without effect" (it only wakes every bare worker of the process at once, where a dispatcher would fetch once and hand out). **In-process is different:** every `WarpWorker` (bare and dispatcher) subscribes to the `ServerTaskSignal.JobEnqueued` channel, so a same-server `Kind=Job` commit in `Enqueued` (from `Publisher`, `MessageRouter`, `ScheduledJobActivation`, `RecurringJobScheduler`, handler outboxes) fires a local signal that shortcuts the worker's exponential backoff — no DB round-trip, independent of `UseDatabasePush`. Transports must not throw from `PublishAsync` — they log + increment `WarpTelemetry.NotificationPublishFailures` instead. Missed notifications are caught by drain-on-reconnect in the listener. **`NotificationListenerTask<TContext>` lives in `Warp.Core.Notifications`** (moved out of `Warp.Worker`) so DB-push RECEIVE works in **any** `AddWarp` process — server or not. It takes no server-only deps: bare-worker wake stays on `ServerTaskSignals.SignalJobEnqueued` (Core), and dispatcher wake goes through the Core **`IDispatcherWake`** seam (injected as `IEnumerable<IDispatcherWake>` — the optional-marker pattern of `IWarpServerPresence`; `DispatcherRegistry` in `Warp.Worker` is the sole impl, registered by `AddWarpServer`, so the set is **empty in an `AddWarp`-only process** and dispatcher-wake is simply inert there). There is no "push enabled but `UseDispatcher=false`" warning any more: it claimed bare workers keep polling, which stopped being true once the listener signals them. Server/worker behavior is unchanged. **SEND side (#322): every committed `TContext` save is announced by `EnqueueNotificationInterceptor<TContext>`** (added by `AddWarp` to `TContext` only, never the server context — server tasks dispatch their own from `OnCommittedAsync`): `IPublisher`/`IBatchPublisher.SaveChangesAsync`, a plain `db.SaveChangesAsync()` (a handler's own included) and saga saves alike. The worker itself never saves a handler's context (§6.17). It captures in `SavingChanges`, and after the save (or, inside an explicit transaction, after the commit; nothing on rollback) wakes this process inline through `ServerTaskSignals` and hands the notifications to `EnqueueAnnouncements`; `EnqueueNotificationRelay` (a §2.19 `DrainService`, registered by `UseDatabasePush()`) publishes them off the saving thread, one per (kind, queue) per batch — measured 2.4% fewer statements/job than 7.7.0's inline per-job NOTIFY on the CI fan-out benchmark. The interceptor deliberately holds **no transport** (the push transport's factory reads the connection; an interceptor depending on the transport deadlocked startup) and the worker sends nothing itself — do not reintroduce an inline send on the worker path. Cross-process send therefore needs a running host, like receive. The explicit call sites go through `EnqueueNotifyingSave`, which falls back to the old capture-save-dispatch only on a context the interceptor is not on. **Single-worker `JobFinalized` goes through the same relay** when push is on (`EnqueueAnnouncements`, resolved once from the worker's scope): the local wake still fires inline, and the relay merges a batch's finalized notifications into one (`FinalizedParentsPayload.Merge`: every parent and settled id once, split at `MaxIds`, an unknown payload wins). Published inline it was a round trip per job on the worker path, and with the SQL Server per-process fan-out ~2 statements per job more than `main` (matrix, single-worker + push, both runs). Dispatcher mode already sent one per flush. Rot guard: `EnqueueNotificationRelayTests.Relay_FinalizedJobsOfOneBatch_PublishesOneNotificationNamingEveryJob`.
